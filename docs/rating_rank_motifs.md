# Rating, rank and motifs — methodology

Three quantities drive everything a player sees: the per-problem **rating** (with its two companions, discrimination slope and guessing floor), the **rank** the rating maps to, and the per-problem and per-cell **motif** vector that describes what kind of skill a problem exercises.

They are built in that order, each depending on the last. The rating is a latent-trait fit over the human attempt log, using features derived from a neural evaluation of the position. The rank is a monotone map from the rating scale to a human kyu/dan scale, calibrated against self-reported ranks on external servers. The motifs are supervised axes fit to whatever between-user response variation the rating model could not explain. Everything after that — problem selection, the displayed rank, spaced repetition, the weakness readouts — is derived from those three on the client from raw numbers.

Chapters 1 and 2 describe the method. Chapter 3 maps it onto the actual modules, artifacts and constants.

# Chapter 1 — Construction

## 1.1 The problem set and its two invariants

Problems are generated by a solver and identified by a hash taken over all eight dihedral transforms of the board, with a canonical orientation chosen by taking the minimum. Two consequences carry through the whole system: the set cannot contain two problems that are rotations or reflections of each other, and every problem has exactly one correct first move.

Both are load-bearing later. Symmetry-canonical identity is what lets ratings, activations, motif vectors and attempt logs all join on one key without any orientation bookkeeping. The single-solution property is what makes "the correct move" a canonical reference point, which the motif direction test relies on: without it, "the move the user played differs from the correct one along axis k" would have no well-defined sign.

**The id is truncated, and the usual birthday worry does not apply.** The identifier is the leading 32 bits of the canonical hash, so at corpus scale a couple of unrelated positions are expected to land on the same value. That is not a data-integrity problem here, because generation **refuses to write an id that already exists** on any board size and discards the candidate instead. A collision therefore cannot produce two different positions sharing one record, which is the outcome that would actually be harmful — it would silently re-point the attempt log, the activations, the rating and the published shard at different content. What a collision produces instead is a **lost tsumego**: a valid position that is never admitted, permanently, since any later rediscovery hashes the same and is skipped again.

That cost is close to nothing. Candidate positions are generated in effectively unbounded supply, so losing a handful is not losing anything scarce, and the loss is unbiased with respect to everything the system cares about — a 32-bit hash prefix is uncorrelated with difficulty, motif or board size, so the discarded positions are a uniform random thinning of the corpus rather than a systematic hole in it. Widening the id would buy back a few problems and cost a rename of every id-keyed artifact, which is why it has not been done.

It is also worth separating this from the *intended* collisions. Two positions related by a rotation or reflection are supposed to map to the same id — that is what the canonicalization is for, and it is the mechanism that keeps the corpus free of eight-fold near-duplicates. "Collision" in that sense is the feature; only the accidental prefix kind is discussed above.

Each problem's move tree carries a per-branch evaluation — win probability and score lead from the solver — which is the source of the candidate-move features below and lets a review be scored without any live engine call.

## 1.2 The four raw signals per problem

**Trunk activations.** A neural Go engine is run on each position and the post-skip-add output of all eighteen residual blocks (eighteen × 384 = 6912 floats) is captured **at every legal cell** for the side to move, along with an index marking which cell is the correct move. This is the only signal that describes the position itself rather than the solver's verdict on it, and it is the only one available per *cell*, which is what later makes per-cell motif vectors possible.

Two structural facts about this capture propagate everywhere. Rows are in board-scan order, not move-tree order, so the correct move is at a recorded index and never positionally first. And the cell set is a **superset** of the move tree's root variations — every clickable move is embedded, some embedded cells have no variation, and the "pass" variation is never embedded at all. Every consumer therefore either selects by the recorded correct index or maps by board coordinate; nothing may index positionally across that boundary.

**Bot ladder pass rates.** A ladder of engine configurations of varying strength solves every problem, giving a per-bot pass rate. This is a difficulty proxy available for the *entire* problem set, including problems no human has ever attempted — which is exactly the population the rating model has to extrapolate to.

**Candidate-move evaluations.** For each problem, the root variations are sorted best-to-worst by (win probability, score) so that slot zero is the winning move, and the winning move plus its nine best alternatives contribute a (logit win probability, score) pair each — twenty raw columns. Missing alternatives repeat the worst real move, so "the gap to a non-existent alternative" is zero rather than undefined. The best-versus-second-best gaps derived from this are the *tightness* of a problem: how much better the solution is than the runner-up, in points and in win probability.

**Game phase.** Parsing each move tree gives the number of setup stones, the number of moves leading to the contested position, and the length of the principal line after the correct move. The model consumes the raw components rather than a derived ratio, on the reasoning that a network can construct a ratio itself while the raw magnitudes additionally carry board-fullness information a ratio discards.

## 1.3 Building the shared feature representation

The two board sizes share one model, so every feature column must mean the same thing on both. Each block is pooled across sizes before any reduction.

**Activations** are reduced by a single shared chain: standardize, randomized principal component analysis, standardize again. Fitting one basis across both boards is what makes a learned activation weight interpretable on either. The *full* transform is retained, not just the projected values, because the motif fanout later needs to project arbitrary cells — not only correct ones — into the same space.

**Bot pass rates** are restricted to the bot set common to both boards, clipped away from zero and one, converted to logits, mean-imputed where a bot is missing a problem, stripped of zero-variance columns and pooled z-scored.

**Candidate-move evaluations** and **game-phase components** are pooled column z-scores of the raw values. Z-scoring at training time rather than at cache time keeps the caches reusable across different problem subsets.

A board-size indicator is appended last. The final row is `[activations | bot pass rates | move evaluations | phase | size indicator]`, and the *order matters operationally*: the trainer's per-block dropout addresses columns by range, so inserting a block anywhere else silently regularizes the wrong thing.

A problem is **scorable** — eligible to receive a rating — when it has both an activation row and a bot row. A missing move-evaluation or phase row is mean-imputed (zero after z-scoring) rather than excluding the problem, since those blocks are refinements rather than prerequisites.

## 1.4 The observations and the ability unit

The training target is **human first-time attempts only**: repeats excluded, de-duplicated to the earliest attempt per (user, problem). Bot results never appear as observations — they enter only through the features. Adding bots as synthetic examinees was tried and rejected: it steepens the mean per-problem slope with no held-out benefit, because a bot ladder's response curve is not a human's.

Users are kept only if they have at least five correct *and* five incorrect first-time attempts. A user who has never failed, or never succeeded, cannot identify an ability at all, and including them only lets the optimizer push their ability to an asymptote.

The examinee is not the user but the **overlapping two-month profile**: an attempt in calendar month M contributes to profile M and profile M−1, so each profile covers a two-month window overlapping its neighbours by one. Profiles below eight attempts are dropped. This buys a slowly-drifting ability with no explicit drift model and no state to carry — a user who improves simply has a rising sequence of profile abilities — at the cost of correlated observations between adjacent profiles, which is acceptable because ability is a nuisance parameter here, not the estimand.

## 1.5 The response model

A four-parameter logistic, one shared network for both boards:

```
P(correct) = floor + (1 − floor − lapse) · sigmoid( slope · (ability − difficulty) )
(difficulty, slope, floor) = network(features)
```

- The network is a small multilayer perceptron with two hidden layers and three outputs.
- **Slope** passes through softplus with a lower clamp only — no upper bound, since a genuinely sharp problem should be allowed to be sharp.
- **Floor** is a sigmoid scaled by `(1 − 2·lapse)`, so the guessing floor structurally cannot cross the ceiling.
- **Lapse** — the slip or fat-finger rate, the upper asymptote's shortfall — is a **single learned global scalar** with a small cap. It is the irreducible failure probability on a problem the user should clear with certainty: a misread or a misclick, most common when strong players are bored by trivial problems.
- **Ability** is a free per-profile parameter with no shrinkage.

The defining structural choice is that there are **no per-problem residual parameters**. The shared feature network *is* the model. This is what gives never-attempted and one-sidedly-attempted problems a well-defined response curve — they get the feature-conditional prediction, which is a real prediction and not an artifact of having no data. An attempted problem departs from the feature-conditional mean only to the extent the network can memorize it through the activation features, which is precisely what the regularization below is designed to limit.

Dropout is applied at 0.3 uniformly: on each input block at **column granularity** (every feature column dropped independently) and between the trunk's hidden layers. Column granularity beats dropping a whole block on or off, and the reason is instructive. Block dropout leaves the fingerprint *fully intact* on the kept fraction of rows, so the network learns a present/absent regime pair and memorizes freely inside the majority regime. Column dropout never presents the same wide code twice, so the exact conjunction that memorization requires is unreliable on every row while the smooth low-order signal survives everywhere. The dose response is a broad plateau that only degrades once so few components survive that the mechanism reverts to the block regime — which is the mechanism's own prediction, and a useful confirmation of it.

Weight decay was measured as a substitute and **rejected**. It degrades the fit generally rather than suppressing memorization selectively: a low-norm readout of a near-unique high-dimensional code still fingerprints. The two kinds of dropout are also strongly super-additive — removing both costs far more than the sum of removing each — so they suppress different failure modes and no single norm penalty stands in for either.

## 1.6 Identification: pinning the scale gauge

The model has an exact scale freedom. Multiply every difficulty by a constant, divide every slope by it, multiply every ability by it, and every predicted probability is unchanged. Something must pin it or the fit wanders.

The gauge is pinned **on the problem side**: the difficulty output is hard-whitened to mean zero and unit standard deviation, batch-normalization style — training batches use their own attempt-weighted statistics (differentiable, so the whitening participates in the gradient) and update an exponential moving average, while evaluation uses the moving average, so the ratings scored at the end live in the same gauge the abilities were trained against. Ability is left completely free; its spread then settles wherever the data puts it.

Pinning on the problem side rather than the ability side is a well-posedness choice, and it is worth being exact about what it does and does not buy. The whitening statistics are taken over training batches of *attempts*, so the distribution the gauge is anchored to is the attempted problem set weighted by attempt count — which moves with the serving policy and the user base, for the same reasons the examinee set does. It therefore does **not** make the rating scale stable across retrains, and nothing else does either: section 1.11 says outright that every run re-fits the whole set and a rating moves whenever the map moves, and the rank curve is re-fit against whatever scale is shipped precisely so that gauge drift is absorbed downstream instead of displayed. What the problem-side pin buys is that the scale is fixed by a quantity with structure — the spread of difficulty across the problems people actually attempt — rather than by constraining the abilities, which are free per-profile parameters with no shrinkage and no reason to have unit spread. Ability is then left alone, which is what lets its spread be read as a result rather than an assumption.

This replaced an earlier staged coordinate descent between phases. With the gauge in place, all three per-problem outputs and the global ceiling train together in a single pass.

## 1.7 Two divergence barriers

The gauge makes the fit well-posed but does not stop the *derived* rating from running away, because the rating is obtained by dividing by the slope. Two one-sided, threshold-free penalties are added, both evaluated over the whole problem set with dropout disabled so they read clean per-problem values.

**Shallow-slope penalty**, proportional to the mean of `1 / slope²`, applied to the *pre-clamp* slope so the gradient is still alive for problems sitting on the clamp. The reciprocal slope is the transition width of the response curve, and against a difficulty spread of order one it is exactly the factor the 80%-clear rating diverges through when an unattempted or never-solved problem's slope collapses flat. Without it, a percent or two of the problem set sat at the rail with ratings in the hundreds. (Order one, not exactly one: the gauge pins the spread over the *attempted* distribution as section 1.6 describes, while both penalties are evaluated over the whole problem set, whose spread is the wider of the two. The weights were swept in these units so the calibration is self-consistent; the distinction would only matter to someone transferring a weight to a differently-served corpus.)

**High-floor penalty**, a squared softplus of the floor output's distance past the point where the floor equals the calibration probability, applied in the floor head's **logit space** with the lapse detached so the barrier cannot train the ceiling. This is the easy-side mirror: as the floor rises toward the calibration probability, the rating goes to negative infinity. Working in logit space keeps a live gradient past the crossing point, where a probability-space penalty would clamp-die exactly where it is needed.

The critical design point is that each penalty acts on the **offending parameter**, never on the derived rating. A direct penalty on the rating is Goodhart-able through the floor: measured, the optimizer inflates floors on hard problems to cancel the penalized number, and held-out calibration collapses below the constant predictor. Both weights were chosen by held-out sweep, and both are small — the tails come in at approximately zero cost while an order of magnitude more starts homogenizing real floor and slope structure.

## 1.8 Optimisation

Adam, a large minibatch, a few hundred epochs, fixed seed. One numerical detail is worth recording: the cross-entropy is reduced explicitly as sum-over-batch-size rather than through the fused mean kernel, because the two differ by a unit in the last place at non-power-of-two batch sizes (the final, smaller minibatch) and that difference compounds over the run in the model's flat slope and floor directions.

## 1.9 The shipped rating is the 80%-clear point

After training, the whole problem set is scored and the shipped rating is

```
rating = difficulty + logit( (0.8 − floor) / (1 − floor − lapse) ) / slope
```

that is, **the ability at which a user clears this problem 80% of the time**, not the 50% midpoint. That 0.8 is the calibration probability: the margin the app both serves at and anchors at, chosen because it is near the sigmoid's maximum-curvature region, so a served problem is maximally informative about ability while still feeling winnable.

The slope-dependent correction is load-bearing and **cannot be deferred downstream**. A flat, low-discrimination problem genuinely requires more ability to clear at 80% than its midpoint suggests, so two problems with identical midpoints differ in true 80%-difficulty — and a monotone rating-to-rank map, being monotone, can never recover a per-problem reordering. It has to be built into the rating itself.

That argument cuts both ways, and the next section is where it bites: the correction divides by the fitted slope, and section 1.10 measures the fitted values to be scale-compressed. Whether the anchor should therefore move is a measured question rather than a definitional one, and it was measured — section 1.11.

Ratings ship raw. A percentile clip once sat here to tame the low-slope tail; it was removed, because the barriers keep the tails finite at the source and the clip only destroyed the ordering of the extreme percentiles. The rating percentiles are printed each run instead, as a tail-sanity check: a blowup there is a barrier regression to fix, not something to clip after the fact.

## 1.10 Phase two: global slope and floor calibration

The per-problem values come out **scale-compressed** toward the feature-conditional mean, so a user's true response curve is steeper per shipped-rating unit than the shipped slope claims. A second stage measures that as two global scalars against the frozen model:

- Every per-problem triple is frozen as a constant.
- The ability field is **refit free**, one ability per user per non-overlapping two-month block. This is not a luxury: plugging in fixed abilities is attenuation-biased — the ability is a regressor measured with error — while the refit-at-every-value profile likelihood is certificate-clean, returning approximately one when run on synthetic outcomes generated at a true scale of one.
- Two scalars train: a slope scale and a floor scale.
- The loss is pure cross-entropy — no dropout, since nothing stochastic remains, and no barriers, since they act on the now-frozen heads — scored in the **client's** response form and pivoting at the shipped rating, so the rating remains the 80%-clear anchor and only the curve's steepness around it is rescaled. Scaling around the internal midpoint instead would rescale the rating axis itself; that this is the right pivot is a held-out result, not a convention (section 1.11).
- It runs twice, scales frozen at unity for a like-for-like baseline and then free, so the reported improvement is honest. It is fully deterministic.

Every first-time attempt on a scorable problem is scored, with no user cull. This replaced a held-out walk-forward calibration whose causal protocol could only score heavy users' post-warmup rows, roughly three fifths of the attempt mass; the two criteria agree to well within noise.

**The two stages therefore run on different populations, and the asymmetry is deliberate.** The first pass keeps only users with a minimum of both correct and incorrect attempts; the second keeps everyone. The reason is that the two stages ask different things of a user. In the first pass an ability is a *free parameter being estimated*, and a user with no failures — or no successes — has no finite maximum-likelihood ability at all, so the cull is an identifiability requirement rather than a quality filter. In the second, abilities are *nuisance* parameters profiled out on the way to two global scalars, and a thin or one-sided unit is largely self-silencing: as its ability escapes toward a rail its rows saturate, and a saturated row's gradient with respect to the scalars vanishes. Such units add variance, not a systematic pull.

More importantly the asymmetry points the right way. What the correction corrects is the *shipped* curve, and the shipped curve is applied to everyone the app serves — including beginners and users whose short record is entirely one-sided. A scale measured only on the culled population would be calibrated to heavy two-sided users and would then be the wrong number for most of the population it is actually applied to.

That said, the first pass's cull is selection on the outcome variable, which is exactly the kind of thing that can bias what it selects on, so the difference is not free. The residual worry is a population difference correlated with response steepness — if thin or new users respond more noisily, their apparent curve is flatter and the measured scale is pulled down. This is one of the things the synthetic certificate is there to bound: outcomes are regenerated from the fitted model, the *whole* recipe is re-run on them, and the substitution happens upstream of the cull, so the certificate run reproduces the same two-population structure rather than papering over it. Returning approximately one against a known truth bounds the net bias of everything the pipeline does, this included. The honest limit of that argument is that a certificate built by generating from the model can only exercise population differences the model can express; a way in which real thin users differ that the generative model cannot represent is outside its reach.

**Why the multiplier exists at all** is settled, and the answer determines the correct functional form. A parametric bootstrap — regenerate outcomes from the fitted model itself with known abilities, retrain the entire recipe on them — reproduces the real multiplier on that clean data, while the same criterion applied to the *true* generating parameters returns approximately one. The machinery manufactures the entire effect. Narrowing further: the compressing regularizer is **dropout specifically**. With dropout removed the multiplier collapses to near one, but held-out logloss explodes below the constant predictor with memorized slopes several times healthy. So a multiplier of one and generalization are mutually exclusive with this feature set: dropout limits per-problem fingerprint memorization, which caps how much idiosyncratic, feature-inexpressible difficulty the fitted values can carry, and the scale correction is the measured price.

Two corollaries. The earlier errors-in-variables explanation (ability noise attenuating the fit) is **wrong** — within-user drift is far too small to predict the observed multiplier, and every ability-noise treatment tried was inert or worse. And the needed correction is **flat across attempt-count strata** on real data, which is the axis a per-problem theory of the compression would most obviously predict structure along, so a per-count correction is ruled out and a global scalar is the right form *along that axis*.

**How far that generalizes is an open measurement, and the claim should not be stretched past it.** Constancy has been checked against attempt count and nothing else. It has *not* been checked across strata of rating, of slope, or of floor, and there is a mechanistic reason to expect the floor axis in particular to misbehave: the attribution of the multiplier decomposes it into compression of the rating scale, shrinkage of the per-problem slope, and homogenization of the floor — and a floor homogenization is by construction a floor-dependent effect, pulling extreme floors toward the middle by more than central ones. A single scalar applied to all floors cannot express that, so if the residual multiplier varies anywhere, the floor axis is the first place to look, followed by the hard rating tail where the fitted values lean hardest on feature extrapolation. Until those strata are measured the same way the attempt-count strata were, the correct statement is that one scalar is unrefuted rather than established, and a per-count correction specifically is ruled out. Explicit per-problem random effects were measured dead in every configuration — co-trained they always find a scale freedom to exploit, and a statistically sound frozen two-stage empirical-Bayes fit yields a real but tiny variance component that shrinks to nothing at the observed attempt density. The idiosyncratic difficulty the compression suppresses is simply not per-problem identifiable yet.

## 1.11 What the fit produces

Per problem: the 80%-clear rating, the discrimination slope and the guessing floor. Globally: the learned lapse rate, the two calibration scalars, and the per-profile abilities.

**Which of those carry the phase-two scalars is not uniform, and the asymmetry is deliberate.** The rating is computed from the first-pass outputs *before* the scalars are applied, and ships unscaled — it is the 80%-clear anchor of the unscaled curve, and the calibration deliberately pivots around it rather than rescaling the axis it lives on. The slope and floor ship *multiplied* by their respective scalars. So a consumer reconstructing the response curve from published values gets the calibrated curve automatically, while the rating keeps its definition; but anyone comparing a published slope against a first-pass slope from a training log is comparing two different quantities.

**That the rating keeps its place is a measured result.** It has to be, because section 1.9's own argument makes it a real fork: the rating's per-problem correction is an offset divided by the fitted slope, phase two says the fitted values are compressed, and shrinking that correction would move each rating by a problem-specific amount — precisely the per-problem reordering section 1.9 says no downstream monotone map could ever perform. So the alternative is well-defined, and it was fit. Scaling the *whole* inner logit rather than the slope alone re-derives the anchor toward the midpoint, and it is algebraically identical to recomputing the rating from the corrected slope. Head to head under the same held-out walk-forward, keeping the rating and scaling the slope alone dominates the re-derived anchor pointwise through the peak. The fitted ratings are correctly-placed anchors; it is the discrimination that is attenuated.

Two things keep that from being over-read. First, most of the multiplier is not a statement about the slope parameter at all. The dominant component is compression of the rating axis, and expanding that axis is the *same operation* as scaling every slope — each user's free ability absorbs the difference exactly — so that part is gauge and implies no reordering whatsoever. Only the per-problem slope shrinkage and the floor homogenization are per-problem effects, and they push the anchor in opposite directions, which is why no clean signed prediction about clear rates falls out of the multiplier's size. Second, the comparison predates the single-pass gauge fit and phase two's in-sample form; the harness that ran it is still in the tree, so re-running it is a cheap re-measurement rather than a standing assumption. It belongs on section 1.10's list of unmeasured strata as the natural fourth item, and the direct version of the same test is to stratify observed clear rates at zero rank gap by slope and by floor.

A word on the term **raw**, which this document uses in a specific sense and which is easy to misread. It means *not repackaged*: no bounded remapping, no rank baked in, no derived quantity substituted for the fitted one. It does **not** mean "first-pass". A published slope is raw in the first sense and calibrated in the second, simultaneously.

Every run re-fits the **whole problem set** from scratch, and because the fit is entirely in the shared map, a rating moves between runs when the map moves — which new attempts anywhere, a refit gauge, a refit feature basis and new calibration scalars all cause. A problem's rating is therefore not stable across runs even if nothing about that problem changed, with consequences for how the recorded history reads later (section 2.5).

The production trainer takes no options; the shipped configuration is fixed in the code. The entire experiment surface — alternative gauges, barrier weights, errors-in-variables probes, the legacy staged configurations, the held-out and survey-correlation evaluation suite, alternative objectives — lives in a separate research entry point that can reproduce the shipped configuration exactly. A test tweak therefore cannot reach the shipped ratings.

## 1.12 Rating to rank: the consensus mapping

The rating scale is internal and arbitrary; users want a kyu/dan rank. That map is fit against **self-reported ranks on external go servers**, and the model has one important shape:

```
time-adjusted rating ──curve──▶ latent consensus rank ──per-server coupling──▶ declared rank
```

There is a **latent consensus rank** and every server, including the European federation's rating, is a free coupling off it. No server is a privileged identity hub. This matters because servers genuinely disagree — a "5 kyu" means different things in different places — and forcing one of them to be the definition imports its idiosyncrasies into the headline. It also fixed a real defect: an earlier federation-anchored fit under-rated dan players by roughly two stones, which vanished once the federation became one coupling among many.

**Anchors are career segments, not one number per user.** Each surveyed user's attempt history is cut into overlapping two-month windows; each window with enough attempts yields its own rating and becomes an anchor row attached to that user's nearest-in-time declaration for that server. The assumption is no rank drift unless a survey says otherwise, which is sound because the survey era is short relative to the attempt history. Rows are weighted by **attempt mass** — each attempt's unit mass split across the windows covering it, so overlapping windows cannot double-count an era — then normalized so each declaration contributes total weight one regardless of career length. Paired cross-validation showed a clear held-out improvement, concentrated in the deep-kyu band, over a single pooled career rating. The same harness tested weighting each anchor by its own statistical confidence interval and **rejected** it: declaration noise dominates rating noise, so confidence weighting over-steepens the curve.

**The anchor quantity is the user's 80%-clear rating**, computed by the same four-parameter fit the client runs, using each attempt's own slope and floor plus the global lapse, pooled across boards. Anchoring on the raw ability instead would mis-place every user by several ranks, because ability is the midpoint and the rating is the 80% point — the mismatch is exactly the offset the rating definition builds in. Keeping the anchor identical to the client's own computation is what closes the loop: the map re-anchors users against whatever scalar is actually shipped, so it stays self-consistent under any change to the rating internals.

**Solve time is folded in.** Each declaration's effective rating is adjusted by a slope times the de-meaned base-ten logarithm of the user's median solve time, with the slope fit **jointly** in the same objective. It is identified because the time feature varies per user while the curve is a function of rating alone and each coupling is a per-server constant, so neither can absorb a per-user time shift. A simple log-time slope is all the data supports — no rating interaction, no power law, no separate rank-residualization step, since the joint couplings absorb the rank-correlated part of solve time by themselves.

**The curve** is monotone by construction: the gap between consecutive rank thresholds is a positive base gap times an exponential deviation term, so monotonicity is structural rather than enforced. The base gaps come from a published even-game win-rate table's fitted shape, used as a **gentle** prior. Gentleness is deliberate and was a correction: when the latent was anchored only to one federation it was kyu-starved and needed a strong prior, but an all-server latent is not, and a strong prior then over-constrains a curve the data can now determine.

**Each server coupling** is a cumulative-link ordinal fit with free thresholds and a uniform-spacing prior, plus a **contamination mixture**: with small probability a declaration is junk — a lie or a misclick — uniform over that server's categories. This caps any single junk row's negative log-likelihood and sends its gradient smoothly to zero, so an impossible declaration stops steering a coupling while a merely improbable one keeps most of its weight. The contamination rate is deliberately small: held-out likelihood degrades monotonically in it, because the plain logistic's linear tails already bound junk influence and a large junk floor mostly lets the fit over-sharpen its couplings.

**The gauge.** With no server privileged, the consensus scale is defined only up to monotone reparameterization. It is pinned by a very weak penalty on the reliability-weighted mean coupling offset toward identity. Weak on purpose: the likelihood is flat in the gauge direction so the scale has no motivation to drift, and a strong pin would shrink the genuine per-server offsets it is meant to leave alone. In practice the data-rich servers set the scale.

The output is one shared curve for both board sizes — the rating fit is already cross-board, so there is nothing per-board left to map — plus one set of coupling knots per server, plus the time-adjustment coefficients.

## 1.13 Population constants

A separate fit produces the population-level constants the client cannot estimate per user from sparse data:

- The **time-benefit bias**: the population-mean coefficient relating extra solving or review time to success. It is confounded negative (a problem that is harder than its rating for a given user takes longer *and* fails more), so the client recenters its own per-user coefficient by this population value. It is both the shrinkage prior and the display offset, and those two must be the same number or an uninformative user can never read as neutral.
- The **retention constants** for the spaced-repetition stability map, fit by retention likelihood over repeat chains clean enough that the elapsed gap is a true retention interval.
- The **per-axis weakness prior**: a precision vector fit by empirical Bayes, where the between-user variance of each motif axis's coefficient is a variance component estimated by expectation-maximization with a Laplace approximation in the E-step. The offline fit carries one coefficient per axis, but the client carries **two** slots per axis and applies this precision to each of them, so the shipped precision is **twice** the inverse of the measured variance. That factor is what makes the client's implied prior on the identified sum equal the measured variance rather than double it (section 2.9); reading the shipped number as a plain inverse variance will mis-state that prior by a factor of two, and with it the level-one finding threshold. Axes along which users genuinely differ get a loose prior and can surface as findings; axes with no between-user signal stay pinned near zero. Because that variance component is a second moment about zero, it is the between-user variance only while each axis's pooled coefficient is itself zero — an assumption the fit now measures and halts on rather than takes on trust (section 2.9). This vector is **mandatory** — if the population is too sparse to fit it, the step fails rather than shipping a fabricated fallback, and the client declines to train rather than invent one.

The global lapse rate is read through from the rating fit, so client and backend share one ceiling.

## 1.14 Motifs: supervised skill axes

Motif vectors replaced an unsupervised component analysis of the activations. The change in philosophy is the point: the axes are now **defined by validated human variation**, not by activation statistics. An unsupervised decomposition finds directions that vary a lot; it has no reason to find directions along which *people* differ, and a direction nobody differs along is useless for personalization however striking it looks.

**The model**, fit on first-time attempts:

```
logit P(success) = per-user intercept + per-user rank slope        (individual difficulty baseline)
                 + population residual difficulty(features)         (quarantined, never shipped)
                 + Σ_k  axis_k(features) · user position_k          (the axes)
```

Per-problem axis loadings are learned so that per-user positions explain the between-user **residual** — what is left after each user's own baseline against problem rank. The population residual-difficulty term is a separate head that is deliberately **never shipped**: its job is to soak up difficulty structure the rating model missed, so that difficulty cannot masquerade as a skill dimension. Without that quarantine the first axis is always "hard problems", which is not a skill.

**The training regimen is fixed, and each element fixed a measured failure:**

- The axis head is a **direct linear map** on the features with unit-norm columns. A free loading scale lets one strong direction dodge the per-user prior by cloning itself across axes; sharing a trunk with the residual head restricts the axes to combinations the residual head already found relevant, which is the wrong constraint.
- A lenient orthogonality penalty, mutual and against the residual head, on batch correlations — enough to stop axes collapsing onto each other, loose enough not to force artificial independence.
- The first three axes **warm-start** at hand-crafted directions (win-rate tightness, score tightness, game phase) obtained by ridge-regressing those scalars onto the features. This breaks a bootstrap deadlock: with all user positions at zero the loadings have no gradient, and vice versa. The learned refinements then subsume the hand-crafted forms.
- Per-user positions carry shrinkage inversely proportional to that user's attempt count, plus a mean-zero pull, so a user with few attempts sits near the population centre rather than at a noisy extreme.

**Features are exactly the rating trainer's inputs** — same loaders, same reduction basis, same seed — plus the rating model's own outputs. Literal parity is a policy, not a coincidence: if the axes could see signals the rating model could not, an "axis" could be nothing more than difficulty the rating model was blind to.

**The number of axes is selected, not chosen.** Starting from three, each candidate count is fit twice on user-disjoint halves and scored by the **held-out walk-forward likelihood gain** of the axes block over a baseline of the production response model: for each held-out user, walk forward in blocks, fit ability on the past only, calibrate both models on the past only, and score the next block. The count grows while the gain stays within a small fraction of the running peak; the selected value is the last before the breach. The axis set therefore grows naturally with data volume, and no consumer may hardcode it.

**The per-user fit inside that criterion is shrunk the same way the client shrinks it.** Scoring a held-out user means fitting that user's own axis coefficients on their past, and left unpenalized this is not always well posed: on a particular window the axis columns can come close enough to collinear — with each other, or with rank — that the fit is effectively unbounded, and a Newton solve with no convergence test then returns coefficients larger than any real effect by many orders of magnitude. This is not a property of the user and not a matter of how much history they have; it was first seen on a user with over a thousand attempts and a near-even split of successes and failures, on a full-length window, after several healthy blocks. The scores built from such a fit are large enough to swamp the pooled calibration, and because that calibration's conditioning then decides the outcome, identical inputs can yield either a normal result or a catastrophic one depending on rounding alone — the failure mode is a silent coin flip rather than an error.

The response is **not** to exclude the affected users. A window that cannot be fit with finite coefficients is one the axes separate unusually well, so discarding it would select on the outcome and throw away the strongest evidence for the very axes being tested. Instead the coefficients carry the same Gaussian prior the client applies to its own. The prior's scale is estimated within the fold rather than read from the published vector, because the count under selection has no published vector yet and using the shipped one would be circular; it is estimated from a **robust** spread of the per-user coefficients, since the pass that supplies them is the unpenalized one and a single unbounded fit would otherwise set the scale for every axis. The pooled score is additionally standardized before calibration. That changes no fitted value — a converged logistic fit is invariant to an affine rescale of a regressor — but it removes the ill-conditioning that let rounding pick the outcome, so the criterion is reproducible rather than merely usually correct.

The final fit uses all users at the selected count, and loadings are standardized per axis, which is what makes a shipped motif value read directly as a z-score.

**On the axis block's collinearity with the per-user difficulty slope.** Problem rank is a column of the feature vector and the axis head is linear over those features, so an axis that loaded only on that column would produce a term exactly collinear with the per-user baseline slope — the same regressor, with the user's axis position standing in for their slope. The orthogonality penalty does not cover this: it acts between axes and against the residual head, not against the baseline's regressor. The structural observation is correct. Explicit residualization is nonetheless unnecessary, for three independent reasons, and the third is why it would be unwelcome.

*The regularization asymmetry actively repels it.* Under exact collinearity the likelihood is indifferent to which of the two routes carries the variation, so the penalty terms decide — and they are lopsided by construction. The baseline intercept and slope are free per-user parameters with no penalty at all, while the axis positions carry a per-user ridge scaled by attempt count plus a strong pull of their population mean to zero. Any mass placed on a rank-shaped axis is therefore paid for while achieving nothing the free baseline slope could not achieve for nothing. Nor can the axis dodge the price by inflating its loading and shrinking its position: the axis output is normalized to unit root-mean-square before it meets the position, so scale lives entirely on the penalized side. The mean-zero pull adds a second bar — an axis can only ever encode *between-user* variation, so a population-level rank effect cannot live there in the first place.

*The selection criterion cannot reward it.* The held-out comparison that decides whether an axis survives is against a baseline that **already contains rank with a freely fitted per-user coefficient**. An axis collinear with rank contributes a column redundant with one the baseline already owns, so the augmented model predicts identically and the measured gain is zero — and the incremental rule then declines to keep that axis at all. This generalizes past the exact case: a *partial* rank proxy is absorbed by the baseline to the extent it is rank-explainable, and only its orthogonal remainder can earn gain. The criterion is therefore performing the residualization implicitly, on held-out data, which is strictly better than imposing it by hand — hand-residualization would also strip the rank-correlated part of a genuine motif, and difficulty and motif are not independent in reality.

*And an axis that survived all that would have earned its place.* Passing the held-out test against a rank-containing baseline means predicting something the per-user slope demonstrably does not — real between-user variation in how people respond to difficulty, which is exactly the quantity the axes exist to capture, and capturing it improves the model rather than corrupting it. This is the point at which the critique's worry inverts: the risk is not that a bad axis sneaks in, but that a good one gets suppressed by a defensive orthogonalization nobody measured the cost of.

What genuinely remains is a **labelling** risk rather than a modelling one, and it is caught downstream: a human inspects both extremes of every new axis, and an axis whose tails carry no coherent motif simply cannot be named — at which point publishing is blocked rather than shipping something mislabeled. The invariant that keeps this argument valid is that **rank must stay in the selection baseline and the baseline slope must stay unpenalized**. Removing either — penalizing the baseline slope, or scoring axes against a rank-free baseline — collapses both the first and second reasons at once, and only then would explicit residualization become necessary.

**Per-cell values require no extra training.** The axes are linear in the features, and among all the feature blocks only the activation block varies per cell — bot pass rates, move evaluations and phase are properties of the position, not of a candidate move. So a cell's axis value is the problem's value plus the projected difference between that cell's activations and the correct cell's, through a single precomputed matrix. This is what makes it affordable to score *the move the user actually played*, not just the move they should have.

**Axis identity survives refits** through frozen per-motif direction anchors. A newly fit axis is matched to an anchor by absolute correlation over shared problems, greedily and one-to-one, always against the **frozen** anchors and never against the previous refit — matching against the previous fit would allow transitive drift, where an axis slowly becomes something else while keeping its name. An axis matching with negative correlation is **sign-flipped to the anchor's orientation before anything is written**, so labels never silently swap sides. Unmatched axes get fresh identifiers and null labels.

**Identity is append-only, and the write enforces it rather than merely intending it.** A motif that drops out of the current fit — because the selected count fell, or because it simply did not resurface — keeps both its banked label text and its frozen direction, so a later fit that finds it again re-adopts the name instead of minting a stranger. This matters asymmetrically: a loading, a value, an entire fit can be recomputed from inputs that still exist, but a frozen anchor is the *only* surviving record of what a motif's direction was, and a human's name for it is the only record of what it meant. Neither can be regenerated by re-running anything. So the write compares what it is about to persist against what it loaded and **refuses outright** if any anchor or banked label would disappear, rather than writing and reporting afterwards. The one path that may legitimately retire a bank — a change of feature space, whose anchors are no longer comparable — archives the old anchors alongside the old labels instead of overwriting them.

**Labels are two-tailed.** The axes are bipolar: both extremes are real, opposite directions, not "motif present" versus "motif absent". Measurement supports this — there are no U-shaped even components at the extremes, and users' coefficients on the two tails are near-antipodal on the trade-off axes. So each axis may name its positive tail, its negative tail, or both, and some axes genuinely have a nameable motif on only one side. Packaging **refuses to publish** while any axis has neither tail named, which forces the intended loop: new data grows an axis, a human inspects both extremes and names it, publishing proceeds. Per-axis tail structure varies — some axes are trade-offs, one is common competence across both tails, one is dominated by its positive tail — so no symmetry should be read into the linear model.

## 1.15 Publishing

Problems are sorted by rating and split into equal-count groups, so each shard is a contiguous difficulty band and a client can load only the bands near a user's level. Each shard carries its problems, a manifest of per-problem `(rating, slope, floor, motif vector)`, and an offset index into a companion binary of per-cell motif vectors. Those four are published exactly as the fit produced them — the unscaled 80%-clear rating and the two phase-two-calibrated companions (section 1.11) — with no rank baked in and no remapping of the slope into a bounded score. Publishing performs no arithmetic on them whatsoever; it joins and copies.

**One row-order contract deserves emphasis** because violating it is silent. The per-cell capture is in board-scan order and is a superset of the move tree's variations, while the client identifies a played move by its position among the root variations. So the published binary is rebuilt in move-tree order, with an all-zero placeholder row for the "pass" variation that is never embedded, so that binary row *i* is exactly variation index *i*. Since the pass is not the last variation in a large fraction of problems, omitting the placeholder shifts every later row and returns a neighbouring cell's motif vector for every played move after it. The binary's layout revision is folded into the published motif version, so a layout change re-derives every client's stored vectors through the standing invalidation path.

**Why an all-zero row is a safe placeholder** rather than a lie is worth spelling out, because zero is not a neutral value in this space — the loadings are standardized, so an all-zero vector reads as "exactly average on every axis", and if such a row were ever consumed it would enter the weakness model as a confident, wrong observation rather than as missing data. It is safe only because the pass row is **structurally unreachable as an answer**. The pass is in the move tree as a terminator — the generator's variations end in a pass once the position is settled — not as a candidate reply, and every path that can produce a played-move index is keyed by board coordinate (section 2.9). There is no coordinate that resolves to a pass, so no lookup can return its index. The placeholder therefore exists purely to keep the row numbering aligned and is never read.

That also makes zero the consistent convention for "no vector" across the published data: a problem absent from the axis fit gets an all-zero row in the set-wide correct-move sidecar, which the client likewise treats as absent rather than as average. The invariant to preserve is that a zero row is only ever *emitted* where it is provably unreachable or explicitly treated as missing — it must never become the fallback for a vector that failed to load.

Two set-wide sidecars avoid the obvious inefficiency of downloading a multi-megabyte shard to read a hundred bytes: one holds every problem's rating triple by id, and one holds every problem's correct-move motif vector **aligned to the sorted problem index the client already has**, so a row can be fetched by index with no key lookup and no offset table.

**Three independent version stamps** carry three different jobs, and conflating them is a real failure mode: a data version busts caches for the fixed-name files, a ratings version gates the client's re-derivation of stored history, and a motif version gates the embedding re-derivation. A release that only *adds* problems changes the data version but not the ratings version, so new problems become servable lazily with no history walk; a re-rate changes the ratings version and triggers an immediate re-derive.

Publishing is change-detected by hashing each size's inputs, so a curve-only or constants-only release skips the expensive shard rebuild entirely while still passing through the single writer. That hash covers input *data*, not the packaging code, so a format change needs an explicit forced run.

# Chapter 2 — How the client uses them

## 2.1 The division of labour

The client receives **raw** numbers and derives every human-facing quantity itself. Publishing is rank-agnostic: it never computes a rank, never repackages the slope into a bounded quality score, never bakes a rank into a manifest.

On loading a shard, each problem gains exactly two derived fields: a **normalized rank**, from the rating through the published curve, and a **selection weight** equal to the Fisher information one at-rank attempt on it carries, for use in section 2.4. Rating, slope, floor and motif vector stay exactly as published.

**The normalized rank is not a fraction of anything, and is never clamped.** It is the rank index divided by the ladder's label span, and that divisor is the width of the kyu/dan range we put *names* on, not a bound on the value. The published curve's knots do not begin at index zero, and applying the curve extrapolates linearly past both end knots, so a problem easier than the weakest knot lands below zero and the unattempted hard tail — material far beyond where human declarations reach — lands above one. Both are ordinary. Treat it as an unbounded continuous coordinate: never clamp it, never read one half as a midpoint, never read it as a percentile. Section 2.7 depends on this directly; a clamp hidden inside the translation once pinned every strong player to the top band, which is invisible in a label and wrong in a plot.

The selection weight is a client-local derivation with no counterpart upstream — nothing in the backend computes it, and the published slope is the response curve's actual discrimination. Beware that the same word, *quality*, names the backend column holding the calibrated slope **and** this client-side weight, which are different quantities (section 3.4).

The rank curve, the server couplings and the population constants are **inlined into the code bundle** at build time rather than fetched. That is a robustness choice: they are then as available as the code itself, with no runtime fetch, no cache entry to evict, and therefore no offline path that can prevent the app from starting. It also means a curve change is a code release, which is the honest description of what it is.

## 2.2 The shared response curve

One module owns the item-response math for both consumers that need it (the rank estimator and the recall scheduler):

```
P(clear) = floor + (1 − floor − lapse) · sigmoid( slope · (rank gap) + offset(floor) )
offset(floor) = logit( (0.8 − floor) / (1 − floor − lapse) )
```

The offset term is what makes `P(clear) = 0.8` exactly when the user's rank equals the problem's, for *any* slope and floor. Without it the published rating's definition would hold only for an average problem. Floors are clamped below the calibration probability so the offset stays finite, and the lapse comes from the fitted population constants. The backend's anchor computation implements the identical formula; if the two drift apart the calibration loop reopens and the displayed rank stops meaning what the ratings say it means.

The two asymptotes are doing visible work in every estimate. The lapse term is why a single careless failure far below one's level barely moves anything: the raw sigmoid saturates, so the gradient vanishes while the variance stays bounded away from zero, and the slip's contribution goes to zero instead of yanking the estimate down. Symmetrically, the guessing floor is why a lucky clear far *above* one's level is weak evidence: the clear probability there approaches the floor regardless of ability, so success carries little information.

## 2.3 The live rank: a positional-weight window estimate

The headline rank is a **pure function of the recent first-time history** — deliberately, and the consequences are worth stating before the mechanics.

Each attempt is first mapped into internal-rank space through *its own board size's* curve: the position becomes the rank the rating maps to, and the slope is converted from logits-per-rating to logits-per-rank by dividing by the local steepness of the curve. That conversion preserves calibration — the response curve has constant slope in rating space, so in rank space it must vary with the map's local gradient — and it is what lets both board sizes pool onto one axis.

The estimate is then a weighted four-parameter maximum likelihood fit over at most a few hundred of the most recent attempts, with each attempt weighted by a **linear positional ramp**: newest weight one, oldest in window approximately zero. The ramp's purpose is the edge. With a flat window, the attempt aging out at the cap leaves at full weight, so a per-attempt rank change is contaminated by an unrelated old problem dropping off; with the ramp it leaves at approximately zero weight by construction. The window is bounded by sample count only, with no time cutoff, so a long-idle return still uses its real recent history rather than starting cold.

The per-problem slope enters through the Fisher information, so a **sharp problem pins the rank harder than a flat one** — the same discrimination the backend anchor uses, which is what closes the loop between published ratings and displayed rank.

**Serving is above the estimate while it is uncertain.** The serve rank is the estimate plus an upper-confidence bonus proportional to the excess of the standard error over an irreducible floor, and the floor is **rank-dependent, not a constant**: it is the standard error a full window of at-rank problems would still leave, which depends on the **mean per-attempt information** of problems near the user's level — the same floor-aware quantity the selection weight uses, and the same one the estimator itself accumulates. Flat kyu-region curves carry so little rank information that even a full window floors well above a stone, while sharp dan curves floor far below that. A constant floor mis-scales badly across the ladder — it implied a slope only dan problems reach, leaving kyu users perpetually served above their level and never converging. Measuring it from problems already loaded near the estimate keeps this off the network hot path and lets it self-refine as the user's level drifts.

Using the *full* information here rather than the two-parameter approximation is what makes the floor reachable at all, and this is where that distinction is load-bearing rather than cosmetic. The approximation claims strictly more information than a real at-rank window can deliver, so it sets the floor *below* the standard error the estimator actually converges to. Two structural consequences follow, neither a matter of degree: the serve bonus never reaches zero, so every converged user carries a permanent over-serve, and the convergence test fires later than its "within a factor of the best achievable" intent. The selection weight in section 2.4 shares the formula mainly for consistency — within a difficulty-matched pool the floors are similar, so the factor barely moves the ranking there.

Because the estimate is a pure function of recent history, **adopting an account on a new device and merging attempts from another device are the same operation** — recompute from scratch. There is no loop state to warm, no anchor to recover, and every device converges to the same number regardless of how attempts were batched. Merges recompute silently, so the rank change reported after an answer is that problem's effect alone rather than a synced batch's.

## 2.4 Problem selection

Candidates are the fifty problems nearest the serve rank among those loaded, excluding recently answered ones; a thin pool or a nearer unloaded band triggers a background load. Weighting is **two-regime**, replacing an earlier product of the two terms that balanced incommensurable units with one opaque constant:

- **While the rank estimate is still converging**, weight by the Fisher information the problem carries about ability, evaluated at the calibration anchor: the squared slope times a floor-dependent factor. Sharp problems are quadratically preferred, and guessable ones are discounted — for the same 80% clear rate, a problem with a high guessing floor tells you less about where the user sits, because the floor and the ceiling both flatten the response curve's gradient without flattening the outcome's variance. A plain squared slope is the special case of that factor at zero floor and zero lapse, and it always *overstates* a problem's information.
- **Once converged and once the weakness model has trained**, weight by the exponential of the weakness score alone, in its own calibrated units.

Convergence fires at roughly a quarter of terminal information — deliberately early, because past that point extra rank information is worth less than personalization, and because a user parked in a band depletes its sharp problems and converges to the band average regardless, so slope priority stops changing the served set anyway. That fresh-pool phase is exactly when the standard error is high, which is why the two regimes partition where the physics does. It fails closed into the information regime, and flapping across the boundary between consecutive picks is a harmless soft blend.

## 2.5 Serving is at-rank; the recorded history is not

Selection is difficulty-matched at the moment of serving: the chosen problem's *then-current* rating sits within about a stone of the *then-current* serve rank, and the calibration means it should be cleared roughly four times in five. It is tempting to carry that property forward and treat the attempt log as a set of near-zero rating gaps. It is not one, and the gap **widens after the fact**.

Both sides of the comparison move after the attempt is recorded:

- **The problem's rating is retrospective.** It is a fit, not a measurement — re-derived from scratch every time the model is retrained on a larger attempt log. Crucially, the revision is **not** a matter of that problem accumulating its own evidence: with no per-problem parameters, its rating is its fixed features through the shared map, so it is revised whenever the map is, and a problem nobody has attempted since the last run is re-rated just the same. That revision then propagates onto history that has *already happened*: the ratings version changes and every stored attempt's rating fields are rewritten (section 2.10). Nothing preserves the rating a problem had on the day it was served — by design, since the whole history has to be scored on one consistent scale.
- **The user's rank is a moving estimate**, and also drifts for real. An attempt served at the user's level months ago is compared against today's estimate whenever the history is re-scored.

So a serve-time gap of approximately zero decays into a spread. Measured on real logs, **30–44% of attempts sit more than two ranks from the user's rank**. Far-from-rank rows are the normal case in the record, not a rare pathology, and no analysis of the log should assume otherwise. This is why nothing downstream pre-filters them: the response model absorbs the bias inside the estimate — the guessing floor discounts far-below clears, the lapse ceiling caps far-above slips — and both the window estimate and the career decomposition are built to stay well-behaved on the whole unfiltered set. A filter would also discard a large fraction of a long career rather than a fringe.

**What this does and does not license as a convergence test.** It is tempting to read the drift as a per-problem signal — a problem whose rating has stopped moving has been learned, so its remaining gap is irreducible. That does not follow from this model, and the reason is worth stating because the intuition comes from a different model class.

In a design with per-problem parameters, a problem's estimate really is fed by its own attempts and really does converge as they accumulate; churn would then be a per-problem read. Here there are no per-problem parameters (section 1.5). A problem's features are fixed the moment it is generated, so its rating is a function of static inputs and the shared map, and between two runs it moves only when **the map** moves. The map moves for reasons that have nothing to do with that problem: attempts anywhere reshape the shared network, the whitening gauge is re-estimated from a changed attempt distribution, a problem-set top-up refits the activation basis so the features themselves shift, the global calibration scalars are refit, and a single-seed fit carries its own stochasticity. A problem that nobody has attempted since the last run gets re-rated too, by a comparable amount.

Section 1.10 closes the one remaining route. The per-problem idiosyncratic component that a problem's own attempts could teach is exactly what dropout is there to suppress, and the frozen variance-component estimate found it real but negligible after shrinkage at the observed attempt density. So per-problem churn is dominated by global refit movement, and reading it as "how much this problem still has to learn" attributes to one problem what is mostly a property of the whole fit.

What survives is a population-level statement, and it needs one further distinction, because the widening has **two sources and only one of them is an artifact**. Rating revision is retrain-driven and does stop: once successive retrains no longer move ratings materially, that half of the widening has run its course. Genuine ability drift is the other half, it never stops, and it should not — a user who improved really is further from a problem they were served months ago, and the gap that opens is a fact about them rather than an error in the rating. So "the ratings have settled" bounds the artifact, not the total spread, and the residual gap remains a mixture of serve-time estimate error and real ability change.

Making the per-problem claim would take a **differenced** measurement rather than raw churn: compare between-run movement for problems that gained attempts against matched controls — same rating band, same feature neighbourhood — that gained none. The controls absorb the global component, and the difference is what per-problem learning actually occurs. It is worth predicting the result in advance: under section 1.10 that difference should be small, since it is precisely the dropout-suppressed memorization channel measured from another angle. A near-null result would corroborate the variance-component finding rather than contradict it, and a large one would mean the two measurements disagree and something needs explaining.

## 2.6 Career decomposition

The statistics view decomposes a full career in internal-rank space, pooling both board sizes through each attempt's own curve. Three tracks:

- **Skill**, a month-scale kernel-weighted fit, run **local-linear in time** rather than local-constant: the level and a drift are fit jointly and the level is reported, with the drift ridge-shrunk. This is the standard boundary correction — a local-constant estimate at the right edge sees only past data and therefore lags a trending user, while a local-linear intercept has second-order rather than first-order boundary bias. The shrinkage constant is a **smoothing bandwidth, not a drift prior**: it fights the boundary slope's measurement noise, not real trend rates, so deriving it from the measured population drift over-shrinks and silently restores the lag.
- Dense histories are thinned for that fit into frequency-weighted two-dimensional bins over time **and rank**, where each cell's count enters as a *frequency* weight so both the point estimate and its standard error are preserved. Binning by rank as well as time is necessary, not merely tidy: attempts scatter several ranks even between neighbours, so a pure time bin's mean rank loses curvature and biases the logistic through Jensen's inequality.
- **Form**, a session-scale residual against the skill track, evaluated once per session rather than once per attempt — the variance being estimated is session-to-session, so a session is one draw, and a larger session should count more *precisely* (its fit pools more attempts) rather than more heavily. The variance is a variance-components maximum likelihood rather than a moment estimate, because the residual's own measurement variance is wildly heteroscedastic — an all-correct session cannot pin a level at all — and likelihood weighting downweights exactly those, where a moment estimator would be poisoned by them. It is fit **separately by direction**, good days and bad days, since form is not symmetric, and each local estimate is shrunk toward its own global value by the effective number of independent sessions, so one isolated session cannot spike the band.

The headline estimator is also re-run along the chart's time grid, so the plotted headline trace reproduces the live number exactly at its right endpoint, and the solve-time median is computed over the identical weighted window as the rank line it docks.

## 2.7 Translating to other rating systems

The user's **continuous** rank is interpolated through each server's coupling and rounded only for display, so a weak and a strong player within the same band can translate differently. Two deliberate asymmetries:

- The **native rank is untimed**; every **server** translation is **time-adjusted** by the fitted solve-time coefficient, applied in rating space and re-mapped through the curve (exactly, rather than linearized, so it stays correct across knots). Practice here is untimed while server ranks reflect timed play, so a slow solver's untimed rank overstates their timed strength. Dropping the adjustment for the headline is a display choice, made once, in one place.
- The translation itself is never clamped, because the chart needs honest continuous values that extrapolate past the top of the ladder; only the displayed *label* is clamped, at the single place labels are built. A clamp inside the translation once silently pinned every strong value to the ladder's top band — harmless for a label, wrong for a plot.

## 2.8 Recall scheduling

Spaced repetition consumes the **rank**, not the rating. A cold-solve log-odds is formed from problem rank, solving and review time percentiles and a board-size effect; memory stability is an exponential-family map of that log-odds plus a growth term per consecutive success; retention decays exponentially in elapsed time over that stability. The population constants supply the sensitivity, the growth rate and the reference difficulty, and only the per-user base durability is fit, shrunk to the population prior so it is sane with little data and adapts with more.

The recall window opens at the same calibration probability the ratings are defined at and closes lower down, so a review is scheduled to land at the same success margin a novel problem is served at. Stability has **no ceiling** — graduation out of the pool is precisely the streak's exponential interval outgrowing the working history window, so a ceiling turns graduation into a perpetual recycle and the pool can only grow. Due problems then win a serve decision only with a probability set by the volume equilibrium for that user, so the recall share self-stabilizes at any practice volume, and the roll is deterministic in the candidate and the last attempt so that resuming a tab re-derives the same decision rather than rolling again.

## 2.9 Motifs on the client

**Per attempt**, the record stores the problem's correct-move motif vector, the index of the move actually played, and that move's motif vector, fetched by byte range from the shard's per-cell binary. The index is the move's position among the root variations — the same order publishing wrote — so no coordinate arithmetic crosses the boundary.

**A pass can never become that index**, which is the client-side half of the placeholder argument in section 1.15. Answering is a purely geometric act: the board surface converts a tap or click to an intersection, the typed-coordinate entry path produces the same pair of numbers, and there is no pass control anywhere in the answering interface. That coordinate is then resolved against the position's replies by **matching coordinates** — a reply is selected only if its own coordinates equal the clicked ones. A pass has no board coordinate, so it can never match, and a coordinate that matches no reply is simply rejected: the click does nothing and no attempt is recorded at all. The index is taken only *after* a reply has been matched this way, so it is by construction the index of a reply with real coordinates.

The reconstruction path has the same shape and therefore the same guarantee. When an attempt arrives from another device it carries the played move as a board coordinate, and recovering its index means parsing that coordinate and matching it against the replies exactly as the live path does. There is no representation of a pass to parse and nothing for it to match. So both the live and the reconstructed index are provably non-pass, and the placeholder row stays unread by construction rather than by luck.

Passes do appear in **review**, where the solution line is walked to its end and a terminating pass is displayed as part of the line. Review records no attempt and produces no played-move vector, so this never meets the embedding path.

**The weakness model** is a single logistic shared across board sizes, with two coefficient blocks:

```
P(correct) = sigmoid( intercept + γ·problem rank
                      + Σ_k correct coefficient_k · correct vector_k
                      + Σ_k picked coefficient_k  · played vector_k )
```

On correct attempts the played vector *is* the correct vector by definition, so those rows inform only the **sum** of the two blocks; wrong attempts are what separate them. Training uses the recent merged history under the mandatory per-axis empirical-Bayes prior applied to *both* slots of each axis. Because the shipped precision already carries a factor of two for exactly this reason (section 1.13), the implied prior on the identified sum is the measured between-user variance rather than double it — an identity that holds for any axis whose precision is not sitting at one of the bounds the population fit clamps it to. A missing or wrong-length prior vector makes the client **skip training** rather than fabricate one — which is why changing the axis count requires refitting the population constants before publishing. A Laplace posterior is retained: diagonal standard errors plus, per axis, the covariance between its two coefficients.

**One term the backend model has and this one does not** is the population residual-difficulty head of section 1.14. That head is quarantined at *axis definition* time so that difficulty cannot become an axis, which is a different job from anything happening here — the client takes the axes as given and fits only per-user coefficients on them. Even so, the structure it modelled is unmodelled here: the rank term is per-user and free, but the residual head was defined precisely as the difficulty structure rank leaves behind. Three things bound what that can do. The axes are pushed toward zero correlation with the residual head over the whole problem set, so the omitted term is close to orthogonal to the regressors by construction; an omitted covariate orthogonal to the included ones attenuates their coefficients toward zero rather than displacing them, which errs toward fewer findings rather than more; and the held-out criterion that selects the axis count scores the axes in this same residual-free per-user form, so every shipped axis earned its place *under* the omission rather than in spite of it.

What is not bounded is the case where the two correlate within one user's served band even though they do not over the corpus — serving is difficulty-restricted, so that is possible — which would put a common offset on every user's coefficient for that axis, and a common offset is exactly what a level-one test against zero cannot tell from a real weakness. This is now measured on every run. The population fit of section 1.13 produces a per-user coefficient for every axis on the way to the variance component, and it forms that component as a second moment about **zero** rather than about the fitted mean — the correct update for the prior actually shipped, but the between-user variance only if the pooled mean really is zero. That mean is now accumulated alongside it and reported per axis as a share of the second moment: how much of what ships as variance is really displacement. On the current population every axis passes with room to spare, and the fit halts past a bar on that share rather than on significance — with hundreds of users a negligible mean sits many standard errors from zero, so a significance test would halt on nothing that matters. The share is also the only form that cannot be evaded by rescaling an axis: shifting a loading is absorbed by the free per-user intercept, and scaling it moves mean and spread together, so mean-over-spread is invariant and no normalization of the shipped values can cure a breach. A pooled mean that is credibly non-zero is, by the axes' own design rule, a rating-model miscalibration to fix upstream rather than a user weakness to display — so the halt names the offending axis and points back at the quarantine of section 1.14. Re-centring the client's prior on a shipped per-axis mean is the fallback for a mean that turns out to be genuinely about users rather than problems, not the first response: it would make the numbers self-consistent while leaving an axis carrying difficulty that belongs to the rating model.

**Selection scores the contrast** between the two blocks against a candidate's correct-move vector, not their sum. The contrast is the identified over/under direction: it up-weights motifs the user underplays or is generically weak at, and down-weights motifs the user *overplays*. Equivalently it treats the unseen problem's generic wrong move as the negation of its correct move — to first order, when wrong, a user plays away from the correct move along their weak axis — which is candidate-varying and therefore actually informs the ranking, whereas a fixed generic move would cancel out of a normalized sampling weight. This replaced a sum-based score that applied the played-move coefficient to the correct move directly, a category error that **inverted the overplay case** and fed an overplayer more of exactly the problems they should have seen less of. With no separating signal the prior shrinks the played block toward zero and the contrast degrades gracefully to the correct-move block alone.

**The findings panel runs two-level detection**, and the split exists because the two questions have different identifiability:

- **Level one — is this axis a weakness?** From the posterior of the identified **sum**, requiring credible non-zero mass. Never the correct/played split, which is prior-dominated because the large majority of rows have played equal to correct. An earlier scheme tested the split directly and its gate was structurally always tripped by that collinearity, so only one of its four outcomes could ever render. Since the axes are bipolar, a credibly negative sum flags the positive-tail motif and a credibly positive sum flags the negative-tail motif — the latter only surfacing when that tail is actually named, since an unnamed tail has nothing actionable to say.
- **Level two — which way do they err?** A paired sign test on the played-minus-correct loading over the user's own wrong attempts, each error attributed to the flagged axis with the largest absolute contrast since axes co-load, with an exact posterior on the direction. Overshoot, undershoot, and an honest "inconsistently" residual when neither is credible. This level needs no model at all and no assumption about which alternative moves are reasonable — the single-solution invariant makes the correct move the canonical reference.

**A per-axis bar alone would not control how many findings are wrong, and this is a case where the natural fix is the wrong one.** Level one screens *every* axis, and the axis count grows with the problem set (section 1.14), so a fixed credibility bar per axis lets the expected number of spurious findings grow linearly with the number of axes — the panel would get noisier precisely as the data got better, which is the opposite of what more data should buy.

The control is therefore an **expected-false-finding budget** rather than a stricter bar. Candidates that clear the per-axis bar are admitted strongest-first while the running sum of their posterior error probabilities — one minus each finding's own confidence — stays within the budget. The reason to spend a budget in exactly this currency is that, by linearity of expectation, that running sum *is* the expected number of spurious findings in the list actually shown. So the bound is pathwise, holds for any number of axes, and — the part that matters here — **assumes nothing about independence**. The axes co-load by construction and their posteriors are correlated, so a family-wise correction dividing the bar by the axis count would have to assume that dependence away, and would additionally spend power on axes that never came close to the bar. Under the budget a single strong finding is admitted exactly as it would have been; it is a long tail of marginal ones that gets truncated.

One constraint ties the two numbers together: the budget must not be smaller than one minus the per-axis bar, or even the single strongest admissible finding is unaffordable and the panel can never show anything.

Level two needs no such correction, because it does not create findings — it phrases one level one already admitted, so an error there is a mislabel rather than an extra finding. It does, however, run on the truncated set, so that its winner-take-all attribution of each mistake to a single axis cannot divert evidence onto rows the user will never see.

One detail of the level-one variance is worth stating because getting it wrong is silent: the posterior variance of the sum needs the **covariance** between the two coefficient blocks, and that term must be read, never defaulted. Under the collinearity that makes the split unidentifiable in the first place, the cross-covariance is strongly negative and dominates the sum's variance, so substituting zero for a missing entry does not err on the safe side — it moves the threshold outright. A missing entry means a stale array rather than a genuine zero, and is treated as such.

Findings expand into links to matching past mistakes, with the per-attempt evidence threshold scaled to the finding's own confidence, and problems currently in the recall window withheld so that browsing examples cannot be used to ace an imminent review.

**In review**, a problem's own strongest motifs are surfaced: components clearing a z-score threshold, a small number of them, each labelled from the tail it actually sits on.

## 2.10 Re-derivation and invalidation

Stored history holds derived per-attempt values that go stale when the backend refits, so three independent gates re-derive them:

- **Ratings changed** → re-derive every stored attempt's rating, rank, slope and floor from the set-wide rating sidecar. The cold, archived tail matters here as much as the recent window: its values are frozen at archival time, so after a re-rate they are stale *and device-dependent* (each device archived at a different rating era) — and the career chart plots them, which is exactly how two synced devices' charts once diverged at their left edge.
- **Curve changed but ratings did not** → recompute only the rank from the stored rating; no problem data needs fetching at all.
- **Motif version changed** → wipe and refill motif vectors. Correct-move vectors come from the index-aligned sidecar as a single small range request per problem; played-move vectors are the only fill that must still visit shards, because it needs per-problem byte offsets.

A problem that has left the set has its rating fields **stripped** rather than left stale — the attempt remains in the record but is skipped by every estimate, which is the honest representation of "this happened but is no longer scoreable". Version stamps are written **last**, once, after all work has persisted, so an interruption leaves nothing stamped and the whole re-derivation repeats idempotently.

## 2.11 Server-side reuse

Two server-rendered surfaces consume the same quantities, and both now run **literally the same** window estimator as the client rather than a reimplementation or a proxy. The leaderboard runs it over each user's materialized attempt buffer. The community rank histogram, which used to take a different route entirely, runs it over the same buffers — the change is recent and the route it replaced is worth recording, because the reasoning that justified it was subtly wrong in a way that only a measurement exposed.

**The histogram is one player per bin, ranked by their own fit.** For every player active in the window it takes the untimed onlymove rank the leaderboard already holds — the same weighted four-parameter fit over the same trailing window the front page displays — rounds it to a rank, and counts players. Players below the board's uniform minimum-attempt gate carry no rank and are left out, exactly as they are left off the leaderboard. Hidden profiles are counted: hiding withholds a name and a country, never the rank. The country distribution is built from the same single scan of that table, so the whole community section costs one pass over a table that is pruned to roughly weekly-active size — the same pass the leaderboard page itself makes.

**What it replaced was a serving proxy**, and the shortcut existed for cost: rather than pull every user's history for a fit, it took each user's distinct first-time problems in the window, replaced each rating with the midpoint of its shard's band, mapped that through the curve, and averaged — no likelihood, no ability solve, no use of success or failure at all, just the mean difficulty of what the selector handed out. Its validity rested entirely on the serving property, that a served problem's rating sits at the user's level, which section 2.5 establishes is a property of **the moment of serving** that decays afterwards. The seven-day window was the defence: short relative to the retrain cadence, so no retroactive revision has intervened for almost any attempt in it, and short relative to real improvement, so both sides of the comparison are nearly static.

**That defence was sound and beside the point, because two other errors did not need time to pass.** The selector aims at the *serve* rank — the estimate plus the upper-confidence bonus of section 2.3 — which is non-negative by construction and largest exactly where the posterior is loose, so an unconverged player was read too strong; at the convergence threshold the bonus is still of the order of the local standard-error floor, around a stone in the flat kyu region, and a session's worth of problems was enough to enter the histogram while convergence takes on the order of a hundred attempts. And a problem's rating was replaced by the **midpoint of its shard's rating range** while shards are equal-count (section 1.15), so tail bands are wide and their mass is not symmetric about the midpoint — a per-band offset whose variance averaging reduces but whose bias it does not, compounded out there by the pool of nearest loaded problems being one-sided. The first error inflates the weak end, the second deflates the strong end, and the proxy's net effect was to **compress the distribution toward the middle**.

Measured against the fit, on the production snapshot: matched player for matched player the proxy was close in the middle of the ladder and fanned at the ends — reading players at 15k and weaker around seven tenths of a rank too strong, a quarter of a rank through the single-digit kyus, and dan players about one rank too weak. The larger change is not a bias at all but the **population**: the proxy counted anyone who answered a handful of problems in the window, the fit counts players who carry a rank, so beginners below the gate leave the histogram and established players having a light week enter it. On the same snapshot that moved the mean by about two ranks — more than either bias — which is worth stating plainly, because it means the new histogram answers a slightly different question: the rank distribution of *ranked players*, not of everyone who opened the app this week.

The general lesson is the one section 2.5 states from the other side. A weighted likelihood fit uses each attempt's current rating, slope and floor, so it is indifferent to how far a problem sat from the user's level — which is why it can look at a whole career, including the large fraction of far-from-rank rows. A serving proxy has to assume the gap is zero, and so could only ever look at a window it had to argue was fresh, while inheriting every distortion sitting between the selector's aim and the recorded rating.

Sharing the interpolation and label code between server and client is what stops the resulting histogram from drifting against the client's own rank display.

## 3.1 Run order

Generation and evaluation take a mandatory board size and run once per size; everything downstream iterates both sizes and takes no size argument.

```
pipeline.generate_tsumegos <size>      → tsumegos/<size>/*.sgf
pipeline.benchmark_bots <size>         → attempts/<size>/*.txt
pipeline.extract_activations           → activations/<size>/<id>.npz
pipeline.cache_move_features           → activations/_signal_cache/move_evals_<size>.npz
pipeline.train_rating                  → ratings/
pipeline.build_axes                    → embeddings/joint/
pipeline.package_for_pwa               → pwa/tsumegos/          (single writer)
```

Board-independent and outside the in-order run, both needing `pipeline.fetch_database` first and neither needing a GPU:

```
pipeline.map_rating_to_rank            → ratings/rating_to_rank.json, ratings/rank_map.json
pipeline.fit_population_constants      → ratings/population_constants.json
```

Two roll-up caches are *not* self-maintaining after a problem-set top-up and must be refreshed before training: the correct-cell activation vectors (`activations/_signal_cache/correct_vecs_<size>.npy` plus its id list, built by `auxiliary.inspect_activation_signals._build_cache`) and the move-evaluation cache. A stale id list silently drops the new problems from the rated set. The per-problem artifacts are incremental by file existence and need no attention.

`pipeline.build_axes` must run after both `train_rating` and `map_rating_to_rank`, since its features include the rating outputs and the derived rank.

**Id collisions** are handled by `tsumego_id_taken` in `pipeline/generate_tsumegos.py`, which checks the id across *all* board sizes and makes the generator discard the candidate (counted as `duplicate_ids_skipped` in the run stats) rather than overwrite. One historical exception survives: four cross-size id pairs predate that guard, so a handful of ids exist as both a 9×9 and a 13×13 problem. Anything keyed by id alone must therefore resolve size from the SGF corpus rather than from the activation-cache id lists — `corpus_tid_size` in `utils/residual_axes.py` exists for exactly this, and skipping it mis-sizes the row's features and aborts packaging. Inside the rating trainer the issue does not arise, since its feature keys are `(size, tsumego_id)` pairs throughout. `auxiliary/check_corpus_ids.py` re-verifies the invariants and can emit a rename map if a future defect ever needs surgery.

**`quality` is an overloaded name — three distinct meanings, and the code comments are not consistent about it.** Track the value, not the label:

| Where | Name | Value |
| --- | --- | --- |
| `ratings/<size>/tsumego_quality_final.csv` | column `quality` | the **calibrated slope**, `slope_scale · slope` |
| shard `metadata.json` | field `slope` | the same calibrated slope, copied verbatim |
| client problem object | field `quality` | **the square** of that, the selection weight |

So the backend's `quality` and the client's `quality` differ by a square, and the shipped field named `slope` *is* the backend's `quality` column. The publishing step reads the `quality` column into a variable called `slope_map` and writes it out as `slope`, which is where the rename happens; its docstring calls that value "the raw 2PL slope", where "raw" means unrepackaged rather than uncalibrated (section 1.11). The rating alongside it is genuinely unscaled, since it is derived before the calibration scalars are applied — so `metadata.json` mixes one unscaled and two scaled values, by design.

Each shard's `metadata.json` entry is `{filename, rating, slope, floor, embedding}` — the client derives `rank` and `quality` on ingest. `embedding_meta.json`, the curve, the couplings and the population constants are **inlined into the JS bundle** at build time; the served copies of the inlined ones are dropped from the dist.
