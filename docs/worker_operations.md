## The HTTP surface

`pwa/src/index.js` is the entrypoint. Static assets ship via the `[assets]` binding in `wrangler.toml`, and an SPA fallback derives board size from `/9` or `/13`. Handlers live under `pwa/src/handlers/`.

| Route | What it does |
| --- | --- |
| `POST /report` | Per-attempt logging. **`createdAt` is REQUIRED in the payload** — the CLIENT owns the event time: it mints one ms per attempt, stores it as the entry's `date`, and the row is inserted VERBATIM, so `row.created_at === entry.date` exactly and sync matching is exact. The server only sanity-bounds it, **REFUSING rather than rewriting** — `400 {error, serverNow}` on missing, future (+2 min) or stale (−7 d) — so the client can self-correct once and resend; a silent rewrite would recreate the duplicate-mint precondition. Responds `{serverId, userSeq, digest}` with no `createdAt` echo. `serverId` is the row id stamped on the matching history entry (its presence = acked, and it is the id-cursor and digest key), so sync pulls skip the device's own rows. `userSeq` is the per-profile attempt count and is the **digest sync signal**: a jump past the device's expected sequence means another device wrote, so pull. |
| `POST /report-backfill` | Inserts historical attempts with their client event time, at the id frontier. This is why the fetch cursor must be `id`. |
| `POST /sync` | Account sync. Pages the user's reports newer than the client's **`sinceId` AUTOINCREMENT-id cursor** — gap-free for rows inserted with a historical `created_at`, such as an offline flush — at 1000 rows. Every response also carries a `serverSeq`/`serverDigest`/`serverMaxId` summary for the cheap in-sync check. An optional `limit` shrinks the page; **`limit: 1` is the client's frontier/existence probe**. A request without a valid `sinceId` gets an empty no-op, so it just resyncs on reload. |
| `GET /push/vapid-public-key`, `POST /push/subscribe`, `POST /push/unsubscribe` | Web Push registration. |
| `POST /schedule` | Recall-reminder schedule, in **diff mode**: the client keeps a per-row hour-rounded snapshot in local storage and sends only changed rows plus explicit removals, because each upsert bills the row *plus its two partial indexes* and replace-all is the heaviest D1 write path. A legacy `{schedule}` replace-all is still accepted. **Every call, even an empty diff, bumps `push_subscriptions.last_seen_at`** — the cron's mid-session suppression watermark. |
| `POST /rank-survey` | Per-server rank declarations → `rank_surveys`. |
| `POST /share-event` | Share-link create/open analytics → `share_events`. The client sends user, problem and size and, for opens, `document.referrer`; the Worker stamps the Cloudflare edge geo-IP `country`. |
| `POST /link`, `POST /unlink` | Bind or release this account's self-selected EGD or AGA player. See `leaderboard_and_community_stats.md`. |
| `POST /google/signin`, `POST /google/link`, `POST /google/unlink` | Google sign-in. `signin` only RESOLVES which code a verified Google account is bound to and writes nothing. See `client_sync_and_cache.md`. |
| `GET /profile` | The federation binding, the `hidden_profiles` flag and a `google` boolean, `no-store` — the Account dialog's whole panel in one read. Its URL is the userId and nothing else, so it **belongs in the service worker's dynamic-GET bypass list**. |
| `GET /server-stats` | Serves the cached community-stats blob. |
| `scheduled()` | Cron-driven: walks `recall_schedule` to deliver due Web Push notifications, **and** recomputes `server_stats` when it is ≥23 h old or the version changed. |

## D1 schema

Binding `DB` → database `tsumego-reports`. Schema lives in `pwa/schema.sql` (idempotent `CREATE … IF NOT EXISTS`); apply new tables and indexes to the remote with `npx wrangler d1 execute tsumego-reports --remote --file=schema.sql`.

- **`tsumego_reports`** — the per-attempt log: `user_id, problem, success, created_at, size, move, time_used, review_time, is_repeat`, plus the per-profile sync-digest columns `user_seq` (attempt count) and `running_sum` (the exclusive-prefix sum of row hashes), lazy-seeded in the INSERT. **There is no `UNIQUE(user_id, problem)` constraint**, so repeat attempts produce their own rows. Two indexes, both load-bearing: **`idx_tsumego_reports_created`** on `created_at` for the server-stats window scan, and **`idx_tsumego_reports_user_id`** on `(user_id, id)` for the per-user id-cursor `/sync` scan and the digest's constant-time latest-row lookup. **When retiring an index, drop it — on the live D1 too — only AFTER the deploy that stops reading it.**
- **`push_subscriptions`** — one row per device, `endpoint` PK with `user_id` indexed, so the recall cron fans each due reminder out to all of a user's devices. Carries the per-device throttle, dead-endpoint cleanup and per-account active-session suppression.
- **`recall_schedule`** — what the cron walks.
- **`rank_surveys`** — self-reported ranks per server.
- **`share_events`** — share-link create/open analytics.
- **`external_ids`** — the leaderboard identity binding, one row per LINKED account, holding the `egd_pin`/`aga_id` plus the `display_name`/`country_code` snapshotted at link time. The per-column UNIQUE indexes are what make a claim exclusive.
- **`hidden_profiles`** — presence means leaderboard opt-out.
- **`google_accounts`** — `google_sub` PK → `user_id` UNIQUE, which is the exclusivity in both directions. The opaque subject id ONLY, no address.
- **`server_stats`** — single-row JSON cache, `key='latest'`.

A `--full` export carries only tables that had rows at export time, whereas the incremental fetch's regenerated dump carries every table it discovered remotely — so an empty table such as `history_refresh_log` is present in one and absent from the other.

## Write-endpoint guards and the maintenance freeze

**Write endpoints are guarded by two cheap, in-Worker abuse/quota layers plus an external WAF rule.** A spoofed/garbage `/report` (or `/schedule`, `/rank-survey`, `/share-event`, `/push/*`) doesn't just hurt integrity — the INSERT spends D1 write quota, and until purged the row inflates every server-stats `created_at >= ?` window scan for 7 days (read quota, the exact thing `idx_tsumego_reports_created` fights). So writes are defended *upstream* of D1, cheapest-first: (1) an **outer Cloudflare WAF rate-limiting rule** (ZONE config, so `wrangler deploy` never touches it — applied out of band like `pwa/migrations/*.sql`, with its desired state + zone/ruleset/rule ids in **`pwa/waf/rate-limit-rule.sh`** (`show` prints the live rule and flags drift, `apply` PATCHes the desired state; `CF_AUTH_TOKEN` from the env, never committed) and its numbers mirrored in `wrangler.toml`'s comment — note `apply` is a PATCH, so it updates but cannot RECREATE a deleted rule: that needs a POST to the ruleset's `/rules` endpoint and mints a new id to paste back into the script; 100 POST/10s per IP matching **ALL POSTs by method** — no path list, so every write endpoint incl. new ones like `/register` is covered automatically, nothing to add per-endpoint — blocked requests never invoke the Worker = zero Worker+D1 cost); (2) **per-IP Workers rate-limit bindings** (`RL_REPORT` 100/60s for the high-volume `/report`, `RL_WRITE` 50/60s shared by the rest), declared as `[[unsafe.bindings]] type=ratelimit` in `wrangler.toml` and checked in the `fetch` dispatcher **before any handler touches D1** (`rateLimited()` keys on `CF-Connecting-IP`, **fails open** on a missing binding or limiter error so a misconfig never drops a legit write); (3) **in-memory format validation** in each handler (no D1 reads) — `isValidProblemId` (`^[0-9a-f]{8}$`, the symmetry-canonical hash) and `isValidUserId` (`^[A-Za-z0-9_-]{1,40}$`) reject malformed identity fields before the INSERT. Limits were calibrated from the production dump (heaviest real user ≈24 reports/60s incl. review re-reports, p99.9=20), giving ~4× headroom for NAT'd shared IPs. **Deliberately format-only** — we don't check the problem id against the real corpus (that needs a bundled set/Bloom filter); the rate limiter bounds valid-looking spoofs. Two consequences: any **deploy smoke test must POST a real 8-hex `problem` id** (a free-form marker is rejected with 400), and `pipeline.fetch_database` is **unaffected** — `wrangler d1 export` hits `api.cloudflare.com` with an API token, a different hostname than the `onlymove.net` zone the WAF guards (the binding limiter never runs for it either). Activating any of this needs a manual `npm run deploy` (+ the manual WAF rule); there's no auto-deploy. **A fourth, deliberate layer is the MAINTENANCE FREEZE** (`MAINTENANCE_MODE`, a wrangler SECRET rather than a `[vars]` entry; `maintenanceFrozen`/`serviceUnavailable` in `guards.js`): `"1"` makes EVERY POST route return `503 {error:'maintenance'}` with `Retry-After`, and makes `scheduled()` early-return; anything else, unset included, reads as open. **A secret so it can be flipped without a build, a commit or a deploy** — `printf 1 | npx wrangler secret put MAINTENANCE_MODE` pushes a new Worker version reusing the deployed code bundle, which keeps the property the freeze depends on (a version rollout replaces the deployed code everywhere, rather than leaving a per-colo cached value that never converges) — though it lands UNEVENLY over a few seconds, so a state counts as read only once several consecutive probes agree, and the authoritative check that nothing slipped through stays the before/after `MAX(id)` comparison while dropping the clean-tree gate and the throwaway FREEZE ON/OFF commit pair the old `[vars]` flip needed. **Do not reintroduce a `[vars]` entry of that name**: it would collide with the secret and win on the next `wrangler deploy`, silently thawing an open window. It is checked in the `fetch` dispatcher **before the rate limiter and before any handler touches D1**, so a frozen request costs one Worker invocation and zero D1. It exists so any snapshot-relative operation can run against tables that are standing still — DB surgery (`auxiliary/purge_tsumegos.mjs`), whose digest fix-ups are stated RELATIVE to a snapshot, so a row inserted between snapshot and apply would be shifted against a chain it never joined, silently; and the leaderboard refresh (`auxiliary/update_leaderboard_ranks.mjs`), whose read-modify-write of `buffer` would permanently drop anything landing in between (see the leaderboard note above) — and which, because the flag is a secret, **opens and closes its own window**: `--remote` freezes, waits for a probe to confirm it, runs `pipeline.fetch_database` inside the window, applies, and thaws on EVERY exit path including `SIGINT` (a thaw it cannot confirm is a loud non-zero exit, never a silent one). Started against an ALREADY-frozen production it takes no ownership: it leaves the freeze on and skips the fetch, which is the runbook's step-8 case. Both are read-modify-write against a snapshot, and the freeze is what makes their race impossible rather than unlikely. Freezing is safe because `sendReport` only acks on `res.ok`: a 503 leaves the attempt un-acked and the durable outbox re-uploads it afterwards with its original event time, so the freeze reuses the offline path instead of adding a client-side maintenance mode. `/sync` is frozen too (though it is a read) so no client can observe a half-applied surgery. GETs stay up so the app keeps serving problems; the one writer left is the lazy `server_stats` recompute, which only rewrites its own cache row. Procedure in `docs/db_surgery_runbook.md`.

## pipeline.fetch_database

**`pipeline.fetch_database` is incremental by default and read-cost-sensitive.** D1 bills rows read, and `tsumego_reports` is ~290k rows (>99% of the DB) while every other table combined is <1000 — so re-exporting the whole DB each run would waste almost all of those reads. The default path pulls **only new `tsumego_reports` rows via `WHERE id > MAX(local id)`** (`id` is the table's `AUTOINCREMENT` PK), which the PK index serves reading just the matching rows, and re-fetches every *other* table whole (cheap). **The cursor MUST be `id`, not `created_at`:** the PWA→D1 backfill (`POST /report-backfill`, see the account-sync note) inserts historical attempts with their *client* `created_at`, so a `created_at` cursor would silently skip those backfilled rows even though they were just inserted — whereas `AUTOINCREMENT id` always increases with insertion order, catching them. `tsumego_reports` being append-only (no `UNIQUE`, never UPDATEd/DELETEd) makes the `id` cursor provably gap-free: after a complete pull we hold the contiguous prefix `[1..N]`, and all new rows are `> N`. The fetch is **schema-tolerant and never hardcodes the table list** (except the one name `tsumego_reports`): it discovers tables from the remote `sqlite_master`, full-refreshes each (drop + recreate from the remote DDL + refill), and only if `tsumego_reports`' column set drifts does it re-pull that table whole. Implementation: `db/d1.sqlite` is the **canonical merge target** (rows fetched via `wrangler d1 execute --remote --json`, inserted parameterized — zero escaping bugs), then `db/d1.sql` is **regenerated from it** in a quoted-table-name + positional-`VALUES` form that every `.sql`-parsing consumer in the repo accepts (some require the quoted name, others forbid a column list — this form satisfies both). The `db/` snapshot is read-only as far as the pipeline is concerned; the **wrangler dev (local) D1 is the read-write one** (the PWA is tested against it and scribbles disposable rows into it), so each fetch simply **resets it to the remote state by `shutil.copyfile`-ing `d1.sqlite` straight onto the miniflare D1 file** (`.wrangler/state/v3/d1/miniflare-D1DatabaseObject/<hash>.sqlite`, the one that isn't `metadata.sqlite`) and deleting its stale `-wal`/`-shm` sidecars — discarding local test writes on purpose, and far faster than a wrangler reimport (verified: D1 read/write still work; its internal `_cf_*` tables aren't required). Stop `npm run dev` before fetching — overwriting the file under a live workerd corrupts its view. The wrangler-import path (`update_local_d1`) survives only as the first-run fallback that *creates* a not-yet-existing local D1. `--full` forces a complete `wrangler d1 export` + SQLite rebuild (also auto-used when no `d1.sqlite` baseline exists). Still WAF-unaffected — both `d1 export` and `d1 execute --remote` hit `api.cloudflare.com`, not the guarded `onlymove.net` zone.
