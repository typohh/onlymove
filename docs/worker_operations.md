## Write-endpoint guards and the maintenance freeze

**Write endpoints are guarded by two cheap, in-Worker abuse/quota layers plus an external WAF rule.** A spoofed/garbage `/report` (or `/schedule`, `/rank-survey`, `/share-event`, `/push/*`) doesn't just hurt integrity — the INSERT spends D1 write quota, and until purged the row inflates every server-stats `created_at >= ?` window scan for 7 days (read quota, the exact thing `idx_tsumego_reports_created` fights). So writes are defended *upstream* of D1, cheapest-first: (1) an **outer Cloudflare WAF rate-limiting rule** (ZONE config, so `wrangler deploy` never touches it — applied out of band like `pwa/migrations/*.sql`, with its desired state + zone/ruleset/rule ids in **`pwa/waf/rate-limit-rule.sh`** (`show` prints the live rule and flags drift, `apply` PATCHes the desired state; `CF_AUTH_TOKEN` from the env, never committed) and its numbers mirrored in `wrangler.toml`'s comment — note `apply` is a PATCH, so it updates but cannot RECREATE a deleted rule: that needs a POST to the ruleset's `/rules` endpoint and mints a new id to paste back into the script; 100 POST/10s per IP matching **ALL POSTs by method** — no path list, so every write endpoint incl. new ones like `/register` is covered automatically, nothing to add per-endpoint — blocked requests never invoke the Worker = zero Worker+D1 cost); (2) **per-IP Workers rate-limit bindings** (`RL_REPORT` 100/60s for the high-volume `/report`, `RL_WRITE` 50/60s shared by the rest), declared as `[[unsafe.bindings]] type=ratelimit` in `wrangler.toml` and checked in the `fetch` dispatcher **before any handler touches D1** (`rateLimited()` keys on `CF-Connecting-IP`, **fails open** on a missing binding or limiter error so a misconfig never drops a legit write); (3) **in-memory format validation** in each handler (no D1 reads) — `isValidProblemId` (`^[0-9a-f]{8}$`, the symmetry-canonical hash) and `isValidUserId` (`^[A-Za-z0-9_-]{1,40}$`) reject malformed identity fields before the INSERT. Limits were calibrated from the production dump (heaviest real user ≈24 reports/60s incl. review re-reports, p99.9=20), giving ~4× headroom for NAT'd shared IPs. **Deliberately format-only** — we don't check the problem id against the real corpus (that needs a bundled set/Bloom filter); the rate limiter bounds valid-looking spoofs. Two consequences: any **deploy smoke test must POST a real 8-hex `problem` id** (a free-form marker is rejected with 400), and `pipeline.fetch_database` is **unaffected** — `wrangler d1 export` hits `api.cloudflare.com` with an API token, a different hostname than the `onlymove.net` zone the WAF guards (the binding limiter never runs for it either). Activating any of this needs a manual `npm run deploy` (+ the manual WAF rule); there's no auto-deploy. **A fourth, deliberate layer is the MAINTENANCE FREEZE** (`MAINTENANCE_MODE`, a wrangler SECRET rather than a `[vars]` entry; `maintenanceFrozen`/`serviceUnavailable` in `guards.js`): `"1"` makes EVERY POST route return `503 {error:'maintenance'}` with `Retry-After`, and makes `scheduled()` early-return; anything else, unset included, reads as open. **A secret so it can be flipped without a build, a commit or a deploy** — `printf 1 | npx wrangler secret put MAINTENANCE_MODE` pushes a new Worker version reusing the deployed code bundle, which keeps the property the freeze depends on (a version rollout replaces every colo, so one probe confirming it stands for all of them) while dropping the clean-tree gate and the throwaway FREEZE ON/OFF commit pair the old `[vars]` flip needed. **Do not reintroduce a `[vars]` entry of that name**: it would collide with the secret and win on the next `wrangler deploy`, silently thawing an open window. It is checked in the `fetch` dispatcher **before the rate limiter and before any handler touches D1**, so a frozen request costs one Worker invocation and zero D1. It exists so any snapshot-relative operation can run against tables that are standing still — DB surgery (`auxiliary/purge_tsumegos.mjs`), whose digest fix-ups are stated RELATIVE to a snapshot, so a row inserted between snapshot and apply would be shifted against a chain it never joined, silently; and the leaderboard refresh (`auxiliary/update_leaderboard_ranks.mjs`), whose read-modify-write of `buffer` would permanently drop anything landing in between (see the leaderboard note above) — and which, because the flag is a secret, **opens and closes its own window**: `--remote` freezes, waits for a probe to confirm it, runs `pipeline.fetch_database` inside the window, applies, and thaws on EVERY exit path including `SIGINT` (a thaw it cannot confirm is a loud non-zero exit, never a silent one). Started against an ALREADY-frozen production it takes no ownership: it leaves the freeze on and skips the fetch, which is the runbook's step-8 case. Both are read-modify-write against a snapshot, and the freeze is what makes their race impossible rather than unlikely. Freezing is safe because `sendReport` only acks on `res.ok`: a 503 leaves the attempt un-acked and the durable outbox re-uploads it afterwards with its original event time, so the freeze reuses the offline path instead of adding a client-side maintenance mode. `/sync` is frozen too (though it is a read) so no client can observe a half-applied surgery. GETs stay up so the app keeps serving problems; the one writer left is the lazy `server_stats` recompute, which only rewrites its own cache row. Procedure in `docs/db_surgery_runbook.md`.

## pipeline.fetch_database

**`pipeline.fetch_database` is incremental by default and read-cost-sensitive.** D1 bills rows read, and `tsumego_reports` is ~290k rows (>99% of the DB) while every other table combined is <1000 — so re-exporting the whole DB each run would waste almost all of those reads. The default path pulls **only new `tsumego_reports` rows via `WHERE id > MAX(local id)`** (`id` is the table's `AUTOINCREMENT` PK), which the PK index serves reading just the matching rows, and re-fetches every *other* table whole (cheap). **The cursor MUST be `id`, not `created_at`:** the PWA→D1 backfill (`POST /report-backfill`, see the account-sync note) inserts historical attempts with their *client* `created_at`, so a `created_at` cursor would silently skip those backfilled rows even though they were just inserted — whereas `AUTOINCREMENT id` always increases with insertion order, catching them. `tsumego_reports` being append-only (no `UNIQUE`, never UPDATEd/DELETEd) makes the `id` cursor provably gap-free: after a complete pull we hold the contiguous prefix `[1..N]`, and all new rows are `> N`. The fetch is **schema-tolerant and never hardcodes the table list** (except the one name `tsumego_reports`): it discovers tables from the remote `sqlite_master`, full-refreshes each (drop + recreate from the remote DDL + refill), and only if `tsumego_reports`' column set drifts does it re-pull that table whole. Implementation: `db/d1.sqlite` is the **canonical merge target** (rows fetched via `wrangler d1 execute --remote --json`, inserted parameterized — zero escaping bugs), then `db/d1.sql` is **regenerated from it** in a quoted-table-name + positional-`VALUES` form that every `.sql`-parsing consumer in the repo accepts (some require the quoted name, others forbid a column list — this form satisfies both). The `db/` snapshot is read-only as far as the pipeline is concerned; the **wrangler dev (local) D1 is the read-write one** (the PWA is tested against it and scribbles disposable rows into it), so each fetch simply **resets it to the remote state by `shutil.copyfile`-ing `d1.sqlite` straight onto the miniflare D1 file** (`.wrangler/state/v3/d1/miniflare-D1DatabaseObject/<hash>.sqlite`, the one that isn't `metadata.sqlite`) and deleting its stale `-wal`/`-shm` sidecars — discarding local test writes on purpose, and far faster than a wrangler reimport (verified: D1 read/write still work; its internal `_cf_*` tables aren't required). Stop `npm run dev` before fetching — overwriting the file under a live workerd corrupts its view. The wrangler-import path (`update_local_d1`) survives only as the first-run fallback that *creates* a not-yet-existing local D1. `--full` forces a complete `wrangler d1 export` + SQLite rebuild (also auto-used when no `d1.sqlite` baseline exists). Still WAF-unaffected — both `d1 export` and `d1 execute --remote` hit `api.cloudflare.com`, not the guarded `onlymove.net` zone.
