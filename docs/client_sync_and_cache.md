# Client/server sync and cache freshness

<!-- Extracted from CLAUDE.md. Same contract as docs/methodology.md's scope note:
     this describes the system as it is now. Past findings belong here; history does not. -->

How a device's attempt history stays in step with D1 across devices, and how served
data files are kept from going stale. Both are pull-based and content-addressed; neither
has a migration ladder. CLAUDE.md carries the short form and points here.

## Account sync

**Account sync: the userId IS the account credential; history syncs by append-only cursor.** The 8-char `userId` (crypto-random — `generateUserId` in `state.js`; exactly 8 chars everywhere, enforced by the Worker's `isValidUserId` since the 2026-07-21 surgery normalized the legacy long ids) doubles as the account password: the Account dialog (hamburger → More, `account-ui.js`) shows it, and entering another code on a device adopts that account (`account-sync.js switchAccount`: wipes account-derived localStorage, reloads; init's `maybeFinishAccountSwitch` then clears the IndexedDB history tail, pulls the full server history, and re-splits it into the working set + tail before the first problem load). Sync is pull-based over `POST /sync` because `tsumego_reports` is append-only — a cursor fully captures "what changed", no content hash. **The cursor is the AUTOINCREMENT `id` (`sinceId`), not `created_at`**: id is arrival order, so a row inserted with a historical `created_at` — an offline flush, a backfill — still gets a fresh high id and is pulled. (created_at stays as event time: charts, stats window, recall intervals; a `/sync` request without a valid `sinceId` is a plain `400`.) **The local representation is MIRROR-BY-ID**: the device's acked history is a 1:1 mirror of the server's rows keyed by `serverId` — identity is the row id, and the merge (`mergeRowsForSize`) does **no timestamp dedup**: a row is "had" iff its id is in the working set or the tail (`getTailSyncIndex` in `history-store.js`), so the digest matches the server **by construction**. A **complete from-0 pull is a TRUE MIRROR sync in both directions**: rows the device lacks merge in, and local acked rows the server no longer has are deleted by the deletion pass (`mirrorDeletePass` — working set AND tail via `pruneTail`, which also collapses evict-seam and tail-internal duplicate ids), so every digest-divergence direction converges to an exact match. `pullReports` settles any pending debounced eviction BEFORE snapshotting the tail index — an eviction landing mid-pull would be invisible to the snapshot, re-insert as working-set copies, and make the deletion pass churn against it (found on the heaviest account during the epoch rollout). Invariants in `account-sync.js`: (1) the cursor advances **only from pulls**, never from this device's report acks; (2) own rows are recognized on pull by their **id** — `/report` returns the row id and `recordReportAck` stamps it (serverId presence = acked); ack-less (offline) entries are claimed by an **EXACT `created_at === date` match** (client-owned event time — no fuzzy window; every era-conditional claim path was retired with the 2026-07-21 state epoch); (3) only an account switch or the epoch gate's re-adoption pulls from the beginning (`fromStart`); a fresh/empty account just falls back to a cheap from-0 pull. **SUM-FIRST digest backstop**: every `/sync` response carries `serverSeq`/`serverDigest`/`serverMaxId` (user_seq + Σ rowHash(id), always defined — the digest chain is a table invariant since the surgery materialized every row, and the INSERT maintains it), and every `/report` response carries `userSeq` + `digest` (the post-insert sum). Count and sum are CO-EQUAL divergence signals — `digestMismatch` returns 'gap'/'surplus'/'content' as log labels only, and any of them escalates to the full mirror reconcile (`checkInSync`; no accept-and-remember state — mirror semantics guarantee convergence). The per-report check (`checkSyncSignal(userSeq, digest)`) treats a seq jump past `lastSeq + 1` as "another device wrote" → debounced incremental pull, and an equal-seq digest as a content check via a 3s-deferred, staleness-guarded compare against the local digest (working-set walk + the tail digest CACHED in `history-store.js`, invalidated by its writers) — so an active session is fully self-verifying with no polling. Merged rows become skeleton entries; `fillSyncedHistoryFields` (`backfill.js`) fills ratings from `problem_params.bin`, correct-move embeddings from the lookup-aligned sidecar, and derives `pickedCellIndex` from the reported move for wrong attempts: **every stored `move` is in the canonical orientation-0 frame** (`buildReportPayload` inverse-transforms the click through the served orientation; the surgery NULLed the pre-2026-07-07 served-frame repeat moves, so no era gate remains). The rank is a **grid POSTERIOR over the measured population prior** (`estimateWindowRank` in `rank-decomposition.js`) — a **pure function** of the recent first-time history: the prior (`rank_prior` in `population_constants.json`, fitted by `pipeline.fit_population_constants`) times a positionally-weighted 4PL likelihood over the last `WIN_CAP`=500 attempts, reported as the posterior mean + SD. There is NO warm start and no self-anchoring: the previous estimate never enters, which is the whole point — a prior centred on the user's own last estimate damps steps but anchors the level to nothing, so an early all-correct/all-wrong run (where the unpenalized likelihood has no interior maximum) carries itself forward. Grid rather than Newton+Laplace because the population is bimodal and so is the posterior on a short window. The per-problem slope `a_p` enters through the likelihood, so a sharp problem pins the rank harder. **Three ranks come out of that one posterior**: `rank` = the mean, the honest value everything CALIBRATED scores against (server translations, recall, weakness, the Worker's `pred_rank`); `displayRank` = `rank + K_DISPLAY·excess` (`K_DISPLAY` = −2), what the badge, the rank-change overlay, the server-translation modal and the Rank chart's front-page-rank line all show; and `serveRank` = `min(rank + excess, displayRank + serveGapCap(attempts))`, what SELECTION targets — information-seeking, but never more above the badge than `1 + the current run of correct answers` (reset by any miss), because uncapped it hands a 20k a dan problem on attempt one (the UCB term at cold start is +0.14, a 1-dan problem). The cap carries a `FRESH_RECORD_BONUS` of 2 extra ranks while the window holds NO miss, and a fresh device's first problem comes from `coldStartServeRank(DEFAULT_USER_RANK)` — an empty window is the prior exactly, so the first problem is drawn from the rule (`shown + 1 + bonus`) rather than from the shown rank itself. The gap resolves to `min(3·excess, cap)`, so the cap is the binding term through onboarding; a CONSTANT cap `c` inverts the bonus (`display + c` sits below the mean whenever `excess > c/2`) and starves the estimator, which is why it grows with demonstrated success instead. `excess` = `max(0, se − se_floor)`, so all three coincide at convergence and neither offset leaves a permanent bias. `displayRank` must never flow back into anything fitted, or the calibration loop closes on a deliberately shifted number. **`se_floor` is RANK-DEPENDENT, not a constant** (`localSeFloor` in `rank-decomposition.js` → `seFloorForMeanInfo` in `rank-window.js`): it is the irreducible SE a full at-rank window would leave, `1/√(WIN_PRIOR_INFO + ((WIN_CAP+1)/2)·⟨I⟩)`, where `⟨I⟩ = ⟨anchorInfo(floor)·slope²⟩` is the mean per-attempt 4PL information of the ≤50 corpus problems nearest the estimate **already loaded** on the active size (no fetch on the hot path; the selector's shard loading keeps the pool warm; the per-problem transform runs only on those 50). The mean is UNWEIGHTED on purpose — it describes the post-convergence steady state, where selection is weakness-driven rather than information-driven. **`⟨I⟩` is the FULL 4PL information, not the 2PL `0.16·⟨slope²⟩` (fixed 2026-07-26)**: the old constant ignored the guessing floor and the lapse, claiming ~1.4× more information than a real at-rank window can deliver, so the floor sat 0.07–0.27 stones BELOW the SE `windowMLE` actually converges to (worst in the 17k–8k bands, where the curves are flattest). Consequences of the mismatch, both now gone: `max(0, se − se_floor)` never reached zero, so every converged user carried a permanent fraction-of-a-stone over-serve; and `rankConverged` (se < 2×floor) fired later than its "within 2× of the best achievable" intent, holding users in the information regime past the point weakness personalization should have taken over. Verified end-to-end on a simulated full at-rank window: residual bonus 0.14–0.33 stones under the old floor vs ≤0.03 under the new one. Flat-curved kyu problems carry so little rank information that even a full window floors at ~1.3 stones (vs the old constant 0.35, which implied a slope only dan problems reach — leaving kyu users perpetually served ~1 stone above rank and never converging); sharp dan curves floor near 0.3. So the bonus collapses to the user's OWN rank at convergence on every part of the ladder. When nothing is loaded near the rank yet (Worker, or a client before any shard loads) it falls back to the constant `WIN_SE_FLOOR` — harmless since se dominates the bonus that early. The Worker's `estimateWindowRankFromFlat` (leaderboard) passes no floor callback, so it is unaffected. Because the estimate is a pure function of the merged recent history, device adoption and an incremental foreign sync are the **same operation** — recompute from scratch; there is no loop state to warm and no anchor to recover. `retrainAfterMerge` (`account-sync.js`) has three modes: `adopt` (account switch) re-fits over the new account's full merged history seeded from the data (the prior account's rank is irrelevant); `feed` (ongoing merge) re-fits warm-started from the current rank; `reconcile` (one-off local backfill) leaves the rank untouched (the merged rows are ancient). The recompute runs **silently** (no overlay), so the next live answer's reported rank change is that tsumego's effect alone — a freshly-synced foreign batch moves the rank between problems, never inside the shown delta. Every device sees the same multiset of recent attempts, so they converge to the same rank regardless of how the attempts were batched. After every merge, `retrainAfterMerge` also fires `refreshShownProblemAfterSync` (`problem-loader.js`) — and the tab-visible resume trigger fires it on EVERY resume, merge or not, since a recall can enter its window from time alone while the tab was hidden. It re-runs the NORMAL problem-presentation selection (a due recall wins subject to the stochastic recall-share gate — see the recall-serving note below; the refresh path rolls the gate only when INTRODUCING a recall over an idle novel, never to swap a shown recall away — else the standing challenge), so a problem solved on another device is swapped off screen and a newly-due recall can appear; an actual swap goes through a GREY `fadeOverlay` with a localized "Problem updated" notice (grey deliberately — white/red are the correct/wrong answer cues). The standing `challengeProblem` is kept by default, so sync can never dodge a served challenge — recalls only delay it; the single exception is that the user completed that exact problem on another client (now inside the recent-repeat window, `challengeAlreadyAnswered`), which makes it illegal to serve, so only then is it swapped for a freshly selected one. The refresh touches the board only when a problem sits idle in SOLVING mode (never mid-answer, in review/analysis, or over a linked problem), and skips the repaint when selection lands on the problem already shown (no timer reset, no recall re-orientation). (This replaced an earlier momentum-loop design — `momentum-rank.js`, hybrid replay, `feedAttemptsThroughLoop` — entirely.) Pulls run on load, tab-visible, and the `online` event — **unthrottled** (an up-to-date incremental poll reads ~0–1 D1 rows via the user-id index, so a session resume merges — and can refresh the shown problem — immediately; overlapping triggers collapse via the in-flight guard, and only the outbox's full-pull flush keeps a throttle); **active sessions need no polling at all** — every `/report` response carries `userSeq` (the per-profile attempt count), and `checkSyncSignal` triggers a debounced pull when it lands past the device's expected `lastSeq + 1` (= another device wrote in between). An up-to-date poll and the latest-row digest summary read ~0–1 D1 rows **via `idx_tsumego_reports_user_id`, which must stay in place**. Known gaps: the ignored-problems list is per-device (it survives the epoch wipe via the durable `ignoredProblems_v1` id set — `performIgnore` maintains it and `applyStoredIgnoredFlags` re-marks the restored history post-adopt — but it doesn't sync across devices), and linked-mode attempts are recorded nowhere (see the PWA-state note above), so there is nothing to round-trip. **Durable offline outbox (`flushOutbox`, permanent — `POST /report-backfill`):** any attempt recorded locally but never acked (offline / failed `/report`) is eventually uploaded so it reaches the server and every device. Runs on load / tab-visible / `online` whenever un-acked entries exist (a cheap no-op otherwise, 30-min throttle + the server daily full-pull cap): a COMPLETE reconcile pull claims rows the server already has (the exact `created_at === date` claim), then the provably-absent remainder is uploaded **with its recorded event time** (historical `created_at` — the id cursor still propagates it; old rows stay out of the server-stats window). `/report-backfill` maintains `user_seq`/`running_sum` like `/report` (shared INSERT) and RETURNs the ids so the client stamps `serverId`; it ALSO pushes the batch's novel attempts into the leaderboard buffer (`updateLeaderboardOnBackfill`, one read + one write for the whole batch, in `ctx.waitUntil` like `/report`'s) — before that a flushed attempt stayed invisible to the leaderboard until the weekly cron reconcile. `HISTORY_BACKFILL_DONE_KEY` is set whenever the backlog is clear — the `ui.js` gate that the device's history is safe to adopt elsewhere. **The state-epoch gate (`js/state-epoch.js`, run at `state.js` import time) is the permanent replacement for migration ladders**: a stale/absent `stateEpoch` wipes the account-derived localStorage (keep-list: userId, board size, audio, onboarding flags, the ignored set) and routes init through the standard adopt path with the device's OWN account (`accountSwitchPending = 'epoch'` — on a failed restore pull the flag stays set and the next boot retries; only a user-initiated switch falls back to a fresh id). For a future breaking state change: bump `CURRENT_STATE_EPOCH`, optionally add a keep-path. There are NO other migrations — `migrations.js`/`boot-migrations.js`, the era constants, the legacy timestamp-dedup merge, absorbed receipts, and `serverCreatedAt` were all removed with epoch 1. The Worker's daily full-pull cap is 5, enforced server-side in `src/handlers/sync.js` (client-side counting is bypassable by clearing localStorage); `account-sync.js` mirrors the number for the prompt's "refreshes left" display only, so the two must be changed together.

## Served-data cache freshness

**Served data files are cache-busted by a content `data_version`, not `APP_VERSION`; `embedding_meta.json` is inlined.** The bug this fixes: data files were fetched `?v=${APP_VERSION}` and cached **cache-first by URL** (`sw.js`), but `APP_VERSION` was `git rev-parse HEAD` while the served data (`pwa/tsumegos/`) is **gitignored** — so a `package_for_pwa` re-ship from the same commit served a **stale** `metadata.json` indefinitely, and a device could stamp the current `ratings_version` while its per-attempt `rating`/`slope`/`floor` came from an older shard set (the gate then skipped forever → two devices on one account rendered different rank graphs). The fix is a content-addressed chain rooted in **one inlined manifest**: (1) `package_for_pwa` writes `data_version = hash(metadata.json files)` into `embedding_meta.json` (covers shards transitively — each `metadata.json` lists every shard's content-hash filename); (2) `embedding_meta.json` is **inlined into the JS bundle** via `pwa/js/data-version.js` (`import`, dropped from dist by `DIST_DEAD_FILES`) — it can never be served stale, and `DATA_VERSION` is read synchronously from it; (3) the only query-busted fetches — `metadata.json` and `lookup.txt` (`problem-loader.js`, `backfill.js`) — use `?v=${DATA_VERSION}`; shard `.zip`/`.embeddings.bin` are already content-addressed by filename (NOTE: Workers static assets answer Range requests with **200 + the full body** — no 206s, cached or not, verified in production — so the `.bin` "Range" fetchers download whole files, slice the requested bytes client-side (`sliceRangeResponse` in `picked-embedding.js`, which also rejects a 206 whose Content-Range offset mismatches), and let the SW cache the full 200 like any asset; `pwa/_headers` (copied to dist by the build) additionally gives `/assets/*` immutable and `/tsumegos/*` + `/lookup.txt` 1-day browser cache-control — safe because the assets layer is deploy-consistent (per-deploy manifest, content-hash blobs; header changes verified to appear instantly across deploys even on cf-cache-status HIT responses) and all fixed-name fetches rotate their `?v` cache key with `data_version`); the curve/pop-constant JSONs are inlined. `DATA_VERSION` is stamped into `sw.js` too so the runtime-cache prune keeps `?v ∈ {VERSION, DATA_VERSION}`. **`data_version` (cache freshness) is deliberately separate from `ratings_version`/`embedding_version` (backfill gate):** a ship that only ADDS tsumegos bumps `data_version` (new shards → new `metadata.json`) but not `ratings_version`, so new problems become serveable **lazily** with no history walk; a ratings change bumps `ratings_version` and triggers the **immediate** re-derive. The Worker's server-stats reads `metadata.json`/`lookup.txt` by **fixed path via the `ASSETS` binding** (server-side, no SW, no `?v`), so it always sees current dist and is unaffected.
