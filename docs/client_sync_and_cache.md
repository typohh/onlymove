# Client/server sync and cache freshness

<!-- Extracted from CLAUDE.md. Same contract as docs/methodology.md's scope note:
     this describes the system as it is now. Past findings belong here; history does not. -->

How a device's attempt history stays in step with D1 across devices, and how served
data files are kept from going stale. Both are pull-based and content-addressed; neither
has a migration ladder. CLAUDE.md carries the short form and points here.

## Account sync

**Account sync: the userId IS the account credential; history syncs by append-only cursor.** The 8-char `userId` (crypto-random — `generateUserId` in `state.js`; exactly 8 chars everywhere, enforced by the Worker's `isValidUserId`) doubles as the account password: the Account dialog (hamburger → More, `account-ui.js`) shows it, and entering another code on a device adopts that account (`account-sync.js switchAccount`: wipes account-derived localStorage, reloads; init's `maybeFinishAccountSwitch` then clears the IndexedDB history tail, pulls the full server history, and re-splits it into the working set + tail before the first problem load). Sync is pull-based over `POST /sync` because `tsumego_reports` is append-only — a cursor fully captures "what changed", no content hash. **The cursor is the AUTOINCREMENT `id` (`sinceId`), not `created_at`**: id is arrival order, so a row inserted with a historical `created_at` — an offline flush, a backfill — still gets a fresh high id and is pulled. (created_at stays as event time: charts, stats window, recall intervals; a `/sync` request without a valid `sinceId` is a plain `400`.) **The local representation is MIRROR-BY-ID**: the device's acked history is a 1:1 mirror of the server's rows keyed by `serverId` — identity is the row id, and the merge (`mergeRowsForSize`) does **no timestamp dedup**: a row is "had" iff its id is in the working set or the tail (`getTailSyncIndex` in `history-store.js`), so the digest matches the server **by construction**. A **complete from-0 pull is a TRUE MIRROR sync in both directions**: rows the device lacks merge in, and local acked rows the server no longer has are deleted by the deletion pass (`mirrorDeletePass` — working set AND tail via `pruneTail`, which also collapses evict-seam and tail-internal duplicate ids), so every digest-divergence direction converges to an exact match. `pullReports` settles any pending debounced eviction BEFORE snapshotting the tail index — an eviction landing mid-pull would be invisible to the snapshot, re-insert as working-set copies, and make the deletion pass churn against it (found on the heaviest account during the epoch rollout). Invariants in `account-sync.js`: (1) the cursor advances **only from pulls**, never from this device's report acks; (2) own rows are recognized on pull by their **id** — `/report` returns the row id and `recordReportAck` stamps it (serverId presence = acked); ack-less (offline) entries are claimed by an **EXACT `created_at === date` match** (client-owned event time — no fuzzy window); (3) only an account switch or the epoch gate's re-adoption pulls from the beginning (`fromStart`); a fresh/empty account just falls back to a cheap from-0 pull. **SUM-FIRST digest backstop**: every `/sync` response carries `serverSeq`/`serverDigest`/`serverMaxId` (user_seq + Σ rowHash(id), always defined — the digest chain is a table invariant since the surgery materialized every row, and the INSERT maintains it), and every `/report` response carries `userSeq` + `digest` (the post-insert sum). Count and sum are CO-EQUAL divergence signals — `digestMismatch` returns 'gap'/'surplus'/'content' as log labels only, and any of them escalates to the full mirror reconcile (`checkInSync`; no accept-and-remember state — mirror semantics guarantee convergence). The per-report check (`checkSyncSignal(userSeq, digest)`) treats a seq jump past `lastSeq + 1` as "another device wrote" → debounced incremental pull, and an equal-seq digest as a content check via a 3s-deferred, staleness-guarded compare against the local digest (working-set walk + the tail digest CACHED in `history-store.js`, invalidated by its writers) — so an active session is fully self-verifying with no polling. Merged rows become skeleton entries; `fillSyncedHistoryFields` (`backfill.js`) fills ratings from `problem_params.bin`, correct-move embeddings from the lookup-aligned sidecar, and derives `pickedCellIndex` from the reported move for wrong attempts: **every stored `move` is in the canonical orientation-0 frame** (`buildReportPayload` inverse-transforms the click through the served orientation; the surgery NULLed the pre-2026-07-07 served-frame repeat moves, so no era gate remains). The rank is a **grid POSTERIOR over the measured population prior** (`estimateWindowRank` in `rank-decomposition.js`) — a **pure function** of the recent first-time history: the prior (`rank_prior` in `population_constants.json`, fitted by `pipeline.fit_population_constants`) times a positionally-weighted 4PL likelihood over the last `WIN_CAP`=500 attempts, reported as the posterior mean + SD. There is NO warm start and no self-anchoring: the previous estimate never enters, which is the whole point — a prior centred on the user's own last estimate damps steps but anchors the level to nothing, so an early all-correct/all-wrong run (where the unpenalized likelihood has no interior maximum) carries itself forward. Grid rather than Newton+Laplace because the population is bimodal and so is the posterior on a short window. The per-problem slope `a_p` enters through the likelihood, so a sharp problem pins the rank harder. **Three ranks come out of that one posterior**: `rank` = the mean, the honest value everything CALIBRATED scores against (server translations, recall, weakness, the Worker's `pred_rank`); `displayRank` = `rank + K_DISPLAY·excess` (`K_DISPLAY` = −2), what the badge, the rank-change overlay, the server-translation modal and the Rank chart's front-page-rank line all show; and `serveRank` = `min(rank + excess, displayRank + serveGapCap(attempts))`, what SELECTION targets — information-seeking, but never more above the badge than `1 + the current run of correct answers` (reset by any miss), because uncapped it hands a 20k a dan problem on attempt one (the UCB term at cold start is +0.14, a 1-dan problem). The cap carries a `FRESH_RECORD_BONUS` of 2 extra ranks while the window holds NO miss, and a fresh device's whole cold start comes from `coldStartEstimate()` — an empty window is the prior exactly, so all three slots are the same rule applied to it, not a case of their own, and there is no starting-rank constant. `state.displayRank`'s fallback chain reads the STORED `userRank`, never the `userRank` getter, whose own fallback is the posterior mean. The gap resolves to `min(3·excess, cap)`, so the cap is the binding term through onboarding; a CONSTANT cap `c` inverts the bonus (`display + c` sits below the mean whenever `excess > c/2`) and starves the estimator, which is why it grows with demonstrated success instead. `excess` = `max(0, se − se_floor)`, so all three coincide at convergence and neither offset leaves a permanent bias. `displayRank` must never flow back into anything fitted, or the calibration loop closes on a deliberately shifted number. **`se_floor` is RANK-DEPENDENT, not a constant, and it is a SHIPPED CORPUS CURVE rather than anything a reader measures** (`pwa/tsumegos/se_floor.json`, written by `package_for_pwa`'s `emit_se_floor_curve`, read through `seFloorAt` in `rank-window.js`, which `estimateWindowRankFromFlat` applies internally so **no caller passes a floor function**). It is the irreducible SE a full at-rank window would leave, `1/√(WIN_PRIOR_INFO + ((WIN_CAP+1)/2)·⟨I⟩)`, where `⟨I⟩ = ⟨anchorInfo(floor)·slope²⟩` is the mean per-attempt 4PL information of the problems near that rank. The file stores **information, not the floor**, because information is what averages; `seFloorForMeanInfo`'s `1/√` is applied after interpolation. The mean is UNWEIGHTED on purpose — it describes the post-convergence steady state, where selection is weakness-driven rather than information-driven. **`⟨I⟩` is the FULL 4PL information, not the 2PL `0.16·⟨slope²⟩`**: the 2PL form is the textbook one and the tempting one, and it ignores the guessing floor and the lapse, claiming ~1.4× more information than a real at-rank window can deliver — which puts the floor 0.07–0.27 stones BELOW the SE `windowMLE` converges to (worst in the 17k–8k bands, where the curves are flattest). Both consequences bite: `max(0, se − se_floor)` never reaches zero, so every converged user carries a permanent fraction-of-a-stone over-serve (0.14–0.33 stones on a simulated full at-rank window, against ≤0.03 under the 4PL floor); and `rankConverged` (se < 2×floor) fires later than its "within 2× of the best achievable" intent, holding the information slot in the serve draw past the point the other slots should have it to themselves. A single constant is no way out either: flat-curved kyu problems carry so little rank information that even a full window floors near a whole stone while sharp dan curves floor near a third of one, so any constant picked for one end leaves the other perpetually over-served and never converging. So the bonus collapses to the user's OWN rank at convergence on every part of the ladder.

**Don't put the measurement back on the reader.** A per-reader scan (average the ≤50 loaded problems nearest the estimate) costs nothing on the network and looks self-refining, and it is wrong in three ways at once, all of which reach the shown rank because that number is the mean less twice the excess. The dominant one is the reader holding NOTHING: with no pool the floor cannot be priced at all and is conceded to zero, landing the shown rank a full band or more low, with the next answer recovering it and the overlay reporting a PROMOTION into a band the user already held. The readers also disagree with each other — a client holds the shards loaded this session, which cluster around the SERVE rank rather than the mean the floor is priced at, while the Worker and each offline rebuild build a different index again. And a 50-problem sample mean drifts as the estimate drifts, re-crossing band edges under a user whose skill has not moved. `seFloorAt`'s knots ARE the rank prior's grid, so `windowMLE`'s weighted mean over that grid can never land outside them and the curve is never extrapolated; the lookup clamps to the range as well, so a grid change degrades to the end knot rather than silently returning `Infinity` (a linear extension of interpolated information goes negative within a few stones, and `seFloorForMeanInfo` maps non-positive information to `Infinity`, which drops the excess term and shows the raw mean with no symptom at the call site). Because the floor no longer depends on load order, `main.js` re-anchors once BEFORE the first problem load, with no pool gate — a stored rank is read (shard pick, badge) before it is rewritten, and a re-shipped curve moves it.

Because the estimate is a pure function of the merged recent history, device adoption and an incremental foreign sync are the **same operation** — recompute from scratch; there is no loop state to warm, no anchor to recover and **no warm start anywhere** (the estimator is a grid posterior over the shipped population prior, never over its own previous value). `retrainAfterMerge` (`account-sync.js`) reflects that: `adopt` (account switch) and `feed` (ongoing merge) take the *same* `reanchorRank` call over the merged history, differing in nothing; `reconcile` (one-off local backfill) leaves the rank untouched (the merged rows are ancient). `adopt` runs BEFORE the first problem load by design, so the restored rank picks the shard, and that costs it nothing now that the floor is corpus-wide. The recompute runs **silently** (no overlay), so the next live answer's reported rank change is that tsumego's effect alone — a freshly-synced foreign batch moves the rank between problems, never inside the shown delta. Every device sees the same multiset of recent attempts, so they converge to the same rank regardless of how the attempts were batched. After every merge, `retrainAfterMerge` also fires `refreshShownProblemAfterSync` (`problem-loader.js`) — and the tab-visible resume trigger fires it on EVERY resume, merge or not, since a recall can enter its window from time alone while the tab was hidden. It re-runs the NORMAL problem-presentation selection (a due recall wins subject to the stochastic recall-share gate — see the recall-serving note below; the refresh path rolls the gate only when INTRODUCING a recall over an idle novel, never to swap a shown recall away — else the standing challenge), so a problem solved on another device is swapped off screen and a newly-due recall can appear; an actual swap goes through a GREY `fadeOverlay` with a localized "Problem updated" notice (grey deliberately — white/red are the correct/wrong answer cues). The standing `challengeProblem` is kept by default, so sync can never dodge a served challenge — recalls only delay it; the single exception is that the user completed that exact problem on another client (now inside the recent-repeat window, `challengeAlreadyAnswered`), which makes it illegal to serve, so only then is it swapped for a freshly selected one. The refresh touches the board only when a problem sits idle in SOLVING mode (never mid-answer, in review/analysis, or over a linked problem), and skips the repaint when selection lands on the problem already shown (no timer reset, no recall re-orientation). Pulls run on load, tab-visible, and the `online` event — **unthrottled** (an up-to-date incremental poll reads ~0–1 D1 rows via the user-id index, so a session resume merges — and can refresh the shown problem — immediately; overlapping triggers collapse via the in-flight guard, and only the outbox's full-pull flush keeps a throttle); **active sessions need no polling at all** — every `/report` response carries `userSeq` (the per-profile attempt count), and `checkSyncSignal` triggers a debounced pull when it lands past the device's expected `lastSeq + 1` (= another device wrote in between). An up-to-date poll and the latest-row digest summary read ~0–1 D1 rows **via `idx_tsumego_reports_user_id`, which must stay in place**. Known gaps: the ignored-problems list is per-device (it survives the epoch wipe via the durable `ignoredProblems_v1` id set — `performIgnore` maintains it and `applyStoredIgnoredFlags` re-marks the restored history post-adopt — but it doesn't sync across devices), and linked-mode attempts are recorded nowhere (see the PWA-state note above), so there is nothing to round-trip. **Durable offline outbox (`flushOutbox`, permanent — `POST /report-backfill`):** any attempt recorded locally but never acked (offline / failed `/report`) is eventually uploaded so it reaches the server and every device. Runs on load / tab-visible / `online` whenever un-acked entries exist (a cheap no-op otherwise, 30-min throttle + the server daily full-pull cap): a COMPLETE reconcile pull claims rows the server already has (the exact `created_at === date` claim), then the provably-absent remainder is uploaded **with its recorded event time** (historical `created_at` — the id cursor still propagates it; old rows stay out of the server-stats window). `/report-backfill` maintains `user_seq`/`running_sum` like `/report` (shared INSERT) and RETURNs the ids so the client stamps `serverId`; it ALSO pushes the batch's novel attempts into the leaderboard buffer (`updateLeaderboardOnBackfill`, one read + one write for the whole batch, in `ctx.waitUntil` like `/report`'s) — before that a flushed attempt stayed invisible to the leaderboard until the weekly cron reconcile. `HISTORY_BACKFILL_DONE_KEY` is set whenever the backlog is clear — the `ui.js` gate that the device's history is safe to adopt elsewhere. **The state-epoch gate (`js/state-epoch.js`, run at `state.js` import time) is the permanent replacement for migration ladders**: a stale/absent `stateEpoch` wipes the account-derived localStorage (keep-list: userId, board size, audio, onboarding flags, the ignored set) and routes init through the standard adopt path with the device's OWN account (`accountSwitchPending = 'epoch'` — on a failed restore pull the flag stays set and the next boot retries; only a user-initiated switch falls back to a fresh id). For a future breaking state change: bump `CURRENT_STATE_EPOCH`, optionally add a keep-path. There are NO other migrations. The Worker's daily full-pull cap is 5, enforced server-side in `src/handlers/sync.js` (client-side counting is bypassable by clearing localStorage); `account-sync.js` mirrors the number for the prompt's "refreshes left" display only, so the two must be changed together.

## Precache ownership and cache lookup order

**A precache asset is looked up in the PRECACHE BY NAME; `caches.match()` is never used for one, because the cache order inverts on the first deploy.** `caches.match(request)` searches every cache in the storage's CREATION order, and `activate` deletes the version-stamped `only-move-precache-<VERSION>` and opens a new one — which appends the fresh precache AFTER the long-lived `only-move-runtime`. So from the first deploy onward a runtime copy of a precached URL OUTRANKS the precache and is what every request gets (verified in Chrome: on a fresh install the same lookup returns the precache; one version bump later it returns the runtime copy). The precached assets are fixed-name and carry no `?v=`, so the activate-time prune — which drops only cross-origin entries, the three dynamic Worker paths, and `?v ∉ {VERSION, DATA_VERSION}` — never reaches them either: a runtime copy that stored badly is served for the life of the install, surviving reloads and every subsequent deploy. The observed cost was a permanently textureless board, and it is quiet in both directions — `/lib/wgo/wood_1024.jpg` is a CSS `background-image` set once by WGo on a board element built once per session, so nothing ever re-requests it, and `.wgo-board`'s `background-color` fallback renders the failure as a flat tan goban rather than a broken image. Three rules in `sw.js` hold it closed. The fetch handler resolves a `PRECACHE_PATHS` hit against `PRECACHE_NAME` explicitly and writes a miss BACK to the precache, never to the runtime cache — so the shadow cannot form and a partial install self-repairs on first use. `activate` deletes any runtime entry whose pathname is a precache path, which is what repairs a device already in that state. And `install` fills the precache **per-URL** under `Promise.allSettled` rather than `cache.addAll`: `addAll` is all-or-nothing, so one flaky fetch rejected the whole install, left the device with NO precache for that session, and pushed all of those URLs through the fetch handler into the permanent runtime cache — which is how the shadow got created to begin with. Separately, a Cache Storage read error falls through to the network instead of rejecting `respondWith()`, which is a hard network error with no browser-level fallback and no retry.

## Served-data cache freshness

**Served data files are cache-busted by a content `data_version`, not `APP_VERSION`; `embedding_meta.json` is inlined.** The bug this fixes: data files were fetched `?v=${APP_VERSION}` and cached **cache-first by URL** (`sw.js`), but `APP_VERSION` was `git rev-parse HEAD` while the served data (`pwa/tsumegos/`) is **gitignored** — so a `package_for_pwa` re-ship from the same commit served a **stale** `metadata.json` indefinitely, and a device could stamp the current `ratings_version` while its per-attempt `rating`/`slope`/`floor` came from an older shard set (the gate then skipped forever → two devices on one account rendered different rank graphs). The fix is a content-addressed chain rooted in **one inlined manifest**: (1) `package_for_pwa` writes `data_version = hash(metadata.json files)` into `embedding_meta.json` (covers shards transitively — each `metadata.json` lists every shard's content-hash filename); (2) `embedding_meta.json` is **inlined into the JS bundle** via `pwa/js/data-version.js` (`import`, dropped from dist by `DIST_DEAD_FILES`) — it can never be served stale, and `DATA_VERSION` is read synchronously from it; (3) the only query-busted fetches — `metadata.json` and `lookup.txt` (`problem-loader.js`, `backfill.js`) — use `?v=${DATA_VERSION}`; shard `.zip`/`.embeddings.bin` are already content-addressed by filename (NOTE: Workers static assets answer Range requests with **200 + the full body** — no 206s, cached or not, verified in production — so the `.bin` "Range" fetchers download whole files, slice the requested bytes client-side (`sliceRangeResponse` in `picked-embedding.js`, which also rejects a 206 whose Content-Range offset mismatches), and let the SW cache the full 200 like any asset; `pwa/_headers` (copied to dist by the build) additionally gives `/assets/*` immutable and `/tsumegos/*` + `/lookup.txt` 1-day browser cache-control — safe because the assets layer is deploy-consistent (per-deploy manifest, content-hash blobs; header changes verified to appear instantly across deploys even on cf-cache-status HIT responses) and all fixed-name fetches rotate their `?v` cache key with `data_version`); the curve/pop-constant JSONs are inlined. `DATA_VERSION` is stamped into `sw.js` too so the runtime-cache prune keeps `?v ∈ {VERSION, DATA_VERSION}`. **`data_version` (cache freshness) is deliberately separate from `ratings_version`/`embedding_version` (backfill gate):** a ship that only ADDS tsumegos bumps `data_version` (new shards → new `metadata.json`) but not `ratings_version`, so new problems become serveable **lazily** with no history walk; a ratings change bumps `ratings_version` and triggers the **immediate** re-derive. The Worker's server-stats reads `metadata.json`/`lookup.txt` by **fixed path via the `ASSETS` binding** (server-side, no SW, no `?v`), so it always sees current dist and is unaffected.
