Two read paths over the same small `leaderboard` table, both cost-sensitive because D1
bills rows read. CLAUDE.md carries the short form and points here.

## The /leaderboard page

**The `/leaderboard` page is a compute-on-read display resolver with a UNITS selector offering onlymove and EVERY coupled ranking system; its two value columns are "Declared" (the player's own rank on the selected system, overridden by a linked federation account's machine-verified rating) and "Predicted" (our estimate, coupled into that system's frame).** The server-rendered page (`src/handlers/leaderboard-page.js`) reads `readLeaderboardRows` (`src/leaderboard.js`) — the single place that stitches each row's display identity from three tables: the onlymove estimate off the (rebuildable) `leaderboard` buffer, name/country off the claimed `invitation` row, and per-user external ranks off ONE latest-per-`(user, server)` pass over `rank_surveys` — BOTH the human declarations (one per surveyed system) and the MACHINE heartbeats: `egd` = the `'EGD'` row (`rank` = raw GoR digits, `rank_label` = the EGD Grade, `last_game_at` = the parsed `Last_Appearance` tournament date — written weekly by the client GoR piggyback, `gor-refresh.js` → `applyGorUpdates`) and `aga` = the `'AGAR'` row (`rank` = the RAW AGA rating, `rank_label` = the AGA's official label, `last_game_at` = `latest_event_date`; written weekly by the Worker cron `refreshAgaRatings`, seeded at claim by `register.js`). A heartbeat WINS on its own system — the `'EGD'` GoR on EGF, the `'AGAR'` rating on AGA — so a player with that federation account linked shows a verified rank there rather than their self-report, while every other system shows the declaration. Declarations still feed calibration exactly as before; the page is a second consumer of them, never an input to a fit. Each verified rating is **activity-gated per the EGF criteria** (`isVerifiedActive`: last tournament within 2 years for dan/pro, 1 year for single-digit kyu, 6 months for double-digit kyu; tier from the official label when present, else the rating; a MISSING date fails OPEN — register-seeded EGD rows carry no date until the first weekly client refresh); a dropped heartbeat hands its cell back to the player's own declaration if they made one. The units selector (a `<select>`) offers onlymove plus every key of `rank_map.json` (`RANK_SYSTEMS`), and picks the frame BOTH value columns speak; the list grows with the couplings rather than being enumerated in the page. It resolves **`?units=` over `localStorage.lbUnits` over onlymove** — an explicit request in the URL beats the device preference, so `/leaderboard?units=Fox` opens on Fox — matching case-insensitively and accepting `onlymove` for `om` (which also carries forward the lowercase `egf`/`aga` the two-system selector stored). The current selection is mirrored back with `history.replaceState` (default = the param's ABSENCE, keeping bare `/leaderboard` canonical; `replaceState`, not `push`, since a units switch is a display toggle rather than a navigation), so the address bar is always shareable and a reload cannot snap back to a stale param. **The response body does not depend on the param** — every frame is already inlined per row and the switch is pure client work — so a param costs its own 60s edge-cache entry and nothing more; there is no second D1 read path, and no `Vary`-style fragmentation of the aggregation itself. Each shown row therefore carries two per-system maps — `est` (the estimate in every frame) and `decl` — built once server-side, so switching units is pure client work. **Every frame is the SHARED band-edge convention and every cell goes through the SHARED `rankProgress`**, which is what lets the two columns be compared at all: a GoR enters via `gorToRank`, an AGA rating via `agaRatingToRank` (the LABEL-PRESERVING ∓1 shift that puts AGA's floor bands exactly on ours — mirroring `aga_rating_to_value` in `utils/rating/rank_surveys.py`), a declaration via `rankLabelToRank`, and the estimate via each system's coupling. A cell shows "rank (pct%)" when its value resolves WITHIN the band (a heartbeat, or an estimate) and the bare band label when it does not (a declaration names a band and nothing more, so its scalar is only that band's centre). Server-frame labels are ladder-clamped (`clampRankBand`) exactly as the client's rank-translation modal does; the onlymove frame is left unclamped in both. onlymove units leave the Declared column blank — an onlymove rank is measured here, never declared. The estimate reaches each frame as the forward coupling `internalToServerRank` applied to the stored rank AFTER `addTimeDockToInternalRank` puts it in the TIME-ADJUSTED frame, deliberately, because that server frame is what the real federation ratings speak (EGF is one coupling among the others here, not a stored special case). **Adding the dock before the coupling is load-bearing: the couplings were fitted against time-adjusted ratings, so mapping the untimed rank forward silently shifts every estimate by the user's personal dock.** Sorting always uses the underlying continuous scalars OF THE DISPLAYED FRAME — the om (untimed) and per-system (time-adjusted) estimate orders differ per user by the personal time dock, so switching units re-sorts. `gorToRank` (1k = 2000, ~100 GoR/stone, less a half-band so it lands on our band centre) survives as the tier/label fallback. `rank_surveys` carries nullable `rank_label` + `last_game_at`; a new column here is appended LAST, since the `fetch_database` dump is positional. **A column change on any table this page reads runs CHAINED — migrate the remote D1 → `npm run deploy` → `fetch_database` → `auxiliary/update_leaderboard_ranks.mjs --remote`.** The migration has to land before the deploy that SELECTs the new columns, so in the gap the running Worker writes columns the new schema no longer has; that is survivable only because every path degrades softly — `/report`'s leaderboard write is a caught `waitUntil`, so the attempt still lands in `tsumego_reports` and merely misses its incremental buffer push (the final `update_leaderboard_ranks.mjs` repairs it by rebuilding buffers from `tsumego_reports`), and the page and the stats aggregation are try/caught. **Country (→ the flag) falls back GoR → invitation → leaderboard geo-IP → survey, and EVERYONE gets a flag:** the `'EGD'` heartbeat's country (the EGD federation code, most reliable since it comes from EGD) wins, then `invitation.country_code` (also EGD, frozen at invite time), then the `leaderboard.country` column, then any human survey's Cloudflare geo-IP `country`. **`leaderboard.country` is the UNIVERSAL fallback**: it's the request's edge geo-IP (`request.cf.country`) stamped into the row's ALREADY-happening `/report` UPDATE/INSERT (`updateLeaderboardOnReport`/`createLeaderboardRow` in `leaderboard.js`) — so it costs **no extra read or write** (the SELECT reads `l.country` off the same row; the write folds `country = COALESCE(?, country)` into the existing statement, `COALESCE` so an unknown geo never clobbers a known-good code, a real code wins last-writer-wins so the flag follows travel), and it gives a flag to EVERY active player (nearly all anonymous rows), not just the registered/surveyed few. The stamp is filtered through `normalizeCountry` (real ISO-alpha-2 only; the Cloudflare sentinels `XX`/`T1` → null, which would else render as a broken flag). When even that resolves nothing (or a hidden profile), the page shows the `UNKNOWN_FLAG` = 🇺🇳 constant (`leaderboard-page.js`) so no row is ever flagless. The EGD/survey survey-`country` still rides the same `MAX(id)` bare-column select as `rank`. A row with no code yet fills it on its owner's next report. **Hide opt-out:** a `hidden_profiles` row (presence = hidden; keyed by `user_id`, its OWN table because even a never-registered user can have declared ranks in `rank_surveys` worth hiding) makes `readLeaderboardRows` withhold that user's name, country, and every declared/verified rank — they render as an **anonymous row carrying only their onlymove estimate** (a hidden-and-unranked row is dropped, matching how a never-registered unranked player is already omitted); the onlymove rank itself is never hidden. Toggled from TWO places, one flag: the bottom of the page — the inline control reads `userId` from localStorage (same-origin with the SPA) — and a checkbox at the foot of the in-app rank survey (`js/rank-survey-prompt.js`), which is where a declaration is actually made. Both call `POST /profile/hide {userId, hidden}` (set/clear) and `GET /profile/hide?userId=` (read state, `no-store`), in `src/handlers/profile.js` (`RL_WRITE`-limited, `isValidUserId` + boolean format-validated). **The survey checkbox READS the flag back on open and writes only on a change** — it is unchecked by default, so posting the current state unconditionally would silently un-hide anyone who had opted out on the leaderboard page. The table is in `schema.sql`. **The row stores the SHOWN rank in the window estimator's OWN frame — `pred_rank` (the UNTIMED internal onlymove rank the player is actually told: `estimateWindowRankFromFlat`'s `displayRank`, the posterior mean less `K_DISPLAY` excess-se, NOT the mean), `pred_rank_se` (the posterior SE in stones) and `time_delta_rating` (the personal time dock in rating units).** Storing the shown rank is what keeps the page, the Community histogram and the player's own badge on one number, and it does not reopen the calibration loop `displayRank` is otherwise kept out of: the rank-map couplings are fitted on the backend from `rank_surveys` + `fit_user_rating` and read nothing from this table, so `pred_rank` is never an input to a fit. Two consequences. **The rank-dependent SE floor is now part of the stored value, so every caller derives it from the params map it is computing against** — `seFloorFnFor` (`src/leaderboard.js`) memoizes one floor function per params map (weakly), rather than the Worker isolate holding a single index: the offline rebuilds (`auxiliary/update_leaderboard_ranks.mjs`, `auxiliary/leaderboard_player_stats.mjs`) load `problem_params.bin` themselves and never call `getProblemParams`, so an isolate-scoped index silently left them on the constant `WIN_SE_FLOOR` and they wrote a shown rank the live Worker disagreed with for the same buffer. **And this table's estimate-vs-verified comparison is NOT a calibration measurement** — `displayRank` is deliberately conservative while a posterior is wide, so the gap is a display policy, not the mapping's bias; `auxiliary/check_mapped_vs_declared_rank.py` scores the calibrated estimate against every declared and verified rating, and `auxiliary/leaderboard_player_stats.mjs` deliberately carries no correlation summary so the two cannot be confused. **The `buffer` column is maintained INCREMENTALLY and is never rebuilt from `tsumego_reports` on the hot path**: `updateLeaderboardOnReport` reads the stored buffer, pushes the one new attempt, writes it back (and `updateLeaderboardOnBackfill` does the same for an outbox batch). **Buffer order is INSERT order (the AUTOINCREMENT `id`), and that is the ONE convention every writer and every rebuild shares** — the two incremental pushes, `buildRowStateFromReports` (`ORDER BY id DESC`, used by `createLeaderboardRow` and the weekly cron `reconcileBuffers`), and `auxiliary/update_leaderboard_ranks.mjs`. A backfilled row carries a historical `created_at` but a fresh id, so under this convention it IS the newest and prepending is correct. Event order would need a `(user_id, created_at)` index that was deliberately dropped, turning a bounded `BUFFER_CAP` read into a full per-user history scan — 3× the rows read across the leaderboard, 34× for the heaviest user, on a path that runs inside `/report`'s `waitUntil`. So anything that overwrites a row's buffer with a stale snapshot drops whatever landed in between **permanently** — later reports append on top of the shortened list rather than restoring it, and the only rebuild path is `createLeaderboardRow`, which runs only for a user with NO row at all. That is the hazard in `auxiliary/update_leaderboard_ranks.mjs`, the retroactive refresh that moves every row's rank onto a new scale after a re-rate (it recomputes `buffer`/`pred_rank`/`pred_rank_se`/`time_delta_rating` only — `country` and `last_active` are untouched, and the `--populate` pass is `INSERT OR IGNORE` so it cannot clobber an existing row). **Run it under the MAINTENANCE FREEZE** (`MAINTENANCE_MODE = "1"` — see the write-guard note below): every attempt reported in the gap between its snapshot and its write is silently truncated out of that user's buffer, with no error and no recovery, and with every POST 503ing nothing can land in that gap, so the race is not merely unlikely but IMPOSSIBLE. That is why the leaderboard refresh belongs INSIDE the surgery window rather than after the lift (`docs/db_surgery_runbook.md` step 8), and it applies to a standalone post-re-rate refresh too — freeze, refresh, unfreeze. Chaining the fetch into the apply (`python3 -m pipeline.fetch_database && node auxiliary/update_leaderboard_ranks.mjs --remote`) only NARROWS the window; it is a fallback, never the guarantee, and `+0 new tsumego_reports rows` on that fetch is evidence the window happened to be clean, not that it was closed. **`--remote` ENFORCES the freeze rather than trusting the operator** (`preflightRemote`): it probes `POST /sync` on the live origin (from wrangler.toml's `custom_domain`) and refuses unless it gets `503 {error:'maintenance'}` — the DEPLOYED Worker is the authority, not the local `wrangler.toml` value — and refuses unless the local mirror's `MAX(id)` on `tsumego_reports` EQUALS production's, so a snapshot taken before the freeze can't be used. It re-checks both after the apply, turning "the window was closed when we started" into "it stayed closed throughout"; a lapse is reported with the remedy (re-freeze, re-fetch, re-run — the rebuild is idempotent) instead of corrupting rows silently. The preflight runs BEFORE the per-user recompute so a missing freeze costs seconds, and it fails CLOSED (any error reaching production is a refusal). `--allow-unfrozen` overrides deliberately. Note `MAX(id)` catches INSERTS, which is the documented hazard; a purge changes existing rows without moving it, so after surgery use the runbook's COUNT/SUM check. Its ordering rule is separate and also load-bearing: `package_for_pwa` → `npm run deploy` → fetch → update, since running it before the deploy lets the next `/report` recompute on the OLD scale and overwrite the work. (`GET /tournament` is a **STATIC final-results page** for the concluded 2026 tournament — `src/handlers/tournament-page.js` bakes the standings in as a `PARTICIPANTS` const (a verbatim snapshot of the production leaderboard's last-week-peak on 2026-07-20) and does NO D1 read; it does not share `readLeaderboardRows`, so this page's frames don't reach it.)

## Server-wide Community stats

**Server-wide "Community" stats are a cached, read-cost-sensitive D1 aggregation.** `GET /server-stats` serves a single `server_stats` row (`key='latest'`, JSON blob) aggregating the **preceding 7 days** of `tsumego_reports`. `computeServerStats` (`pwa/src/server-stats.js`) runs **one** window query (`WHERE created_at >= ?`) and does all bucketing in JS — totals, daily activity, by-size split, solving/review time histograms (10s buckets capped at 600s, but **bucketing each user's *median* time, so the histogram counts users, not attempts** — heavy users don't dominate; for review time, which is **cumulative across a problem's repeats** (each repeat re-reports the running total), only the last instance per (user, problem) is kept before taking the median, else the running total double-counts), a **recall-time** distribution (per user, the *median* over problems of the novel→first-repeat gap — from the first in-window non-repeat attempt to the very next attempt on that problem, **≥6h** (shorter gaps are ignored entirely), into hardcoded `6h–1d / 1–2d / 2–3d / 3–4d / 4–5d / 5d+` day bins; only gaps whose novel attempt *failed* count, because the spaced-repetition interval lengthens with each success and isn't comparable), and a per-user attempts-per-active-day distribution (`attemptsPerUserDist`). The **rank histogram and the country distribution do NOT come from that scan** — `computeLeaderboardStats` builds both from ONE scan of the `leaderboard` table via `readActivePlayers` (`src/leaderboard.js`), which is pruned to roughly weekly-active size, so it's the same small full scan the `/leaderboard` page already runs (NOT another pass over `tsumego_reports`). Rank = each active player's **untimed SHOWN onlymove rank** — `resolveRowRank` (the stored `pred_rank`, else recomputed from the row's buffer), read verbatim with no coupling to invert and no dock to undo, i.e. the SAME `displayRank` off the same window posterior, over the same materialized buffer, that the front-page badge and `readLeaderboardRows` show — rounded, one player per bin, weakest→strongest; players below `RANK_START_MIN` carry no rank and drop out, **hidden profiles are counted** (hiding withholds a name/country, never the rank). Countries: `GROUP BY` in JS over the same rows' stamped edge geo-IP `country`, **hidden profiles excluded** (they opted their country out of the board), commonest-first. **Rank must not be averaged off the problems a user was SERVED.** That is the free-looking derivation — the attempts are already in hand from the window scan, so it saves the leaderboard scan — and it is biased in BOTH directions, compressing the distribution toward the middle: selection centres on `serveRank` = the estimate plus a non-negative UCB bonus, so an unconverged user reads too STRONG (~0.7 ranks at 15k and weaker, ~0.25 in the 15k–8k band), while taking each rating from its equal-count shard band's midpoint — the bands are wide out in the tails and their mass is not symmetric about that midpoint, and the nearest-loaded pool is one-sided out there too — reads a dan player ~1 rank too WEAK. The scan it saves costs no extra D1 rows anyway. Note which population this histogram counts: *ranked players* active in the window, so a beginner under `RANK_START_MIN` is absent from it and an established player having a light week is present. **D1 bills rows read, so `created_at` MUST stay indexed (`idx_tsumego_reports_created`)** — without it every `created_at >= ?` is a full-table scan of all history that blows the daily read quota. Keep the one shared window scan **over `tsumego_reports`**; don't split THAT back into per-metric queries. Freshness: the blob is stamped with `APP_VERSION`; `handleServerStats` recomputes lazily on a version mismatch and returns `Cache-Control: no-store` (otherwise Cloudflare edge-caches the blob; the client also fetches `/server-stats?v=APP_VERSION`); the hourly `scheduled()` cron recomputes on version-mismatch OR ≥23h age. Rendered by `buildServerStatsPane` (`stats-community.js`) as the Community tab; the country distribution renders as a flag+code bar list — EVERY country, no top-N fold (folding the tail into one "Other" row is the tidier rendering and hides exactly the small communities the list is interesting for) — via the shared `flag()` (`pwa/shared/flag.js`, one definition for the Worker `/leaderboard` page and this client pane), the requester's own bar highlighted from the `X-Client-Country` header `handleServerStats` stamps on the response (the blob is community-wide, so per-request identity cannot live in its body, and the client has no other read of its own geo).

**The pane's "you are here" marker on that histogram is the reader's own `displayRank`.** `computeUserCommunityBuckets` (`js/stats-compute.js`) reproduces the Worker's per-user bucketing on the client's own last-7-day history for the time / attempts-per-day / recall bars; the RANK bar instead takes what `stats-ui.js` hands it — `state.displayRank`, the badge's number — and bins it with `rankToLabel(clampRankBand(rankBand(shownRank)))`, the expression `computeLeaderboardStats` bins the bars with, so the marker and the bar it lands in are the same quantity. Two gates hold it to the bars' population, and both matter because the client can always produce a rank where the Worker declines to: **`RANK_START_MIN`** (in `shared/rank-window.js` so the client, the Worker and the offline rebuilds read one definition; `src/leaderboard.js` re-exports it for the Worker-side consumers) — under it no `pred_rank` is stored and the player is absent from the histogram, while the client's `displayRank` getter still answers with the cold-start prior, which would mark a bin for someone the distribution excludes; and the function's "no attempt in the last 7 days → no buckets at all" return, which is the client-side reading of the leaderboard's `last_active` window.
