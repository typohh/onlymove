# Leaderboard page and Community stats

Two read paths over the same small `leaderboard` table, both cost-sensitive because D1
bills rows read. CLAUDE.md carries the short form and points here.

## The /leaderboard page

**The `/leaderboard` page is a compute-on-read display resolver with a UNITS selector offering onlymove and EVERY coupled ranking system; its two value columns are "Declared" (the player's own rank on the selected system, overridden by a linked federation account's machine-verified rating) and "Predicted" (our estimate, coupled into that system's frame).** The server-rendered page (`src/handlers/leaderboard-page.js`) reads `readLeaderboardRows` (`src/leaderboard.js`) — the single place that stitches each row's display identity from three tables: the onlymove estimate off the (rebuildable) `leaderboard` buffer, name/country off the `external_ids` binding (`display_name`/`country_code`, snapshotted from EGD/AGA at link time), and per-user external ranks off the row's own `declared` cache (the latest `rank_surveys` row per server; see below) — BOTH the human declarations (one per surveyed system) and the MACHINE heartbeats: `egd` = the `'EGD'` row (`rank` = raw GoR digits, `rank_label` = the EGD Grade, `last_game_at` = the parsed `Last_Appearance` tournament date — written weekly by the client GoR piggyback, `gor-refresh.js` → `applyGorUpdates`) and `aga` = the `'AGAR'` row (`rank` = the RAW AGA rating, `rank_label` = the AGA's official label, `last_game_at` = `latest_event_date`; written weekly by the Worker cron `refreshAgaRatings`, seeded at link time by `link.js`). A heartbeat WINS on its own system — the `'EGD'` GoR on EGF, the `'AGAR'` rating on AGA — so a player with that federation account linked shows a verified rank there rather than their self-report, while every other system shows the declaration. Declarations still feed calibration exactly as before; the page is a second consumer of them, never an input to a fit. Each verified rating is **activity-gated per the EGF criteria** (`isVerifiedActive`: last tournament within 2 years for dan/pro, 1 year for single-digit kyu, 6 months for double-digit kyu; tier from the official label when present, else the rating; a MISSING date fails OPEN); a dropped heartbeat hands its cell back to the player's own declaration if they made one. The units selector (a `<select>`) offers onlymove plus every key of `rank_map.json` (`RANK_SYSTEMS`), and picks the frame BOTH value columns speak; the list grows with the couplings rather than being enumerated in the page. It resolves **`?units=` over `localStorage.lbUnits` over onlymove** — an explicit request in the URL beats the device preference, so `/leaderboard?units=Fox` opens on Fox — matching case-insensitively and accepting `onlymove` for `om` (which also carries forward the lowercase `egf`/`aga` the two-system selector stored). The current selection is mirrored back with `history.replaceState` (default = the param's ABSENCE, keeping bare `/leaderboard` canonical; `replaceState`, not `push`, since a units switch is a display toggle rather than a navigation), so the address bar is always shareable and a reload cannot snap back to a stale param. **The response body does not depend on the param** — every frame is already inlined per row and the switch is pure client work — so a param costs its own 60s edge-cache entry and nothing more; there is no second D1 read path, and no `Vary`-style fragmentation of the aggregation itself. Each shown row therefore carries two per-system maps — `est` (the estimate in every frame) and `decl` — built once server-side, so switching units is pure client work. **Every frame is the SHARED band-edge convention and every cell goes through the SHARED `rankProgress`**, which is what lets the two columns be compared at all: a GoR enters via `gorToRank`, an AGA rating via `agaRatingToRank` (the LABEL-PRESERVING ∓1 shift that puts AGA's floor bands exactly on ours — mirroring `aga_rating_to_value` in `utils/rating/rank_surveys.py`), a declaration via `rankLabelToRank`, and the estimate via each system's coupling. A cell shows "rank (pct%)" when its value resolves WITHIN the band (a heartbeat, or an estimate) and the bare band label when it does not (a declaration names a band and nothing more, so its scalar is only that band's centre). Server-frame labels are ladder-clamped (`clampRankBand`) exactly as the client's rank-translation modal does; the onlymove frame is left unclamped in both. onlymove units leave the Declared column blank — an onlymove rank is measured here, never declared. The estimate reaches each frame as the forward coupling `internalToServerRank` applied to the stored rank AFTER `addTimeDockToInternalRank` puts it in the TIME-ADJUSTED frame, deliberately, because that server frame is what the real federation ratings speak (EGF is one coupling among the others here, not a stored special case). **Adding the dock before the coupling is load-bearing: the couplings were fitted against time-adjusted ratings, so mapping the untimed rank forward silently shifts every estimate by the user's personal dock.** Sorting always uses the underlying continuous scalars OF THE DISPLAYED FRAME — the om (untimed) and per-system (time-adjusted) estimate orders differ per user by the personal time dock, so switching units re-sorts. `gorToRank` (1k = 2000, ~100 GoR/stone, less a half-band so it lands on our band centre) survives as the tier/label fallback. `rank_surveys` carries nullable `rank_label` + `last_game_at`; a new column here is appended LAST, since the `fetch_database` dump is positional. **A column change on any table this page reads runs CHAINED — migrate the remote D1 → `npm run deploy` → `fetch_database` → `auxiliary/update_leaderboard_ranks.mjs --remote`.** The migration has to land before the deploy that SELECTs the new columns, so in the gap the running Worker writes columns the new schema no longer has; that is survivable only because every path degrades softly — `/report`'s leaderboard write is a caught `waitUntil`, so the attempt still lands in `tsumego_reports` and merely misses its incremental buffer push (the final `update_leaderboard_ranks.mjs` repairs it by rebuilding buffers from `tsumego_reports`), and the page and the stats aggregation are try/caught. **Country (→ the flag) falls back GoR → the binding → leaderboard geo-IP → survey, and EVERYONE gets a flag:** the `'EGD'` heartbeat's country (the EGD federation code, most reliable since it comes from EGD) wins, then `external_ids.country_code` (also EGD, frozen at link time; an AGA link stores none, since the Ratings Explorer reports a US state rather than a country), then the `leaderboard.country` column, then any human survey's Cloudflare geo-IP `country`. **`leaderboard.country` is the UNIVERSAL fallback**: it's the request's edge geo-IP (`request.cf.country`) stamped into the row's ALREADY-happening `/report` UPDATE/INSERT (`updateLeaderboardOnReport`/`createLeaderboardRow` in `leaderboard.js`) — so it costs **no extra read or write** (the SELECT reads `l.country` off the same row; the write folds `country = COALESCE(?, country)` into the existing statement, `COALESCE` so an unknown geo never clobbers a known-good code, a real code wins last-writer-wins so the flag follows travel), and it gives a flag to EVERY active player (nearly all anonymous rows), not just the registered/surveyed few. The stamp is filtered through `normalizeCountry` (real ISO-alpha-2 only; the Cloudflare sentinels `XX`/`T1` → null, which would else render as a broken flag). When even that resolves nothing (or a hidden profile), the page shows the `UNKNOWN_FLAG` = 🇺🇳 constant (`leaderboard-page.js`) so no row is ever flagless. The EGD/survey `country` rides in the same cached entry as `rank`. A row with no code yet fills it on its owner's next report. **Hide opt-out:** a `hidden_profiles` row (presence = hidden; keyed by `user_id`, its OWN table because even a never-registered user can have declared ranks in `rank_surveys` worth hiding) makes `readLeaderboardRows` withhold that user's name, country, and every declared/verified rank — they render as an **anonymous row carrying only their onlymove estimate** (a hidden-and-unranked row is dropped, matching how a never-registered unranked player is already omitted); the onlymove rank itself is never hidden. Toggled from TWO places, one flag: the Leaderboard section of the in-app Account dialog (`js/account-ui.js`), beside the identity link it applies to, and a checkbox at the foot of the in-app rank survey (`js/rank-survey-prompt.js`), which is where a declaration is actually made. Both call `POST /profile/hide {userId, hidden}` (set/clear) and `GET /profile?userId=` (read state, `no-store`; it also returns the latest declaration per survey server, `declared`, which the survey prefills its pickers with), in `src/handlers/profile.js` (`RL_WRITE`-limited, `isValidUserId` + boolean format-validated). The /leaderboard page carries NO control of its own, and no pointer to one either — it is server-rendered and edge-cached, so a control there had to bootstrap its own state from a second read, while the dialog that already reads `/profile` for the identity gets the flag in the same response. **Both checkboxes READ the flag back on open and write only on a change** — each is unchecked by default, so posting the current state unconditionally would silently un-hide anyone who had opted out in the other place. **`GET /profile` is in the service worker's dynamic-GET bypass list** (`sw.js`): its URL is the userId and nothing else, so a cache-first copy would keep reporting the settings the dialog just changed as un-changed, permanently. The table is in `schema.sql`. **The row stores the SHOWN rank in the window estimator's OWN frame — `pred_rank` (the UNTIMED internal onlymove rank the player is actually told: `estimateWindowRankFromFlat`'s `displayRank`, the posterior mean less `K_DISPLAY` excess-se, NOT the mean), `pred_rank_se` (the posterior SE in stones) and `time_delta_rating` (the personal time dock in rating units).** Storing the shown rank is what keeps the page, the Community histogram and the player's own badge on one number, and it does not reopen the calibration loop `displayRank` is otherwise kept out of: the rank-map couplings are fitted on the backend from `rank_surveys` + `fit_user_rating` and read nothing from this table, so `pred_rank` is never an input to a fit. Two consequences. **The rank-dependent SE floor is part of the stored value, so every caller must price it from the same numbers** — which is why no caller measures it: it is a corpus property, shipped once as `pwa/tsumegos/se_floor.json` by `package_for_pwa`'s `emit_se_floor_curve` and read through `seFloorAt` (`shared/rank-window.js`), which `estimateWindowRankFromFlat` applies internally so no caller passes a floor function at all. `src/leaderboard.js` computes none, and neither do the offline rebuilds (`auxiliary/update_leaderboard_ranks.mjs`, `auxiliary/leaderboard_player_stats.mjs`) — which is the failure this closes, since they load `problem_params.bin` themselves and never call `getProblemParams`, so any reader-scoped floor index left them writing a shown rank the live Worker disagreed with for the same buffer. **And this table's estimate-vs-verified comparison is NOT a calibration measurement** — `displayRank` is deliberately conservative while a posterior is wide, so the gap is a display policy, not the mapping's bias; `ablations/check_mapped_vs_declared_rank.py` scores the calibrated estimate against every declared and verified rating, and `auxiliary/leaderboard_player_stats.mjs` deliberately carries no correlation summary so the two cannot be confused. **The `buffer` column is maintained INCREMENTALLY and is never rebuilt from `tsumego_reports` on the hot path**: `updateLeaderboardOnReport` reads the stored buffer, pushes the one new attempt, writes it back (and `updateLeaderboardOnBackfill` does the same for an outbox batch). **Buffer order is INSERT order (the AUTOINCREMENT `id`), and that is the ONE convention every writer and every rebuild shares** — the two incremental pushes, `buildRowStateFromReports` (`ORDER BY id DESC`, used by `createLeaderboardRow` and the weekly cron `reconcileBuffers`), and `auxiliary/update_leaderboard_ranks.mjs`. A backfilled row carries a historical `created_at` but a fresh id, so under this convention it IS the newest and prepending is correct. Event order would need a `(user_id, created_at)` index that was deliberately dropped, turning a bounded `BUFFER_CAP` read into a full per-user history scan — 3× the rows read across the leaderboard, 34× for the heaviest user, on a path that runs inside `/report`'s `waitUntil`. So anything that overwrites a row's buffer with a stale snapshot drops whatever landed in between **permanently** — later reports append on top of the shortened list rather than restoring it, and the only rebuild path is `createLeaderboardRow`, which runs only for a user with NO row at all. That is the hazard in `auxiliary/update_leaderboard_ranks.mjs`, the retroactive refresh that moves every row's rank onto a new scale after a re-rate (it recomputes `buffer`/`pred_rank`/`pred_rank_se`/`time_delta_rating` only — `country` and `last_active` are untouched, and the `--populate` pass is `INSERT OR IGNORE` so it cannot clobber an existing row). **Run it under the MAINTENANCE FREEZE** (`MAINTENANCE_MODE = "1"` — see the write-guard note below): every attempt reported in the gap between its snapshot and its write is silently truncated out of that user's buffer, with no error and no recovery, and with every POST 503ing nothing can land in that gap, so the race is not merely unlikely but IMPOSSIBLE. That is why the leaderboard refresh belongs INSIDE the surgery window rather than after the lift (`docs/db_surgery_runbook.md` step 8), and it applies to a standalone post-re-rate refresh too — freeze, refresh, unfreeze. Chaining the fetch into the apply (`python3 -m pipeline.fetch_database && node auxiliary/update_leaderboard_ranks.mjs --remote`) only NARROWS the window; it is a fallback, never the guarantee, and `+0 new tsumego_reports rows` on that fetch is evidence the window happened to be clean, not that it was closed. **`--remote` ENFORCES the freeze rather than trusting the operator** (`preflightRemote`): it probes `POST /sync` on the live origin (from wrangler.toml's `custom_domain`) and refuses unless it gets `503 {error:'maintenance'}` — the DEPLOYED Worker is the authority, not the local `wrangler.toml` value — and refuses unless the local mirror's `MAX(id)` on `tsumego_reports` EQUALS production's, so a snapshot taken before the freeze can't be used. It re-checks both after the apply, turning "the window was closed when we started" into "it stayed closed throughout"; a lapse is reported with the remedy (re-freeze, re-fetch, re-run — the rebuild is idempotent) instead of corrupting rows silently. The preflight runs BEFORE the per-user recompute so a missing freeze costs seconds, and it fails CLOSED (any error reaching production is a refusal). `--allow-unfrozen` overrides deliberately. Note `MAX(id)` catches INSERTS, which is the documented hazard; a purge changes existing rows without moving it, so after surgery use the runbook's COUNT/SUM check. Its ordering rule is separate and also load-bearing: `package_for_pwa` → `npm run deploy` → fetch → update, since running it before the deploy lets the next `/report` recompute on the OLD scale and overwrite the work. (`GET /tournament` is a **STATIC final-results page** for the concluded 2026 tournament — `src/handlers/tournament-page.js` bakes the standings in as a `PARTICIPANTS` const (a verbatim snapshot of the production leaderboard's last-week-peak on 2026-07-20) and does NO D1 read; it does not share `readLeaderboardRows`, so this page's frames don't reach it.)

## Linking a federation identity

**A player puts their own name on the board: the Account dialog searches EGD and AGA and binds the account to the row they pick.** `js/account-ui.js` renders a Leaderboard section under the account code — the current binding or a search box, plus the hide opt-out — reading both in ONE `GET /profile?userId=` (`src/handlers/profile.js`, which calls `readLinkedIdentity` from `link.js`). The search runs in the BROWSER (`js/identity-search.js`), and that is forced rather than chosen: **the Worker cannot reach EGD at all** (behind Cloudflare, so a Worker→CF-zone subrequest returns 403 "error code: 1106", the orange-to-orange restriction), while the page can, since EGD sends `Access-Control-Allow-Origin: *`. The AGA Ratings Explorer sends it too, which is what lets ONE box cover both: an all-digits query is ambiguous between an EGD PIN and an AGA member id, so it is looked up as both, and a name query is tried BOTH ways round against each database's first/last split, since nobody typing their own name knows which half it considers the surname. A database that errors or times out contributes nothing and the other's results still show.

**`leaderboard.declared` is a CACHE of `rank_surveys`, and every statement that writes or deletes `rank_surveys` rows refreshes it in the same batch.** `rank_surveys` is the log: every declaration and every weekly heartbeat, kept for drift, so it grows without bound. Grouping it per render is what the page would otherwise pay on every view, while the cache is one JSON array per row, `[{server, rank, country, rank_label, last_game_at}]` holding the newest row per server by id. **It is derived and never written directly.** Its one expression is `declaredJsonSql` (`src/leaderboard.js`), which `refreshDeclaredStmt` applies to an existing row. The survey (`handlers/rank-survey.js`), both heartbeats (`applyGorUpdates`, `refreshAgaRatings`), link and unlink (`handlers/link.js`) each end their batch with that statement. A row created later takes the expression inline: `createLeaderboardRow`, the link upsert (refreshed after it in the same batch), and `update_leaderboard_ranks.mjs --populate`, which has the TARGET database compute it from its own log. So a player returning after the idle prune gets their Declared column back with the reseeded row, and the expression admits an `'EGD'`/`'AGAR'` heartbeat only while the account has an `external_ids` row, which is what makes unlink correct: the heartbeat stays in the log but leaves the cache, and the user's own EGF/AGA declaration, if any, takes its cell back. **The heartbeat refreshes are guarded to an insert that landed** (an `EXISTS` on the row carrying the batch's own timestamp). The week guard makes most GoR re-submits a no-op insert, and an unguarded UPDATE would still bill a row written for each one. A missed refresh leaves that user's cell stale, not wrong forever: `migrations/2026-09-23_leaderboard_declared_backfill.sql` recomputes every row and is idempotent, so it is the repair.

**`POST /link {userId, service, id, name, country}` binds; `POST /unlink {userId}` releases.** What the Worker takes on trust differs by service, and only because of what it can reach. **AGA is fetched Worker-side** (`fetchAgaPlayer` — Azure, not Cloudflare), so an id that does not resolve is REFUSED (`unreachable`), the stored `display_name` is the Explorer's own, and the first `'AGAR'` heartbeat is written from that same fetch, so the player shows a verified rank immediately. **EGD is taken from the linking client's fetch** for the name and country, and **no rating is accepted on the link path at all**: the GoR arrives through the existing weekly client piggyback (`js/gor-refresh.js` → `applyGorUpdates`), which already bounds it, week-guards it, and requires the pin to be linked. `bufferGorUpdate` hands the search's already-fetched EGD record straight to that buffer so it rides the very next `/report` rather than waiting for some other client to be asked, and `invalidateStaleGor` drops the in-memory stale-pin cache so a pin linked seconds ago is advertised at once instead of waiting out the 5-minute TTL. So linking opens no path by which a rating could be asserted that did not already exist.

**NOTHING VERIFIES THAT THE USER IS THE PLAYER, and no such check exists to add** — neither database authenticates anyone, so a linked name is a claim rather than a credential. Two properties stand in for verification and both are enforced server-side. The claim is **EXCLUSIVE**: a player id already bound to another account is refused (`id_taken`), on top of the per-column UNIQUE index that is the hard backstop. And it is **REVERSIBLE**: Unlink deletes the `external_ids` row, freeing the id for whoever asks next, and relinking REPLACES in one write (the other service's column is cleared in the same statement, since an account binds to one identity). **Unlinking deletes only the binding; the account's `'EGD'`/`'AGAR'` heartbeats stay.** A heartbeat is a dated statement about the account made on the user's behalf, the machine counterpart of a survey answer, and the rank-mapping fit reads the whole log — so a user moving their identity to another account must not retroactively erase what the old account recorded. What unlinking changes is display: `declaredJsonSql` admits heartbeats only for a linked account, so an unlinked one shows its own declarations. Heartbeats carry `user_id` and no player id, which is sound because an account is one person and has no reason to be relinked to a different player. The `leaderboard` row is untouched too: it is the account's own rank state, shown for every active player, so unlinking makes the row anonymous rather than removing the player.

**The Account dialog shows `<name> · <grade>`, and only the NAME is stored on the binding.** The grade is read live off the account's latest `'EGD'`/`'AGAR'` heartbeat (`readLinkedIdentity`), preferring the federation's own `rank_label` and deriving one through `gorToRank`/`agaRatingToRank` only for a legacy heartbeat written before that column existed — a band-edge approximation rather than the grade itself (a 2347 GoR reads `4d` officially and `3d` derived), which is why the stored label wins and why those rows age out on their next weekly refresh. **Snapshotting the grade onto the binding instead is the tempting mistake and buys nothing**: `rank_surveys` already keeps that rating, keeps it CURRENT, and is what the Declared column reads, so a copy is a second source that goes stale and can disagree with the board. The cost argument for a copy does not survive either: a per-user read of `rank_surveys` is an index read (`idx_rank_surveys_user`), and `GET /profile` fires when somebody opens a dialog. An EGD link has no heartbeat until the GoR piggyback lands on the next `/report`, so `POST /link` answers with a grade only for AGA (which it fetched itself) and the client fills that one render from the search result it just picked.

**The binding carries the display fields, which is why they live on `external_ids` and not beside it.** `display_name` and `country_code` are snapshotted from the service at link time and go away with the row — a property the retired invitation flow could not have, since a claim is a historical fact rather than a current state. Before 2026-08-25 registration was invite-only and `readLeaderboardRows` joined the claimed `invitation` row for the name; `migrations/2026-08-25_self_link_identity.sql` adds the two columns and copies every existing registration's name and country across, and the `invitation` table is left in place, read and written by nothing, droppable once the live board is confirmed showing names off `external_ids`. **That migration must land BEFORE the deploy that SELECTs the new columns** — the chained order in the page section above.

## A self-chosen leaderboard alias

**An account with no linked federation identity may pick a three-word pseudonym ("Brave Crimson Fox") for the public board; until it does, it stays Anonymous.** The alias is opt-in and user-authored — nothing is assigned automatically and existing accounts are not backfilled — so an account that never opens the picker renders exactly as it always did. The `/leaderboard` "Player" column resolves identity in ONE order: a linked `external_ids.display_name` wins, then the account's own alias, then `Anonymous`; a `hidden_profiles` row withholds all three, so a hidden player shows `Anonymous` whatever alias they picked. The Account dialog's Alias row reads and writes the choice through `GET /profile` and `POST /profile/alias`.

**The stored triplet is ENGLISH and the three word tables are the legal set.** `alias_adjectives`/`alias_colors`/`alias_animals` — seeded by `pwa/scripts/gen-alias-seed.mjs` from `pwa/shared/alias-words.js` — are what `canonicalAlias` validates a submission against, and `user_aliases` stores the word each table returned, never the raw input, so a stale or hand-edited client bundle cannot widen the vocabulary. English is also the IDENTITY: `idx_user_aliases_triplet` is a UNIQUE index on the three columns, so a translation can never create, free or collide a claim, and a change to the word lists never renames an existing player. The Worker pre-checks legality in one round trip; **the index, not the pre-check, settles a race between two accounts submitting the same triplet**, and its violation is reported as `alias_taken`.

**Translations are display-only, one entry per word in en/zh/ja/ko plus a per-language join.** A word cannot be translated and concatenated word-by-word — Japanese needs the attributive form and a の before the animal, Chinese the 的 on the adjective, Korean the 관형형 — so `composeAlias` supplies the grammar, and `composeAliasAll` pre-composes all four for the server-rendered board, which resolves its language on the CLIENT (the page is edge-cached, so it cannot pick one). A word this module no longer holds falls back to the stored English, which is what keeps a retired word's alias renderable.

**The alias row is a THIRD display state, not the negation of `registered`.** `readLeaderboardRows` carries `alias` beside `registered` and nulls it for a hidden profile; the page's `anon` flag means "no name AND no alias" and keeps the muted italic treatment, while a chosen alias renders as a name. `user_aliases` is deliberately **not pruned** — unlike `leaderboard`, which the weekly cron deletes and the next novel `/report` rebuilds, this is a durable choice — and clearing it returns the account to `Anonymous` and frees the triplet for anyone else. **Linking does not delete the alias**: a linked player's alias is unread while the name wins, so Unlink restores it instead of dropping the account back to Anonymous.

## Monthly historical boards

**The `/leaderboard` period selector offers the live week plus every finished month, and a month's board shows the HIGHEST rank each player held during it.** The live `leaderboard` row carries the tracker: `best_rank` is the max UNTIMED internal rank an observed attempt has reached in the CURRENT UTC month, `best_rank_timed` that same observation's TIME-ADJUSTED internal rank (the frame the server couplings speak), and `best_rank_month` the month they belong to. A rank observed in a new month REPLACES the peak, so the tracker resets at the boundary by itself; within a month the max wins. **Only the attempt paths write these** (`updateLeaderboardOnReport`, `updateLeaderboardOnBackfill`, `createLeaderboardRow`) — the weekly `reconcileBuffers` must NOT, because a rebuild is not activity and folding it in would attribute an inactive user's recomputed rank to a month they never played. `handlers/link.js` seeds no peak either (linking is not an attempt); its upsert leaves the columns alone.

**The finished month is frozen as RAW USER IDS and identity is resolved at READ time.** At the month change `recordMonthlyLeaderboards` writes one `monthly_leaderboards` row (`month` = the UTC calendar month that just ended, `data` = a JSON array of `[user_id, best_rank, best_rank_timed, country]`) for every live row whose `best_rank_month` is that month — i.e. exactly the users active in it who reached the list-entry gate. It is idempotent and runs on every hourly tick, no-oping once the month exists, so a tick dropped by the freeze or the platform is repaired by the next one rather than losing the month — and a month with no entries is not written at all, so the selector never offers an empty board (which is also what keeps the deploy month, whose peaks were never tracked, out of the list). It needs no reset step, since each live row carries its own month key. **The snapshot must not bake in an identity**, because a linked name can be unlinked, an alias re-picked, and a profile hidden AFTER the month closed, and all three have to apply to history: `readMonthlyLeaderboard` stitches `external_ids`/`user_aliases`/`hidden_profiles` on the way out, so a hidden account still renders Anonymous and a changed alias shows the new words. **The country is the one baked field**: the freeze stores the country the weekly board would show (`resolveRowCountry`, the same precedence), because its geo-IP source lives on the live row and the prune removes it, and the read overrides it with the CURRENT country while the user's live row survives (fetched for the blob's ids only, by primary key) and withholds it from a hidden profile — baked regardless, so an un-hide restores it. The baked value is what a user shows once the prune has taken their row. A monthly board shows no Declared column — a survey declaration is a CURRENT claim, and the monthly board's single value column is "Highest".

**The live table is pruned at 5 WEEKS, not 7 days, so the freeze can still see a month's first days.** A user active on the 1st must survive to the month boundary, up to 31 days later, for their peak to be frozen; 35 days covers the longest month with margin, so the freeze never races the prune. The `/leaderboard` page and the Community rank histogram still filter `last_active` to the trailing week, so the visible board is unchanged — the extra retention is read only by the freeze, which full-scans the table once a month. **The month attribution is the report's own timestamp, not the attempt's `created_at`**: a backfilled historical attempt is folded into the month the flush lands in, matching `last_active`'s presence-not-event-time convention, so the one gap is a report landing between UTC midnight on the 1st and the freeze a moment later — that row's `best_rank_month` rolls to the new month and the closing month can miss that player's peak.

**A re-rate REBUILDS the frozen months rather than clearing them, and the same walk gives a fresh deployment full history.** The frozen JSON holds ranks, so a change to the rank scale invalidates every month at once; `auxiliary/update_leaderboard_ranks.mjs` therefore replays each user's whole NOVEL attempt history once — `monthlyPeaksFromAttempts`, over the O(n) `windowRankWalk` in `shared/rank-window.js`, which maintains the estimator's window posterior incrementally instead of re-summing it per step — takes the peak per UTC month, and rewrites `monthly_leaderboards` for every finished month plus the live row's `best_*` for the open one. Month attribution there is the attempt's `created_at` (the month it happened), not the upload time the live tracker sees. `--no-history` opts out and only clears the peak columns, which is the correct fallback when the walk cannot run: a `--user`-scoped run skips the rebuild, because it would rewrite a month from a single user's history. `--local` applies to the miniflare D1 and adds the monthly columns/table if the local mirror predates them; `--remote` refuses when production has not had the migration applied.

## Server-wide Community stats

**Server-wide "Community" stats are a cached, read-cost-sensitive D1 aggregation.** `GET /server-stats` serves a single `server_stats` row (`key='latest'`, JSON blob) aggregating the **preceding 7 days** of `tsumego_reports`. `computeServerStats` (`pwa/src/server-stats.js`) runs **one** window query (`WHERE created_at >= ?`) and does all bucketing in JS — totals, daily activity, by-size split, solving/review time histograms (10s buckets capped at 600s, but **bucketing each user's *median* time, so the histogram counts users, not attempts** — heavy users don't dominate; for review time, which is **cumulative across a problem's repeats** (each repeat re-reports the running total), only the last instance per (user, problem) is kept before taking the median, else the running total double-counts), a **recall-time** distribution (per user, the *median* over problems of the novel→first-repeat gap — from the first in-window non-repeat attempt to the very next attempt on that problem, **≥6h** (shorter gaps are ignored entirely), into hardcoded `6h–1d / 1–2d / 2–3d / 3–4d / 4–5d / 5d+` day bins; only gaps whose novel attempt *failed* count, because the spaced-repetition interval lengthens with each success and isn't comparable), and a per-user attempts-per-active-day distribution (`attemptsPerUserDist`). The **rank histogram and the country distribution do NOT come from that scan** — `computeLeaderboardStats` builds both from ONE scan of the `leaderboard` table via `readActivePlayers` (`src/leaderboard.js`), whose rows are filtered to the trailing week, so it's the same small full scan the `/leaderboard` page already runs (NOT another pass over `tsumego_reports`). Rank = each active player's **untimed SHOWN onlymove rank** — `resolveRowRank` (the stored `pred_rank`, else recomputed from the row's buffer), read verbatim with no coupling to invert and no dock to undo, i.e. the SAME `displayRank` off the same window posterior, over the same materialized buffer, that the front-page badge and `readLeaderboardRows` show — rounded, one player per bin, weakest→strongest; players below `RANK_START_MIN` carry no rank and drop out, **hidden profiles are counted** (hiding withholds a name/country, never the rank). Countries: `GROUP BY` in JS over the same rows' stamped edge geo-IP `country`, **hidden profiles excluded** (they opted their country out of the board), commonest-first. **Rank must not be averaged off the problems a user was SERVED.** That is the free-looking derivation — the attempts are already in hand from the window scan, so it saves the leaderboard scan — and it is biased in BOTH directions, compressing the distribution toward the middle: selection centres on `serveRank` = the estimate plus a non-negative UCB bonus, so an unconverged user reads too STRONG (~0.7 ranks at 15k and weaker, ~0.25 in the 15k–8k band), while taking each rating from its equal-count shard band's midpoint — the bands are wide out in the tails and their mass is not symmetric about that midpoint, and the nearest-loaded pool is one-sided out there too — reads a dan player ~1 rank too WEAK. The scan it saves costs no extra D1 rows anyway. Note which population this histogram counts: *ranked players* active in the window, so a beginner under `RANK_START_MIN` is absent from it and an established player having a light week is present. **D1 bills rows read, so `created_at` MUST stay indexed (`idx_tsumego_reports_created`)** — without it every `created_at >= ?` is a full-table scan of all history that blows the daily read quota. Keep the one shared window scan **over `tsumego_reports`**; don't split THAT back into per-metric queries. Freshness: the blob is stamped with `APP_VERSION`; `handleServerStats` recomputes lazily on a version mismatch and returns `Cache-Control: no-store` (otherwise Cloudflare edge-caches the blob; the client also fetches `/server-stats?v=APP_VERSION`); the hourly `scheduled()` cron recomputes on version-mismatch OR ≥23h age. Rendered by the standalone **`/statistics` page** (`src/handlers/statistics-page.js`), server-rendered on the shared page shell like `/leaderboard`: the handler reads the blob through `loadServerStats`, folds the time histograms into the display bins of `pwa/shared/community-bins.js`, and inlines the rows for the page's own script to draw; `GET /server-stats` stays as the JSON form of the same blob. The response is **`no-store`** because the requester's edge geo-IP country is stamped into it for the country chart's own bar — the blob is community-wide, so per-request identity cannot live in its body — and it is one cached-row read, so an edge cache would save nothing and would hand one viewer's country to the next. The country distribution renders as a flag+code bar list — EVERY country, no top-N fold (folding the tail into one "Other" row is the tidier rendering and hides exactly the small communities the list is interesting for) — via the shared `flag()` (`pwa/shared/flag.js`, one definition for both Worker pages).

**The page's "you are here" markers come from the app, through the URL fragment.** The page holds no history, so the app's Statistics menu link writes the reader's bins into the fragment at click time (`communityYouFragment`, `js/stats-compute.js`); a fragment never reaches the server, and a link shared without one shows the plain community data. `computeUserCommunityBuckets` reproduces the Worker's per-user bucketing on the client's own last-7-day history for the time / attempts-per-day / recall bars, in the same `TIME_BINS` the Worker folds the bars into; the RANK bar instead takes `state.displayRank`, the badge's number, and bins it with `rankToLabel(clampRankBand(rankBand(shownRank)))`, the expression `computeLeaderboardStats` bins the bars with, so the marker and the bar it lands in are the same quantity. Two gates hold it to the bars' population, and both matter because the client can always produce a rank where the Worker declines to: **`RANK_START_MIN`** (in `shared/rank-window.js` so the client, the Worker and the offline rebuilds read one definition; `src/leaderboard.js` re-exports it for the Worker-side consumers) — under it no `pred_rank` is stored and the player is absent from the histogram, while the client's `displayRank` getter still answers with the cold-start prior, which would mark a bin for someone the distribution excludes; and the function's "no attempt in the last 7 days → no buckets at all" return, which is the client-side reading of the leaderboard's `last_active` window.

## The /contest page

**`GET /contest` renders the contribution-rewards rules and the live entry lists off one cached blob, `server_stats` key `'contest'`, recomputed ON REQUEST only when the row is missing or was produced by an older `APP_VERSION`** — there is no age expiry (`loadContest`, `src/contest.js`; page in `src/handlers/contest-page.js`). There is no cron path: the recompute replays every entrant's WHOLE novel-attempt history, which is cheap for a handful of accounts and pointless to run for a page nobody opened. **Entries are written only by `auxiliary/contest_entries.mjs`**, which drops the cached blob on every write so an edit shows on the next view. That drop is also when an entrant's name is resolved: a rename, link or hide made afterwards reaches the page only at the next organiser write or deploy, which is acceptable because a video entry is almost always a throwaway account. The script finds an account through what the entrant already set up in the app — the linked EGD/AGA record (`external_ids`) for a strong player, the leaderboard alias (`user_aliases`) for a video — because the user id is the account credential, and **neither the blob nor the script's output carries a user id.**

**`contest_entries` stores only what the account cannot supply** — the entry date, and for a video the link, the problems solved on camera, the views and the quality score. Identity is resolved at compute time with the leaderboard's precedence (linked name > alias > Anonymous, `hidden_profiles` withholding both), so **anonymity is the account's hide flag and the entry has none of its own**. A strong player's federation grade (the latest `'EGD'`/`'AGAR'` heartbeat's label) is shown even for a hidden profile, since the grade is what the entry is. The OnlyMove figures come from `rankWalkFromAttempts` (`src/leaderboard.js`), the same shown-rank window walk the monthly rebuild uses, over novel attempts in id order: a strong player's **average is the mean of the shown rank after every attempt past `RANK_START_MIN`, over the account's whole history**, and a video's **peak is the maximum over the first `video_problems` novel attempts**, which is why a video must be played on a fresh account. **The organiser is not an entry**: there is no strength requirement, but the page notes how few players are stronger than the organiser, so the blob carries the organiser's CURRENT figures for that sentence — the EGF rank from the latest `'EGD'` GoR heartbeat of the account linked to `ORGANISER_EGD_PIN`, and that account's current shown OnlyMove rank from `buildRowStateFromReports` (the leaderboard row's own computation over the last `BUFFER_CAP` novel attempts, used rather than the stored row because an idle row is pruned) — refreshed with the lists.
