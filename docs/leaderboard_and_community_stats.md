Two read paths over the same small `leaderboard` table, both cost-sensitive because D1
bills rows read. CLAUDE.md carries the short form and points here.

## The /leaderboard page

**The `/leaderboard` page is a compute-on-read display resolver with a UNITS selector (onlymove / EGF / AGA); the "Verified" column shows ONLY machine-verified linked-account ratings — human survey declarations are never revealed.** The server-rendered page (`src/handlers/leaderboard-page.js`) reads `readLeaderboardRows` (`src/leaderboard.js`) — the single place that stitches each row's display identity from three tables: the onlymove estimate off the (rebuildable) `leaderboard` buffer, name/country off the claimed `invitation` row, and per-user VERIFIED external ratings off ONE latest-per-`(user, server)` pass over `rank_surveys`, MACHINE heartbeats only: `egd` = the `'EGD'` row (`rank` = raw GoR digits, `rank_label` = the EGD Grade, `last_game_at` = the parsed `Last_Appearance` tournament date — written weekly by the client GoR piggyback, `gor-refresh.js` → `applyGorUpdates`) and `aga` = the `'AGAR'` row (`rank` = the RAW AGA rating since 2026-07-21 — legacy label-format rows read as rating-less and age out with the next weekly heartbeat — `rank_label` = the AGA's official label, `last_game_at` = `latest_event_date`; written weekly by the Worker cron `refreshAgaRatings`, seeded at claim by `register.js`). Human survey rows are read ONLY for the last-resort country/flag fallback — their declared ranks feed calibration, never this page. Each verified rating is **activity-gated per the EGF criteria** (`isVerifiedActive`: last tournament within 2 years for dan/pro, 1 year for single-digit kyu, 6 months for double-digit kyu; tier from the official label when present, else the rating; a MISSING date fails OPEN — register-seeded EGD rows carry no date until the first weekly client refresh). The units selector (persisted in `localStorage.lbUnits`) picks the frame BOTH value columns speak. onlymove units: the estimate as the UNTIMED internal rank label (matching the client's front-page headline — read straight off the stored `pred_rank`, which is already in that frame), and the Verified column deliberately BLANK (there is no raw onlymove-frame source datum). EGF/AGA units: both columns as "(pct%) rank" too, decomposed in that federation's OWN convention — EGF band from the GoR (2389 → "(39%) 4d", the GoR convention), AGA through its FLOOR convention (`agaPctRank` in `leaderboard-page.js`: dan = floor(rating), kyu band tops at its integer, hence a 99 clamp; 5.7 → "(70%) 5d"; `agaRankToRating` crosses AGA's (−1, 1) gap first) — the raw GoR/AGA numbers are no longer displayed but remain the sort keys, and the official `rank_label` now drives only the activity-gate tier. The estimate is converted into the same frame via `currentEgf` / `currentAga` — both the forward coupling `internalToServerRank` applied to the stored rank after `addTimeDockToInternalRank` puts it in the TIME-ADJUSTED frame, deliberately, because that server frame is what the real federation ratings speak (EGF is one coupling among the others here, not a stored special case). **Adding the dock before the coupling is load-bearing: the couplings were fitted against time-adjusted ratings, so mapping the untimed rank forward silently shifts every estimate by the user's personal dock.** Sorting always uses the underlying continuous scalars OF THE DISPLAYED FRAME — the om (untimed) and EGF/AGA (time-adjusted) estimate orders differ per user by the personal time dock, so switching units re-sorts. `gorToRank` (1k = 2000, ~100 GoR/stone, less a half-band so it lands on our band centre) survives as the tier/label fallback. `rank_surveys` grew nullable `rank_label` + `last_game_at`, appended LAST (the fetch_database dump is positional): `pwa/migrations/2026-07-21_rank_surveys_verified.sql` (applied to the live D1) — a migration adding columns an updated `readLeaderboardRows` SELECTs must always land on the live D1 BEFORE the deploy that reads them. **Country (→ the flag) falls back GoR → invitation → leaderboard geo-IP → survey, and EVERYONE gets a flag:** the `'EGD'` heartbeat's country (the EGD federation code, most reliable since it comes from EGD) wins, then `invitation.country_code` (also EGD, frozen at invite time), then the `leaderboard.country` column, then any human survey's Cloudflare geo-IP `country`. **`leaderboard.country` is the UNIVERSAL fallback**: it's the request's edge geo-IP (`request.cf.country`) stamped into the row's ALREADY-happening `/report` UPDATE/INSERT (`updateLeaderboardOnReport`/`createLeaderboardRow` in `leaderboard.js`) — so it costs **no extra read or write** (the SELECT reads `l.country` off the same row; the write folds `country = COALESCE(?, country)` into the existing statement, `COALESCE` so an unknown geo never clobbers a known-good code, a real code wins last-writer-wins so the flag follows travel), and it gives a flag to EVERY active player (nearly all anonymous rows), not just the registered/surveyed few. The stamp is filtered through `normalizeCountry` (real ISO-alpha-2 only; the Cloudflare sentinels `XX`/`T1` → null, which would else render as a broken flag). When even that resolves nothing (or a hidden profile), the page shows the `UNKNOWN_FLAG` = 🇺🇳 constant (`leaderboard-page.js`) so no row is ever flagless. The EGD/survey survey-`country` still rides the same `MAX(id)` bare-column select as `rank`. The column is additive (`pwa/migrations/2026-07-20_leaderboard_country.sql`, `ALTER TABLE leaderboard ADD COLUMN country`; existing rows backfill on their owner's next report). **Hide opt-out:** a `hidden_profiles` row (presence = hidden; keyed by `user_id`, its OWN table because even a never-registered user can have declared ranks in `rank_surveys` worth hiding) makes `readLeaderboardRows` withhold that user's name, country, and verified ratings — they render as an **anonymous row carrying only their onlymove estimate** (a hidden-and-unranked row is dropped, matching how a never-registered unranked player is already omitted); the onlymove rank itself is never hidden. Toggled from the bottom of the page — the inline control reads `userId` from localStorage (same-origin with the SPA), calling `POST /profile/hide {userId, hidden}` (set/clear) and `GET /profile/hide?userId=` (read state, `no-store`), both in `src/handlers/profile.js` (`RL_WRITE`-limited, `isValidUserId` + boolean format-validated). The table is in `schema.sql` **and** `pwa/migrations/2026-07-19_leaderboard_all_users.sql` (applied to the live D1). **The row stores the rank in the window estimator's OWN frame — `pred_rank` (the UNTIMED internal onlymove rank), `pred_rank_se` (its SE in stones) and `time_delta_rating` (the personal time dock in rating units) — replacing the EGF-frame `pred_egf_rank`/`pred_egf_se` on 2026-07-27** (`pwa/migrations/2026-07-27_leaderboard_internal_rank.sql`, applied to the live D1 — a table REBUILD that adds the new columns and drops the old ones in one step, so production keeps `schema.sql`'s exact column order (verified: the live `leaderboard` column order matches `schema.sql` exactly); such a switchover is run CHAINED — migrate remote D1 → `npm run deploy` → `fetch_database` → `update_leaderboard_ranks.mjs --remote`. Between the migration and the deploy the old Worker briefly writes columns that no longer exist; every path degrades softly — `/report`'s leaderboard write is a caught `waitUntil` so the attempt still lands in `tsumego_reports` and only misses its incremental buffer push, which the final `update_leaderboard_ranks.mjs` repairs by rebuilding buffers from `tsumego_reports`; the page and the stats aggregation are try/caught). **The `buffer` column is maintained INCREMENTALLY and is never rebuilt from `tsumego_reports` on the hot path**: `updateLeaderboardOnReport` reads the stored buffer, pushes the one new attempt, writes it back (and `updateLeaderboardOnBackfill` does the same for an outbox batch). **Buffer order is INSERT order (the AUTOINCREMENT `id`), and that is the ONE convention every writer and every rebuild shares** — the two incremental pushes, `buildRowStateFromReports` (`ORDER BY id DESC`, used by `createLeaderboardRow` and the weekly cron `reconcileBuffers`), and `auxiliary/update_leaderboard_ranks.mjs`. A backfilled row carries a historical `created_at` but a fresh id, so under this convention it IS the newest and prepending is correct. Event order would need a `(user_id, created_at)` index that was deliberately dropped, turning a bounded `BUFFER_CAP` read into a full per-user history scan — 3× the rows read across the leaderboard, 34× for the heaviest user, on a path that runs inside `/report`'s `waitUntil`. So anything that overwrites a row's buffer with a stale snapshot drops whatever landed in between **permanently** — later reports append on top of the shortened list rather than restoring it, and the only rebuild path is `createLeaderboardRow`, which runs only for a user with NO row at all. That is the hazard in `auxiliary/update_leaderboard_ranks.mjs`, the retroactive refresh that moves every row's rank onto a new scale after a re-rate (it recomputes `buffer`/`pred_rank`/`pred_rank_se`/`time_delta_rating` only — `country` and `last_active` are untouched, and the `--populate` pass is `INSERT OR IGNORE` so it cannot clobber an existing row). **Run it under the MAINTENANCE FREEZE** (`MAINTENANCE_MODE = "1"` — see the write-guard note below): every attempt reported in the gap between its snapshot and its write is silently truncated out of that user's buffer, with no error and no recovery, and with every POST 503ing nothing can land in that gap, so the race is not merely unlikely but IMPOSSIBLE. That is why the leaderboard refresh belongs INSIDE the surgery window rather than after the lift (`docs/db_surgery_runbook.md` step 8), and it applies to a standalone post-re-rate refresh too — freeze, refresh, unfreeze. Chaining the fetch into the apply (`python3 -m pipeline.fetch_database && node auxiliary/update_leaderboard_ranks.mjs --remote`) only NARROWS the window; it is a fallback, never the guarantee, and `+0 new tsumego_reports rows` on that fetch is evidence the window happened to be clean, not that it was closed. **`--remote` ENFORCES the freeze rather than trusting the operator** (`preflightRemote`): it probes `POST /sync` on the live origin (from wrangler.toml's `custom_domain`) and refuses unless it gets `503 {error:'maintenance'}` — the DEPLOYED Worker is the authority, not the local `wrangler.toml` value — and refuses unless the local mirror's `MAX(id)` on `tsumego_reports` EQUALS production's, so a snapshot taken before the freeze can't be used. It re-checks both after the apply, turning "the window was closed when we started" into "it stayed closed throughout"; a lapse is reported with the remedy (re-freeze, re-fetch, re-run — the rebuild is idempotent) instead of corrupting rows silently. The preflight runs BEFORE the per-user recompute so a missing freeze costs seconds, and it fails CLOSED (any error reaching production is a refusal). `--allow-unfrozen` overrides deliberately. Note `MAX(id)` catches INSERTS, which is the documented hazard; a purge changes existing rows without moving it, so after surgery use the runbook's COUNT/SUM check. Its ordering rule is separate and also load-bearing: `package_for_pwa` → `npm run deploy` → fetch → update, since running it before the deploy lets the next `/report` recompute on the OLD scale and overwrite the work. (`GET /tournament` is now a **STATIC final-results page** for the concluded 2026 tournament — `src/handlers/tournament-page.js` bakes the standings in as a `PARTICIPANTS` const (a verbatim snapshot of the production leaderboard's last-week-peak on 2026-07-20) and does NO D1 read; it no longer shares `readLeaderboardRows`, so the leaderboard's frame changes above don't touch it.)

## Server-wide Community stats

**Server-wide "Community" stats are a cached, read-cost-sensitive D1 aggregation.** `GET /server-stats` serves a single `server_stats` row (`key='latest'`, JSON blob) aggregating the **preceding 7 days** of `tsumego_reports`. `computeServerStats` (`pwa/src/server-stats.js`) runs **one** window query (`WHERE created_at >= ?`) and does all bucketing in JS — totals, daily activity, by-size split, solving/review time histograms (10s buckets capped at 600s, but **bucketing each user's *median* time, so the histogram counts users, not attempts** — heavy users don't dominate; for review time, which is **cumulative across a problem's repeats** (each repeat re-reports the running total), only the last instance per (user, problem) is kept before taking the median, else the running total double-counts), a **recall-time** distribution (per user, the *median* over problems of the novel→first-repeat gap — from the first in-window non-repeat attempt to the very next attempt on that problem, **≥6h** (shorter gaps are ignored entirely), into hardcoded `6h–1d / 1–2d / 2–3d / 3–4d / 4–5d / 5d+` day bins; only gaps whose novel attempt *failed* count, because the spaced-repetition interval lengthens with each success and isn't comparable), and a per-user attempts-per-active-day distribution (`attemptsPerUserDist`). The **rank histogram and the country distribution do NOT come from that scan** — `computeLeaderboardStats` builds both from ONE scan of the `leaderboard` table via `readActivePlayers` (`src/leaderboard.js`), which is pruned to roughly weekly-active size, so it's the same small full scan the `/leaderboard` page already runs (NOT another pass over `tsumego_reports`). Rank = each active player's **untimed onlymove rank** — `resolveRowRank` (the stored `pred_rank`, else recomputed from the row's buffer), read verbatim with no coupling to invert and no dock to undo, i.e. the SAME window MLE, over the same materialized buffer, that the front page and `readLeaderboardRows` run — rounded, one player per bin, weakest→strongest; players below `RANK_START_MIN` carry no rank and drop out, **hidden profiles are counted** (hiding withholds a name/country, never the rank). Countries: `GROUP BY` in JS over the same rows' stamped edge geo-IP `country`, **hidden profiles excluded** (they opted their country out of the board), commonest-first. **This replaced an answer-derived serving proxy (2026-07-27)** — mean shard-band-midpoint rank of the user's last-7-days first-time attempts, gated at 10 distinct problems — which was biased in BOTH directions: serving was centered on `serveRank` = estimate + a non-negative UCB bonus (unconverged users read too strong, ~0.7 ranks at 15k and weaker, ~0.25 in the 15k-8k band), while the equal-count shard bands' midpoint substitution plus the one-sided nearest-loaded pool read dan players ~1 rank too weak, so it compressed the distribution toward the middle. The population also changed and by MORE than either bias (~2 ranks of mean shift on the production snapshot): it now counts *ranked players* active in the window, not everyone who answered ≥10 problems in it — beginners below the gate leave, established players having a light week enter. Don't reintroduce a serving-difficulty proxy; the buffer fit costs no extra D1 rows. **D1 bills rows read, so `created_at` MUST stay indexed (`idx_tsumego_reports_created`)** — without it every `created_at >= ?` is a full-table scan of all history that blows the daily read quota. Keep the one shared window scan **over `tsumego_reports`**; don't split THAT back into per-metric queries. Freshness: the blob is stamped with `APP_VERSION`; `handleServerStats` recomputes lazily on a version mismatch and returns `Cache-Control: no-store` (otherwise Cloudflare edge-caches the blob; the client also fetches `/server-stats?v=APP_VERSION`); the hourly `scheduled()` cron recomputes on version-mismatch OR ≥23h age. Rendered by `buildServerStatsPane` (`stats-community.js`) as the Community tab; the country distribution renders as a flag+code bar list — EVERY country, no top-N fold (the fold hid exactly the small communities the list is interesting for; `statsCountriesOther` was retired with it) — via the shared `flag()` (`pwa/shared/flag.js`, one definition for the Worker `/leaderboard` page and this client pane), with no "you" highlight since the client has no read of its own geo-IP country.
