# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

YoseTsumego / onlymove.net — a Go (Baduk/Weiqi) tsumego pipeline. KataGo generates problems and rates them; the rated set is packaged into zip archives served by a Cloudflare-hosted PWA. There are four cooperating subsystems:

1. **`pipeline/`** — ten executable scripts run in order (see "Pipeline commands" below). Each is a standalone `python -m pipeline.<step>` entrypoint. `package_for_pwa` is the single writer of `pwa/tsumegos/`; there are no side-channel patch scripts — to publish a labels-only or curve-only change without rebuilding zips, re-run `package_for_pwa` (its per-size change detection skips the heavy shard rebuild). Survey-driven rank calibration (`map_rating_to_rank.py`) and population-constant fitting (`fit_population_constants.py`) take no size arg and need no GPU, but **board-independent is not detachable — both sit INSIDE the sequence**: `map_rating_to_rank` reads `ratings/`, and `fit_population_constants` reads `ratings/` plus `rating_to_rank.json` (the time-adjust it passes through, and the knot range the rank prior's grid must cover), so each must follow the step that writes its input. `fit_population_constants` reads NOTHING from `axes/` — it fits no per-axis quantity.
2. **`utils/`** — shared logic, **split into two subpackages that import nothing from each other** (verified when the split was made, and worth keeping true): **`utils/katago/`** is the Go/KataGo side — `controller` (`KatagoController`: subprocess + thread-safe query dispatcher), `queries` (`KatagoQueries`, the analysis-engine wrapper), `problem_finder` (`ProblemFinder`, move-difficulty heuristics), `add_variations` (SGF tree construction, including `construct_initial_sgf`), `coords`, `models` (KataGo network downloads), `board_render`, `torch_model` (bootstraps `vendor/`, the vendored PyTorch KataGo — it puts that directory on `sys.path` so `import katago.…` resolves there; that top-level `katago` package is the VENDOR's, distinct from this `utils.katago`, and they do not shadow each other). **`utils/rating/`** is the statistical side — `features` (the rating trunk's inputs), `mirt_net` (the trunk's layer stack, stated ONCE — `train_mirt` fits it, `write_mirt_per_cell` rebuilds it to project every cell, and a stack matching by shape while differing in its activation loads cleanly and projects through the wrong function), `ratings_io` (the `ratings/` artifacts + curve reader), `fit_rank_curves`, `rank_surveys`, `rank_curve_shape`, plus `residual_axes` and `slope_calibration`, which are the retired two-stage axes machinery and have NO production importer left — only `auxiliary/rating_dev/` reads them. `utils/constants.py` holds the few values both need — `ALL_BOARD_SIZES`, `KOMI`, `RULES`, `DEFAULT_MODEL`, the debug flag.
3. **`pwa/`** — vanilla-JS ESM PWA built with esbuild, deployed as a Cloudflare Worker. The Worker entrypoint `pwa/src/index.js` handles these HTTP routes — `POST /report` (per-attempt logging; `createdAt` is REQUIRED in the payload — the CLIENT owns the event time (it mints one ms per attempt, stores it as the entry's `date`, and the row is inserted VERBATIM, so row.created_at === entry.date exactly and sync matching is exact) — and the server only sanity-bounds it, REFUSING (never rewriting) with `400 {error, serverNow}` on missing/future(+2min)/stale(−7d) so the client can self-correct once and resend (a silent rewrite would recreate the dup-mint precondition); responds `{serverId, userSeq, digest}` (no createdAt echo) — `serverId` the row id stamped on the matching answerHistory entry (its presence = acked; the id-cursor + digest key) so sync pulls skip the device's own rows; `userSeq` the per-profile attempt count, the **digest sync signal** (a jump past the device's expected seq = another device wrote → pull); see the account-sync note below), `POST /sync` (account sync: pages the user's reports newer than the client's **`sinceId` AUTOINCREMENT-id cursor** — gap-free for rows inserted with a historical `created_at` such as an offline flush — at 1000 rows; every response also carries a `serverSeq`/`serverDigest`/`serverMaxId` digest summary for the cheap in-sync check; an optional `limit` shrinks the page — `limit: 1` is the client's frontier/existence probe. A request without a valid `sinceId` gets an empty no-op so it just resyncs on reload — see the account-sync note below), `GET /push/vapid-public-key`, `POST /push/subscribe`, `POST /push/unsubscribe`, `POST /schedule` (recall-reminder schedule; **diff mode** — the client keeps a per-row hour-rounded snapshot in localStorage and sends only changed rows + explicit removals, since each upsert bills the row plus its two partial indexes and replace-all is the heaviest D1 write path; legacy `{schedule}` replace-all still accepted; every call, even an empty diff, bumps `push_subscriptions.last_seen_at`, the cron's mid-session suppression watermark), `POST /rank-survey` (per-server rank declarations → `rank_surveys`), `POST /share-event` (share-link create/open analytics → `share_events`; the client sends user/problem/size and, for opens, `document.referrer`, while the worker stamps the Cloudflare edge geo-IP `country`), `POST /link` + `POST /unlink` (bind/release this account's self-selected EGD or AGA player — see the leaderboard note below), `POST /google/signin` + `POST /google/link` + `POST /google/unlink` (Google sign-in — see the Google note below; `signin` only RESOLVES which code a verified Google account is bound to and writes nothing, so the CLIENT can ask before either logging in or linking), `GET /profile` (that binding, the `hidden_profiles` flag, and a `google` boolean, `no-store`, the Account dialog's whole panel in one read), `GET /server-stats` (serves the cached community-stats blob — see the server-stats note below) — plus a cron-driven `scheduled()` handler that walks `recall_schedule` to deliver due Web Push notifications **and** recomputes `server_stats` (≥23h old or on a version change), and an SPA fallback that derives board size from `/9` or `/13`. Static assets ship via the `[assets]` binding in `wrangler.toml`. D1 binding `DB` → database `tsumego-reports`, tables: `tsumego_reports` (per-attempt log: `user_id, problem, success, created_at, size, move, time_used, review_time, is_repeat`, plus the per-profile sync-digest columns `user_seq` (attempt count) + `running_sum` (Σ rowHash(id) exclusive prefix), lazy-seeded in the INSERT — see the account-sync note; no `UNIQUE(user_id, problem)` constraint, so repeat attempts produce their own rows; **indexed on `created_at`** — `idx_tsumego_reports_created` — for the server-stats window scan, **and on `(user_id, id)`** — `idx_tsumego_reports_user_id` — for the per-user id-cursor `/sync` scan + the digest's O(1) latest-row lookup (when retiring an index, drop it — on the live D1 too — only AFTER the deploy that stops reading it)), `push_subscriptions` (one row per device — `endpoint` PK, `user_id` indexed — so the recall cron fans each due reminder out to all of a user's devices; per-device throttle + dead-endpoint cleanup, per-account active-session suppression), `recall_schedule`, `rank_surveys`, `share_events`, `external_ids` (the leaderboard identity binding — one row per LINKED account, holding the `egd_pin`/`aga_id` plus the `display_name`/`country_code` snapshotted at link time; the per-column UNIQUE indexes are what make a claim exclusive), `hidden_profiles` (presence = leaderboard opt-out), `google_accounts` (Google sign-in — `google_sub` PK → `user_id` UNIQUE, which is the exclusivity in both directions; the opaque subject id ONLY, no address), and `server_stats` (single-row JSON cache, `key='latest'`). Schema lives in `pwa/schema.sql` (idempotent `CREATE … IF NOT EXISTS`); apply new tables/indexes to the remote D1 with `npx wrangler d1 execute tsumego-reports --remote --file=schema.sql`.
4. **`analysis_server/`** — a tiny HTTP server wrapping KataGo for the PWA's analysis fallback when SGFs lack embedded win-rate data. `server.py` runs on the cloud box (stdlib + sgfmill only — it is deployed with no repo beside it); `worker.py` runs on a fast machine and takes that box's work over while it is up (see the worker note below).

Plus `auxiliary/` (one-off diagnostics, legacy code; not part of the main flow) and `vast_orchestration.py` (rents Vast.ai GPU instances to run the heavy pipeline steps remotely).

## Pipeline commands

Always invoke pipeline modules through the venv's Python so PYTHONPATH resolves correctly:

```bash
./.venv/bin/python3 -m pipeline.fetch_database        # INCREMENTAL by default: pull only new tsumego_reports rows (by AUTOINCREMENT id) + re-fetch the small tables whole, merge into db/d1.{sqlite,sql}, sync local D1. --full forces a complete re-download (auto-used when there's no local db/d1.sqlite baseline)
./.venv/bin/python3 -m pipeline.tune_engine <size>    # tune nnMaxBatchSize / numAnalysisThreads in bots/analysis.cfg (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.generate_tsumegos <size>  # long-running generator → tsumegos/<size>/ (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.benchmark_bots <size> # bots solve generated tsumegos → attempts/<size>/ (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.extract_activations   # KataGo trunk activations per problem → activations/<size>/<id>.npz (GPU; resumable); feeds both the rating features (bw_act) and the axis fit
./.venv/bin/python3 -m pipeline.extract_ownership_swing  # per problem, how many stones' worth of ownership the correct first move swings against the best RESOLVED refutation → activations/_signal_cache/ownership_swing.csv (GPU via the KataGo analysis binary; RESUMABLE by the tid column, appended and fsynced every FLUSH_EVERY rows). MANDATORY, not diagnostic: it is a feature block `utils.rating.features` reads, and `joint_feature_tail` RAISES on a live tsumego with no row, so a corpus top-up that skips this step aborts train_mirt one step later and points at the wrong place. An unreadable SGF likewise ABORTS rather than being logged and skipped, for the same reason. Iterates ALL_BOARD_SIZES and takes no args — production-lean, no argparse, no alternate evaluator. Two of the five shipped motif rules (`life and death`, `territory`) read this file too, and `build_motif_proxies` SILENTLY SKIPS a problem with no row, so a gap here quietly shrinks the taught set as well
./.venv/bin/python3 -m pipeline.cache_rating_features  # build BOTH aggregate caches the rating trainer reads — run before train_mirt. (a) the candidate-move-eval cache `activations/_signal_cache/move_evals_<size>.npz`, holding BOTH the root `feats` array (20 cols) that the move block reads AND the `cont` array (75 cols) that the continuation block reads — one SGF parse fills both, and a row counts as cached only when both are present, so they cannot drift apart (a cache predating `cont` re-extracts whole), and (b) the correct-cell activation vectors `activations/_signal_cache/correct_vecs_<size>.npy` + `correct_ids_<size>.json` (read by utils.rating.features.load_joint_activations), built by `utils.rating.features.build_correct_vec_cache` which this step calls FIRST — correct_ids is both the rated set and this step's own tid set, so one command keeps them in lockstep. Both are INCREMENTAL and RECONCILE IN BOTH DIRECTIONS — new tids are added (so a tsumego TOP-UP is picked up automatically; a stale correct_ids would silently drop the new problems from the rated set) and departed tids are PRUNED (so a corpus purge leaves no orphan rows). "Up to date" means the cached tid set EQUALS the target set, never just "nothing new to add". `--force` re-extracts the move features only; `--rebuild-activation-cache` additionally re-reads every activation .npz (hours — for a corrupt cache, not routine). **The .npz set must be a SUBSET of `tsumegos/<size>/`, asserted before any work** (`_assert_activations_subset_of_corpus`) — ONE-DIRECTIONAL: corpus ⊋ activations is normal (extraction is resumable, so a fresh top-up has SGFs with no .npz yet), but an .npz with no SGF is a hard failure, because `correct_ids` is derived from that listing and an orphan silently promotes a problem that NO LONGER EXISTS into the rated set — it gets features, a rating, a slope and a floor, ships nowhere (packaging works off `tsumegos/`), and nothing downstream can tell it from a real one. **Any unreadable input is likewise an ABORT, never a dropped row**: a corrupt .npz raises out of the worker, and a non-finite row inherited from an older cache is refused at write time (the tmp is removed, the existing cache left intact). The rejected alternative is a NaN row, which is invisible — the tid stays in correct_ids while `_fit_joint_pca`'s finite mask removes it from the fit, so the problem leaves the rated set with nothing anywhere recording it. (The per-problem npz artifacts — activations, per_cell embeddings — are inherently incremental via file existence; only these two roll-up caches needed explicit incremental support.)
./.venv/bin/python3 -m pipeline.build_motif_proxies   # label every problem against the motif PROXY RULES → axes/motif_proxies.npz (one bool column per rule, plus the `rules` array so a reader never assumes column order). These are the directions train_mirt teaches its axes onto. INCREMENTAL BY TID and reconciling in BOTH directions — new problems labelled, departed ones pruned, "up to date" meaning the stored tid set EQUALS the corpus. Every rule is a threshold on the problem's OWN numbers, which is what makes that sound: a stored row can never be made wrong by a problem added later (`opening` is an absolute prefix length per board for exactly this reason — as a corpus PERCENTILE it moved as the corpus grew, silently re-labelling problems that had not changed). **A rule or threshold change is invisible to the tid key, so it needs `--force`.** The rules live in `utils/rating/motif_rules.py`, which is ALSO the single source for what each motif is CALLED
./.venv/bin/python3 -m pipeline.train_mirt         # SINGLE-STAGE rating + skill axes in ONE fit (compensatory M4PL). PRODUCTION-ONLY: no argparse, config baked as module constants, always seed 0 → ratings/ AND axes/{per_problem.csv,axes.npz}. Needs pipeline.extract_activations + pipeline.cache_rating_features first, AND the motif proxies `axes/motif_proxies.npz` + `axes/labels.json` — the rule columns it teaches its axes onto, paired onto axes by `labels.json`'s `components` (`"A/B"` = rule A at the positive tail, rule B at the negative), without which it ABORTS; it derives no directions of its own (see the proxy note below). It prints a per-axis identity report at the end — hinged tail agreement for both ends, over attempted problems — which says how well the fit EXPRESSES each rule; **read the TAIL count, not the correlation** (see the identity note below). Note what that report does NOT mean here: against a rule a low figure says the model cannot represent the criterion, not that a motif drifted, because the criterion is still sitting in motif_rules.py to be re-read. It does NOT write axes/per_cell/ (that is pipeline.write_mirt_per_cell, the next step) and does not write labels.json (hand-maintained). It RETIRES any existing axes/per_cell/ by renaming it, because per_problem.csv from this fit beside per_cell/ from the previous one ships a shard whose two embedding sources disagree and no client check can catch that. The experiment surface is auxiliary.rating_dev.train_joint_mirt
./.venv/bin/python3 -m pipeline.write_mirt_per_cell  # axes/per_cell/<size>/<tid>.npz — a K-vector for EVERY legal cell, which the client needs because it scores the move the user PICKED, not only the answer. RESUMABLE by file existence. The two-stage map was linear on features so a cell folded into one matmul; this map reads the trunk, so a cell needs the full PCA projection plus a trunk pass. That is ~128x the arithmetic and irrelevant — 16 TFLOP measures ~13s, and the pass is bound by reading ~125 GB of activation npz, so read parallelism is the whole optimization
./.venv/bin/python3 -m pipeline.map_rating_to_rank      # rank_surveys + db/d1.sqlite (timed attempts for the career-block anchors + median solve time) → ratings/{rating_to_rank.json (curve + a top-level time_adjust{alpha,center}), rank_map.json (per-server couplings INCL EGF)}. CONSENSUS model (rating→consensus rank→every server incl EGF; time α fit jointly); anchors are overlapping 2-month CAREER-BLOCK ratings, attempt-mass-weighted, each declaration normalized to total weight 1 (see the `M` note below). BACKEND; package_for_pwa publishes it. Production-clean (no experiment flags; the CV harness that validated the anchors is auxiliary/eval_rank_map_cv.py)
./.venv/bin/python3 -m pipeline.fit_population_constants  # ratings/ 3PL params + attempts DB → ratings/population_constants.json (retention/time-bias constants (incl. `first_success_step`, the POST-LAPSE term — see the recall note; MOMENT-MATCHED from the within-user rung-0-vs-rung-1+ odds ratio, never likelihood-fitted) AND the rank_prior; the time-adjust {alpha,center} is READ THROUGH from rating_to_rank.json, NOT fit here; BACKEND; package_for_pwa publishes it; the PWA build inlines it into the JS bundle. It fits NO weakness constants — the motif readings are computed client-side from the user's own attempts against their own neutral point, so there is no population centre to fit, ship or validate (see the motif-stats note below))
./.venv/bin/python3 -m pipeline.package_for_pwa       # SINGLE writer of pwa/tsumegos/: zip + lookup.txt + embedding_meta.json + copies the rating→rank curve across; change-detects per size (skips unchanged shard rebuilds; --force to override). Reads ratings/.
```

Run on a remote Vast.ai GPU instead: `python vast_orchestration.py` (no args prints subcommands; only `tune`, `generate`, `benchmark` are remoted — the rest stay local).

**Several of these steps run for HOURS, none of them checkpoint, and a naively launched run WILL be killed part-way — losing all of it.** `pipeline.train_mirt` is **up to a couple of hours** — a FIXED budget of `EPOCHS` = 3000, so the length is known before it starts and nothing is selected along the way. The stop split is measured and printed every `CHECK_EVERY` = 10 epochs as the RECORD of where the fit got to, and is not a stopping rule: it goes flat well before the end and then wanders inside a band a thousandth wide, so an epoch chosen on it is chosen out of that noise and the choice moves by thousands of epochs between runs that are otherwise identical. The final epoch is what ships. **Do not read a long run as a hung one**: the split improves in BURSTS separated by flat stretches of a couple of hundred epochs, and the train/stop gap widens throughout. The per-step cost is dominated by the shallow-slope barrier, which is why it reads `SHALLOW_SAMPLES` = 20000 corpus rows rather than all ~181k: an unbiased sample of the same mean, and 2.4x faster per step than reading the whole corpus, which costs two thirds of a step's trunk work for no extra coverage. `pipeline.write_mirt_per_cell` is ~15 minutes and RESUMES by file existence, so an interruption there costs only the batch in flight. `generate_tsumegos`, `benchmark_bots` and `extract_activations` are hours as well. Three ways such a run dies quietly, and what to do instead:

- **A shell that backgrounds with `&` and then exits takes the child down with it** (SIGTERM, exit 143) — including a wrapper that backgrounds the real work and then returns. Launch detached: `setsid nohup ./.venv/bin/python3 -u -m pipeline.<step> > /tmp/<step>.log 2>&1 < /dev/null &`.
- **`timeout N` kills at N with exit 124 and no partial result.** Don't wrap a step in a timeout unless you are certain it exceeds the real runtime; a too-short guess is indistinguishable from a crash after the fact.
- **Piping through `tail`/`head` buffers everything until exit**, so a healthy long run looks hung and a dead one looks alive. Run python with `-u`, redirect to a file, and poll the file.

**The steps that write `ratings/`, `activations/`, `pwa/tsumegos/` and `axes/` overwrite IN PLACE — do NOT copy them aside before a refit.** They are derived artifacts: the inputs (corpus, attempts DB, committed code) are what's kept, and a fit that comes out wrong is reverted by re-running the step, not by restoring a snapshot. Copying them aside costs GB and creates a second thing to keep straight, so back one up only when the user asks. The exception worth knowing is that TWO files under `axes/` are TRACKED — `labels.json` (`components`, the ordered rule pairs this fit ships, plus the dev motif store's names and provenance per id) and `label_anchors.npz` (that store's directions, keyed by an `ax_<hex>` content hash of the direction itself) — while the rest of that directory and all of the others are gitignored. Neither can be regenerated by re-running anything, which is what makes them the exception. `motif_proxies.npz` is NOT tracked despite being a train_mirt INPUT: it is a pure function of the rules and the corpus, so the committed rule in `utils/rating/motif_rules.py` is the durable artifact and the npz is a cache of it — and it is corpus-shaped, so a direction in it cannot be content-hashed the way a stored one is. `axes.npz` is NOT tracked: it is written by every `train_mirt` run and carries the `embedding_version` packaging stamps, so a committed copy is a stale version waiting to be shipped onto a different fit's embeddings.

```bash
cd pwa

```

Local testing must go through `npm run dev`: the Worker runs `/report` and the SPA fallback (URL-based size hints), so opening the static bundle alone will misbehave. Deployment is **manual** — there is no git-triggered auto-deploy.

**Two live routes return 404 ON PURPOSE, and probing them by hand reads as an outage — use `npm run status` rather than a bare `curl`.** (a) `/`, `/9` and `/13` have no file behind them: the Worker's SPA fallback rewrites them to index.html **only for a navigation-shaped request** (`sec-fetch-dest: document`, or an `Accept` naming text/html), because an asset-style miss has to keep 404ing so a stale service worker re-fetches instead of receiving HTML where JS is expected. `curl` defaults to `Accept: */*` and therefore gets the 404. (b) The five `INLINED_DATA_FILES` (`build.mjs`) are compiled into the bundle, so `/tsumegos/{rating_to_rank,rank_map,population_constants,se_floor,embedding_meta}.json` 404 — and a 200 there is the real regression, since it would let a client fetch a curve under a fixed name with no `?v=DATA_VERSION` and pin itself to a stale one. `check_live_status.mjs` asserts both directions, plus the freeze state (`--expect-frozen` / `--expect-unfrozen` for the runbook's two flips). **It retries**, because a deploy propagates over seconds and the previous version answers until it does — an unfreeze that still reports `maintenance` on the first probe is usually propagation, not a failed unfreeze.

## Single-stage rating + axes (`pipeline.train_mirt`)

**One model produces the rating and the K skill axes together**, a compensatory M4PL where the axes are factors 2…K+1 and the rating is factor 1:

`P = c_p + (1 − c_p − λ)·σ( a_p·(θ_u − b_p) + Σ_k g_k(x_p)·v_u[k] )`

**ONE TRUNK feeds every head, axes included.** A `Linear`'s output rows are independent, so this is exactly a shared head emitting `(b, a, c, g_1..g_K)`. The axis path is COUPLED — the axis objective reaches the trunk, so the trunk learns what the AXES need and not only what the rating needs. Detaching measures the same but is feature reuse rather than a joint fit, which is the two-stage split again one layer down.

**READ THE COMBINED COLUMN, PAIRED — `axis adds` RISES WITH K WHETHER OR NOT THE MODEL PREDICTS BETTER**, because more axes mechanically absorb more residual. Measured on nested rule banks (K=4 ⊂ K=6 ⊂ K=8, four draws each): axis adds says −0.23 / +0.58 / +1.00 and recommends K=8, while the combined logloss flattens — K=6 beats K=4 by +1.90 ± 1.43 mnat on ALL FOUR draws, and K=8 beats K=6 by only +0.45 ± 0.44 on three of four. Arm-vs-arm at the SAME draw is paired and cancels the draw noise that swamps any single level, which is why a comparison pins the draw and a magnitude does not. Detail: `docs/mirt_benchmark.md`.

**AXIS VALUE IS A PROPERTY OF THE HOLDOUT DRAW — NEVER QUOTE A SINGLE-DRAW AXIS-ADDS FIGURE AS THE EFFECT.** Measured over FOUR independent draws (training seed and holdout seed moving together, K=6): axis adds +3.59 / +2.81 / **−1.40** / **−1.44** mnat, mean **+0.89 ± 2.69** — indistinguishable from zero, with TWO OF FOUR NEGATIVE. Never-trained is worse, +5.18 ± 7.83. Pinning the holdout seed is what hides this: every arm then scores the SAME users, so the spread measures initialisation and batch order only, and the seed count reads as replication it is not delivering. **The protocol depends on the question and the two are opposite** — comparing ARMS wants the draw PINNED (paired, same rows, so the difference is the arm), estimating a MAGNITUDE wants it MOVING. A figure produced under the first must not be quoted as though it came from the second. **Identifiability is stable where prediction is not**: across those same four draws, split-half N50 (attempts to reliability 0.5) reproduces tightly — counting 398 [309, 493], ko 580 [363, 831], life and death 871 [786, 982], against ability's 13 [10, 15]. So a user's axis position is measurable at a consistent cost in attempts while whether it improves a held-out prediction depends on who is held out; do not read either as evidence for the other. Detail and provenance: `docs/mirt_benchmark.md`.

**The axes pay only for long-history users.** Binned by how many attempts precede the one being scored, the axis contribution is ~0 below 100 attempts and +4.95 mnat above 500 on ONE draw (see the draw-dependence note above — the SHAPE is the finding, the level is one sample) — so the headline figure is an average over a population most of whom get nothing. **500 IS A BIN EDGE, NOT A THRESHOLD — the 100-500 band carried no observations and is very likely POSITIVE.** Per-axis reliability, which does have data there, is already 0.50/0.40/0.87 at 250-499 against 0.28/0.18/0.71 at 100-249, so a user's axis position is substantially identified well before 500 and the payoff plausibly starts there too. Never quote 500 as the point where the axes begin to work. In probability terms a user past 500 attempts gets their predicted chance of success moved 0.87 percentage points closer to the outcome, and 0.32 points more predictions on the correct side of 50%. `auxiliary/rating_dev/axis_by_history.py` measures it.

**`ORTHO_RATING` = 0.5 keeps the axes off the SHIPPED TRIPLE — rating, slope and floor — and nothing else in the objective does; there is no axis-axis decorrelation term, the taught columns being near-independent already.** Centring `v` (`user_axis`) removes only its population mean, which blocks an axis acting as a global difficulty shift but not one tracking a rating parameter per problem — and it is EXACT rather than priced, so there is no weight to tune and no arm in which an axis buys a population shift by paying for it. Left free a fit SPENDS AN AXIS on one and that axis is unnameable when it does: the free control's third axis sits at −0.64 with SLOPE, scores worst on rating of any arm, and is worst on never-trained problems. The penalty is a sum of squared cosines against the three DETACHED heads, each centred and normalised (floor lives on (0, 1−2λ) and rating on its own scale, so an unnormalised term would be whichever is widest), and detachment means it can only push the axes off the rating side, never degrade the rating to satisfy itself — the direction that matters, since the client's rank path reads rating, slope and floor and never an axis.

**IT IS SCORED PER TAIL, NOT PER AXIS, and that is not a refinement.** A whole-axis correlation is a LINEAR statistic and cannot see a symmetric dependence: an axis whose two tails are both rating-laden in OPPOSITE directions averages to zero and satisfies the penalty completely, while both named tails — the only part the client reads — are laden. Measured, that is what was happening: a free fit whose whole-axis correlations sat at 0.02–0.09, and which was recorded as rating-orthogonal on that basis, carried tail correlations of 0.27/0.29/0.31. Penalising `tail_weight(+g)` and `tail_weight(−g)` separately cuts the worst tail from 0.291 to 0.105. The whole-axis figure rises slightly under this (0.016 → 0.084 on one axis) and that is expected — it is no longer the statistic being optimised and was never the one that mattered. The weight is the same `tail_weight` the measurement uses, so the objective and the report are the same shape; **its exponent must be CLAMPED in torch**, because `torch.where` evaluates both branches and a large positive z overflows the discarded one to inf, which the backward pass turns into NaN and which surfaces as BCE's `[0,1]` assert a step later.

**Penalising DIFFICULTY ALONE only displaces the leak** — measured, closing `b` sent one axis from −0.04 to −0.43 on the floor head and left another at +0.62 with slope, because each axis simply finds a different rating parameter to absorb. Closing all three removes it (every correlation under 0.13, slope and floor under 0.04) and on a free fit is 6.4 mnat BETTER on rating than b-only, with the axes still worth 3.7 mnat.

**A RATING-CORRELATED BANK CAN FIGHT THE PENALTY, but how much that costs is NOT settled — do not treat orthogonality as a prerequisite.** Teaching directions that are themselves rating-correlated while pushing the axes off every rating channel is over-determined in principle, and one arm did lose to that conflict: a ONE-SIDED bank whose columns reached 0.357 correlation left the axes worth 0.16 mnat against 4.41. But a BIPOLAR bank at 0.274 under the same penalty reached 4.21 mnat with leakage eliminated and its six poles retained BETTER on average than under the weaker penalty (mean 0.661 against 0.542), which is the opposite outcome. So the penalty tolerates an imperfect bank at least that far, and the two arms differ in three ways at once — correlation level, one-sided against bipolar, and the bank construction — so which of them matters is unresolved. What is safe to say: a bank drawn from a fit under this same penalty carries no conflict at all, and the store's rating-orthogonal entries exist for that reason.

**Expect the rating-orthogonal axes to be UNFAMILIAR.** They are a different slice of the residual, not a cleaned-up version of the old one: measured, a free fit under the full penalty matches nothing in the store above 0.39, where the same fit under b-only found `ko` at 0.73. The motifs and the rating parameters are genuinely entangled — `ko`-ness is partly guessability, life-and-death is partly discrimination — so forbidding the correlation forbids those motifs and returns different ones. They still predict (3.7 mnat); they simply have to be named afresh.

**What it does not do.** It does not select K — K equals the number of `components` in `axes/labels.json`, one axis per taught rule, so the count follows the SHIPPING DECISION rather than a loss curve. That is not a fallback: over four PAIRED draws the combined logloss separates K=4/6/8 by less than the draw-to-draw spread and so cannot adjudicate the count, while split-half reliability separates the RULES several-fold and can (see the rule-tier note below). It writes no `labels.json`: a human names an axis by eyeballing its extremes, and an unnamed axis ships and works, it just stays silent on the client. The per-legal-cell vectors come from `pipeline.write_mirt_per_cell`, a separate pass. It renames any existing `per_cell/` aside rather than leaving it — mixing this fit's correct-move vectors with the previous fit's picked-move vectors ships a shard whose two embedding sources disagree, and both files are individually well-formed so nothing downstream can catch it.

**`slope_scale` is 1.0 and slopes ship as fitted — no post-hoc multiplier.** Swept on held-out users and split by whether training saw the problem, since a never-trained problem is priced from the feature prior alone and honestly wants a shallower slope, so pooling those rows drags the optimum down. Measured optimum is **0.90** on both `all` and the seen partition; 1.0 costs 0.2 mnat against it, inside the 0.85 mnat seed noise.

**Pricing unattempted content is measured, in the never-trained partition of the same walk** — 19% of held-out users' rows are on problems no training user ever attempted, so those are priced from features alone. Rating-only logloss there: 0.5186 / 0.5458 across the two folds. That partition is a SELECTION (problems nobody played) rather than a random draw of attempted problems, so it is not identical to a dedicated problem holdout, but it does test feature-only pricing directly.

## Architecture notes that span multiple files

**Tsumego identity is symmetry-aware and single-solution.** Filenames come from `get_orientation_invariant_hash` (`pipeline/generate_tsumegos.py:154`) — SHA-256 taken over all 8 D4 transforms of the board, with `min()` picking a canonical orientation. The dataset therefore cannot contain two problems that are rotations or reflections of each other; `tsumego_id` is the symmetry-canonical hash truncated to 8 hex chars. `auxiliary/check_corpus_ids.py` re-verifies the corpus against it, and `--emit-map` regenerates an id-remap (`surgery/id_map.json`) if a defect ever needs one. By generator design every problem has exactly one correct first move (the `solution` returned by `ProblemFinder.create_problem`); downstream code can rely on the "one canonical answer per problem" invariant. **That answer is also `variation_nodes[0]`, and generation ENFORCES it rather than assuming it** — `promote_winning_first_move` (`utils/katago/add_variations.py`) reorders the decision node's children so the move the SHIPPED evaluation comments name (highest winrate for the mover, score breaking exact ties — the client's `findBestMoveFromChildren` rule) leads. The two can disagree at generation time: the solution written first is what `ProblemFinder.is_valid` verified on a deeper re-read, while the candidates' comments come from later passes at their own playout budgets. Reorder, don't discard — such a position is still well-posed, and `first_move_is_well_formed` (the separate single-solution gate) passes it. **The invariant is load-bearing because the two consumer kinds read the solution differently**: the client picks by evaluation and is order-blind, while every backend stage takes it POSITIONALLY (`extract_activations`' `correct_idx`, `benchmark_bots`' grading), so a misordered file silently feeds a LOSING move's activations into the rating features and the shipped per-problem axis vector while still playing correctly in the app. `auxiliary/check_tsumego_sequences.py` re-verifies the corpus (`winner is NOT variation_nodes[0]` must be 0). Note the SGF variation order is NOT what the activation npz uses — that is board-scan order, addressed by `correct_idx` (see the extraction note below).

**Board size — two supported modes: 9x9 and 13x13.** Both ship in production; the PWA picks one from the URL path (`/9` or `/13`) via the SPA fallback in `pwa/src/index.js`, and the D1 `report` endpoint records `size` per attempt. **`/9` and `/13` are entry-only size HINTS, not persistent addresses.** They are read once at boot (`getBoardSizeFromPath` → `resolveInitialBoardSize` in `pwa/js/main.js`); the chosen size persists in state/localStorage thereafter, not in the URL. `cleanUrl()` (lives in `pwa/js/problem-loader.js`, called from `displayProblem`) **collapses the path to `/` and strips `?id`/`?o`/`?recall` whenever a NON-linked problem is painted**, so once you're on a normal problem the address bar is `/`. Do NOT assume a reload leaves the bar at `/9` or `/13`; it does not. **Linked (shared) problems are the deliberate exception: their `?id`/`?o` are KEPT in the address bar for the whole linked session** (`displayProblem` skips `cleanUrl` while `appMode === LINKED`), so that any reload — a service-worker update takeover (`index.html`'s `controllerchange` → `location.reload()`, the most common one; in-app browsers like Instagram hit it when a stale cached SW is replaced by a freshly-deployed version), the `?id`-404 / repeated-load-failure reloads in `problem-loader.js`, the version-mismatch `maybeReload`, or a manual refresh — **re-enters the SAME shared problem at boot** (`parseUrlIntent` reads `?id`) instead of dropping to the standing challenge. The URL is cleaned the instant the user moves on to a non-linked problem (`returnToChallenge`/`advanceToNextProblem` → `displayProblem`). On the **pipeline side** there is no single global `BOARD_SIZE` and no in-process dual-size run. The three single-size generation steps — `pipeline.tune_engine`, `pipeline.generate_tsumegos`, `pipeline.benchmark_bots` — take a **mandatory positional `size` arg** (`{9,13}`), which is threaded through the utils (`KatagoQueries(controller, board_size)` owns it as a public `board_size` attribute; `KatagoController.start_engine(model, board_size, …)`, `ProblemFinder` reads `queries.board_size`, and the leaf helpers `construct_initial_sgf(…, board_size)` / `get_child_move(…, board_size)` take it explicitly). The downstream steps (`extract_activations`, `train_mirt`, `write_mirt_per_cell`, `map_rating_to_rank`, `package_for_pwa`) instead iterate `ALL_BOARD_SIZES` and process both sizes in one run — they take no size arg. Artifact directories are keyed by size: `tsumegos/<size>/`, `attempts/<size>/`, `ratings/<size>/`, `pwa/tsumegos/<size>/`. To refresh both sizes, run each generation step once per size (e.g. `… generate_tsumegos 9` then `… generate_tsumegos 13`), then run the downstream steps once. On the remote, `vast_orchestration.py run <step> <size>` forwards the size verbatim (validated locally against `ALL_BOARD_SIZES`).

**On the client, rank + stats + the learned models are merged across sizes; histories, `M` curves, and problem pools stay per-size.** From the user's perspective 9x9 and 13x13 share one rank (front-page label, problem selection, recall eligibility) and one stats page. `pwa/js/state.js` keeps `answerHistory` as ONE unified cross-size array (date-ordered, each entry tagged with `size`; the recent working set in localStorage, the older tail in IndexedDB — see the answerHistory-storage-split note below) plus single shared values (`userRank`, `displayRank`, `serveRank`, the recall model `modelParams`). The motif readings are NOT among them — they carry no persisted state at all, being recomputed from the merged history on demand; the only per-size persisted bucket is `challengeProblem`. (A `mergeSharedAcrossSizes_v2` migration flattens any legacy per-size rank/model buckets: `userRank = max(rank_9, rank_13)` — a strong 9x9 player immediately gets hard 13x13 problems — and the model buckets are dropped so the shared models retrain.) `getMergedAnswerHistory()` returns that unified array (the WORKING SET), each entry tagged with `size`; the recall and weakness models train from it (they slice the recent window, so the working set suffices). The stats panel (`showDetailedStats`, in `pwa/js/stats-ui.js`) instead awaits `getMergedFullAnswerHistory()` so its charts span the whole career (working set + IndexedDB tail). Pooling is sound because every feature they read is board-independent — `problemRank` is the consensus internal rank (a normalized 0.5 means the same internal rank on either board), and the embedding axes are jointly fit across sizes. Play-time size-awareness is preserved: a recall problem can only be re-shown on its own board, so `getRecallCandidates` takes an explicit `history` (defaults to the active size; the merged union is passed only for stats counts) and `buildRecallSchedule(size)` reads the shared model + shared rank but that size's history. Two consumers do real work to pool: the recall logistic carries a `SIZE_IS_13` fixed effect (9x9 = baseline) whose coefficient ÷ logit-per-rank is the stats panel's "stronger/weaker on 13x13" readout; and the skill decomposition (`rank-decomposition.js`) pools in **internal-rank space** with a per-attempt slope `LOGIT_PER_RATING / |M'(rating)|` (each attempt mapped through its own size's curve), so both sizes share one skill curve without the rank-space slope bias.

**answerHistory storage is split: a unified working set in localStorage, the cold tail in IndexedDB.** `answerHistory` is ~99% of localStorage and on heavy users overflows the ~5MB quota, so `pwa/js/state.js` keeps the most-recent `ANSWER_HISTORY_WORKING_SET` (3000, `constants.js`) attempts — unified across both sizes — as a synchronous localStorage array; everything older is evicted to IndexedDB via `pwa/js/history-store.js` (`appendTail`/`getTail`/`updateTail`/`clearTail`, durable via `navigator.storage.persist()`, every method a safe no-op/empty if IDB is unavailable so play degrades to working-set-only, never breaks). 3000 is the largest hot window the app uses on the *merged* history (the recall-candidate replay warms over the last 3000), so the working set is a superset of every synchronous read: all the existing consumers read `state.answerHistory` (a cached active-size filtered view of the unified array) or `getMergedAnswerHistory()` (the working set) and already slice ≤3000 (`getRecallCandidates` −3000, the models −`MODEL_INPUT_HISTORY_LENGTH`). Only the full-career charts await `getMergedFullAnswerHistory()` (tail ⧺ working set, de-duped by `(problemId, date)`). The write path stays synchronous — `setAnswerHistoryForSize`/`updateAnswerHistory` route through one `reconcileSize` that replaces a size's entries in the unified array and persists; a debounced `evictColdTail()` then appends overflow to IDB **and confirms before trimming** the in-memory/localStorage working set (crash-safe seam: a kill mid-evict leaves a de-duped dup in both, never a gap; an IDB-unavailable append keeps the rows in the working set). `initHistoryStorage()` runs once at boot (the state-epoch gate at `state.js` import time has already settled the storage shape) — `main.js` awaits it before the embedding backfill writes, freeing localStorage on a quota-stressed device. The cold tail feeds ONLY the full-career chart (it is all older than `MODEL_INPUT_HISTORY_LENGTH`, carries no embeddings, and no model reads it). **"Carries no embeddings" is ENFORCED AT THE WRITE BOUNDARY, not assumed** — `history-store.js` drops the embedding block from every row it stores (`appendTail`, `replaceTail`), because the only pass that clears stale vectors is the refit wipe and that walks the WORKING SET alone: a vector evicted to IDB is beyond any refill, frozen at the `embedding_version` of the day it was evicted, and unreachable by every later gate. On top of that a refit sweeps the tail (`sweepTailEmbeddings`), which is redundant against the write boundary on purpose — it gives the invariant a repair rather than only an assertion, and it is deliberately NOT gated into the refit's `allOk`, since nothing reads those vectors and re-running a whole refit to reclaim dead bytes would be the expensive half paying for the cheap one. A **curve-only** refit recomputes the tail's `problemRank` from its stored raw rating (`backfill.js` via `updateTail`, no shard walk). A **ratings change** instead re-derives the tail's full rating fields from the shards — the SAME shard walk the working set uses, extended to the tail's problem ids — because the tail's ratings are frozen at eviction time, so after a re-rate they go stale AND device-dependent (each device evicted at a different rating era), and the chart plots them: two synced devices' Rank-tab graphs diverged at the start until this. A problem that left the corpus has its rating fields STRIPPED rather than left stale (the attempt stays, rating-less; `flattenAttempts` then drops it from every estimate — front-page rank, chart, weakness, recall all already skip rating-less/embedding-less rows). An account switch `clearTail()`s then re-splits the full pull. Two accepted tradeoffs, both kept synchronous on purpose: a re-draw of a problem last seen >3000 attempts ago is treated as new (repeat-detection scans the working set only), and `timeAdjustDeltaRating` uses the working-set median solve time.

**A faster machine can take the analysis server's work over, and what it buys is SEARCH — not speed.** `analysis_server/worker.py` (run it as `ONLYMOVE_WORKER_TOKEN=… ./.venv/bin/python3 -m analysis_server.worker`) Measured, the cloud box answers in about 200ms of compute and a GPU in about 45, but reaching that GPU costs a round trip that spends nearly the whole saving — so at equal visits the two are a wash and the feature would be pointless. What the box CANNOT do is search: one visit is the raw policy, and 30 visits there would take seconds. The worker therefore REPLACES the visit count on every query it takes (`WORKER_VISITS`, 30), costing roughly a second end to end against the box's third of one, and returns a genuinely read answer instead of an opinion. Three things follow and all three are load-bearing. `interpret_response` branches on WHAT CAME BACK — moveInfos when present, policy otherwise — never on the server's own `PLAYOUTS`, because the two backends deliberately search to different depths and reading the constant sends a searched reply down the policy path, discarding the search with no symptom. The reply carries `visits`, and the client shows its blinking-red unreliable marker only for a single-visit answer (`_searched` in `analysis.js`, tested in `ui.js`) — `_origin` stays `'api'` either way, since the move-selection waterfall keys on it. And `SEARCH_THREADS` is a LATENCY setting, unrelated to `POLL_THREADS`: visits are sequential within one query unless several threads explore at once. opens a few long polls against `api.onlymove.net` and runs whatever jobs come back down them; `server.py` prefers a parked poll and otherwise answers with its own KataGo exactly as it always has. The PWA is not involved at all — `pwa/js/analysis-api.js` posts to the same URL either way — so there is no client version to keep in step, and no inbound port, DNS record or certificate on the worker's side. **THE POOL'S CAPACITY IS THE NUMBER OF PARKED POLLS**: a job is only ever handed to a poll that is already waiting, so a busy or absent worker degrades to local service rather than queueing behind itself, and stopping the worker at any instant is safe. **An EMPTY `ONLYMOVE_WORKER_TOKEN` on the cloud box means the feature is off with no second switch** — the three `/worker` routes 404 and every request is served locally — so the server can be deployed before any worker exists; turning it on is setting that variable and restarting. Token auth is the only thing separating a worker from anyone on the internet, and its answers are shown to users as ours. Failure is bounded rather than absent: a worker that dies holding a poll is usually caught on the write and the job comes straight back, but a dropped network gives no such error, so ONE request pays `WORKER_JOB_TIMEOUT` before `WORKER_COOLDOWN` takes the worker out of the rotation. **Deploy with `analysis_server/deploy.sh`** (`--token` also installs the shared secret, `--no-restart` ships without one). It reaches `typo_hh@api.onlymove.net` over plain ssh and edits nothing under `/etc`: that account owns its working directory but is NOT in `google-sudoers`, so the script restarts by killing the main process and letting the unit's `Restart=always` bring it back, and installs the token as a 0600 file beside `server.py` rather than a unit `Environment=` line — which would need root AND be world-readable through `systemctl show`. It ships by `scp` (the box has no rsync) and verifies by md5 what actually landed. The box's own `analysis.cfg` is tracked at `analysis_server/analysis.cfg` and is NOT `bots/analysis.cfg`, which is the pipeline's and tuned for the opposite machine. **The board-size ceiling is stated TWICE and the two must move together** — `MAX_BOARD_SIZE` in `server.py` refuses anything larger with a 400 before any evaluation, and `maxBoardXSizeForNNBuffer` in that cfg sizes the NN buffer to the same bound, so an oversized board fails inside KataGo regardless.

**The trap is `requireMaxBoardSize = true` in `bots/analysis.cfg`, and it belongs to THIS REPO's config only** — the deployed `server.py` uses its own `analysis.cfg` on the box and passes no board-size override, so it has always served both sizes and is untouched by this. `maxBoardXSizeForNNBuffer` is a MAX; `requireMaxBoardSize` is what turns it into an exact requirement (KataGo names it `requireExactNNLen` at runtime, and the cfg's own comment says "EXCLUSIVELY for exactly the board size specified"). A query on any other size then kills KataGo's async bot thread with a message on stderr and NO response on stdout, so the caller waits out its full query timeout on a request that can never be answered. Anything reaching KataGo through `utils.katago.controller` inherits it, since `start_engine` always emits the override: the pipeline never notices because each of its runs is single-size, but a server takes both, so `worker.py` passes `requireMaxBoardSize=false` and runs one engine sized to the largest board. Verified: 9x9 answers on the padded buffer match a native 9x9 engine to float rounding.

**KataGo binary selection.** `utils/katago/controller.py` reads `KATAGO_PATH` from env, defaulting to `bots/katago` (OpenCL build). `vast_orchestration.py` uploads `bots/katago_cuda` and sets `KATAGO_PATH=bots/katago_cuda` on the remote. Don't hardcode the binary path; rely on the env var.

**`bots/analysis.cfg` is hardware-tuned in place.** `pipeline.tune_engine` rewrites `numAnalysisThreads` and `nnMaxBatchSize` for the current GPU. `vast_orchestration.py`'s `setup` ships the local cfg once but `update` deliberately skips it so remote tuning isn't clobbered. If you edit the cfg, expect the tuner to overwrite your changes.

**`KatagoController` is thread-safe by design.** A single master reader thread fans responses out via per-query `threading.Event`s keyed on query IDs. `send_query` is blocking from the caller's perspective. Multiple worker threads in `generate_tsumegos.py` and `benchmark_bots.py` rely on this.

**Models live outside git.** `models/` is gitignored. `utils.katago.models.get_model(filename)` lazily downloads from `media.katagotraining.org` (or GitHub for 9x9 / human models) on first use. The default model is `MODEL_FULL` (`kata1-b18c384nbt-...`).

**PWA SGF format carries embedded analysis.** Each branch comment in a tsumego SGF is `"<winrate>%/<score>"` (e.g., `"86.4%/3.1"`). Client-side analysis (`pwa/js/sgf.js`) reads this directly; only when missing does it call the server (`pwa/js/analysis-api.js` → `analysis_server/server.py`). Don't strip these comments when manipulating SGFs.

**Branches read to a conclusion are MARKED `TE[1]`; the client must never deduce them again.** A branch carries the mark when the generator drove it to a **DOUBLE PASS** — `generate_variations_directly_to_sgf` (`utils/katago/add_variations.py`) returns whether a line at or under a node reached one and marks each child that did, leaving branches abandoned at the `MIN_PLAYOUT_PERC` cutoff bare so the two are distinguishable in the file. `analysis.js` prefers marked children and falls back to its old rule only where a node has none. **The retired deduction was `subtreeReachesPass` — A SINGLE pass ANYWHERE in the subtree — and it is not a conclusion**: the generator plays some low-visit branches out to a pass without the move quality to match, so the client offered continuations along which the solver's own recorded moves degrade into a loss. That is the whole cause of the 2026-08-02 and 2026-08-08 purges; don't reintroduce any weakened form of the test. **Selection is unchanged and the mark only narrows the pool** (black: `findBestMoveFromChildren`; white: lowest winrate + lowest score, so two ghosts still appear when those differ), and **correctness still reads the UNRESTRICTED `findBestMoveFromChildren`** — a data annotation must not redefine what counts as the right answer. **At the decision node only the ANSWER may be marked** (`mark_children=False` on the refuted-first-move call): a root mark reads as "this is the move to find", so were the answer's own lines to fail to resolve, marked refuted moves would be offered as the solution. `auxiliary/mark_recommended_variations.py` is the retrofit that marked the existing corpus (idempotent, `--unmark` reverses); it approximates generator intent by minimax over the resolved branches and cannot observe it directly.

**`tsumegos/retired_ids.txt` lists ids that are removed from the corpus but KEPT in the DB, and `generate_tsumegos` treats them as taken.** Removing a problem no longer deletes its `tsumego_reports` rows — that is what forced the maintenance freeze and the digest repair on earlier purges — so the id must never be handed to a new problem or it silently inherits a stranger's history, the one failure mode that raises nothing anywhere and cannot be untangled afterwards. `tsumego_id_taken` checks the file alongside the corpus; the format is one 8-hex id per line with `#` comments, appended in blocks that say when and why. Regenerate it from a fresh `pipeline.fetch_database` as *distinct `problem` in `tsumego_reports` not present in `tsumegos/`* — an id whose rows were deleted by an older purge is legitimately absent and reusable.

**`auxiliary/audit_solution_lines.py` is the corpus soundness check.** Exact minimax over the branches that reach a double pass: the answer must hold the win, and no refuted first move may be winnable. **Only resolved branches count** — an abandoned stub is not evidence in either direction, which is what the retired `depth >= 10` ply floor in `broken_review_paths.txt` was standing in for and got wrong in both directions (it scored abandoned lines, and its floor hid resolved short ones). Answer coverage is complete on both boards. **Refuted-move coverage is complete on 9x9 and a FLOOR on 13x13**: `auxiliary/add_losing_lines.py` gave every 9x9 problem lacking one a losing line — the best refuted first move by the client's own rule, played out to a double pass at the generator's `PLAYOUTS` — and the 2858 that could not get a sound one were purged. The generator still pursues refutations far less often on 13x13, so a refuted-move count there counts only what it happened to resolve. Note what the 9x9 pass cost to learn: coverage is what MAKES the audit able to fail, and 2847 problems whose refutation the corpus contradicted were invisible until they had a resolved line to judge. Measured-rejected, don't re-attempt: any rule that PRUNES a side's options and then judges it — pruning to double-pass-reaching branches forces a side into a move it would never play, most visibly a forced pass whose score-it-now terminal reverses the whole line, and it manufactures both false positives and false negatives.

**PWA state is centralized.** `pwa/js/state.js` holds the single mutable object; all changes go through exported setters. `state.appMode` switches between `'solving'` (game-logic.js), `'analyzing'` (analysis.js), and `'linked'` (rank-frozen URL-shared problems). Click handling in `board.js` routes by `appMode` (LINKED clicks go through game-logic, same as SOLVING). **Linked-mode attempts are deliberately recorded nowhere:** `sendReport` and `updateUserStats` (`attempt-recorder.js`) both early-return on `state.problemHistory[0]?.linked` (the canonical flag, set in `problem-loader.js`), so a solved shared-link problem reaches neither D1 (`tsumego_reports`) nor local `answerHistory`. Keep the two guards in lockstep on that one flag — a rank-frozen share must not count toward the corpus, anyone's stats, or the server-stats/rank histograms.

**Account sync: the userId IS the account credential; history syncs by append-only cursor.** Full protocol — the id cursor, mirror-by-id semantics, the sum-first digest backstop, the offline outbox, the state-epoch gate, and the invariants in `account-sync.js` — is `docs/client_sync_and_cache.md`. What must not be broken from anywhere else: the 8-char `userId` doubles as the account password (entering another code adopts that account); the cursor is the AUTOINCREMENT `id` (`sinceId`), **never `created_at`**, because backfill inserts historical event times at the id frontier; a device's acked history is a 1:1 **mirror** of the server's rows keyed by `serverId`, so a complete from-0 pull converges in both directions and there is no timestamp dedup anywhere; the front-page rank is a **pure function** of the recent merged history (`estimateWindowRank`), so adoption and incremental sync are the same operation — recompute, no loop state to warm (there is no warm start at all: the estimator is a grid posterior over the shipped population prior, never over its own previous value); **`idx_tsumego_reports_user_id` must stay in place** (it is what makes an up-to-date poll read ~0–1 rows); and the client-side daily full-pull cap is display only — the real one is server-side in `src/handlers/sync.js`, so the two must be changed together. Known gaps: the ignored-problems list is per-device, and linked-mode attempts are recorded nowhere (see the PWA-state note above).

**Google sign-in is a LOOKUP KEY ONTO AN ACCOUNT CODE, never a second kind of account.** The account is still the 8-char `userId` and nothing else; linking a Google account adds a way to find that code again on a device that does not have it, which is the whole feature — a user who never wrote the code down is otherwise locked out. Client id, verifier and handlers: `pwa/shared/google-auth.js`, `pwa/src/google-token.js`, `pwa/src/handlers/google.js`; the dialog row and its sign-in view are `js/account-ui.js` + `js/google-signin.js`. The rules that bind from elsewhere: **a Google login ends in the SAME `switchAccount` a typed code goes through**, so there is one adoption path and sync, rank and history know nothing about Google. **`shared/google-auth.js` holds the client id ONCE**, imported by the Worker (which pins every ID token's `aud` to it) and by the browser (which initializes the button with it) — the `aud` pin is the only thing stopping a token minted for any OTHER site that uses Google sign-in from logging its bearer in here, and it is only as good as the two ends agreeing, which one env var read by one of them would not deliver. **EMPTY means the feature is off everywhere with no second switch** — the Account row is not drawn and the three routes 404 — which is what lets it ship before the Google Cloud project exists; turning it on is pasting the id there and deploying, after listing the two production origins on the OAuth client's authorized JavaScript origins. **`http://localhost:8787` belongs on a SEPARATE dev client, never on the production one** — that list is the only thing deciding which pages can obtain a token carrying this audience, the audience is all the Worker checks, and the client id is public by construction; `npm run dev` sits on the wrangler DEFAULT port, so authorizing it would let any page another project serves there mint a token this Worker accepts. Not remotely reachable (no page can claim localhost as its origin), so the exposure is the developer's own machine rather than a user's, and a dev id committed by mistake fails LOUDLY — the dev client does not authorize onlymove.net, so the button refuses to render in production. **`POST /google/signin` RESOLVES and writes NOTHING**: a verified token has two possible meanings — log in as the code it is bound to, or attach it to the code in hand — and which one the user meant is not in the token, so the client asks, naming the CODE in the question. Auto-binding an unbound token to whatever code the device holds is the trap that avoids: a returning user's fresh install holds a throwaway code at exactly that moment. **ONLY the opaque subject id is stored** (`google_accounts`, `google_sub` PK → `user_id` UNIQUE = exclusive in both directions, which is what lets a sign-in resolve to one code rather than a list). The address rides in on every token and is deliberately not kept: it is decoded client-side for display only, stored against the code it belongs to so a stale copy from a previous account is IGNORED rather than shown, and deliberately NOT in `ACCOUNT_WIPE_KEYS` — a Google login has to carry it across that wipe. **Apply `pwa/migrations/2026-08-25_google_accounts.sql` BEFORE any deploy that carries a non-empty client id**: `GET /profile` reads `google_accounts`, so a missing table takes out the Account dialog's whole panel, not just its Google row. The button is GOOGLE'S OWN rendered button (their branding terms require it) and the GIS library is fetched ON DEMAND when the sign-in view opens — never at boot, being a cross-origin script in an offline-first app that almost no launch needs. **`POST /google/unlink` takes the code and no token**, like every other write here: the code IS the credential, and requiring a token would put the removal behind the very thing a user unlinks because they lost access to it.

**The live rank is a grid posterior over a measured population prior, and THREE ranks come out of it.** Model, the prior's provenance and survivorship caveat, and the offsets: `docs/methodology.md` §2.3, `docs/client_sync_and_cache.md`. The rules that bind from elsewhere: `pipeline.fit_population_constants` fits `rank_prior` (a log-density on a rank grid) and it is **MANDATORY with no fallback** — an unanchored estimator still returns a number, it just tracks wherever it last drifted, so the failure is invisible. The prior is **never** the user's own previous estimate (that was the overshoot root cause: it damps steps but anchors level to nothing, and early windows are frequently all-correct/all-wrong where the unpenalized likelihood has no interior maximum). The posterior is evaluated on a GRID, not by Newton+Laplace, because the population is bimodal and so is a short-window posterior — a mode fit would report a falsely tight `se`, the unsafe direction for every offset built on it. From that one posterior: **`userRank`** = the mean, the honest number everything CALIBRATED reads (server-coupling anchors, the Worker's `pred_rank`, recall, weakness) — never feed a shifted value here or the calibration loop closes on it; **`displayRank`** = `mean + K_DISPLAY·excess` (`K_DISPLAY` = −2), what the user is told (badge, rank-change overlay, the rank-translation modal, and the Rank chart's front-page-rank line — the chart's slow SKILL line deliberately stays on the mean); **`serveRank`** = `min(mean + excess, displayRank + serveGapCap(attempts))`, what selection targets. `excess` = `max(0, se − seFloor)` so all three collapse onto the mean at convergence and neither offset leaves permanent bias. **Serving must NOT simply follow the display down** — measured: it starves the estimator (successes on far-below problems carry no information, `se` never falls, the display never recovers) and a beginner sits several ranks under their true rank for hundreds of attempts. **The gap resolves to `min(3·excess, cap)`, so the CAP — not the UCB term — is what binds through onboarding and therefore what sets how fast a strong user is found.** It is `1 + the current run of correct answers + (FRESH_RECORD_BONUS = 2 while the window holds NO miss)` (`serveGapCap`, reset by any miss, never zero) — **NOVEL attempts only**, since `flattenAttempts` filters `isRepeat`/`linked` before the array reaches it (Worker side: `is_repeat = 0` in the leaderboard buffer), and that is deliberate: a missed REVIEW is evidence about forgetting, not about serve difficulty. **The point of the streak form is the ASYMMETRY, obtained with no branch and no threshold**: a weak player misses often so their run stays short and the cap stays near its floor, while a strong player's run grows monotonically and the cap stops binding within ~10 attempts. Measured (fixed-ability sim, shipped corpus, first 30 problems of a true 20k, share landing >3 ranks above them): streak 13.3%, constant-5 12.0%, **attempt-count 64.9%** — so `cap = attempts` reaches the same speed by serving beginners far over their head, and is the specific thing this form exists to avoid. **A fresh device's ENTIRE cold start comes from the same rule** — `coldStartEstimate()` (`shared/rank-window.js`), the ordinary window estimate over an empty window, which is the population prior exactly. There is no starting-rank constant: `state.js` computes it once at import and each of the three getters falls back to its own slot of it. **The `displayRank` getter must fall back to the STORED `userRank`, never to the `userRank` GETTER** — that getter's own fallback is the posterior MEAN (7k), so chaining through it puts the population's average on a brand-new user's badge, which is the one thing the display offset exists to prevent. `estimateWindowRankFromFlat` still returns **null** on an empty window so callers leave a stored rank alone, which is why the cold start is a separate export.

**The SE floor is a SHIPPED CORPUS CURVE, not a runtime scan — `pwa/tsumegos/se_floor.json`, written by `package_for_pwa` (`emit_se_floor_curve`) and read through `seFloorAt` in `pwa/shared/rank-window.js`, which `estimateWindowRankFromFlat` applies internally so no caller passes a floor function.** It holds the corpus's mean per-attempt 4PL information (`slope_in_rank_space² · anchorInfo(floor)`) on a rank grid — information, not the floor, because information is what averages and `seFloorForMeanInfo`'s 1/√ is applied after interpolation. **Its knots ARE the rank prior's grid, and that is load-bearing**: `windowMLE` returns a weighted mean over `PRIOR_X`, so no reachable rank falls outside the knots and the curve is never extrapolated. **That grid is DERIVED, never hardcoded** — `fit_population_constants` sets it to the fitted user distribution's mean ± `PRIOR_GRID_SD` (4) SDs, narrowed to what the corpus can actually price a floor on, and REFUSES to ship one that no longer contains `PRIOR_GRID_MUST_CONTAIN` (20k..10d — M's OWN knot range, past which `applyM` is extrapolating, so requiring a floor beyond it would demand a measurement where the curve itself has none). It is deliberately NOT the labelled 30k..9d ladder: representability does not need it (an outermost knot absorbs everything past it and `seFloorAt` clamps, so a user beyond the edge is served the edge knot), and a rating IS the 80%-clear point, so pricing a problem at 30k asserts a 30-kyu player finds the single correct move four times in five — which the corpus does not contain. That bound was satisfiable only while a fit emitted a pathological rating tail, so a better-behaved fit failed it. Both halves are needed and a fixed pair can satisfy neither: too tight pins an off-scale user at the edge, too wide hands the emitter a knot with no measurement behind it. The geometry both steps use — kernel, bar, corpus read, edge and interpolation rules — is single-sourced in **`utils/rating/se_floor.py`**, imported by the step that CHOOSES the grid and the step that EMITS the curve, so the two cannot drift apart (they did: a fixed envelope plus a refit that moved the corpus tail is exactly how a knot ends up unmeasurable) (the lookup clamps to the range as well, so a future grid change degrades to the end knot instead of silently returning `Infinity` — a linear extension of interpolated information goes negative within a few stones, and `seFloorForMeanInfo` maps non-positive information to `Infinity`, which drops the excess term and shows the raw mean with no symptom at the call site). **Do not go back to measuring it per-reader.** **The dominant cost is the reader that holds NOTHING**: with no pool the floor could not be priced at all and was conceded to zero, which lands the shown rank `2·floor` LOW — measured on real histories, 0.65–1.8 ranks, a whole band or more for 6 of 7 users. The next attempt recomputes it with a pool loaded, and the overlay reports the recovery as a PROMOTION to a band the user already held (the account-adoption re-anchor is the standing route into it: it runs before the first problem load by design, so the pulled rank can pick the shard). Two smaller costs on top: the readers disagreed with each other — a client held only the shards loaded that session, which cluster around the SERVE rank rather than the mean the floor is priced at, while the Worker and the offline rebuilds each built a different index, worth up to 1.27 stones — and a 50-problem sample mean drifts with the estimate (median 0.10 in the floor per ±0.25 stone). That last one is the SMALLEST term and must not be oversold: of the band crossings a converged user sees, measured 25 of 231 came from the display offset moving and 206 from the posterior mean itself. Re-crossing a band edge and being told each time is CORRECT behaviour — the shown rank really is moving across it — so the target here is the crossing that no answer caused. Emitter constants: a Gaussian kernel at `SE_FLOOR_BANDWIDTH` = 0.25 stones (measured optimum — wider flattens the fall from the kyu plateau into the dan range, narrower tracks its own sampling noise) and `SE_FLOOR_MIN_EFFECTIVE` = 5, an ABORT tripwire and deliberately NOT a widen-the-kernel trigger: the nearest dense region to the sparse tails is the slope-clamp ridge at M's leftmost knot (rank −20, where M's first interval is far shallower in rank-per-rating than its second, so rank-space slope roughly quadruples across one knot), so a widened tail knot imports that ridge and lands 5× off its own neighbours. Two mechanisms cover the sparsity instead, each for a case the other cannot reach: an **OUTERMOST knot absorbs everything past it** at full weight — the reader's own semantics, since `seFloorAt` clamps to the range, and the only option at an edge that has no outward neighbour to borrow from (it also LOWERS edge information, hence a higher floor, the safe direction for every offset built on `se`); and an **isolated interior thin knot interpolates from its measurable neighbours**, which is local and imports nothing distant, unlike widening. A thin RUN longer than `SE_FLOOR_MAX_INTERP_RUN` (2, one stone) ABORTS rather than bridging — past that the curve is invented across a real gap rather than filled across a pinhole — and every interpolated knot is printed, because a silently patched curve reads as a measured one. The ridge itself is shipped faithfully — the information the estimator accumulates has it too, so smoothing it here would put the floor out of step with the se it is a floor ON. `data_version` folds the file in, `build.mjs` inlines it (`INLINED_DATA_FILES`), and because the floor no longer depends on load order, `main.js` re-anchors once BEFORE the first problem load (a stored rank is read — shard pick, badge — before it is rewritten) with no pool gate. **`reanchorRank` (`rank-decomposition.js`) remains the SINGLE writer of the three rank slots** — attempt-recorder, account-sync and boot all route through it — so they can never be written under different rules; it is a pure function of the history, hence idempotent and safe to re-run. `estimateWindowRankFromFlat` still returns **null** on an empty window so callers leave a stored rank alone, which is why the cold start is a separate export (`coldStartEstimate`).

**Do not put the cap back to a constant.** A constant `c` doesn't just limit the bonus, it INVERTS it — `display + c` is BELOW the mean whenever `excess > c/2`, i.e. all of onboarding at `c` = 5, so the app serves under its own best guess and starves exactly as above (measured at `c` = 5: an unlimited-strength player needs ~38 first-time attempts to reach a dan badge vs ~25 under the streak rule, and a simulated fixed-ability 20k clears 0.91 of what it is served against the 0.80 target). The accepted cost is that the badge-vs-served gap is bounded only in distribution (typically ~2 ranks, 10+ during a long run) rather than by a constant.

**Recall serving is volume-targeted via a stochastic gate; stability has NO ceiling.** Model, equilibrium and the full measurement against the attempt log: `docs/methodology.md` §2.8 (harness `auxiliary/eval_recall_model.py`). The operating rules:

A due recall wins a serve decision only with probability `recallServeShare()` (`pwa/js/recall-model.js`), the constant-volume equilibrium share solved at **`SHARE_VOLUME_FRACTION` = HALF the user's trailing-week daily average** — deliberately, and note the direction is the opposite of what "half" suggests: the working window is counted in ATTEMPTS, so a lower assumed volume makes the served share RISE. While the share is not estimable (no model / no week volume / too few recent novels / no rank) due recalls always win, and the gate **FAILS OPEN** on any estimator error (`recallGateAllows` in `problem-loader.js`; `selectNextProblem`'s never-throws contract). The roll happens BEFORE the recall is built, so a gated-out recall costs no shard fetch, and it is **DETERMINISTIC — hashed from (most-due candidate id, last recorded attempt date), not `Math.random()`**: the tab-visible `refreshShownProblemAfterSync` must re-derive the same decision rather than re-roll, since independent resume rolls would compound into `1−(1−share)^n` chances to swap a due recall onto an idle novel. Every new attempt re-seeds, so genuine serve decisions stay independent Bernoulli(share) draws. **The gate paces only UNPROMPTED serves**: an explicit user request bypasses it — notification clicks (`?recall=1`, `main.js`) and the Recall button (`showDueRecall` in `problem-loader.js`, wired in `main.js`), which serves the most-due candidate exactly as the automatic path would and leaves `challengeProblem` standing for afterwards. That button takes the last button slot while SOLVING (Share keeps it in analysis/linked mode — `updateSolvingModeUI`/`updateAnalysisModeUI` in `ui.js` show exactly one, so positions don't jump), and carries a badge of `waitingRecallCount()` (`recall-model.js`) — the due candidates MINUS the one on screen, since a served recall is not waiting. It is disabled with nothing due, while a recall is already shown, and while `acceptClicks` is false; the count is recomputed per repaint, so it is only as fresh as the last `updateAllUI`.

**`stabilityDaysForRepeat` has NO upper clamp — don't reintroduce one.** Graduation IS the streak's exponential interval outgrowing the `RECALL_CANDIDATE_HISTORY_LENGTH` working window; a ceiling turns graduation into a perpetual recycle, so the pool can only grow and serving drifts toward 100% recalls. Overflow needs no clamp (lnS is a small linear form) and `!isFinite(S)` maps to Infinity = never-due, which `buildRecallSchedule` skips explicitly.

**The recall fitter is damped-NEWTON, cold-started, and carries no optimizer state.** (It is the only client fitter left — the weakness logistic it used to share this section with is gone; the motif readings need no optimizer.) `pwa/js/optimizer.js` holds the shared step — linear solve, Armijo backtrack, and the NEWTON DECREMENT as the convergence measure. `recall-model.js` fits its two heads as SEPARATE BLOCKS: the correctness head on the EXPECTED (Fisher) information — a 4PL log-likelihood with a non-zero guessing floor is not concave everywhere, so the observed Hessian need not be positive definite where the expected one is — then LN_C alone on its exact second derivative (non-negative for both outcomes) against the `z` that block settled on. **One pass over the two blocks is exact and no alternation is needed**, because `predictAndGrad`'s stop-gradient means the correctness block's objective does not involve LN_C at all. **The decrement — not a loss delta — is the stopping rule, and that is the whole point**: the objective is anisotropic in the direction the model is READ for, so a loss-delta rule stops while that direction is still moving, and the decrement is curvature-weighted so it does not. Measured against an exhaustive reference (the old Adam loop at 200k epochs, no time cap, 1e-12): the shipped Adam budget reported `converged` after 78–202 epochs while sitting 2e-2..1.2e-1 away in parameter space — worth 35% on `SIZE_IS_13` (the stats panel's 13x13 readout) and 52% on `REVIEW_TIME` at a 500-row window — and Newton reaches that reference to 1e-6..1e-7 in a handful of steps, ~10× faster wall-clock. There is therefore **no yield-slicing, no work-time budget and no coalescing queue** on the recall retrain (it is synchronous and milliseconds), and no refine loop on the result overlay: taking extra optimizer steps until the displayed delay agreed with the answer only ever worked because the fit was stopping short, and from a converged fit the remaining disagreement is the two heads genuinely disagreeing. **Cold start is deliberate**: the fit is a pure function of the window, so two devices with the same history agree and an account adoption or state-epoch wipe is the ORDINARY path rather than a rare one (verified — a full window whose optimum is far from zero converges like an incremental one). A separable window (all-correct/all-wrong) sends the unpenalized intercept to the `RIDGE_GUARD`-bounded saturation point rather than Adam's slow crawl; harmless, the intercept being a nuisance parameter. `adamState`/`weaknessAdam`/`weaknessParams`/`weaknessSe`/`weaknessAxisCov` stay in the wipe lists as LEGACY blobs — nothing writes them. The recall SE step accumulates the same Fisher matrix directly instead of forming `D' W D` with a dense n×n diagonal `W` through math.js: bit-identical output (max relative difference 0), and it — not the fit — was the dominant cost of a retrain.

**`first_success_step` is fit by MOMENT MATCHING, never by retention likelihood** (`fit_population_constants`). It is an INDICATOR on "the previous attempt succeeded", not a second growth rate — the second success adds nothing measurable. The likelihood is the wrong instrument here: it scores predictions on intervals the scheduler itself chose, and sizes the step about threefold too small. Two cautions when quoting the measurements: the 0.80 test is ONE-SIDED (a ceiling, not a tolerance edge — a serve realizes less retention than the window's open), and the raw delivery figure of ~0.55 serves per entry is mostly confound — don't quote it (§2.8).

**Worker-version-driven graceful reload.** `pwa/build.mjs` writes `pwa/src/version.js` so the Worker imports the same hash the client gets via the esbuild `define`. Every `/report` response stamps `X-App-Version`; if it differs from the client's `APP_VERSION`, the client sets `state.reloadPending`. `maybeReload` fires from `setAcceptClicks(true)` only when `appMode !== ANALYZING`, so the refresh always lands between problems — never mid-review. New JS-side features that depend on the Worker version (e.g. embedding/ratings backfills keyed by content hashes shipped in `embedding_meta.json`) ride this reload signal. **`computeVersion()` folds a hash of every inlined data file (`INLINED_DATA_FILES` — `embedding_meta.json` + the curve/rank-map/population JSONs) into `APP_VERSION`** so the reload signal moves on a data-only re-ship: `pwa/tsumegos/` is **gitignored**, so a git-HEAD-only version would be blind to a `package_for_pwa` re-ship from the same commit (see the data-version note).

**Never resolve a precached asset through `caches.match()` — it searches caches in CREATION order, which puts the runtime cache ahead of the precache from the first deploy onward.** `activate` deletes and re-opens the version-stamped `only-move-precache-<VERSION>`, which appends it after the long-lived `only-move-runtime`, so a runtime copy of a precached URL wins every lookup; and precache URLs are fixed-name with no `?v=`, so the activate-time prune never removes one either. A copy that stored badly is then served for the life of the install, across reloads and every deploy — measured as a permanently textureless board, which is silent because WGo sets the wood as a CSS `background-image` once per session and `.wgo-board`'s `background-color` makes the failure look like a plain tan goban. So in `sw.js`: precache paths resolve against `PRECACHE_NAME` explicitly and a miss is written BACK to the precache, never to the runtime cache; `activate` sweeps runtime entries that shadow a precache path (the repair for devices already in that state); and `install` fills **per-URL under `Promise.allSettled`, not `cache.addAll`** — all-or-nothing means one flaky fetch costs the whole precache for the session and pushes every one of those URLs into the permanent runtime cache, which is what creates the shadow. Detail in `docs/client_sync_and_cache.md`.

**Served data files are cache-busted by a content `data_version`, not `APP_VERSION`; `embedding_meta.json` is inlined.** The content-addressed chain, the Range-request behaviour of Workers static assets, and the `_headers` rules are in `docs/client_sync_and_cache.md`. The rule that governs new code: `pwa/tsumegos/` is **gitignored**, so a git-HEAD version is blind to a `package_for_pwa` re-ship from the same commit — any fixed-name data fetch must carry `?v=${DATA_VERSION}` (read synchronously from the inlined manifest via `pwa/js/data-version.js`), and content-hash-named files need nothing. **`data_version` (cache freshness) is deliberately separate from `ratings_version`/`embedding_version` (backfill gate):** a ship that only ADDS tsumegos bumps `data_version` so new problems become serveable lazily with no history walk, while a ratings change bumps `ratings_version` and triggers the immediate re-derive.

**Server-wide "Community" stats are a cached, read-cost-sensitive D1 aggregation.** Metric-by-metric definitions (the median-per-user bucketing, the review-time double-count fix, the recall-gap bins) are in `docs/leaderboard_and_community_stats.md`. The cost rules, which are the reason the shape is what it is: **D1 bills rows read, so `created_at` MUST stay indexed (`idx_tsumego_reports_created`)** — without it every window scan is a full-table scan that blows the daily read quota — and there is **ONE shared 7-day window query over `tsumego_reports`**, bucketed in JS; don't split it back into per-metric queries. The rank histogram and country distribution deliberately do NOT come from that scan: they ride the small `leaderboard` table scan the `/leaderboard` page already runs, reading each active player's stored `pred_rank` verbatim. **Don't take rank off that window scan** — the attempts are already in hand so it looks free, but what it measures is the difficulty a user was SERVED, which is biased in both directions, and the leaderboard scan it would save costs no extra D1 rows.

**The `/leaderboard` page is a compute-on-read display resolver with a UNITS selector covering onlymove and EVERY coupled ranking system; its "Declared" column shows the player's own survey declaration on the selected system, overridden by a linked federation account's machine-verified rating (EGD GoR on EGF, AGA rating on AGA), and its "Predicted" column the onlymove estimate coupled into that same frame.** The full resolver — the three-table stitch in `readLeaderboardRows`, the EGD/AGA heartbeats and their activity gates, the units frames, the country fallback chain, the hide opt-out, the self-link flow, and the stored-column history — is `docs/leaderboard_and_community_stats.md`. The invariants that reach beyond that file: **a player LINKS THEMSELVES from the Account dialog and NOTHING VERIFIES THE CLAIM** — neither EGD nor AGA authenticates anyone, so a linked name is a claim, not a credential, and the two properties standing in for verification are both server-enforced: exclusivity (an id bound elsewhere is refused) and reversibility (Unlink frees it again). **Every path that removes or replaces a binding must delete the account's `'EGD'`/`'AGAR'` heartbeat rows with it** — they are keyed by `user_id`, not by player id, so one left behind reports the PREVIOUS player's verified rating under the next name linked. **The EGD side accepts no rating on the link path**: the Worker cannot reach EGD at all, so the GoR arrives only through the weekly client piggyback, which already bounds and week-guards it — linking must not become a second, unguarded way to assert one. **`GET /profile` belongs in the service worker's dynamic-GET bypass list**, its URL being the userId and nothing else. **Survey declarations are SHOWN, so the opt-out is part of the collection path** — the same `hidden_profiles` flag is offered in the Account dialog and at the foot of the rank-survey dialog, each reading the flag back on open and writing only on a change (unchecked-by-default plus an unconditional write would un-hide anyone who opted out in the other place); **every unit frame is the shared band-edge convention and every cell goes through the shared `rankProgress`**, so an AGA rating enters via the label-preserving `agaRatingToRank` rather than a display-only half-band shift — otherwise the two columns sit on frames half a band apart and the comparison the page exists for is biased; the row stores the SHOWN rank (`pred_rank` = `displayRank`, untimed internal) so the page, the Community histogram (bars and the reader's own "you are here" marker alike) and the player's own badge are one number — which makes the **rank-dependent SE floor part of the stored value, so every caller must price it identically** — and that is exactly why the floor is no longer measured per reader at all but read from the shipped corpus curve through `seFloorAt` (`shared/rank-window.js`), which `estimateWindowRankFromFlat` applies internally. Nothing in `src/leaderboard.js` or in the offline rebuilds computes a floor of its own; a reader-side scan is what silently let a rebuild write ranks the live Worker disagreed with for the same buffer. It also means **est-vs-verified on this table is not a calibration measurement** — `displayRank` is deliberately conservative while a posterior is wide, and `auxiliary/check_mapped_vs_declared_rank.py` is the script that scores the mapping; **the personal time dock must be added BEFORE any server coupling** — the couplings were fitted against time-adjusted ratings, so mapping an untimed rank forward silently shifts every estimate; **buffer order is INSERT order (the AUTOINCREMENT `id`) and every writer and rebuild shares that one convention**, so anything that overwrites a row's buffer with a stale snapshot drops what landed in between permanently; and `auxiliary/update_leaderboard_ranks.mjs` therefore **runs under the maintenance freeze, which `--remote` OPENS AND CLOSES ITSELF** — it freezes (a `wrangler secret put`, no build/commit/deploy), waits for a probe to confirm it, runs `pipeline.fetch_database` inside the window, applies, then thaws on EVERY exit path including SIGINT, reporting a thaw it cannot confirm as a loud non-zero exit. So a post-re-rate refresh is one call in the order `package_for_pwa` → `npm run deploy` (so the Worker computes on the new scale) → this script. Started against an ALREADY-frozen production it takes no ownership: freeze left ON at the end and NO fetch, because a post-surgery mirror is the intended state and an incremental pull cannot reproduce it (the runbook's step 8).

**Write endpoints are guarded by three cheap layers upstream of D1, plus a maintenance freeze.** Layer-by-layer detail, the calibration behind the limits, and the freeze's rationale are in `docs/worker_operations.md`. What you need when touching a write path: a spoofed write costs D1 write quota *and* inflates every server-stats window scan for 7 days, so writes are defended cheapest-first — an outer **Cloudflare WAF rule** matching ALL POSTs by method (zone config, applied out of band via `pwa/waf/rate-limit-rule.sh`; new endpoints are covered automatically), **per-IP Workers rate-limit bindings** checked in the dispatcher before any handler touches D1 (**fails open**, so a misconfig never drops a legit write), and **in-memory format validation** (`isValidProblemId`, `isValidUserId`) before the INSERT. Validation is **deliberately format-only**, with two consequences: any deploy smoke test must POST a real 8-hex problem id, and `pipeline.fetch_database` is unaffected because it hits `api.cloudflare.com`, not the guarded zone. The fourth layer is **`MAINTENANCE_MODE`**, a wrangler **secret** (deliberately NOT a `[vars]` entry — a var of that name would collide with it and win on the next deploy, silently thawing an open window): `"1"` makes every POST return `503 {error:'maintenance'}` and `scheduled()` early-return, checked before the rate limiter and before any D1 access; unset reads as open. Being a secret is what lets a script flip it — `printf 1 | npx wrangler secret put MAINTENANCE_MODE` is a version rollout reusing the deployed bundle, so no build, no commit, no clean-tree gate. A rollout lands UNEVENLY over a few seconds, so a freeze counts as confirmed only when several consecutive probes agree (measured: a single 503 from a straggler colo, with unanimous OPEN seconds later) — and the authoritative check that no write slipped through remains the before/after `MAX(id)` comparison, never the probe alone. Never put the flag behind a per-request lookup (D1 or KV): the check sits upstream of the rate limiter precisely so a flood costs zero D1, and a D1-backed flag would read D1 to decide whether to write D1. It exists so snapshot-relative operations run against tables that are standing still; freezing is safe because `sendReport` only acks on `res.ok`, so the durable outbox re-uploads afterwards with the original event time. Procedure: `docs/db_surgery_runbook.md`.

**`pipeline.fetch_database` is incremental by default and read-cost-sensitive.** Implementation detail — the schema-tolerant table discovery, the `d1.sqlite` merge target, the local-D1 reset by file copy — is in `docs/worker_operations.md`. The two rules: D1 bills rows read and `tsumego_reports` is >99% of the DB, so the default path pulls **only new rows via `WHERE id > MAX(local id)`**; and **the cursor MUST be `id`, not `created_at`**, because `POST /report-backfill` inserts historical attempts with their client event time, which a `created_at` cursor would silently skip. Append-only makes the id cursor provably gap-free. Stop `npm run dev` before fetching — the fetch overwrites the miniflare D1 file, and doing that under a live workerd corrupts its view. `--full` forces a complete re-download. **The Cloudflare authorization check fails spuriously on a first call** (`code: 7403`, "the given account is not valid or is not authorized"), and the identical call succeeds seconds later — it is not a credentials problem and re-authenticating is the wrong response. `_run_wrangler_json` therefore retries a STRUCTURED D1 error on the `RETRY_BACKOFFS` ladder rather than treating it as fatal; if a fetch still aborts this way, just run it again before investigating anything else.

**The detailed-stats modal is tabbed; its charts size to the viewport.** `showDetailedStats` → `showStatsModal(tabs)` (`stats-ui.js` holds the stats/chart rendering; `recall-model.js` holds only the numeric recall model + stats computation; the dependency is one-directional, stats-ui→model) renders Summary / Weaknesses / Rank / Time / Community pages (a pane with no content is dropped, and the tab bar is omitted when only one remains). Both SVG charts derive their `viewBox` height from the visible modal area (`chartViewBoxHeight`) so each fits whole when scrolled. The Time chart is a Gaussian-kernel-smoothed daily solving/review-time trend — a no-data gap **breaks the line** rather than reading as zero — with a multiplier (exponential-weight) bootstrap CI band (empirical, robust to idle-tab outliers) and daily problem-count bars on a secondary right axis. The hamburger menu (`index.html` + `updateMenuItems` in `ui.js`) is grouped into Practice / Review / More categories; the Review group (share, ignore) shows only in analysis mode.

**Skill-axes recommender (per-component weakness mining).** The axes are per-problem SKILL DIMENSIONS (supervised residual axes — see *Axes fit* below) but shipped per-CELL: every legal first-move cell gets its own K-dim vector, so the system can score both the **correct** move (a property of the position) and the move the user **actually picked** on a wrong attempt.

*Extraction* — `pipeline/extract_activations.py` runs a vendored PyTorch copy of KataGo b18 (`utils/katago/vendor/`, bootstrapped via `utils/katago/torch_model.py`) and captures the post-skip-add output of all 18 residual blocks (18 × 384 = 6912 floats) **at every legal cell**. Output: `activations/<size>/<id>.npz` with `candidates (n_legal, 6912) fp16`, `xys (n_legal, 2) int32`, `correct_idx () int32`.

**Row order is board-scan order (sorted by `(y, x)`), NOT SGF-variation order, and the cell set is a *superset* of the SGF's root variations.** `extract_activations.process_one_sgf` enumerates every legal cell for the player to move (the color of `variation_nodes[0]`) in scan order and records a `correct_idx` pointing at the correct move's scan position (non-zero in general; e.g. 13×13 `00000f4c` has `correct_idx=38` — verified byte-for-byte that a re-extraction reproduces the on-disk corpus). Do not instead walk the SGF's pruned variations in document order with `correct_idx=0`: that ships a non-superset cell set and does not match the on-disk corpus. Two consequences every downstream consumer must respect:
  - **Pick the correct row by `correct_idx`, never positionally.** Every consumer (the activation-cache builder feeding `utils.rating.features`, `pipeline.write_mirt_per_cell`' per-cell fanout) selects `candidates[int(correct_idx)]`; do not assume row 0.
  - **The npz embeds every legal cell; SGF root variations are a pruned subset, plus the SGF carries a `pass` variation the npz never embeds.** So npz ⊇ {SGF non-pass variations}: every move a user can actually click is embedded (no picked-move ever misses), but ~10% of problems have extra embedded cells with no SGF variation, and 100% have a `pass` that is not embedded. Map cells by `(x, y)` coordinate, not by index, when crossing the npz↔SGF boundary.

*Axes fit* — the axes are factors 2…K+1 of `pipeline.train_mirt`, fitted jointly with the rating rather than afterwards against a frozen 4PL. The axis map is a linear layer on the TRUNK's representation, so it shares every feature the rating heads see and the axis objective reaches the trunk. Measurements behind that shape, and behind the axis count, `V_RIDGE`, the barrier and the axis bank: `docs/mirt_benchmark.md`.

**THE AXES ARE TAUGHT ONTO PROXY RULES — `axes/motif_proxies.npz` + `axes/labels.json`, a hard prerequisite of `pipeline.train_mirt`.** Without a fixed target a refit re-rolls the basis: the objective is exactly invariant to rotating the axis space (the likelihood reads the loadings and user positions only through their product, and `V_RIDGE` and the centring of `v` are each rotation-invariant), so there is a continuum of equal solutions and nothing picks among them — a 2% data change moves the basis as far as a different seed does, which would silently reattach every name in `labels.json` to a direction it was not written for. So production does not derive directions at all. It adds an auxiliary MSE pulling the loadings onto the target at a CONSTANT `TEACH_WEIGHT` = 0.25 for the whole run, while the trunk trains normally. Measured across a real refit: 0.204 min canonical without it, 0.899 with, at no loss cost.

**THE TARGET IS A STATED RULE, NOT A DIRECTION A PREVIOUS FIT FOUND, and that is the whole reason the store was demoted.** A rule (`utils/rating/motif_rules.py`) is a criterion over the board and the engine's own evaluation, evaluated on EVERY problem both ways, so the target exists before any fit does, covers the corpus completely, and is a FIXED, RE-READABLE REFERENCE across refits. **What it does not do is guarantee the fitted axis means the rule.** The axis is whatever the model lands on when pulled toward the rule and then released — a rule is a STARTING POINT, and the hope is that it lands close enough to be a good representation of it. How close it landed is what the identity report MEASURES rather than something the design assumes. `labels.json`'s `components` pairs rules onto axes in axis order, `"A/B"` putting rule A at the positive tail and rule B at the negative; a bare `"A"` is one-sided. Columns are glued as `f(A) − f(B)` with the shared tail weight, so a problem at neither pole contributes ~0 rather than cancelling two plateaus, and each column is z-scored because scale is arbitrary (a rescale is absorbed by `v`). Each fit stamps the taught spec into `axes.npz`.

**Selection is BY RULE NAME, and that is safe here in a way it is NOT for the store.** A rule name is unique by construction (asserted on `LABEL_SET`) and identifies exactly one column, resolved through the npz's stored `rules` array rather than by position. The store cannot be read that way and never should be: it holds three directions called `counting`, three called `opening`, and a `ko` that is one entry's POSITIVE tail and another's NEGATIVE — so a name lookup there fixes neither the direction nor the sign, which is why the store is keyed by content hash. The converse also holds: a rule column has one entry per problem and is recomputed as the corpus grows, so it CANNOT be content-hashed stably, and a hand-assigned id would just be the rule name with a prefix. **`motif_rules.py` is also the single source for what a motif is CALLED** — `RULE_LABELS`, which `package_for_pwa` resolves shipped tails through. Nothing in production reads the store.

**THE SHIPPED SET IS FIVE ONE-SIDED RULES — `ko`, `counting`, `tenuki`, `life and death`, `territory` — AND THEY ARE CHOSEN ON RELIABILITY, NOT ON LIKELIHOOD.** A rule earns an axis by how fast a user's POSITION on it becomes identifiable — split-half reliability against history length, summarised as N50, the attempts at which reliability reaches 0.5 (`auxiliary/rating_dev/split_half.py`). That follows from what the axes are FOR: reporting weaknesses and tilting selection, both of which need a user's coordinate pinned from a history somebody actually has. Measured over four paired draws the eight rules split into two tiers that hold at EVERY K tried and that no K rescues — working at 348–787 (counting, tenuki, ko, life and death, territory) against 3,510–8,220 (opening, sente, shape), where ability as a positive control sits at 16. The combined logloss cannot decide this: paired, K=4→6→8 moves it by less than the draw-to-draw spread. **`tenuki` ships against its own evidence, deliberately** — its N50 qualifies but its reliability curve is FLAT across three banks and twelve seeds, which says between-user variance ≈ 0 and makes the N50 a curve-fit artifact. That second reading no longer exists as a pipeline gate — the empirical-Bayes pass that tested it was removed with the population constants — so `tenuki`'s between-user variance is now checked, if at all, by measuring the client's own readings across users.

**RESIDUALIZING THE RULE COLUMNS AGAINST RATING/SLOPE/FLOOR IS MEASURED-REJECTED, don't re-attempt.** The motivation is sound — a rule can be rating-DEPENDENT without being collinear (`tenuki` fires on 3.6% of the corpus at the weak end and 33% at the strong end, r_pb +0.236), while `ORTHO_RATING` pushes the fitted axes off rating and nothing constrains the TARGET — but it splits along the tier line in the wrong direction. Paired over the same four draws, four of the five working rules DEGRADE (ko 518→787, counting 348→399, tenuki 493→578, life and death 751→824) and only the two worst improve (shape 8,220→2,482, sente 3,510→1,460), with the combined logloss 0.68 mnat worse. Nothing clears p<0.05, so the DIRECTION is the finding and not the margins — but it is consistent across the split and the combined column agrees. A rule's rating dependence is part of what the rule MEANS.

**TEACHING FROM PREVIOUSLY-FITTED DIRECTIONS IS THE STANDING ALTERNATIVE, AND IT FAILS IN THE WAY THAT IS WORSE THAN FAILING: IT HALF-WORKS.** Directions a fit was observed to find are stored under a content hash and taught back. Measured they return at 0.43–0.73 tail agreement, which reads as retention — and inspection of the axes at exactly those figures found FOUR OF SIX poles mutated or unnameable (see the calibration note below). So the number that would certify identity was satisfied while the names it certified had come loose. **And the round trip buys no stability to pay for that risk: re-teaching from a previous fit's direction does not stabilise an axis any better than teaching from the rule directly does.** Since the fitted direction is itself only an approximation of the rule it was taught from, chaining through it adds a reference that moves, for nothing — so the fixed reference is the one to teach from every time. A free fit also tends to land on one-sided axes and does not hold a taught direction well, which is what closed off the remaining route. The store therefore remains as a DEV tool — `auxiliary.rating_dev.{update_motif_store,build_bank_from_dumps,bank_identity,tail_overlap}` — for exploring what a fit lands on, and its entries stay tracked because a direction found once is otherwise never rediscovered.

**A RATING-CORRELATED TARGET CAN FIGHT THE PENALTY, but how much that costs is NOT settled — do not treat orthogonality as a prerequisite.** Teaching directions that are themselves rating-correlated while pushing the axes off every rating channel is over-determined in principle, and one arm did lose to that conflict: a ONE-SIDED bank whose columns reached 0.357 correlation left the axes worth 0.16 mnat against 4.41. But a BIPOLAR bank at 0.274 under the same penalty reached 4.21 mnat with leakage eliminated and its six poles retained BETTER on average than under the weaker penalty (mean 0.661 against 0.542), which is the opposite outcome. So the penalty tolerates an imperfect target at least that far, and the two arms differ in three ways at once — correlation level, one-sided against bipolar, and the construction — so which of them matters is unresolved. The rules are NOT selected for orthogonality and carry no guarantee of it.

**A FREE FIT DOES NOT REPRODUCE ITSELF, AS EXPECTED — measured, two seeds of one configuration agree on their directions at 0.56 / 0.25 / 0.20, mean 0.34.** The objective is exactly invariant to rotating the axis space, so nothing prefers one basis and two free seeds have no reason to agree; this is that known arbitrariness on a scale, and the full penalty widens the space it is arbitrary within. The practical consequence: **a direction named off ONE free fit is a candidate, not a settled motif** — name it and store it, but expect the next fit to need it taught rather than to find it again. Their rating and axis-contribution figures also differ (5.3 mnat, 4.4x), but two free fits are DIFFERENT SOLUTIONS rather than repeats of one, so that spread bounds free-against-free comparisons only and says nothing about taught arms, which a fixed target pins.

**DEV WORKFLOW — HOW A DIRECTION GETS FOUND AND NAMED. This is exploration, not the production path**, which always teaches from the rules. Two stages, and doing them at once is what makes a fit hard to read.

*Stage one — get a direction to exist.* Two routes, neither needing to produce a shippable axis set. A HANDCRAFTED rule labels the corpus from a stated criterion and seeds a motif nobody has seen yet; an UNINITIALIZED fit (no `--teach-directions`) is let go and names whatever it lands on, which is how `escape atari`, `defend territory` and `capture stone to gain liberty` were found. Rules bootstrap a motif that does not exist; a free fit finds one nobody thought to write a rule for. Either way a human reads the extremes (`inspect_axes --dump ... --rank-max 0`, capped for legibility only) and names what is there. Each accepted direction goes into the motif store with its provenance (`update_motif_store`) — the durable record that a direction was found at all.

*Stage two — glue directions onto K axes.* `build_bank_from_dumps` composes a bank from store entries: one motif per axis, or TWO per axis as a bipolar column. Nothing is re-derived; this stage only decides what goes together and in what order. **`components` in `labels.json` is the production analogue** and works the same way over RULE names.

Pairing costs nothing and buys names: six motifs on three axes retained every pole, the two WEAKEST improving most (counting 0.26 → 0.67, escape atari 0.17 → 0.74 against the one-sided arm), and posted the best never-trained pricing of any fit measured. Do NOT try to discover and glue in one step — a fit asked to both find directions and satisfy a prescribed set does neither cleanly, which is the content of the conflict note above.

**A bank of CONVERGED axes scores HIGHER RETENTION NUMBERS than a bank of rule labels — and that is not a reason to ship one.** Directions a previous fit settled on are continuous, cover the corpus at that fit's own confidence, and are expressed in the space the trunk learned, whereas a rule supplies a binary column whose negative side is merely "everything else"; taught from converged axes the motifs come back at or above the rate the SAME motif reproduces between two independent fits (ko +0.91 against a +0.84 cross-fit norm, life and death +0.53 against +0.45). Two things cut against reading that as identity. The numbers OVERSTATE it — 0.43–0.73 read as retention while inspection found four of six poles mutated (see the calibration note below) — and the round trip buys no stability anyway, since a stored direction is only an approximation of the rule behind it and chaining through it holds an axis no better than the rule does directly. So a converged direction is worth STORING, as the record that a motif exists; the thing to teach from is the fixed reference.

Two properties of the teaching term are load-bearing, both learned by getting them wrong first. **It rides the `gh` each attempt batch already computes** — sampling problems separately makes the trunk adapt to a mixture of two input distributions rather than the one the rest of the objective sees (measured: same seed, same bank, sampling alone is worth 0.200). Riding `gh` also matches the population the axes are DEFINED on, since loadings are identified by between-user residuals, which exist only where somebody attempted the problem; the never-attempted third keeps its banked values untaught, those being the previous fit's extrapolation into a region that never carried signal. **The pull never ends** — released completely, a rule-taught fit does not keep the direction it was taught.



**`BURN_IN_EPOCHS` IS GONE and so is every phase — the training loop is uniform.** Pinning `v` at zero for an opening span is the obvious companion to teaching (at `v = 0` the loading gradient from the likelihood is identically zero, so the bank would shape `g` unopposed) and it was MEASURED to buy nothing: same bank and seed, pin 300 against no pin, per-axis bank correlation came back 0.938/0.955/0.953 vs 0.938/0.955/0.952 with tails 512/640/492 vs 511/630/492, and the loss was marginally better WITHOUT it (0.4974@1110 vs 0.4978@1090). The pin does cost ~2 mnat over the opening few hundred epochs — free positions fitting a random projection then unlearning it — but that is a transient, repaid by epoch 1000. So: no `v_pinned` state, no release event, no gating of the axis penalties, and the ortho penalty is on from step one rather than switching on at full weight mid-run. Don't reintroduce a pin without re-measuring both columns. The eigen warm start is likewise retired, not merely unused — at adequate patience it was loss-equivalent to random init, buying ~4x fewer epochs and a particular arbitrary subspace, which is exactly what the bank exists to stop being arbitrary.

**The axes pay only for long-history users** — ~0 below 100 attempts, +4.95 mnat above 500 on one draw, with the 100-500 band unmeasured and very likely positive — 500 is a bin edge, not a measured onset. Quoted as a single number they read as a population fact and are not one, and the LEVEL is not repeatable either: over four draws the overall axis adds runs +3.59 to −1.44 (see the draw-dependence note above).

Output to `axes/{per_problem.csv, axes.npz}` from `train_mirt`, and `axes/per_cell/` from `write_mirt_per_cell`; `axes.npz` carries the axis map plus the content-hash `embedding_version` that packaging reads. `labels.json` is hand-maintained. **`K_AXES` in `utils/rating/model_constants.py` MUST equal the number of `components` in `axes/labels.json`** — the count is the SHIPPING DECISION (one axis per taught rule), not a fitted hyperparameter. The two are kept in step BY HAND and the failure is one-sided: `train_mirt` aborts when `components` is shorter than `K_AXES`, but silently TRUNCATES when it is longer, so a rule dropped from the tail of the list ships an axis that is still fitted and still consumes a weakness slot. Every CONSUMER still reads the shipped count from `embedding_meta.json` rather than assuming it, so changing `K_AXES` needs no downstream code edits and no `fit_population_constants` re-run either — nothing it ships is per-axis (see the population-constants note above).

**Labels are OPTIONAL to ship and an unnamed axis is silent, not broken.** `package_for_pwa` prints which components are unlabeled and ships them anyway; an unnamed axis steers selection and carries its share of the weakness posterior exactly like a named one, and the CLIENT declines to print it — `stats-weaknesses.js` requires the flagged tail to be named (**both** tails, tested at candidate time so an undescribable axis doesn't consume the false-flag budget) and `motif-bubble.js` skips an unnamed tail. There is deliberately NO placeholder label: a sentence like "you are weak at style #2" is not a finding a user can act on, so the pane says nothing rather than something meaningless. Expected flow: new data → a refit grows an axis → publish whenever the rest of the pipeline is ready → a human eyeballs the extremes with `auxiliary.rating_dev.inspect_axes` (renders both tails straight from `axes/per_problem.csv`) → names it in `labels.json` → re-run packaging, which publishes label TEXT on the cheap no-rebuild path.

`package_for_pwa` has no axis-related ship gate: nothing downstream of a refit needs a matching population vector any more, so an axis refit that changes K needs no `fit_population_constants` re-run before packaging. Every consumer reads the shipped count from `embedding_meta.json`.


**AXIS IDENTITY IS MEASURED BY TAIL-WEIGHTED AGREEMENT — z-score each direction, weight it `z` above `TAIL_HINGE` = 1.0 and `at·exp((z−at)/at)` below, correlate.** A name is a claim about one END of an axis, and an axis is a trunk output rather than a linear map on nameable inputs, so the extremes and the bulk are free to diverge. **Bulk correlation is the wrong instrument** and gets answers backwards: it reversed which of two arms held identity better, and it reported a bipolar column collapsing onto one pole when the tails show every pole retained. **Top-N overlap is also wrong** — N is arbitrary, the cutoff is hard so problem N and N+1 are total agreement and total disagreement, and membership discards magnitude, so it manufactures matches out of problems that merely landed inside the boundary. The hinged form has no N, weights linearly by depth into the tail, and is EXACTLY ZERO under independence (hinging two independent variables leaves them independent), so there is no chance baseline to quote. **The two pieces meet in VALUE AND SLOPE, and that smoothness is what makes the threshold safe.** A hard floor `max(z, at)` collapses everything below the cut to one plateau, so a problem just short of the tail and one far from it are declared identical — and the cut then DECIDES the answer: two arms swapped places between z = 0.5 and 1.0. The exponential branch keeps their order while decaying it toward zero, and sweeping 1.0 to 3.0 moves agreement by ~0.01 and never reverses an ordering. Above the threshold the weight is the IDENTITY, which is what keeps one confident problem from dominating a squared error — the reason a plain `exp()` is unusable. Do not tune the threshold to move a result. It also scores what top-N cannot: against a BINARY rule bank, ~100k tied zeros make `argsort` pick an arbitrary tail, while hinging leaves the positives at one value and measures whether the fitted tail concentrates on them. A tail that is constant after hinging returns NaN, never 0 — an empty tail makes no claim and must not read as "measured, independent". Single-sourced in `auxiliary/rating_dev/tail_agreement.py`; `bank_identity.py` scores a fit against its bank (`--cross` for the axes x poles matrix a bipolar bank needs), `tail_overlap.py` scores stored motifs against each other. Everything is scored on ATTEMPTED problems: HALF the corpus is never attempted (49.5%), its loadings there are unconstrained extrapolation, and the enrichment is one-sided — the UNTAUGHT tail of every axis runs 61-81% never-attempted while the taught, named tail runs 30-50%.

**AGREEMENT IS A ONE-WAY TEST.** High tail agreement establishes that two directions name the same thing; LOW agreement establishes NOTHING and must never be read as a motif having failed to transfer. A motif can be present and expressed along a different direction — nothing forces two fits to place it in the same coordinates — and a K-axis fit structurally cannot span a bank of more motifs than it has axes, so near-zero agreement against most of a 16-motif store is a statement about the number of slots. The way to test whether a stored motif survives is to TEACH it and measure retention.

**TAIL AGREEMENT BELOW ~0.75 DOES NOT PRESERVE A NAME — the measure is calibrated against human inspection at exactly one point, and it is not where the numbers suggest.** Six legacy poles taught into the current model retained at 0.43–0.73, which reads as success; a human reading the boards found four of six mutated or unrecognisable. `killing` at 0.43 had become SEMEAI; `judgement` at 0.64 and `attack` at 0.66 were unnameable and are now stored unnamed; `defence` at 0.73 had become ESCAPE ATARI AND KO; `ko threat` at 0.66 had narrowed to FIND KO THREAT AND ANSWER FORCING MOVE. For contrast `ko` reproduces at 0.91–0.97 across fits and keeps its name. So treat agreement as ordinal only, and **anything under about 0.75 as a direction that must be re-inspected and probably re-named before it ships** — retention is not identity, and the gap between them is wide enough to attach a wrong name to a real axis. That is the failure the whole teaching arrangement exists to prevent, so the inspection step is not optional — and it applies to a rule-taught axis too, since a rule is a starting point rather than a guarantee that the axis means it.

**Agreement measures CO-SELECTION, which has two causes it cannot separate** — one direction under two names, or two real motifs whose situations co-occur in Go. `escape atari` and `opening` share a third of both tails because on a small board escaping atari is frequently the opening answer, and they are still distinct: hold opening-ness fixed and escape atari varies MORE than corpus-wide (sd 1.93 within the top 2% of opening against 0.89 overall), so it is discriminating hard among openings rather than restating them. Treat a high-overlap pair as a pair to EXAMINE, never as a redundancy — the conditional check is what decides, and without it the measure will condemn perfectly good motifs.

**There is no input-attribution tool, and that is a property of the model.** Naming an axis by what DRIVES it needs the axis to be a linear map on nameable inputs, so a problem's value decomposes exactly into per-column contributions. The MIRT puts a trunk between the features and the loadings, so no such decomposition exists — any per-input number would be a surrogate model's opinion presented in the one place a human is deciding what a motif IS. The boards are the evidence.

*Packaging* — `pipeline/package_for_pwa.py` ships two things per shard, plus one corpus-wide sidecar:
1. The correct-move axis vector (length K = the selected axis count) joined into the shard's `metadata.json` under `embedding` — what a drawn category's tail criterion reads on any candidate problem.
2. A sibling `<hash>.embeddings.bin` per shard (fp16, K floats per cell, all problems concatenated **in SGF root-variation order**), plus an `embeddings_index.json` inside the zip mapping `{tid: {offset, n_cells}}`. This is the picked-move sidecar: the PWA Range-fetches `bytes=offset+i·bytes_per_cell..offset+(i+1)·bytes_per_cell-1` to recover the embedding at cell index `i` of a tsumego, where `i = children.indexOf(moveNode)` over the SGF root variations.
3. `pwa/tsumegos/lookup.embeddings.bin` — the **lookup-aligned correct-move sidecar**: row i is the K-dim fp16 correct-cell embedding of the problem on `lookup.txt` line i (lookup is id-sorted and spans both sizes, so the line index — which the client already has from its lookup.txt binary search — doubles as the row address; no keys, no offsets). Emitted like `problem_params.bin` (`emit_correct_embeddings`, every non-sentinel run, straight from `per_problem.csv` + the final lookup.txt — no shard rebuild), and folded into `data_version` so it can never cache-desync from lookup.txt. **Row alignment is the contract**: it must be written after the run's final lookup.txt; the client additionally verifies the file size against its line count via `Content-Range` and poisons the sidecar for the session on mismatch. Ids missing from `per_problem.csv` get an all-zeros row the client treats as absent. This is what lets the backfills fetch a correct-move embedding as one ~130-byte Range request instead of downloading the ~2MB shard zip whose `metadata.json` carries the same vector.

   **The bin order is set here, not upstream.** Because the npz is scan-order and a superset (see *Extraction*), `package_for_pwa.project_cells_for_problem` re-parses each SGF and rebuilds the per-cell rows in SGF-variation order via an `(x, y) → npz row` map — dropping the extra scan-order cells, while the `pass` variation (never embedded) gets an **all-zeros placeholder row** so bin row i == SGF child index i exactly (`BIN_FORMAT_REV` 2; rev 1 skipped the pass, which shifted every row after a non-last pass off by one against the PWA's `children.indexOf` — and the pass is not last in ~half of 9x9 / ~3/4 of 13x13 problems). The rev is folded into the **shipped** `embedding_version` (`shipped_embedding_version` = pca-content hash + `-b<rev>`), so a bin-layout change wipes/re-derives clients' stored picked embeddings through the standing version gate and rebuilds shards without `--force`. This reorder is **load-bearing**, not defensive: the PWA indexes the bin by SGF-variation position, so shipping raw scan order would silently return the wrong cell's embedding for every picked move. The sgfmill parse dominates packaging time, so shard building is parallelized across processes (`--workers`, default `os.cpu_count()`).

The joint `pwa/tsumegos/embedding_meta.json` carries `K` (the shipped axis count — read it, never assume it), `dtype` (`float16`), `bytes_per_cell` (so the PWA can decode the bin without guessing), `embedding_version` (from `axes.npz`), and the two-tailed `labels`.

*PWA model — per-motif readings from the user's own attempts (`pwa/js/motif-stats.js`).* No trained model, no prior, no population constant. Two independent readings per axis, both pure functions of the user's own window, so two devices with the same history agree and an account adoption is the ordinary path:

  **TENDENCY** — of the user's WRONG attempts, the share whose picked cell loaded HIGHER on the motif than the correct cell did (`d = correct_emb[k] − picked_emb[k] < 0`). A plain SIGN TEST, null 50%, binomial interval on the user's own error count. Displayed as `share − 0.5`: the share of their errors that would have to lean the other way to balance. **Availability does not enter, and that is why no baseline is needed** — each error is a within-problem counterfactual about that user's own choice (had they leaned the other way they would have been closer to the answer on that axis), which holds whatever else was on the menu.

  **STRENGTH** — the shipped 3PL's residual (`correct − predicted`, prediction from the problem's own rating/slope/floor and the user's rank) regressed on the motif loading, converted to ranks by the curve's local `dP/drank`. This half genuinely NEEDS the difficulty control: motif loading correlates with problem rank (tenuki fires on a few percent of the corpus at the weak end against roughly a third at the strong end), so a bare correlation between loading and outcome would score a user weak at whatever motif happens to live in hard problems.

**A STORED PER-ATTEMPT FIELD IS GOVERNED BY ITS GENERATION'S DEVICE-LEVEL VERSION — NO PER-ROW STAMP — AND THERE ARE THREE GENERATIONS UNDER ONE RULE**: the motif fit (`EMBEDDING_VERSION_KEY` → the two vectors), the rating fit (`RATINGS_VERSION_KEY` → rating/slope/floor/quality) and the rank curve (`RANK_CURVE_VERSION_KEY` → `problemRank`), all three keys in `constants.js` and all three read through `storedVersionMatches` (`data-version.js`). The scheme is sound only under two conditions, both of which were broken: **(1) NOTHING WRITES A DERIVED FIELD WHILE ITS OWN BUILD'S GENERATION AND THE DEVICE'S DISAGREE** — asked AT WRITE TIME in `attempt-recorder` (vectors on `motifDataIsCurrent()`, the rating block on ratings AND curve) and again inside the deferred picked-vector patch, which lands after an await. The case it exists for: the app upgrades between problems, but the signal rides `X-App-Version` on the `/report` RESPONSE (`attempt-recorder.js`, the only place it is read) while the row is written before that response arrives — so an instance a release behind ALWAYS records exactly one attempt out of the generation the device has moved past. **A BOOT-TIME CHECK CANNOT SEE IT** (it booted when the versions agreed) and no later check can either, every version by then agreeing. Refusing rather than wiping-and-restamping is a cost choice: a behind instance that wipes buys the device two full refills for one attempt. **(2) THE RE-DERIVE REACHES EVERY HOLDER**, because a value that survives it can never be found again: history rows, the standing challenge (DISCARDED on a motif change, not refreshed — the sidecar restores its vector but not the rating fields from the same superseded shard), `previousProblem`, the on-screen problem in memory (the backfill runs DETACHED so the first problem can already be painted — `main.js`), and the **sessionStorage resume slot**, cleared for ANY generation change since it is serialized JSON that cannot be refreshed in place. Those two misses are the reported bug, twice. **`repopulateMissingFields` (PERMANENT, ungated, per generation, runs while that generation's versions agree)** gives any in-window row missing a vector or a rating block its current value — from the set-wide sidecars, so it is one range read per problem and `problem_params.bin` is fetched ONLY if some row needs it (never, in the steady state). That is also what makes an interrupted re-derive cheap: the next load finishes it instead of waiting for the next version change. **`noEmb` IS SET FROM THE CORPUS LIST AND NOTHING ELSE** (`lookup.txt`, already loaded, binary-searched): absence from it is the only unambiguous "can never be filled". An empty sidecar read is NOT — an offline load and a problem the fit published no vector for are indistinguishable at the reader — so those rows are simply retried, and the mark clears with the vectors so a new fit gives every marked row one fresh attempt. `verifyStoredVectorsOnce` is the ONE-TIME audit of what was stored before any writer respected the version: each in-window vector checked against the sidecar, mismatches replaced and their `pickedEmbedding` dropped (`pickedCellIndex` kept), since the tendency reading compares the two INSIDE one row. **The rejected alternative is a per-row `embedding_version` stamp** — measured 28 B per row carrying a vector, ~28 KB per device, +2.5% of `answerHistory`. It buys DETECTION after the fact, which the two conditions make unnecessary, and post-hoc diagnosis does not need it either: a poisoned row is identifiable offline by comparing its stored rating against the shipped `problem_params.bin`, which is how the reported one was found. The standing risk is that condition (2) is an ENUMERATION — **any new place that stores a problem object must be added to the re-derive**; it has been wrong three times. **And the reader's K test is a SHAPE guard only** (`SHIPPED_K`, so a per-axis loop cannot run off the end), never a provenance test, because K is the shipping decision and a refit that keeps it moves every axis underneath. **The rejected reader is `K = rows[0].embedding.length` plus voiding the window on any disagreement**: measured, ONE row in 795 blanked the whole pane ("not enough data yet"), emptied `weaknessServeCategories()` so no motif steered selection, and left the bubble naming no training focus.

**EVERY LONG RE-DERIVE PASS MUST MAKE ITS PROGRESS DURABLE IN BATCHES, NOT ONCE AT THE END.** A version stamp written last is what marks the work DONE (a kill leaves nothing stamped and the whole pass re-runs idempotently) — but it says nothing about the work already paid for, and these passes are network walks that are killed routinely: a backgrounded tab, a closed app, a dropped connection. `backfillForSize` persisted only after BOTH the sidecar fill and the picked-shard walk, so a kill inside that walk (minutes, multi-MB zips) also discarded the correct-vector refills and the rating re-derive — while `wipeStaleEmbeddings` HAD persisted, so a device that never survives one uninterrupted walk sits with its vectors wiped, the pane empty and no forward progress ever. `fillSyncedHistoryFields` had the same shape on the ADOPTION path, the heaviest walk in the app. Both now checkpoint: after the ratings rewrite, after the correct fill, every `FILL_CHECKPOINT_EVERY` fills inside it, and after every shard. Safe because the fills are fill-if-MISSING hence idempotent, and `persistAnswerHistory` writes the LIVE array so a mid-walk write cannot clobber attempts recorded during the awaits. Verified by stalling the shard walk mid-pass: 467 refilled rows survived the kill with the version key un-advanced, so the next boot finished the rest. **The rest of the chain was audited at the same time and is already interruption-safe — do not "fix" it**: `/sync` persists a page's rows BEFORE advancing the id cursor (a kill re-pulls the page; the merge is by `serverId`, so it cannot gap); `evictColdTail` confirms the IDB append before trimming the working set (a kill dups, never gaps); the cold-tail passes are each ONE readwrite transaction, so they are atomic; `pruneRemovedProblems` writes its signature last; and the account switch clears `SWITCH_FLAG_KEY` last, so an interrupted adoption re-runs from scratch.

**The displayed band is the GATE's own width (`MOTIF_Z`), not a conventional 95%.** At any other multiple a flagged row can show a band straddling the neutral point — a reported finding contradicting the number printed under it. Locked so "band clear of the neutral line" IS "flagged", by construction. The gate is CONFIDENCE ONLY, with no minimum effect size: a bias the user is reliably making is worth reporting however small.

**WHY THE POPULATION CENTRE WAS REMOVED, so it does not come back.** The retired model was a 2K+2 logistic whose readings were scored against shipped scalars (`weakness_axis_lambda`, `weakness_contrast_mean`, `weakness_axis_mean`). Motif prevalence varies several-fold across the ladder, so a scalar averaged over users partly encodes WHICH PROBLEMS THAT USER'S RANK IS SERVED: measured over 487 users, rank explained 15.5% of the between-user contrast variance on `ko` and 11.7% on `territory` — part of what the pane called a tendency was the user's rank. Worse, the client's ridge centred the CONTRAST prior at zero while the read-time statistic subtracted a centre of +0.639 (2.35·τ) on `tenuki`, which flagged a spurious deficit for essentially every user. Both defects are structural to scoring a personal quantity against a population point; neither is fixable by a better constant.

`problem-loader.js`'s selection is ONE CATEGORICAL DRAW over a slot list, and `rankConverged()` (fail-closed) gates only whether the INFORMATION slot (slope prioritization) is IN that list — NOT whether motifs serve at all. `weaknessServeCategories()` (`weakness.js`) flags every (axis, NAMED tail) whose motif-stats reading clears the shared `MOTIF_Z` (`constants.js` — ONE constant deliberately gating problem-motif display in `motif-bubble.js`, the serve flag, and the stats pane's admission bar `normCdf(MOTIF_Z)`, locked so the three cannot drift apart; they are z-scores of DIFFERENT statistics, corpus salience vs posterior confidence, so retuning it anywhere retunes all three), the serve decision hash-picks ONE slot uniformly (deterministic, recall-gate style, seeded on the last attempt date so a resumed tab re-derives the same pick) and argmaxes that axis's tail loading `max(sign·emb[k], 0)` alone. **The slots are the flagged categories PLUS one NEUTRAL no-criterion slot (= the pool's nearest-to-rank head), ALWAYS — `slots = categories.length + 1`, no lone-motif special case** — so n flagged motifs take 1/(n+1) each, no motif exceeds half, and EVERY user gets some share of serves drawn under no criterion. That share is the identification mixture that keeps "weak at the motif" separable from "generally weak" (a near-constant motif loading is collinear with the intercept, and the deficit launders into the rank estimate). **Don't go back to letting two or more motifs cap each other with no neutral slot**: that reaches the same bound only if distinct motifs select distinct problems, and the rules are NOT chosen for orthogonality — their tails overlap in the corpus, so two correlated flags can both argmax into the same corner and leave the mixture with no un-criterioned component at all. The neutral slot is also the only part of the draw that is blind to a motif's CORPUS ABUNDANCE at the user's rank (motif occupancy is strongly non-uniform over rank — see the ko-occupancy note below), so it is what bounds how far that abundance carries into a served history. The INFORMATION slot draws UNIFORMLY from the top `INFO_TOP_FRACTION` of the pool by `quality` (the 4PL Fisher information at the 80%-clear anchor) rather than argmaxing it, and is in the draw ONLY while the rank estimate is converging — **a plain argmax is an EXTREME-VALUE pick and therefore a motif choice nobody asked for**: the single best-scoring problem of fifty is atypical on every axis at once, and measured it served the moderate `ko`/`tenuki` tail at ~2.5x the rate the pool contains it. Drawing from a slice removes that (within the slice nothing prefers one motif), and the pool's quality curve is FLAT at the top — 1st is 1.84x the pool mean, 5th 1.38x, 10th 1.21x, only the bottom falls away — so the slice costs far less information than its width suggests: best-of-50 is worth 1.86x a random pick against the slice's ~1.46x. A residual tilt survives on a motif whose loading genuinely CORRELATES with discrimination (`tenuki`); randomising removes the extreme-value part only. Residualising `quality` against the pool's own loadings removes that too and is deliberately NOT done — measured at ~1.40x information for a second-order gain; the NEUTRAL slot is the pool's nearest-to-rank head and is in it ALWAYS — `slots = categories.length + (withInfo ? 1 : 0) + 1`, so n motifs take 1/(n+1) each once converged and 1/(n+2) before. Nothing flagged (untrained model included — the flag needs the posterior, so there is no separate readiness gate) plus a converged rank means the neutral slot is the whole draw. **Don't put the motif slots back behind `rankConverged()`**: a flag is a property of the weakness posterior, identified from the user's own picked-vs-correct contrast independently of how tight the rank posterior is, so gating on convergence withholds personalization from exactly the users whose rank is still moving while `motif-bubble.js` — reading the SAME `weaknessServeCategories()` — already names those motifs as the training focus. Uniform one-at-a-time is measured, not a simplification bet: within a difficulty-matched pool the criteria are near-orthogonal (winner coincidence ~3% of pools; one criterion's winner captures ~0 of any other's achievable-over-average value, stable across pool sizes 25/100 and the rank range), so a blended/Thompson score has no joint value to harvest. **Don't go back to sampling proportional to any weight.** Measured on the shipped corpus: over 50 difficulty-matched candidates a criterion's weights span so narrow a range that a softmax at the old `WEAKNESS_TEMPERATURE` = 0.5 left the effective pool at 49.9 of 50 — a 0.013-rank tilt costing the entire candidate set. The old whole-pool contrast argmax delivered ~0.27 ranks out-of-sample and 214 distinct picks across 220 accounts; variety still comes from pool turnover, every answered problem being excluded for the next `RECALL_CANDIDATE_HISTORY_LENGTH` attempts. Cold start (≤20 attempts with embeddings): nothing flags, neutral serve. **`tenuki` is barred from selection by name** (`SELECTION_EXCLUDED`, `weakness.js`) while remaining fully REPORTED: nearly every user reads as over-reaching it, and a category almost everyone carries is near-constant, hence collinear with the intercept, so its deficit launders into the rank estimate instead of steering anything. `flaggedMotifCategories()` is the reporting list (the bubble's), `weaknessServeCategories()` that list minus the excluded. **Only a NAMED tail can DESCRIBE a category, and each carries FOUR possible kinds across the two readings** (`kind` on the category): WEAK and UNDERPLAY both argmax the named tail's loadings — drill the deficit, drill recognising when it applies; OVERPLAY argmaxes the OPPOSITE direction, problems whose answer is NOT the motif, because that is where reaching for it actually costs the user (a REDIRECT, not a de-prioritisation — skipping those problems would skip the very ones that expose the habit); STRONG argmaxes the opposite direction too, as a plain suppression. `motif-bubble.js` drops `strong` from the training-focus list: "you are good at this, serve less" is a serve direction, not something to work on. The unnamed negative tail still never becomes its OWN category — untaught residual, undescribable — but an overplay serves that direction under the positive tail's name.

**MOTIF OCCUPANCY IS STRONGLY NON-UNIFORM OVER RANK, AND A NEAR-ZERO CORRELATION DOES NOT SAY OTHERWISE.** Measured on the shipped corpus for `ko` (loading z-scored corpus-wide, gated z > 1; z > 0 gives the same shape more weakly): the corpus ko share runs 0.58x its own base rate at 21k up to 1.83x at 4k, peak/trough 3.1x pooled, and 0.52x at 19k to 2.08x at 4k on 13x13 alone. Both boards show it independently, and the taught PROXY RULE column reproduces it (0.65x at 21k, 1.69x at 4k), so it is a property of the corpus rather than of the fit. The pooled Pearson r(ko loading, rank) is only **+0.079** (Spearman +0.004) because the shape is non-monotone — down through the weak kyus, up to 4k, flat after — and a linear statistic cancels it. So `ORTHO_RATING`, which penalises TAIL correlation with rating/slope/floor, is doing its job and constrains none of this: **never read a low axis-vs-rating correlation as an evenly-spread motif.** The practical consequence is that a flagged motif's serve category has a genuinely thin pool at the weak end and a rich one around SDK, which is a difference in what the criterion can find, not just a headline number.

**THE INFORMATION CRITERION IS ITSELF A KO SELECTOR IN THE SDK/LOW-DAN RANGE — that is why it RETIRES at convergence rather than persisting as a criterion, and why the neutral slot is nearest-to-rank rather than `quality`.** Simulated over non-overlapping 50-problem difficulty-matched pools, the argmax by `slope^2 * anchorInfo(floor)` is a ko problem 97-100% of the time across 6k-2k on 13x13 (pool rate 23-34%), 78.7% at 1d, 47.5% at 2d — and essentially **0%** across 20k-15k, where the within-band correlation of ko loading with log information is about -0.3. 9x9 behaves the same (0.5% at 20k, 94% at 3k, 71.6% at 1d). Both factors do it independently: `slope^2` alone gives 100% at 6k-2k and `anchorInfo` alone 92-98%, ko problems carrying the LOWER floor (13x13 0.237 against 0.279). The within-band correlations are modest (slope +0.097, floor -0.331) — **an argmax lives in the extreme tail, where a modest correlation is enough to make the pick near-deterministic**, so don't read a small correlation as a small selection effect. Measured on the live log: with the weakness tilt disabled (`WEAKNESS_TILT_ENABLED = false`, 2026-08-21 to 2026-08-23) a converged 1d user fell back onto this criterion and took 53% ko against a 19% rank-matched expectation, having taken 98% under the tilt.

**CANDIDATES COME FROM THE UNBROKEN RUN OF LOADED SHARDS CONTAINING THE SERVE RANK'S OWN BAND — NEVER FROM `state.allProblems` AT LARGE.** Contiguity plus reaching the covering band is what makes the run's nearest 50 trustworthy: no unloaded shard can sit between the serve rank and a candidate, so they are the 50 nearest available, and a PARTIAL run stays safe on the same argument — fewer than 50, or 50 out of one band, is still a neighbourhood of the user's level, with the error against the true 50 bounded by ONE BAND'S WIDTH. The pool at large is not safe, and a DEEP LINK is how it goes wrong: opening a shared problem loads that problem's shard and nothing else (the linked path never assigns a challenge), so with `state.allProblems` as the candidate set any reassignment during that session — answering the standing challenge is enough — drew the next challenge from one arbitrary off-rank shard, and `setChallengeProblem` PERSISTS, so the pick outlived the session. Measured on the live corpus: a 3d who opened a 2k share was handed a 2k challenge, ~4 ranks under them. **`selectChallengeCandidate` returns null when the run is empty**, and `assignNewChallenge` then awaits `expandPoolForCandidate` — which probes the SW cache BEFORE spending a network attempt, so an offline device keeps playing from the bands it holds. **A run that is merely short is NOT a reason to block** — it is already a correct neighbourhood, so selection serves it and widens in the background; blocking on "these 50 aren't the corpus's true 50" instead stalls a serve that had a good answer in hand. **`warmBeyondCandidateSpan` loads the shards just OUTSIDE the bands the current 50 occupy** (not the serve rank's neighbours — the window is what must be fillable, so the window is what we widen around) and is SELF-LIMITING with no cap: bands are contiguous in rating and M monotone, so once the band beyond an edge is loaded everything in it is farther than the edge band's own problems, the 50 cannot reach past it, and the prefetch runs dry. Without it the run only grows after a serve has already found it too small, putting a download inside the answer-result overlay — simulated over 300 serves, 3–20 blocking loads against 1. **Only an EMPTY run after expansion serves off-rank**, via `anchorToLoaded` (re-anchor to the nearest LOADED band, keeping the run property) under `enterOffRankServing()` — the user is told. The recently-answered exclusion applies on EVERY path including that one. **Measured-rejected, don't add: predicting the post-answer rank for a correct vs incorrect outcome and preloading those bands.** An answer moves the rank far less than a band is wide (median band ~0.10 ranks), so both outcomes already sit inside the widened span; same blocking count at small drift, worse at large (3.8 vs 1.5), more shards downloaded.

**A NEGATIVE SCORE IS A REAL POSITION ON THE AXIS, NOT "no motif"** — the loading is signed and the linear model reads it as such at both ends. What is NOT symmetric is what the two ends MEAN: a one-sided component teaches only the positive tail, so the negative tail is untaught residual, ships unnamed, and the client stays silent on it (`stats-weaknesses.js` tests each side for its own name, so an axis named on one side only still produces findings on that side). Don't read symmetry into the linear model, and don't read an unnamed negative tail as a missing label.

**There is NO shipped weakness constant of any kind — no ridge prior, no population centre, no EB pass.** `fit_population_constants` fits none and `population-constants.js` asserts none. Both readings stand against a neutral point of the user's own (0 ranks of residual effect; a 50/50 split of their own errors), so there is nothing to length-check against K and nothing that can go stale across an axis refit. **Don't reintroduce a population baseline to "correct" either reading**: the two things it would correct for — how prevalent a motif is at the user's rank, and what the typical player scores — are exactly what makes the reading about the user's RANK rather than their play (see the note above).





`weaknessAxisCov` is length-checked against K like `weaknessSe` and read with **no zero default**: `weakness.js` already substitutes 0 for a non-finite covariance, so a missing entry means the array is STALE against the current K — and under the picked/correct collinearity the cross-covariance is strongly negative and dominates the sum variance, so defaulting it to 0 moves the detection threshold rather than erring on the safe side of it.

*Picked-move fetch.* `pwa/js/picked-embedding.js` Range-fetches the per-cell sidecar. Two entry points:
- `fetchPickedEmbedding({tsumegoId, cellIndex, zipFilename, boardSize})` — live path, called from `game-logic.handleBoardClick` on every move via `state.embeddingsIndexCache` (loaded alongside shard metadata in `problem-loader`). The cell index is `children.indexOf(moveNode)` against the SGF root variations — same order as extraction/packaging, no coordinate recomputation.
- `fetchPickedEmbeddingWithIndexEntry(...)` — backfill path, used by `backfill.js` when iterating shards.

Answer-history entries carry `embedding` (correct-move, from shard `metadata.json`), `pickedCellIndex` (SGF variation index), and `pickedEmbedding` (decoded sidecar fp16).

*Backfill + invalidation.* `pwa/js/backfill.js` runs on app load: reads the **inlined** joint `embedding_meta.json` (version, labels, K/dtype/bytes_per_cell all joint — a build-time `import` via `data-version.js`, not a fetch; see the data-version cache note), then iterates per size — it fills missing `embedding` fields from the lookup-aligned correct-move sidecar (`fillCorrectEmbeddingsViaSidecar`: binary-search the id in the already-fetched lookup.txt lines → fetch that ~130-byte row of `lookup.embeddings.bin`; repeats share a memoized fetch; hosts that ignore Range — wrangler dev AND production Workers assets — cost one whole-file download, cached by the SW and served row-by-row from memory thereafter) and missing `pickedEmbedding` fields by Range-fetching each shard's per-cell bin with the entry's stored `pickedCellIndex` — the per-problem byte offsets live in the zip's `embeddings_index.json`, so the picked fill is the **only** embedding fill that still downloads shard zips (`walkPickedShards`, only shards carrying such a need). The account-adoption synced fill (`fillSyncedHistoryFields`) uses the same sources, and its zip walk covers just the `syncedMove → pickedCellIndex` derivation (needs the SGF) + the picked fill — measured on a worst-case 2k-attempt adoption: 38 zips vs 342 with the sidecar absent (and ~830 before the problem_params/stamp fixes). Entries older than `MODEL_INPUT_HISTORY_LENGTH` get the embedding fields stripped to keep localStorage bounded. Because the weakness model is a single shared instance (see the cross-size merge note), an embedding wipe on *either* size needs no model invalidation and no retrain: the motif readings are a pure function of whatever entries still carry an embedding, so a refreshed or pruned history is picked up on the next read. Refits auto-invalidate: `train_mirt` writes a content-hash `embedding_version` into `axes/axes.npz` (computed over the projection-relevant arrays), `package_for_pwa.py` surfaces it in `pwa/tsumegos/embedding_meta.json`, and the PWA wipes stale embeddings (correct + picked) per size whenever the localStorage-cached version differs. No manual JS edit needed on refit. **The version gate covers the PERSISTED PROBLEM OBJECTS too (`refreshPersistedProblems`), and that is load-bearing rather than tidy:** `challengeProblem` and `previousProblem` are whole problem objects in localStorage carrying the same fit-derived fields (`rating`/`rank`/`slope`/`floor`/`quality`/`embedding`) the history rewrite refreshes, so while they sat outside the gate a standing challenge kept its pre-refit vector across the update and `attempt-recorder` stamped it onto the NEXT attempt of that problem — one row from the previous fit inside a window from this one, on essentially every user, since everyone holds a standing challenge when a refit lands. Nothing downstream can screen that out: a refit can keep K and move every axis under it, so the stale vector is the right length and simply means something else. The refresh mutates IN PLACE, which is what reaches a challenge already painted this session (`displayProblem` sets `currentProblem` to the same object), and re-reads the vector from the same lookup sidecar the history fill uses so the two can never disagree.

Extraction needs ~1.4 GPU minutes per 1k problems on a Quadro M2200 — measured end to end over a full 160k-problem corpus rebuild, so it includes SGF parsing and npz compression, not just the forward pass. The two boards differ by about the ratio of their legal-cell counts (~14/s on 9x9, ~9/s on 13x13), and the rate is FLAT over hours rather than decaying, unlike the ownership sweep — this run is bound by writing ~95 GB, so it never pins the GPU hard enough to throttle. A full corpus is therefore ~4 hours locally and does NOT need remoting; budget disk instead, at ~0.6 MB per 9x9 problem and ~1.15 MB per 13x13 one.

**Ranks are derived client-side from raw ratings; packaging is rank-agnostic.** `package_for_pwa.py` ships per problem the raw `rating`, the raw slope `a_p` and the `floor` — **no rank at all**; shard `min_rating`/`max_rating` are raw too. The rating→rank map `M` is fitted separately into the backend `ratings/`, and `package_for_pwa` — the single writer of `pwa/tsumegos/` — copies that curve across. The client does *all* rating→rank conversion: `problem-loader.js` derives `p.rank = applyM(rating)` on ingest and leaves `p.rating` raw. **Don't reintroduce a baked rank into `metadata.json` — `rating` means raw everywhere.**

**The rank is never clamped.** The kyu/dan ladder is what we LABEL, not a bound: `applyM`/`interpExtrap` extrapolate linearly past both end knots, so problems easier than the weakest knot fall below 30k and the unattempted KataGo-hard tail runs past 9d. Treat it as an unbounded continuous coordinate — don't clamp it, don't read it as a percentile. Clamping lives only where LABELS are built. **`M` is required** — `main.js` awaits `loadRatingRankMap()` at init and aborts if it can't load, with no fallback.

Answer-history entries store `problemRating` (raw), `problemRank` (internal) and `problemSlope` (raw `a_p`). `backfill.js` refreshes all three, triggered by a **single** `ratings_version` (the joint cross-board fit re-rates both boards together, so there is no per-board rating version) **and** by a client-computed `ratingRankCurveVersion`, so a `map_rating_to_rank` re-fit with unchanged ratings still refreshes stored ranks. The version gate and stamp live ONCE in the orchestrator, wrapped around the per-size work loop: stamps are written only AFTER every size's walk has persisted, so **stamp-last = crash-safe** and an interrupted run re-runs idempotently. **Consequence:** a curve-only re-fit publishes through `package_for_pwa` on the cheap path (change detection sees shard inputs unchanged and copies just the curve); a raw-rating change re-ships shards. A change to the *packaging format itself* is NOT captured by the input hash — run `package_for_pwa --force` once after such a code change.

**`M` (rating→rank) maps to a latent CONSENSUS rank; every server INCLUDING EGF is a coupling off it (EGF is NOT special).** The consensus model, the gauge pin, the shape prior, the career-block anchors and the joint time-slope fit are in `docs/methodology.md` §1.12. Operationally: `pipeline/map_rating_to_rank.py` fits the curve, every per-server coupling and the solve-time slope α in ONE objective, and is **production-clean** — config baked as module constants, no experimentation code (that lives in `auxiliary/map_rating_to_rank_dev.py`; the CV harness is `auxiliary/eval_rank_map_cv.py`). Run `pipeline.fetch_database` first; it then needs `ratings/` + `db/d1.sqlite` for median solve time, but neither GPU nor the heavy pipeline.

Outputs, both board keys identical: `ratings/rating_to_rank.json` (`{ratings, ranks}` plus a top-level `time_adjust {alpha_per_log10_min, center_log10_min}`) and `ratings/rank_map.json` (`{server: {our, server}}` knots, **including a real EGF coupling**, not an identity line). **RATINGS ARE TIME-ADJUSTED THROUGHOUT THE MAPPING**, so: **the client headline (onlymove rank) maps the RAW rating through M (untimed); every server translation — EGF among them — maps the TIME-ADJUSTED rating** (`rank-translation.js`). Dropping the dock for the headline is a client display choice. `fit_population_constants` READS α/center through from `rating_to_rank.json` (no separate time fit), and `package_for_pwa` copies both curve files across under the single-writer rule. Measured-rejected, don't re-add: errors-in-variables weighting over each rating's Fisher CI (declaration noise dominates; consistently worse held-out).

**Any accuracy statistic comparing our rank against a DECLARED server rank must be computed on the TIME-ADJUSTED rating — never the raw one.** The couplings were fitted against time-adjusted ratings, so a raw comparison has the two sides in different units and scores nothing the app shows; it fails SILENTLY, because the wrong number is still a plausible one. `auxiliary/check_mapped_vs_declared_rank.py` emits both and they are NOT interchangeable: **`err_server`** — the time-adjusted rank forward-mapped into that server's own units — is what every printed table uses and the only one to quote, while **`err_internal`** (raw, pooled internal units) exists in the `--csv` output only. Measured on one fit the gap is 40%/68% within one/two ranks against 31%/60% raw, and per-server n-weighted Spearman 0.882 against 0.854 — worth about nine points, not a rounding difference. That rho is NOT printed by the script: its definition (per-server, user-count-weighted) lives in `auxiliary/rating_dev/validate_ratings.py`, which needs a held-out split the production trainer doesn't produce, so compute it over the same `--csv`. **These figures are PUBLISHED and go stale on every refit** — `pwa/about.html` carries them in FOUR languages (en/zh/ja/ko), so re-measure and update all four in the same pass as a rank-map change, with declaration and player counts rounded to the nearest ten.

**There is ONE internal rank scale, AGA-style, and `pwa/shared/rank-math.js` owns it.** The convention: **0 is the 1k/1d boundary, every rank is one unit wide, and integers are band EDGES** — 1d = [0, 1), 2d = [1, 2), 1k = [−1, 0), so "2 dan" averages 1.5. It is **AGA-STYLE, not AGA**: real AGA ratings carry a (−1, 1) gap and put 2d at [2, 3), so crossing into that frame stays a real conversion — `agaRatingToRank` (`src/leaderboard.js`) and its pipeline mirror `aga_rating_to_value` (`utils/rating/rank_surveys.py`), one label-preserving ∓1 shift, used by every AGA reader. The module holds `interpExtrap`, `rankToLabel`, `rankLabelToRank` (label → band CENTRE, so the "− 0.5 for the band's lower edge" idiom stays literal), `rankBand` (**FLOOR** — integers are edges), `rankProgress`, and `clampRankBand` (the 30k..9d ladder, for LABELS only — never clamp a rank you compute with). Imported by both the Worker (`src/index.js`) and the client, deliberately: one module, so the server-computed Community rank histogram cannot drift against the client's display. **Don't make a local copy.** The `rating_to_rank.json` key is `ranks` (a stale reader looking for `rank_indices` fails loudly rather than silently double-shifting), and there is no named cold-start rank constant — `state.js` derives all three cold-start slots from `coldStartEstimate()` (see the live-rank note above). Any change to this scale must be label-preserving by construction, verified value-by-value across ratings, (rank, server) pairs, the GoR/AGA tier gates and synthetic users through the real `computeRank` — and shipped behind a state-epoch bump, because every STORED rank changes units and a stale value is not detectably wrong.

**KataGo PyTorch loader requires `.ckpt`, not `.bin.gz`.** `models/kata1-b18c384nbt-...bin.gz` is the binary export the C++ analysis engine reads — not loadable via `torch.load`. The feature-embedding pipeline expects `models/kata1-b18c384nbt-s9996604416-d4316597426/model.ckpt` (extracted from the corresponding `.zip` checkpoint distribution). Don't point `extract_activations.py --ckpt` at a `.bin.gz`; KataGo's training code only goes PyTorch → binary, not the other way.

## Conventions to be aware of

- **There are no tests and no test runner** — no `tests/` directory, no CI. Don't add a "run the tests" step to claims of completion unless tests are actually added, and don't assume a change is covered by anything automated. Verification is manual: for pipeline changes, run the step and check its printed diagnostics; for PWA changes, `npm run dev` and exercise the path in the browser.
- Python code uses absolute imports rooted at the repo (e.g., `from utils.constants import ...`). Pipeline scripts append `PROJECT_ROOT` to `sys.path` defensively.
- KataGo coordinates skip the letter `I` (so cols are `ABCDEFGHJKLMNOPQRST`). SGF coordinates do not. **Every conversion lives in `utils/katago/coords.py`** — `sgf_to_gtp`, `gtp_to_sgfmill_point`, `sgfmill_point_to_sgf`, `gtp_to_xy`, and the two letter/index helpers. Prefer reusing them over rewriting coordinate math, and add a new one there rather than beside its caller.
- `pwa/README.md` has additional context on the PWA's overall structure (sections 1–5: overview, tech stack, project layout, architecture, dev workflow). Read it before substantive PWA edits.
- **For local DB analysis, prefer the binary `db/d1.sqlite` over the raw `db/d1.sql` dump.** Both are produced from `pipeline.fetch_database` and both gitignored. `fetch_database` treats `d1.sqlite` as the **canonical merge target** and keeps both artifacts in sync on every run, so you normally don't import by hand. If you ever need to rebuild the `.sqlite` from a raw dump manually: `{ echo "BEGIN;"; cat db/d1.sql; echo "COMMIT;"; } | sqlite3 db/d1.sqlite` — the `BEGIN/COMMIT` wrapper matters: a full D1 export emits one un-batched `INSERT` per row (~290k for `tsumego_reports`), so without a wrapping transaction sqlite fsyncs per row and the import takes many minutes. **Never pipe the import through `head`/`tail`** — it SIGPIPE-kills `sqlite3` mid-import and silently leaves a partial table. Query the `.sqlite` thereafter (no re-import per session). Note a full `--full` dump only carries the tables that have rows at export time (D1 export drops empty tables), whereas the incremental path's regenerated dump carries every table it discovered remotely (so e.g. an empty `history_refresh_log` is present).
- **Many artifact directories hold 100k+ files** — `tsumegos/9/` and `activations/9/` (~113k each), `tsumegos/13/` and `activations/13/` (~102k each), `axes/per_cell/<size>/` (per-tid files), and shard zips. **Shell globs like `ls dir/*.npz` will silently expand past `ARG_MAX` and report 0** — verified false-negative on `activations/9/`. Use `find <dir> -maxdepth 1 -name '*.ext' -printf . | wc -c` (or `find ... | wc -l` if newlines are safe) to count, and `find ... -exec` / `xargs -0` to iterate. The same trap applies to anything piping a glob into another command. Treat any directory under `tsumegos/`, `activations/`, `axes/`, `attempts/`, `ratings/`, or `pwa/tsumegos/<size>/` as "may exceed argv" by default.
