# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

YoseTsumego / onlymove.net — a Go (Baduk/Weiqi) tsumego pipeline. KataGo generates problems and rates them; the rated set is packaged into zip archives served by a Cloudflare-hosted PWA. There are four cooperating subsystems:

1. **`pipeline/`** — nine executable scripts run in order (see "Pipeline commands" below). Each is a standalone `python -m pipeline.<step>` entrypoint. `package_for_pwa` is the single writer of `pwa/tsumegos/`; there are no side-channel patch scripts — to publish a labels-only or curve-only change without rebuilding zips, re-run `package_for_pwa` (its per-size change detection skips the heavy shard rebuild). Survey-driven rank calibration (`map_rating_to_rank.py`) and population-constant fitting (`fit_population_constants.py`) are board-independent and run outside the in-order pipeline — see the rank architecture note below.
2. **`utils/`** — shared logic: `KatagoController` (subprocess + thread-safe query dispatcher), `KatagoQueries` (analysis-engine wrapper), `ProblemFinder` (move-difficulty heuristics), `add_variations` (SGF tree construction), `models` (KataGo network downloads), `configurations` (global knobs).
3. **`pwa/`** — vanilla-JS ESM PWA built with esbuild, deployed as a Cloudflare Worker. The Worker entrypoint `pwa/src/index.js` handles these HTTP routes — `POST /report` (per-attempt logging; `createdAt` is REQUIRED in the payload — the CLIENT owns the event time (it mints one ms per attempt, stores it as the entry's `date`, and the row is inserted VERBATIM, so row.created_at === entry.date exactly and sync matching is exact) — and the server only sanity-bounds it, REFUSING (never rewriting) with `400 {error, serverNow}` on missing/future(+2min)/stale(−7d) so the client can self-correct once and resend (a silent rewrite would recreate the dup-mint precondition; see docs/client_owned_event_time_plan.md); responds `{serverId, userSeq, digest}` (no createdAt echo) — `serverId` the row id stamped on the matching answerHistory entry (its presence = acked; the id-cursor + digest key) so sync pulls skip the device's own rows; `userSeq` the per-profile attempt count, the **digest sync signal** (a jump past the device's expected seq = another device wrote → pull); see the account-sync note below), `POST /sync` (account sync: pages the user's reports newer than the client's **`sinceId` AUTOINCREMENT-id cursor** — gap-free for rows inserted with a historical `created_at` such as an offline flush — at 1000 rows; every response also carries a `serverSeq`/`serverDigest`/`serverMaxId` digest summary for the cheap in-sync check; an optional `limit` shrinks the page — `limit: 1` is the client's frontier/existence probe. A request without a valid `sinceId` (a pre-redesign client on the retired created_at cursor) gets an empty no-op so it just resyncs on reload — see the account-sync note below), `GET /push/vapid-public-key`, `POST /push/subscribe`, `POST /push/unsubscribe`, `POST /schedule` (recall-reminder schedule; **diff mode** — the client keeps a per-row hour-rounded snapshot in localStorage and sends only changed rows + explicit removals, since each upsert bills the row plus its two partial indexes and replace-all is the heaviest D1 write path; legacy `{schedule}` replace-all still accepted; every call, even an empty diff, bumps `push_subscriptions.last_seen_at`, the cron's mid-session suppression watermark), `POST /rank-survey` (per-server rank declarations → `rank_surveys`), `POST /share-event` (share-link create/open analytics → `share_events`; the client sends user/problem/size and, for opens, `document.referrer`, while the worker stamps the Cloudflare edge geo-IP `country`), `GET /server-stats` (serves the cached community-stats blob — see the server-stats note below) — plus a cron-driven `scheduled()` handler that walks `recall_schedule` to deliver due Web Push notifications **and** recomputes `server_stats` (≥23h old or on a version change), and an SPA fallback that derives board size from `/9` or `/13`. Static assets ship via the `[assets]` binding in `wrangler.toml`. D1 binding `DB` → database `tsumego-reports`, tables: `tsumego_reports` (per-attempt log: `user_id, problem, success, created_at, size, move, time_used, review_time, is_repeat`, plus the per-profile sync-digest columns `user_seq` (attempt count) + `running_sum` (Σ rowHash(id) exclusive prefix), lazy-seeded in the INSERT — see the account-sync note; no `UNIQUE(user_id, problem)` constraint, so repeat attempts produce their own rows; **indexed on `created_at`** — `idx_tsumego_reports_created` — for the server-stats window scan, **and on `(user_id, id)`** — `idx_tsumego_reports_user_id` — for the per-user id-cursor `/sync` scan + the digest's O(1) latest-row lookup (the legacy `(user_id, created_at)` index was dropped with the created_at `/sync` path; on the live D1 drop it AFTER the deploy, never before)), `push_subscriptions` (one row per device — `endpoint` PK, `user_id` indexed — so the recall cron fans each due reminder out to all of a user's devices; per-device throttle + dead-endpoint cleanup, per-account active-session suppression), `recall_schedule`, `rank_surveys`, `share_events`, and `server_stats` (single-row JSON cache, `key='latest'`). Schema lives in `pwa/schema.sql` (idempotent `CREATE … IF NOT EXISTS`); apply new tables/indexes to the remote D1 with `npx wrangler d1 execute tsumego-reports --remote --file=schema.sql`.
4. **`analysis_server/`** — a tiny HTTP server wrapping KataGo for the PWA's analysis fallback when SGFs lack embedded win-rate data.

Plus `auxiliary/` (one-off diagnostics, legacy code; not part of the main flow) and `vast_orchestration.py` (rents Vast.ai GPU instances to run the heavy pipeline steps remotely).

## Pipeline commands

Always invoke pipeline modules through the venv's Python so PYTHONPATH resolves correctly:

```bash
./.venv/bin/python3 -m pipeline.fetch_database        # INCREMENTAL by default: pull only new tsumego_reports rows (by AUTOINCREMENT id) + re-fetch the small tables whole, merge into attempts/database.{sqlite,sql}, sync local D1. --full forces a complete re-download (auto-used when there's no local database.sqlite baseline)
./.venv/bin/python3 -m pipeline.tune_engine <size>    # tune nnMaxBatchSize / numAnalysisThreads in bots/analysis.cfg (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.generate_tsumegos <size>  # long-running generator → tsumegos/<size>/ (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.benchmark_bots <size> # bots solve generated tsumegos → attempts/<size>/ (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.extract_activations   # KataGo trunk activations per problem → activations/<size>/<id>.npz (GPU; resumable); feeds both the rating features (bw_act) and build_embedding
./.venv/bin/python3 -m pipeline.cache_move_features  # build the candidate-move-eval cache (activations/_signal_cache/move_evals_<size>.npz) the rating trainer's move block reads — run before train_rating. INCREMENTAL by default (adds only tids missing from the cache; --force rebuilds all). NOTE: train_rating ALSO reads a sibling AGGREGATE cache — the correct-cell activation vectors `activations/_signal_cache/correct_vecs_<size>.npy` + `correct_ids_<size>.json` (read by utils.rating_features.load_joint_activations) — built by `auxiliary.inspect_activation_signals._build_cache` (also INCREMENTAL). After a tsumego TOP-UP both aggregate caches must be refreshed BEFORE train_rating (extract_activations writes per-problem npz, but these two roll them up); a stale correct_ids silently drops the new problems from the rated set. (The per-problem npz artifacts — activations, per_cell embeddings — are inherently incremental via file existence; only these two roll-up caches needed explicit incremental support.)
./.venv/bin/python3 -m pipeline.train_rating       # STAGED self-consistent cross-board 4PL rating model → ratings/<size>/ (2-phase coordinate descent; 80%-clear rating). PRODUCTION-ONLY: takes NO CLI args (config baked in as module constants; always seed 0 → ratings/); features bw_act+move so run pipeline.extract_activations + pipeline.cache_move_features first; the full experiment surface (joint M0b + staged flags, --stage-plan, --separate-trunks, eval suite, alternative objectives) lives in auxiliary.rating_dev.train_rating_staged (and …_research)
./.venv/bin/python3 -m pipeline.build_embedding       # rating-residualized PCA over activations → embeddings/<size>/
./.venv/bin/python3 -m pipeline.package_for_pwa       # SINGLE writer of pwa/tsumegos/: zip + lookup.txt + embedding_meta.json + copies the rating→rank curve across; change-detects per size (skips unchanged shard rebuilds; --force to override). Reads ratings/.
```

Survey-driven rank calibration and population-constant fitting (both board-independent, not part of the in-order run; need `ratings/` + the `attempts/` DB, no GPU). Both write only to the backend `ratings/`; `package_for_pwa` copies their outputs into `pwa/tsumegos/` (single-writer rule):

```bash
./.venv/bin/python3 -m pipeline.map_rating_to_rank      # rank_surveys + attempts/database.sqlite (timed attempts for the career-block anchors + median solve time) → ratings/{rating_to_rank.json (curve + a top-level time_adjust{alpha,center}), rank_map.json (per-server couplings INCL EGF)}. CONSENSUS model (rating→consensus rank→every server incl EGF; time α fit jointly); anchors are overlapping 2-month CAREER-BLOCK ratings, attempt-mass-weighted, each declaration normalized to total weight 1 (see the `M` note below). BACKEND; package_for_pwa publishes it. Production-clean (no experiment flags; the CV harness that validated the anchors is auxiliary/eval_rank_map_cv.py)
./.venv/bin/python3 -m pipeline.fit_population_constants  # ratings/ 3PL params + attempts DB (+ embeddings/joint/per_problem.csv & rating_to_rank.json for the weakness-model ridge λ) → ratings/population_constants.json (retention/time-bias constants AND weakness_ridge_lambda; the time-adjust {alpha,center} is READ THROUGH from rating_to_rank.json, NOT fit here; BACKEND; package_for_pwa publishes it; the PWA build inlines it into the JS bundle)
```

Run on a remote Vast.ai GPU instead: `python vast_orchestration.py` (no args prints subcommands; only `tune`, `generate`, `benchmark` are remoted — the rest stay local).

## Rating pipeline (combined cross-board MLP-2PL)

The rating backend writes under `ratings/`, and `package_for_pwa` ships it to `pwa/tsumegos/`. The three commands — `train_rating`, `map_rating_to_rank`, `package_for_pwa` — are listed under "Pipeline commands" above.

Key design (validated in `docs/rating_model_comparison_results.md`): a single model `P = σ(a_p·θ_u + d_p)` pooled across 9×9+13×13 with a **shared per-user ability θ**; features are **joint-PCA activations ⊕ common-column bot winrate ⊕ a candidate-move-eval block** (`bw_act` + move; `pipeline.cache_move_features` must build the move cache first). The feature heads are a **prior** (`d_p = diff_mlp(feat) + δ_p`, `a_p = softplus(b0+slope(feat)+η_p)`) and the **human first-time attempts** (the only training target) add per-problem residuals `δ_p`/`η_p` on top — ridge-shrunk toward the prior, so sparsely/never-attempted problems fall back to it (bot data enters only via the features). **The 2PL slope `a_p` is the per-problem discrimination**, shipped **raw** as the per-problem `slope` field (no min-max repackaging, no separate `quality` field). The client uses it two ways: (1) as the per-attempt success-curve slope in its rank estimator (see the rank-derivation note); (2) as the problem-selection weight ∝ the Fisher information the problem provides, `I = a_p²·P(1−P)` — and since selection draws from a difficulty-matched pool (the 50 nearest in rank, all ≈80%-clear) `P(1−P)` is ~constant, so the weight is simply **`a_p²`** (sharp = quadratically more informative; no arbitrary [0,1] range). **Rating = `(logit(0.8) − d_p)/a_p = b_p + logit(0.8)/a_p`** — the ability at which the user clears the problem **80% of the time** (`CALIBRATION_P`, the margin the PWA serves *and* anchors at), NOT the 50%-point `b_p = −d_p/a_p`; winsorized to tame the low-slope tail, shipped as the per-problem `rating`. The slope-dependent 80% correction is load-bearing: a flat low-discrimination problem needs more ability to clear at 80% than its 50%-point implies, so two equal-`b_p` problems differ in true 80%-difficulty — and a monotone rating→rank map cannot recover that per-problem reordering, so it must be built at the rating stage (the consensus mapping re-anchors users' 80%-clear ratings against whatever scalar is shipped, so it stays self-consistent). `map_rating_to_rank` then maps it to the latent consensus rank and writes ONE shared rating→rank curve to both board keys, self-contained (it fits every server coupling, EGF included, itself). Critically it anchors on each survey user's **80%-clear v2-rating** (the same `fit_user_rating` @ `CALIBRATION_P=0.8` the client/`utils.fit_rank_curves` use, pooled across boards), **NOT raw θ**: θ is the 2PL 50%-point (`θ = b_p ⇒ P = 0.5`), so a θ-anchored curve would mis-display every user's 80%-clear rating by ~4.4 ranks. The curve is a shared monotone piecewise-linear fit with a uniform-spacing (linear) prior. The fit is joint (rating→rank + per-server couplings via `fit_joint_shared`), reusing `utils.fit_rank_curves`' stateless helpers (`fit_user_rating`, `ordinal_nll_vec`, …). `package_for_pwa` ships `rating` + raw `slope` per problem; the `rating_model` tag in `embedding_meta.json` records provenance (`"v2"`), and the PWA does not branch on it. Open calibration items: `--lambda-resid` (prior precision) is set by hand, and the corpus hard tail (KataGo-hard, unattempted) extrapolates far beyond the human rank knots. **Production fit = STAGED self-consistent two-phase coordinate descent.** `pipeline.train_rating` is the **production-only** trainer (takes no CLI args; the shipped config is baked in as module constants — there is no argparse, so it always trains seed 0 and writes straight to `ratings/`). Phase 1 fits the per-problem difficulty AND simultaneously **LEARNS a single global slope + global floor + global ceiling** (`--global-stage1`); phase 2 individualizes the per-problem slope + per-problem floor and keeps refitting the global ceiling, while difficulty is held at its phase-1 values by a soft L2 consistency penalty (Adam's per-parameter scale-invariance lets difficulty drift ~0.3 units regardless of the penalty weight; that drift is the joint re-optimization and is fine). The feature trunk is `bw_act` ⊕ the move-eval block with **0.3 dropout uniformly — on each input block (act/bw/move) AND between the trunk's own hidden layers** (0.3 maximizes survey-ρ and held-out flatness and sits at the held-out-LL floor; less dropout overfits). The move-eval block (winning move ⊕ 9 alts' winrate/score) is **ρ-neutral and only marginally better on held-out LL** (≈−0.0006 at the 0.3 trunk dropout); it ships by product decision, not because the metrics demand it. **Learning the globals jointly with the rating auto-finds the self-consistent anchors — no hand fixed-point search, so it stays calibrated as the corpus drifts** (the `--stage-*-const`/`--lapse-init` values are only inits; the globals land near slope ~1.3 / floor ~0.15–0.20 / ceiling ~0.97). The model trains on human attempts alone, with **no mechanistic floor, no hierarchical-slope shrinkage prior, and no bot-anchor examinees** — bot-anchor examinees are deliberately excluded because they steepen the per-problem slope (mean ~1.38 vs ~1.23 human-only) with no held-out-logloss benefit. The ceiling λ is **learned (≈0.03)**, so `fit_population_constants` reads that λ through. Difficulty↔slope coupling leaves the per-problem slope mean ~0.1 above the learned global (intrinsic residual, not a bug). Single-seed in production — multi-seed plus the structure-table checks are the open validation. **The full experiment surface — the joint M0b config, every flag, the held-out / survey-ρ / time-adjusted-ρ eval suite, `--stage-plan` (arbitrary phase orders), `--two-stage`, `--separate-trunks` (per-head trunks for EXACT freezing), `--free-lapse`, and the alternative objectives (even-error DRO, gap-balance, kNN) — lives in `auxiliary.rating_dev.train_rating_staged`** (the production superset; `…_research` holds a non-staged research variant of the same surface), so a test tweak can't break the shipped ratings. The staged structural study (difficulty↔slope coupling, the ceiling's order-dependence vs floor, the fixed-point search) is in `docs/rating_backbone_overfit_and_feature_dropout.md`. Do experiments there; the even-error DRO study (its flatness↔cost knee, and why centering on the per-bin base-rate loss is load-bearing — raw-loss DRO/CVaR chase the aleatoric floor and lose to ERM) is in `docs/rating_model_comparison_results.md` (the `--even-error` section). The PWA reads the same `rating` + `slope` fields regardless of model internals.

## Architecture notes that span multiple files

**Tsumego identity is symmetry-aware and single-solution.** Filenames come from `get_orientation_invariant_hash` (`pipeline/generate_tsumegos.py:154`) — SHA-256 taken over all 8 D4 transforms of the board, with `min()` picking a canonical orientation. The dataset therefore cannot contain two problems that are rotations or reflections of each other; `tsumego_id` is the symmetry-canonical hash truncated to 8 hex chars. By generator design every problem has exactly one correct first move (the `solution` returned by `ProblemFinder.create_problem`); downstream code can rely on the "one canonical answer per problem" invariant.

**Board size — two supported modes: 9x9 and 13x13.** Both ship in production; the PWA picks one from the URL path (`/9` or `/13`) via the SPA fallback in `pwa/src/index.js`, and the D1 `report` endpoint records `size` per attempt. **`/9` and `/13` are entry-only size HINTS, not persistent addresses.** They are read once at boot (`getBoardSizeFromPath` → `resolveInitialBoardSize` in `pwa/js/main.js`); the chosen size persists in state/localStorage thereafter, not in the URL. `cleanUrl()` (lives in `pwa/js/problem-loader.js`, called from `displayProblem`) **collapses the path to `/` and strips `?id`/`?o`/`?recall` whenever a NON-linked problem is painted**, so once you're on a normal problem the address bar is `/`. Do NOT assume a reload leaves the bar at `/9` or `/13`; it does not. **Linked (shared) problems are the deliberate exception: their `?id`/`?o` are KEPT in the address bar for the whole linked session** (`displayProblem` skips `cleanUrl` while `appMode === LINKED`), so that any reload — a service-worker update takeover (`index.html`'s `controllerchange` → `location.reload()`, the most common one; in-app browsers like Instagram hit it when a stale cached SW is replaced by a freshly-deployed version), the `?id`-404 / repeated-load-failure reloads in `problem-loader.js`, the version-mismatch `maybeReload`, or a manual refresh — **re-enters the SAME shared problem at boot** (`parseUrlIntent` reads `?id`) instead of dropping to the standing challenge. The URL is cleaned the instant the user moves on to a non-linked problem (`returnToChallenge`/`advanceToNextProblem` → `displayProblem`). (Before this fix `cleanUrl` ran once at boot and stripped `?id` immediately, so a linked problem could not survive any reload — that was the bug.) On the **pipeline side** there is no single global `BOARD_SIZE` and no in-process dual-size run. The three single-size generation steps — `pipeline.tune_engine`, `pipeline.generate_tsumegos`, `pipeline.benchmark_bots` — take a **mandatory positional `size` arg** (`{9,13}`), which is threaded through the utils (`KatagoQueries(controller, board_size)` owns it as a public `board_size` attribute; `KatagoController.start_engine(model, board_size, …)`, `ProblemFinder` reads `queries.board_size`, and the leaf helpers `construct_initial_sgf(…, board_size)` / `get_child_move(…, board_size)` take it explicitly). The downstream steps (`extract_activations`, `build_embedding`, `train_rating`, `map_rating_to_rank`, `package_for_pwa`) instead iterate `ALL_BOARD_SIZES` and process both sizes in one run — they take no size arg. Artifact directories are keyed by size: `tsumegos/<size>/`, `attempts/<size>/`, `ratings/<size>/`, `pwa/tsumegos/<size>/`. To refresh both sizes, run each generation step once per size (e.g. `… generate_tsumegos 9` then `… generate_tsumegos 13`), then run the downstream steps once. On the remote, `vast_orchestration.py run <step> <size>` forwards the size verbatim (validated locally against `ALL_BOARD_SIZES`).

**On the client, rank + stats + the learned models are merged across sizes; histories, `M` curves, and problem pools stay per-size.** From the user's perspective 9x9 and 13x13 share one rank (front-page label, problem selection, recall eligibility) and one stats page. `pwa/js/state.js` keeps `answerHistory` as ONE unified cross-size array (date-ordered, each entry tagged with `size`; the recent working set in localStorage, the older tail in IndexedDB — see the answerHistory-storage-split note below) plus single shared values (`userRank`, `serveRank`, the recall model `modelParams`/`adamState`, the weakness model `weaknessParams`/`weaknessAdam`/`weaknessSe`/`weaknessAxisCov`); the only per-size persisted bucket is `challengeProblem`. (A `mergeSharedAcrossSizes_v2` migration flattens any legacy per-size rank/model buckets: `userRank = max(rank_9, rank_13)` — a strong 9x9 player immediately gets hard 13x13 problems — and the model buckets are dropped so the shared models retrain.) `getMergedAnswerHistory()` returns that unified array (the WORKING SET), each entry tagged with `size`; the recall and weakness models train from it (they slice the recent window, so the working set suffices). The stats panel (`showDetailedStats`, in `pwa/js/stats-ui.js`) instead awaits `getMergedFullAnswerHistory()` so its charts span the whole career (working set + IndexedDB tail). Pooling is sound because every feature they read is board-independent — `problemRank` is the consensus internal rank (a normalized 0.5 means the same internal rank on either board), and the embedding axes are jointly fit across sizes. Play-time size-awareness is preserved: a recall problem can only be re-shown on its own board, so `getRecallCandidates` takes an explicit `history` (defaults to the active size; the merged union is passed only for stats counts) and `buildRecallSchedule(size)` reads the shared model + shared rank but that size's history. Two consumers do real work to pool: the recall logistic carries a `SIZE_IS_13` fixed effect (9x9 = baseline) whose coefficient ÷ logit-per-rank is the stats panel's "stronger/weaker on 13x13" readout; and the skill decomposition (`rank-decomposition.js`) pools in **internal-rank space** with a per-attempt slope `LOGIT_PER_RATING / |M'(rating)|` (each attempt mapped through its own size's curve), so both sizes share one skill curve without the rank-space slope bias.

**answerHistory storage is split: a unified working set in localStorage, the cold tail in IndexedDB.** `answerHistory` is ~99% of localStorage and on heavy users overflows the ~5MB quota, so `pwa/js/state.js` keeps the most-recent `ANSWER_HISTORY_WORKING_SET` (3000, `constants.js`) attempts — unified across both sizes — as a synchronous localStorage array; everything older is evicted to IndexedDB via `pwa/js/history-store.js` (`appendTail`/`getTail`/`updateTail`/`clearTail`, durable via `navigator.storage.persist()`, every method a safe no-op/empty if IDB is unavailable so play degrades to working-set-only, never breaks). 3000 is the largest hot window the app uses on the *merged* history (the recall-candidate replay warms over the last 3000), so the working set is a superset of every synchronous read: all the existing consumers read `state.answerHistory` (a cached active-size filtered view of the unified array) or `getMergedAnswerHistory()` (the working set) and already slice ≤3000 (`getRecallCandidates` −3000, the models −`MODEL_INPUT_HISTORY_LENGTH`). Only the full-career charts await `getMergedFullAnswerHistory()` (tail ⧺ working set, de-duped by `(problemId, date)`). The write path stays synchronous — `setAnswerHistoryForSize`/`updateAnswerHistory` route through one `reconcileSize` that replaces a size's entries in the unified array and persists; a debounced `evictColdTail()` then appends overflow to IDB **and confirms before trimming** the in-memory/localStorage working set (crash-safe seam: a kill mid-evict leaves a de-duped dup in both, never a gap; an IDB-unavailable append keeps the rows in the working set). `initHistoryStorage()` runs once at boot **after `runMigrations()`** (so the legacy `{9,13}` bucket shape is flattened into the unified array in full *first*, then split) — `main.js` awaits it before the embedding backfill writes, freeing localStorage on a quota-stressed device. The cold tail feeds ONLY the full-career chart (it is all older than `MODEL_INPUT_HISTORY_LENGTH`, carries no embeddings, and no model reads it). A **curve-only** refit recomputes the tail's `problemRank` from its stored raw rating (`backfill.js` via `updateTail`, no shard walk). A **ratings change** instead re-derives the tail's full rating fields from the shards — the SAME shard walk the working set uses, extended to the tail's problem ids — because the tail's ratings are frozen at eviction time, so after a re-rate they go stale AND device-dependent (each device evicted at a different rating era), and the chart plots them: two synced devices' Rank-tab graphs diverged at the start until this. A problem that left the corpus has its rating fields STRIPPED rather than left stale (the attempt stays, rating-less; `flattenAttempts` then drops it from every estimate — front-page rank, chart, weakness, recall all already skip rating-less/embedding-less rows). An account switch `clearTail()`s then re-splits the full pull. Two accepted tradeoffs, both kept synchronous on purpose: a re-draw of a problem last seen >3000 attempts ago is treated as new (repeat-detection scans the working set only), and `timeAdjustDeltaRating` uses the working-set median solve time.

**KataGo binary selection.** `utils/katago_controller.py` reads `KATAGO_PATH` from env, defaulting to `bots/katago` (OpenCL build). `vast_orchestration.py` uploads `bots/katago_cuda` and sets `KATAGO_PATH=bots/katago_cuda` on the remote. Don't hardcode the binary path; rely on the env var.

**`bots/analysis.cfg` is hardware-tuned in place.** `pipeline.tune_engine` rewrites `numAnalysisThreads` and `nnMaxBatchSize` for the current GPU. `vast_orchestration.py`'s `setup` ships the local cfg once but `update` deliberately skips it so remote tuning isn't clobbered. If you edit the cfg, expect the tuner to overwrite your changes.

**`KatagoController` is thread-safe by design.** A single master reader thread fans responses out via per-query `threading.Event`s keyed on query IDs. `send_query` is blocking from the caller's perspective. Multiple worker threads in `generate_tsumegos.py` and `benchmark_bots.py` rely on this.

**Models live outside git.** `models/` is gitignored. `utils/models.get_model(filename)` lazily downloads from `media.katagotraining.org` (or GitHub for 9x9 / human models) on first use. The default model is `MODEL_FULL` (`kata1-b18c384nbt-...`).

**PWA SGF format carries embedded analysis.** Each branch comment in a tsumego SGF is `"<winrate>%/<score>"` (e.g., `"86.4%/3.1"`). Client-side analysis (`pwa/js/sgf.js`) reads this directly; only when missing does it call the server (`pwa/js/api.js` → `analysis_server/server.py`). Don't strip these comments when manipulating SGFs.

**PWA state is centralized.** `pwa/js/state.js` holds the single mutable object; all changes go through exported setters. `state.appMode` switches between `'solving'` (game-logic.js), `'analyzing'` (analysis.js), and `'linked'` (rank-frozen URL-shared problems). Click handling in `board.js` routes by `appMode` (LINKED clicks go through game-logic, same as SOLVING). **Linked-mode attempts are deliberately recorded nowhere:** `sendReport` and `updateUserStats` (`user-stats.js`) both early-return on `state.problemHistory[0]?.linked` (the canonical flag, set in `problem-loader.js`), so a solved shared-link problem reaches neither D1 (`tsumego_reports`) nor local `answerHistory`. Keep the two guards in lockstep on that one flag — a rank-frozen share must not count toward the corpus, anyone's stats, or the server-stats/rank histograms.

**Account sync: the userId IS the account credential; history syncs by append-only cursor.** The 8-char `userId` (crypto-random for new users — `generateUserId` in `state.js`; legacy `Math.random` ids grandfathered) doubles as the account password: the Account dialog (hamburger → More, `account-ui.js`) shows it, and entering another code on a device adopts that account (`account-sync.js switchAccount`: wipes account-derived localStorage, reloads; init's `maybeFinishAccountSwitch` then clears the IndexedDB history tail, pulls the full server history, and re-splits it into the working set + tail before the first problem load). Sync is pull-based over `POST /sync` because `tsumego_reports` is append-only — a cursor fully captures "what changed", no content hash. **The cursor is the AUTOINCREMENT `id` (`sinceId`), not `created_at`**: id is arrival order, so a row inserted with a historical `created_at` — an offline flush, a backfill — still gets a fresh high id and is pulled, the gap the old created_at cursor left. (created_at stays as event time: charts, stats window, recall intervals.) **The local representation is MIRROR-BY-ID**: after the one-time `migrateMirrorById()` (flag `mirrorByIdMigrated_v1`), the device's acked history is a 1:1 mirror of the server's rows keyed by `serverId` — identity is the row id, `serverCreatedAt` is event-time metadata only, and the merge (`mergeRowsForSizeById`) does **no timestamp dedup**: a row is "had" iff its id is in the working set, the tail (`getTailSyncIndex` in `history-store.js`, one cursor pass returning ids + per-stamp content), or the **absorbed-id receipts** (`syncAbsorbedIds` in localStorage) — a server row that claims nothing but is an identical-content copy of an acked entry with the same `created_at` (an accidental double-upload) is held as a receipt id instead of a visible duplicate entry. The digest therefore matches the server **by construction**: server-side duplicate `created_at` rows, which the old timestamp-dedup silently dropped, can no longer open a permanent digest gap (that gap made every dup-carrying active account burn its full daily refresh cap on futile reconciles, forever — the `history_refresh_log` cap-burners of 2026-07). The migration: a cheap path (every acked entry already carries `serverId` — young accounts, post-redesign adopters, fresh/empty devices) just sets the flag; the full path is one raw from-0 pull (counts against the daily cap; `capExceeded`/network failure → flag unset, retried next boot) followed by a pure rebuild (`buildMirror`) — match locals by id → exact stamp + identical content → fuzzy claim; absorb identical twin rows as receipts; **drop** unmatched local copies of attempts the mirror already holds (the rescue-era stale duplicates whose re-upload is exactly how the server dups were minted on 2026-07-07: the legacy merge's stamp-dedup preempted the fuzzy claim when the acked twin's stamp sat in the cold tail, so the outbox judged the un-acked copy "provably absent"); unmatched reportable locals stay as the outbox. Un-migrated devices keep the legacy timestamp-dedup merge (`mergeRowsForSize`) until their migration completes; that legacy merge + the migration code are removable on the normal client-update schedule. Invariants in `account-sync.js`: (1) the cursor advances **only from pulls**, never from this device's report acks; (2) own rows are recognized on pull by their **id** — `/report` returns the row id and `recordReportAck` stamps it (serverId presence = acked; devices still on the legacy merge also store the ISO stamp, their dedup key); ack-less (offline) entries are claimed EXACTLY for client-time-era rows (created_at === date by construction) with the greedy ±10-min fuzzy match kept only for pre-CLIENT_TIME_ERA_MS edge-stamped rows — on the id-first path the claim runs for EVERY un-held row, **never preempted by a timestamp match**; (3) the steady-state pull is **pure id-cursor** — a one-time, flag-gated `migrateIdCursor()` (subsumed by `migrateMirrorById`'s full path, still run first so the cheap path lands with a cursor) brings a device that only has a legacy `created_at` cursor onto `cursorId` by probing the frontier (a `limit:1` /sync that learns `serverMaxId` without a full pull); the digest backstop heals any gap, and a fresh/empty account just falls back to a cheap from-0 pull. Only an account switch pulls from the beginning (`fromStart`). A cheap **digest backstop** rides every pull: the response's `serverSeq`/`serverDigest` (user_seq + Σ rowHash(id)) are compared to the device's local acked-row count + `Σ rowHash(serverId)` (working set + cold tail + absorbed receipts), and a gap the incremental pull couldn't close escalates to a full reconcile. Merged rows become skeleton entries; `fillSyncedHistoryFields` (`backfill.js`) fills ratings from `problem_params.bin`, correct-move embeddings from the lookup-aligned sidecar, and derives `pickedCellIndex` from the reported move for wrong attempts whose coordinate is canonical: **the reported `move` is in the canonical orientation-0 frame since `CANONICAL_MOVE_ERA_MS` (2026-07-09)** — `buildReportPayload` inverse-transforms the click through the served orientation — so repeats round-trip too from that era on; older repeat rows are served-frame (randomly reoriented, unrecoverable) and stay skipped, while older non-repeats were always served at identity and still work. The front-page rank is the **linear-information window MLE** (`estimateWindowRank` in `rank-decomposition.js`) — a **pure function** of the recent first-time history: a positionally-weighted 4PL Newton fit over the last `WIN_CAP`=500 attempts, warm-started at the prior rank, R clamped to a wide [-15, 45] index range (so sub-20k kyu still extrapolates; the clamp is a numerical guard, not a display floor). The per-problem slope `a_p` enters through the Fisher information, so a sharp problem pins the rank harder; `serveRankIndex` adds an uncertainty-scaled UCB bonus (`WIN_UCB_K`·max(0, se−se_floor)) that problem SELECTION uses while display uses the raw `rankIndex`. **`se_floor` is RANK-DEPENDENT, not a constant** (`localSeFloor` in `rank-decomposition.js` → `seFloorForMeanSqSlope` in `rank-window.js`): it is the irreducible SE a full at-rank window would leave, `1/√(WIN_PRIOR_INFO + ((WIN_CAP+1)/2)·0.16·⟨slope²⟩)`, where `⟨slope²⟩` is the mean squared rank-space success-curve slope of the ≤50 corpus problems nearest the estimate **already loaded** on the active size (no fetch on the hot path; the selector's shard loading keeps the pool warm; `slope²` is evaluated only on those 50). Flat-curved kyu problems carry so little rank information that even a full window floors at ~1.3 stones (vs the old constant 0.35, which implied a slope only dan problems reach — leaving kyu users perpetually served ~1 stone above rank and never converging); sharp dan curves floor near 0.3. So the bonus collapses to the user's OWN rank at convergence on every part of the ladder. When nothing is loaded near the rank yet (Worker, or a client before any shard loads) it falls back to the constant `WIN_SE_FLOOR` — harmless since se dominates the bonus that early. The Worker's `estimateWindowRankFromFlat` (leaderboard) passes no floor callback, so it is unaffected. Because the estimate is a pure function of the merged recent history, device adoption and an incremental foreign sync are the **same operation** — recompute from scratch; there is no loop state to warm and no anchor to recover. `retrainAfterMerge` (`account-sync.js`) has three modes: `adopt` (account switch) re-fits over the new account's full merged history seeded from the data (the prior account's rank is irrelevant); `feed` (ongoing merge) re-fits warm-started from the current rank; `reconcile` (one-off local backfill) leaves the rank untouched (the merged rows are ancient). The recompute runs **silently** (no overlay), so the next live answer's reported rank change is that tsumego's effect alone — a freshly-synced foreign batch moves the rank between problems, never inside the shown delta. Every device sees the same multiset of recent attempts, so they converge to the same rank regardless of how the attempts were batched. After every merge, `retrainAfterMerge` also fires `refreshShownProblemAfterSync` (`problem-loader.js`) — and the tab-visible resume trigger fires it on EVERY resume, merge or not, since a recall can enter its window from time alone while the tab was hidden. It re-runs the NORMAL problem-presentation selection (a due recall wins, else the standing challenge), so a problem solved on another device is swapped off screen and a newly-due recall can appear; an actual swap goes through a GREY `fadeOverlay` with a localized "Problem updated" notice (grey deliberately — white/red are the correct/wrong answer cues). The standing `challengeProblem` is kept by default, so sync can never dodge a served challenge — recalls only delay it; the single exception is that the user completed that exact problem on another client (now inside the recent-repeat window, `challengeAlreadyAnswered`), which makes it illegal to serve, so only then is it swapped for a freshly selected one. The refresh touches the board only when a problem sits idle in SOLVING mode (never mid-answer, in review/analysis, or over a linked problem), and skips the repaint when selection lands on the problem already shown (no timer reset, no recall re-orientation). (This replaced an earlier momentum-loop design — `momentum-rank.js`, hybrid replay, `feedAttemptsThroughLoop` — entirely; only a one-time momentum→window migration remains (`maybeInitWindowRankOnce` in `migrations.js`, called from `main.js`).) Pulls run on load, tab-visible, and the `online` event — **unthrottled** (an up-to-date incremental poll reads ~0–1 D1 rows via the user-id index, so a session resume merges — and can refresh the shown problem — immediately; overlapping triggers collapse via the in-flight guard, and only the outbox's full-pull flush keeps a throttle); **active sessions need no polling at all** — every `/report` response carries `userSeq` (the per-profile attempt count), and `checkSyncSignal` triggers a debounced pull when it lands past the device's expected `lastSeq + 1` (= another device wrote in between). An up-to-date poll and the latest-row digest summary read ~0–1 D1 rows **via `idx_tsumego_reports_user_id`, which must stay in place**. Known gaps: pre-2026-07-09 repeats' picked moves and the ignored-problems list don't round-trip (linked-mode attempts are recorded nowhere — see the PWA-state note above — so there is nothing to round-trip). **Durable offline outbox (`flushOutbox`, permanent — `POST /report-backfill`):** any attempt recorded locally but never acked (offline / failed `/report`, or a pre-2026-05-15 `PER_ATTEMPT_ERA_MS` one-row-per-problem gap) is eventually uploaded so it reaches the server and every device. Runs on load / tab-visible / `online` whenever un-acked entries exist (a cheap no-op otherwise, 30-min throttle + the server daily full-pull cap): a COMPLETE reconcile pull claims rows the server already has (the fuzzy claim relaxes `is_repeat` pre-era), then the provably-absent remainder is uploaded **with its recorded event time** (historical `created_at` — the id cursor still propagates it; old rows stay out of the server-stats window). `/report-backfill` lazy-seeds `user_seq`/`running_sum` and RETURNs the ids so the client stamps `serverId`. `HISTORY_BACKFILL_DONE_KEY` is set whenever the backlog is clear — the `ui.js` gate that the device's history is safe to adopt elsewhere. (The round-2 `/report-enrich` handler + client routine, the `prevCreatedAt` piggyback, the legacy created_at `/sync` path, and `idx_tsumego_reports_user_created` were all **removed** in the post-rollout cleanup. A request without a valid `sinceId` now gets an empty no-op, so a not-yet-reloaded old bundle just resyncs in full on reload.)

**Worker-version-driven graceful reload.** `pwa/build.mjs` writes `pwa/src/version.js` so the Worker imports the same hash the client gets via the esbuild `define`. Every `/report` response stamps `X-App-Version`; if it differs from the client's `APP_VERSION`, the client sets `state.reloadPending`. `maybeReload` fires from `setAcceptClicks(true)` only when `appMode !== ANALYZING`, so the refresh always lands between problems — never mid-review. New JS-side features that depend on the Worker version (e.g. embedding/ratings backfills keyed by content hashes shipped in `embedding_meta.json`) ride this reload signal. **`computeVersion()` folds a hash of every inlined data file (`INLINED_DATA_FILES` — `embedding_meta.json` + the curve/rank-map/population JSONs) into `APP_VERSION`** so the reload signal moves on a data-only re-ship: `pwa/tsumegos/` is **gitignored**, so a git-HEAD-only version would be blind to a `package_for_pwa` re-ship from the same commit (the original cause of the cross-device staleness — see the data-version note).

**Served data files are cache-busted by a content `data_version`, not `APP_VERSION`; `embedding_meta.json` is inlined.** The bug this fixes: data files were fetched `?v=${APP_VERSION}` and cached **cache-first by URL** (`sw.js`), but `APP_VERSION` was `git rev-parse HEAD` while the served data (`pwa/tsumegos/`) is **gitignored** — so a `package_for_pwa` re-ship from the same commit served a **stale** `metadata.json` indefinitely, and a device could stamp the current `ratings_version` while its per-attempt `rating`/`slope`/`floor` came from an older shard set (the gate then skipped forever → two devices on one account rendered different rank graphs). The fix is a content-addressed chain rooted in **one inlined manifest**: (1) `package_for_pwa` writes `data_version = hash(metadata.json files)` into `embedding_meta.json` (covers shards transitively — each `metadata.json` lists every shard's content-hash filename); (2) `embedding_meta.json` is **inlined into the JS bundle** via `pwa/js/data-version.js` (`import`, dropped from dist by `DIST_DEAD_FILES`) — it can never be served stale, and `DATA_VERSION` is read synchronously from it; (3) the only query-busted fetches — `metadata.json` and `lookup.txt` (`problem-loader.js`, `backfill.js`) — use `?v=${DATA_VERSION}`; shard `.zip`/`.embeddings.bin` are already content-addressed by filename (NOTE: Workers static assets answer Range requests with **200 + the full body** — no 206s, cached or not, verified in production — so the `.bin` "Range" fetchers download whole files, slice the requested bytes client-side (`sliceRangeResponse` in `picked-embedding.js`, which also rejects a 206 whose Content-Range offset mismatches), and let the SW cache the full 200 like any asset; `pwa/_headers` (copied to dist by the build) additionally gives `/assets/*` immutable and `/tsumegos/*` + `/lookup.txt` 1-day browser cache-control — safe because the assets layer is deploy-consistent (per-deploy manifest, content-hash blobs; header changes verified to appear instantly across deploys even on cf-cache-status HIT responses) and all fixed-name fetches rotate their `?v` cache key with `data_version`); the curve/pop-constant JSONs are inlined. `DATA_VERSION` is stamped into `sw.js` too so the runtime-cache prune keeps `?v ∈ {VERSION, DATA_VERSION}`. **`data_version` (cache freshness) is deliberately separate from `ratings_version`/`embedding_version` (backfill gate):** a ship that only ADDS tsumegos bumps `data_version` (new shards → new `metadata.json`) but not `ratings_version`, so new problems become serveable **lazily** with no history walk; a ratings change bumps `ratings_version` and triggers the **immediate** re-derive. The Worker's server-stats reads `metadata.json`/`lookup.txt` by **fixed path via the `ASSETS` binding** (server-side, no SW, no `?v`), so it always sees current dist and is unaffected. Devices already corrupted by the old cache (stale per-attempt `rating`/`slope`/`floor` under a now-*matching* `ratings_version` stamp) heal through the **standing mechanism, not a bespoke one-time migration**: the deploy that ships this cache fix is itself a data ship that re-rates the corpus, so `package_for_pwa` writes a NEW `ratings_version` — every device's stored stamp then differs from the server's and the normal `ratingsChanged` gate re-derives on the next load. (A hypothetical code-only deploy that left `ratings_version` unchanged would leave a corrupted device stuck until the next genuine ratings change — but the fix shipped alongside one by construction, so no `BACKFILL_REPAIR_EPOCH`-style migration is needed.)

**Server-wide "Community" stats are a cached, read-cost-sensitive D1 aggregation.** `GET /server-stats` serves a single `server_stats` row (`key='latest'`, JSON blob) aggregating the **preceding 7 days** of `tsumego_reports`. `computeServerStats` (`pwa/src/index.js`) runs **one** window query (`WHERE created_at >= ?`) and does all bucketing in JS — totals, daily activity, by-size split, solving/review time histograms (10s buckets capped at 600s, but **bucketing each user's *median* time, so the histogram counts users, not attempts** — heavy users don't dominate; for review time, which is **cumulative across a problem's repeats** (each repeat re-reports the running total), only the last instance per (user, problem) is kept before taking the median, else the running total double-counts), a **recall-time** distribution (per user, the *median* over problems of the novel→first-repeat gap — from the first in-window non-repeat attempt to the very next attempt on that problem, **≥6h** (shorter gaps are ignored entirely), into hardcoded `6h–1d / 1–2d / 2–3d / 3–4d / 4–5d / 5d+` day bins; only gaps whose novel attempt *failed* count, because the spaced-repetition interval lengthens with each success and isn't comparable), a per-user attempts-per-active-day distribution, and an **answer-derived** rank histogram (NOT self-reported `rank_surveys`): per active user, the mean internal-rank of their last-7-days **first-time** attempts — sound because problem selection serves difficulty-matched (~80%-clear) problems near the user's rank, so the served set centers on it. Each problem's coarse rating is the midpoint of the shard it lives in (`lookup.txt` resolves problem id→shard hash; per-size `metadata.json` gives that shard's `min/max_rating`), mapped to a rank index via `M` (`rating_to_rank.json`); `computeAnswerRankHist` fetches these via the `ASSETS` binding. Users with `< MIN_RANK_PROBLEMS` (10) distinct first-time problems are dropped; ordered weakest→strongest. **D1 bills rows read, so `created_at` MUST stay indexed (`idx_tsumego_reports_created`)** — without it every `created_at >= ?` is a full-table scan of all history that blows the daily read quota. Keep the one shared window scan; don't split this back into per-metric queries. Freshness: the blob is stamped with `APP_VERSION`; `handleServerStats` recomputes lazily on a version mismatch and returns `Cache-Control: no-store` (otherwise Cloudflare edge-caches the blob; the client also fetches `/server-stats?v=APP_VERSION`); the hourly `scheduled()` cron recomputes on version-mismatch OR ≥23h age. Rendered by `buildServerStatsPane` (`stats-ui.js`) as the Community tab.

**Write endpoints are guarded by two cheap, in-Worker abuse/quota layers plus an external WAF rule.** A spoofed/garbage `/report` (or `/schedule`, `/rank-survey`, `/share-event`, `/push/*`) doesn't just hurt integrity — the INSERT spends D1 write quota, and until purged the row inflates every server-stats `created_at >= ?` window scan for 7 days (read quota, the exact thing `idx_tsumego_reports_created` fights). So writes are defended *upstream* of D1, cheapest-first: (1) an **outer Cloudflare dashboard WAF rate-limiting rule** (account config, **not in the repo** — documented in `wrangler.toml`; 100 POST/10s per IP matching **ALL POSTs by method** — no path list, so every write endpoint incl. new ones like `/register` is covered automatically, nothing to add per-endpoint — blocked requests never invoke the Worker = zero Worker+D1 cost); (2) **per-IP Workers rate-limit bindings** (`RL_REPORT` 100/60s for the high-volume `/report`, `RL_WRITE` 50/60s shared by the rest), declared as `[[unsafe.bindings]] type=ratelimit` in `wrangler.toml` and checked in the `fetch` dispatcher **before any handler touches D1** (`rateLimited()` keys on `CF-Connecting-IP`, **fails open** on a missing binding or limiter error so a misconfig never drops a legit write); (3) **in-memory format validation** in each handler (no D1 reads) — `isValidProblemId` (`^[0-9a-f]{8}$`, the symmetry-canonical hash) and `isValidUserId` (`^[A-Za-z0-9_-]{1,40}$`) reject malformed identity fields before the INSERT. Limits were calibrated from the production dump (heaviest real user ≈24 reports/60s incl. review re-reports, p99.9=20), giving ~4× headroom for NAT'd shared IPs. **Deliberately format-only** — we don't check the problem id against the real corpus (that needs a bundled set/Bloom filter); the rate limiter bounds valid-looking spoofs. Two consequences: any **deploy smoke test must POST a real 8-hex `problem` id** (a free-form marker is rejected with 400), and `pipeline.fetch_database` is **unaffected** — `wrangler d1 export` hits `api.cloudflare.com` with an API token, a different hostname than the `onlymove.net` zone the WAF guards (the binding limiter never runs for it either). Activating any of this needs a manual `npm run deploy` (+ the manual WAF rule); there's no auto-deploy.

**`pipeline.fetch_database` is incremental by default and read-cost-sensitive.** D1 bills rows read, and `tsumego_reports` is ~290k rows (>99% of the DB) while every other table combined is <1000 — so re-exporting the whole DB each run would waste almost all of those reads. The default path pulls **only new `tsumego_reports` rows via `WHERE id > MAX(local id)`** (`id` is the table's `AUTOINCREMENT` PK), which the PK index serves reading just the matching rows, and re-fetches every *other* table whole (cheap). **The cursor MUST be `id`, not `created_at`:** the PWA→D1 backfill (`POST /report-backfill`, see the account-sync note) inserts historical attempts with their *client* `created_at`, so a `created_at` cursor would silently skip those backfilled rows even though they were just inserted — whereas `AUTOINCREMENT id` always increases with insertion order, catching them. `tsumego_reports` being append-only (no `UNIQUE`, never UPDATEd/DELETEd) makes the `id` cursor provably gap-free: after a complete pull we hold the contiguous prefix `[1..N]`, and all new rows are `> N`. The fetch is **schema-tolerant and never hardcodes the table list** (except the one name `tsumego_reports`): it discovers tables from the remote `sqlite_master`, full-refreshes each (drop + recreate from the remote DDL + refill), and only if `tsumego_reports`' column set drifts does it re-pull that table whole. Implementation: `attempts/database.sqlite` is the **canonical merge target** (rows fetched via `wrangler d1 execute --remote --json`, inserted parameterized — zero escaping bugs), then `attempts/database.sql` is **regenerated from it** in a quoted-table-name + positional-`VALUES` form that every `.sql`-parsing consumer in the repo accepts (some require the quoted name, others forbid a column list — this form satisfies both). The `attempts/` artifacts are read-only as far as the pipeline is concerned; the **wrangler dev (local) D1 is the read-write one** (the PWA is tested against it and scribbles disposable rows into it), so each fetch simply **resets it to the remote state by `shutil.copyfile`-ing `database.sqlite` straight onto the miniflare D1 file** (`.wrangler/state/v3/d1/miniflare-D1DatabaseObject/<hash>.sqlite`, the one that isn't `metadata.sqlite`) and deleting its stale `-wal`/`-shm` sidecars — discarding local test writes on purpose, and far faster than a wrangler reimport (verified: D1 read/write still work; its internal `_cf_*` tables aren't required). Stop `npm run dev` before fetching — overwriting the file under a live workerd corrupts its view. The wrangler-import path (`update_local_d1`) survives only as the first-run fallback that *creates* a not-yet-existing local D1. `--full` forces a complete `wrangler d1 export` + SQLite rebuild (also auto-used when no `database.sqlite` baseline exists). Still WAF-unaffected — both `d1 export` and `d1 execute --remote` hit `api.cloudflare.com`, not the guarded `onlymove.net` zone.

**The detailed-stats modal is tabbed; its charts size to the viewport.** `showDetailedStats` → `showStatsModal(tabs)` (`stats-ui.js` holds the stats/chart rendering; `model.js` holds only the numeric recall model + stats computation; the dependency is one-directional, stats-ui→model) renders Summary / Weaknesses / Rank / Time / Community pages (a pane with no content is dropped, and the tab bar is omitted when only one remains). The hamburger menu (`index.html` + `updateMenuItems` in `ui.js`) is grouped into Practice / Review / More categories; the Review group (share, ignore) shows only in analysis mode.

**Feature-embedding recommender (per-component weakness mining).** Per-cell, not per-problem: every legal first-move cell gets its own K-dim embedding, so the system can score both the **correct** move (a property of the position) and the move the user **actually picked** on a wrong attempt.

*Extraction* — `pipeline/extract_activations.py` runs a vendored PyTorch copy of KataGo b18 (`utils/katago_vendor/`, bootstrapped via `utils/katago_torch.py`) and captures the post-skip-add output of all 18 residual blocks (18 × 384 = 6912 floats) **at every legal cell**. Output: `activations/<size>/<id>.npz` with `candidates (n_legal, 6912) fp16`, `xys (n_legal, 2) int32`, `correct_idx () int32`.

**Row order is board-scan order (sorted by `(y, x)`), NOT SGF-variation order, and the cell set is a *superset* of the SGF's root variations.** `extract_activations.process_one_sgf` enumerates every legal cell for the player to move (the color of `variation_nodes[0]`) in scan order and records a `correct_idx` pointing at the correct move's scan position (non-zero in general; e.g. 13×13 `00000f4c` has `correct_idx=38` — verified byte-for-byte that a re-extraction reproduces the on-disk corpus). Do not instead walk the SGF's pruned variations in document order with `correct_idx=0`: that ships a non-superset cell set and does not match the on-disk corpus. Two consequences every downstream consumer must respect:
  - **Pick the correct row by `correct_idx`, never positionally.** `build_embedding._load_correct_vec` does this (`build_embedding.py:102` → `candidates[int(correct_idx)]`); do not assume row 0.
  - **The npz embeds every legal cell; SGF root variations are a pruned subset, plus the SGF carries a `pass` variation the npz never embeds.** So npz ⊇ {SGF non-pass variations}: every move a user can actually click is embedded (no picked-move ever misses), but ~10% of problems have extra embedded cells with no SGF variation, and 100% have a `pass` that is not embedded. Map cells by `(x, y)` coordinate, not by index, when crossing the npz↔SGF boundary.

*Joint embedding fit* — `pipeline/build_embedding.py` fits a joint PCA across all configured sizes on the **correct-cell row only** (residualize per-feature on `[rating, size_is_13]` jointly, z-score, randomized SVD with K=64, then standardize component scores to unit variance). **Then by default rotates the K-dim subspace with FastICA using a `skew` contrast** (`_skew_contrast`, `G(u) = u³/3, g(u) = u²` — the 3rd-cumulant objective). **FastICA warm-starts from the prior fit's unmixing** (`--ica-warm-start auto`, the default): `compute_ica_warm_start` maps the saved `ica_unmixing` into the new PCA-whitened basis and passes it as `w_init`, so the rotation converges back to the same axes unless the data moved enough to relocate them — refits are reproducible (verified: identical data → 1-iteration convergence, all axes align at 1.0) rather than reshuffling the low-skew tail per seed, which also spares the PWA needless embedding-cache wipes. `--ica-warm-start off` forces random init. After convergence, axes are sign-canonicalized so skewness is non-negative, which makes the **positive tail the heavy tail that concentrates the motif and the negative tail Gaussian baseline by construction** — i.e. negative scores don't represent an "opposite motif," they represent "no motif present." That asymmetry is the reason the recommender, the `labels.json` curation, and `inspect_extreme_problems.py` all treat the positive side as the only meaningful direction. `--rotation none` (raw PCA) and `--ica-fun {logcosh, exp, cube}` (symmetric contrasts) are also supported; under those the two sides would be symmetric, but production uses skew. Output to `embeddings/joint/{pca.npz, per_problem.csv, explained_variance.csv, extreme_problems.json, labels.json}`. `per_problem.csv` carries `size` so packaging filters by it. After the fit, `write_per_cell_projections` fans out the projection (PCA + ICA rotation) to **every cell of every problem** in parallel workers and writes `embeddings/joint/per_cell/<size>/<tid>.npz` with `embeddings (n_cells, K) fp16` + `xys (n_cells, 2) int32`. `labels.json` (v3 = `{version, _doc, bank, components}`) carries human motif labels; under skew-ICA only the positive tail carries a motif (the negative tail is Gaussian baseline), so there is no `negative` side. `components` is keyed by current PC index — `components[k].positive` / `positive_i18n` are what ship and what the PWA reads — and `bank` is a `motif_id → {positive, positive_i18n}` registry that may hold **more motifs than K** (motifs absent from a given fit persist for a later one). **Labels survive refits via an anchored bank, not transitive remapping**: each motif owns a *frozen* direction in the sibling `embeddings/joint/label_anchors.npz` (a `motif_id`-keyed unit vector in the 6912-dim residual feature space), and on each `build_embedding` run `update_labels_and_bank` matches every new axis to the nearest anchor by signed cosine (≥0.8, greedy 1-1). Matching compares against the frozen anchor — *never* the previous refit — so labels can't drift transitively across many refits. Phase 1 banks the prior run's human labels (text lifted into `bank[motif_id]`, anchor direction frozen from the prior fit's loadings the first time a motif appears, refreshed text thereafter); clearing a component's `positive` to null while its `motif_id` persists (used nowhere else) **retires** that motif from bank + anchors. Editing `components[k].positive` relabels; filling `positive` on an unmatched component adds a label. To publish hand-edited `labels.json` changes (text or `positive_i18n`), re-run `package_for_pwa` — it reads `labels.json` straight into the joint `pwa/tsumegos/embedding_meta.json` on **every** run, including the cheap skip-the-shard-rebuild path (so a labels-only change costs nothing beyond the meta rewrite, no rezip).

*Packaging* — `pipeline/package_for_pwa.py` ships two things per shard, plus one corpus-wide sidecar:
1. The correct-move embedding (length K=64) joined into the shard's `metadata.json` under `embedding` — what `weaknessScore` reads against any candidate problem.
2. A sibling `<hash>.embeddings.bin` per shard (fp16, K floats per cell, all problems concatenated **in SGF root-variation order**), plus an `embeddings_index.json` inside the zip mapping `{tid: {offset, n_cells}}`. This is the picked-move sidecar: the PWA Range-fetches `bytes=offset+i·bytes_per_cell..offset+(i+1)·bytes_per_cell-1` to recover the embedding at cell index `i` of a tsumego, where `i = children.indexOf(moveNode)` over the SGF root variations.
3. `pwa/tsumegos/lookup.embeddings.bin` — the **lookup-aligned correct-move sidecar**: row i is the K-dim fp16 correct-cell embedding of the problem on `lookup.txt` line i (lookup is id-sorted and spans both sizes, so the line index — which the client already has from its lookup.txt binary search — doubles as the row address; no keys, no offsets). Emitted like `problem_params.bin` (`emit_correct_embeddings`, every non-sentinel run, straight from `per_problem.csv` + the final lookup.txt — no shard rebuild), and folded into `data_version` so it can never cache-desync from lookup.txt. **Row alignment is the contract**: it must be written after the run's final lookup.txt; the client additionally verifies the file size against its line count via `Content-Range` and poisons the sidecar for the session on mismatch. Ids missing from `per_problem.csv` get an all-zeros row the client treats as absent. This is what lets the backfills fetch a correct-move embedding as one ~130-byte Range request instead of downloading the ~2MB shard zip whose `metadata.json` carries the same vector.

   **The bin order is set here, not upstream.** Because the npz is scan-order and a superset (see *Extraction*), `package_for_pwa.project_cells_for_problem` re-parses each SGF and rebuilds the per-cell rows in SGF-variation order via an `(x, y) → npz row` map — dropping the extra scan-order cells, while the `pass` variation (never embedded) gets an **all-zeros placeholder row** so bin row i == SGF child index i exactly (`BIN_FORMAT_REV` 2; rev 1 skipped the pass, which shifted every row after a non-last pass off by one against the PWA's `children.indexOf` — and the pass is not last in ~half of 9x9 / ~3/4 of 13x13 problems). The rev is folded into the **shipped** `embedding_version` (`shipped_embedding_version` = pca-content hash + `-b<rev>`), so a bin-layout change wipes/re-derives clients' stored picked embeddings through the standing version gate and rebuilds shards without `--force`. This reorder is **load-bearing**, not defensive: the PWA indexes the bin by SGF-variation position, so shipping raw scan order would silently return the wrong cell's embedding for every picked move. The sgfmill parse dominates packaging time, so shard building is parallelized across processes (`--workers`, default `os.cpu_count()`); `--no-sgf-reorder` skips the parse but is correct **only** if the npz has been pre-reordered into SGF-variation order upstream (it has not, on current `build_embedding` output).

The joint `pwa/tsumegos/embedding_meta.json` carries `K`, `dtype` (`float16`), `bytes_per_cell` (so the PWA can decode the bin without guessing), `embedding_version`, and `labels` (variance curve, extreme problems, kurtosis, etc. live in `embeddings/joint/` locally as inspection artifacts and aren't shipped).

*PWA model — augmented weakness regression.* `pwa/js/weakness.js` trains a logistic regression with **2K+2 params**:
```
P(correct) = σ(α + γ·rating
                + Σ β_correct[k] · correct_emb[k]
                + Σ β_picked[k]  · picked_emb[k])
```
The `γ·rating` term is actually `γ·problemRank` (the board-independent internal rank), and the model is a **single shared instance trained on `getMergedAnswerHistory()`** (both sizes pooled — the embedding axes are joint, so this is well-posed); see the cross-size merge note above. `β_correct[k]` is the position's effect (problem's correct-move embedding); `β_picked[k]` is the user's choice effect (whatever they actually clicked). On correct attempts `picked_emb = correct_emb`, so those rows inform the sum `β_correct + β_picked` jointly; wrong attempts with a sidecar-fetched `pickedEmbedding` disambiguate the two. Recommendation scoring uses `(β_correct + β_picked)` against the candidate's correct-move embedding — algebraically equivalent to assuming "user will pick correctly" on the unseen problem. `problem-loader.js`'s `selectProblem` weights candidates by `quality · exp(WEAKNESS_TEMPERATURE · weaknessScore)`. Because the embedding is skew-ICA-oriented (positive tail = motif present, negative tail ≈ baseline), the recommender is effectively asymmetric in practice: large positive scores along an axis where the user is weak get mined; large negative scores don't represent an "opposite motif" the user is good at, just baseline problems with no motif. Don't read symmetry into the linear model. Ridge-regularized with a **per-axis prior** (`β_k ~ N(0, 1/λ_k)`, `λ_k` applied to both the `β_correct[k]` and `β_picked[k]` slots): the primary is `weakness_axis_lambda` in `population_constants.json` — a length-K vector fit by **empirical Bayes** in `pipeline.fit_population_constants` (EM with a Laplace E-step over per-user MAP fits estimates the between-user variance `τ_k²` of each axis's weakness coefficient; shipped as `λ_k = 2/τ_k²` so the client's implied prior on the identified sum `β_correct + β_picked` is exactly `N(0, τ_k²)` — axes users genuinely differ along get a loose prior, no-signal axes stay pinned). The scalar `weakness_ridge_lambda` (held-out-CV fit, ≈200) remains as the fallback when the vector is absent or its length mismatches K (an embedding refit without a constants refit). Cold start (≤20 attempts with embeddings): `weaknessScore` returns 0, weighting collapses to pure quality. Weakness training also stores a Laplace-approx posterior diagonal SE + per-axis 2×2 cov on `(β_correct[k], β_picked[k])`, and the Weaknesses pane (`stats-weaknesses.js`) runs **two-level detection** on them: **level 1** flags axis k as a weakness when the posterior of the identified **sum** `β_correct[k] + β_picked[k]` (variance `var_c + var_p + 2·cov`) is credibly negative — never the correct/picked split, which is prior-dominated because ~80% of rows have `picked = correct` (every correct attempt + the missing-pickedEmbedding fallback); **level 2** qualifies the direction with a **paired sign test on `picked_emb[k] − correct_emb[k]` over the user's own wrong attempts** (`computeAxisDirections` in `stats-compute.js`; each error attributed to the flagged axis with the largest |contrast| since axes co-load; exact Beta-posterior direction probability) — overshoot → "too much", undershoot → "not often enough", inconclusive → "inconsistently" as the honest residual. The sign test needs no assumption about which moves are reasonable alternatives: the single-solution invariant makes the correct move the canonical reference. (This replaced an earlier four-way sign-quadrant scheme — `bivariate-normal.js`, deleted — whose `cov<0` gate was structurally always tripped by the collinearity, so only "inconsistently" ever rendered.)

*Picked-move fetch.* `pwa/js/picked-embedding.js` Range-fetches the per-cell sidecar. Two entry points:
- `fetchPickedEmbedding({tsumegoId, cellIndex, zipFilename, boardSize})` — live path, called from `game-logic.handleBoardClick` on every move via `state.embeddingsIndexCache` (loaded alongside shard metadata in `problem-loader`). The cell index is `children.indexOf(moveNode)` against the SGF root variations — same order as extraction/packaging, no coordinate recomputation.
- `fetchPickedEmbeddingWithIndexEntry(...)` — backfill path, used by `backfill.js` when iterating shards.

Answer-history entries carry `embedding` (correct-move, from shard `metadata.json`), `pickedCellIndex` (SGF variation index), and `pickedEmbedding` (decoded sidecar fp16).

*Backfill + invalidation.* `pwa/js/backfill.js` runs on app load: reads the **inlined** joint `embedding_meta.json` (version, labels, K/dtype/bytes_per_cell all joint — a build-time `import` via `data-version.js`, not a fetch; see the data-version cache note), then iterates per size — it fills missing `embedding` fields from the lookup-aligned correct-move sidecar (`fillCorrectEmbeddingsViaSidecar`: binary-search the id in the already-fetched lookup.txt lines → fetch that ~130-byte row of `lookup.embeddings.bin`; repeats share a memoized fetch; hosts that ignore Range — wrangler dev AND production Workers assets — cost one whole-file download, cached by the SW and served row-by-row from memory thereafter) and missing `pickedEmbedding` fields by Range-fetching each shard's per-cell bin with the entry's stored `pickedCellIndex` — the per-problem byte offsets live in the zip's `embeddings_index.json`, so the picked fill is the **only** embedding fill that still downloads shard zips (`walkPickedShards`, only shards carrying such a need). The account-adoption synced fill (`fillSyncedHistoryFields`) uses the same sources, and its zip walk covers just the `syncedMove → pickedCellIndex` derivation (needs the SGF) + the picked fill — measured on a worst-case 2k-attempt adoption: 38 zips vs 342 with the sidecar absent (and ~830 before the problem_params/stamp fixes). Entries older than `MODEL_INPUT_HISTORY_LENGTH` get the embedding fields stripped to keep localStorage bounded. Because the weakness model is a single shared instance (see the cross-size merge note), an embedding wipe on *either* size clears the shared `weaknessParams`/`Adam`/`Se`/`AxisCov`, and a single `trainWeakness()` retrain runs once after the whole walk (not per size). Refits auto-invalidate: `build_embedding.py` writes a content-hash `embedding_version` into `pca.npz` (computed over the projection-relevant arrays — feature mask/means/stds, OLS coefs, PCA components/mean/stds, ICA unmixing/stds), `package_for_pwa.py` surfaces it in `pwa/tsumegos/embedding_meta.json`, and the PWA wipes stale embeddings (correct + picked) per size whenever the localStorage-cached version differs. No manual JS edit needed on refit.

Extraction needs ~8 GPU minutes per 1k problems on a Quadro M2200; remote it via Vast.ai for full-corpus runs.

**Ranks are derived client-side from raw ratings; packaging is rank-agnostic.** `package_for_pwa.py` ships per problem in `metadata.json` the raw black-box `rating` (from `ratings/<size>/tsumego_ratings_final.csv`) and the raw 2PL `slope` a_p (from `tsumego_quality_final.csv`, un-normalized — the client uses it as the rank-estimator's per-attempt slope and as the selection weight ∝ `a_p²`) — no rank, no `rank_index`, no `/29`; shard `min_rating`/`max_rating` are raw too. It does not *compute* ranks (rank-agnostic); the rating→rank map `M` is fitted separately (see next note) into the backend `ratings/` dir, and `package_for_pwa` — the **single writer of `pwa/tsumegos/`** — copies that curve (`rating_to_rank.json` + `rank_map.json`) across into the served path. The client does *all* rating→rank conversion. On ingest, `problem-loader.js` derives `p.rank` (normalized 0..1 = `applyM(rating)/29`, via `normalizedRankForSize` in `rank-decomposition.js`) and leaves `p.rating` raw; zip boundaries become `minRank`/`maxRank`. Everything rank-shaped reads `rank`: problem selection, the rank label (`getDescriptiveRank`), recall (`model.js`), and the weakness model (`weakness.js`). `state.userRank` is a single value shared across both sizes (see the cross-size merge note), and the skill decomposition pools both sizes in internal-rank space — each attempt is mapped through its size's `M` first, not estimated in raw-rating space. **`M` is required** — `main.js` awaits `loadRatingRankMap()` at init and aborts if it can't load (no fallback). Answer-history entries store `problemRating` (raw), `problemRank` (0..1), and `problemSlope` (raw a_p — the skill decomposition's per-attempt success-curve slope, converted to internal-rank space as `a_p/|M'|`; legacy entries without it fall back to a constant). The client rank loop closes on this per-problem `a_p`: `rank-decomposition.js`'s `poolLogistic` AND the consensus anchor `fit_user_rating` (`map_rating_to_rank`) both use it, so a sharp problem pins a user's rank more tightly than a flat one. `backfill.js` migrates/refreshes all three, triggered by a **single** `ratings_version` (the joint cross-board rating fit re-rates both boards together, so `data-version.js` collapses the manifest's per-size sub-hashes to one gate value — there is no independent per-board rating version) **and** by a client-computed curve-version (`ratingRankCurveVersion`) so a `map_rating_to_rank` re-fit with unchanged ratings still refreshes stored ranks. The version gate + stamp live ONCE in the orchestrator (`backfillMissingEmbeddings`), wrapped around the per-size work loop (`backfillForSize` does only the per-size shard walk — problems live in per-size shards — and never touches the stamps): the single `embedding`/`ratings`/`curve` stamps are written only AFTER every size's walk has persisted, so **stamp-last = crash-safe** (a shutdown mid-run leaves nothing stamped and the whole backfill re-runs idempotently). The run is bracketed by `backfill: triggered`/`backfill: complete` console logs, and a retrain-if-null guard re-fits the shared weakness model if an interrupted refit left it cleared. **Consequence:** a curve re-fit (`map_rating_to_rank`) writes only to the backend `ratings/`; publish it with `package_for_pwa` — its per-size change detection sees the shard inputs unchanged and **skips the heavy rebuild, copying just the curve** (near-instant), so a curve-only change is cheap but still goes through the single writer. A raw-rating change re-ships shards. (A change to the *packaging format itself* — e.g. adding/renaming a `metadata.json` field — is NOT captured by the input hash, so run `package_for_pwa --force` once after such a code change.) Don't reintroduce a baked rank into `metadata.json` — `rating` means raw everywhere.

**`M` (rating→rank) maps to a latent CONSENSUS rank; every server INCLUDING EGF is a coupling off it (EGF is NOT special).** `pipeline/map_rating_to_rank.py` fits, in ONE objective, the rating→consensus-rank curve, the per-server ordinal couplings (EGF among them — no identity hub), AND the solve-time slope α. The consensus scale would otherwise be free (a gauge freedom, since no server is privileged); it is pinned by a **VERY WEAK** penalty (`GAUGE_WEIGHT≈1`) on the **reliability-weighted (declaration-count-weighted) mean coupling offset** toward identity — weak because the likelihood is flat in the gauge direction so the scale has no motivation to drift, and a strong pin would shrink the real per-server offsets; the data-rich servers (OGS/Fox/EGF/KGS) set the scale, which lands ≈ EGF so the headline barely moves. The curve uses the statistics.txt cubic SHAPE as a **GENTLE** prior (`LAMBDA_SHAPE=0.3`, softened from the old 3.0 once the all-server latent is no longer EGF-kyu-starved — this also recovered the dan under-rating). It anchors users on their **80%-clear rating** (`fit_user_rating` @ 0.8, pooled, full 4PL) — and **per overlapping 2-month CAREER BLOCK, not one pooled rating per user**: each user's first-time attempts are cut into 60d windows stepped 30d, every block with ≥20 joined attempts gets its own 80%-clear rating and anchors the user's **nearest-in-time declaration** per server (no-drift assumption: surveys only began 2026-05, so older attempt eras carry the same declared rank; a user with no fittable block falls back to the pooled career rating). Block rows are weighted by **attempt mass** (each attempt's unit mass split over the blocks covering it — overlap can't double-count an era) and normalized so each declaration contributes total weight 1. Validated by paired 50-folding CV (`auxiliary/eval_rank_map_cv.py`): held-out NLL −0.04±0.01 and deep-kyu MAE 5.2→4.2 ranks vs the pooled-career anchor, dan band unchanged; the same harness tested errors-in-variables over each rating's Fisher CI and **REJECTED it** (declaration noise dominates; consistently worse held-out — don't add CI weighting). **RATINGS ARE TIME-ADJUSTED THROUGHOUT THE MAPPING**: each declaration's effective rating is `rating + α·(log10 median solve min − center)`, α fit JOINTLY (identified because the time feature is per-user while the curve is f(rating) and each coupling is a per-server constant). Outputs (both board keys identical): `ratings/rating_to_rank.json` (`{ratings, rank_indices}` + a top-level `time_adjust {alpha_per_log10_min, center_log10_min}`) and `ratings/rank_map.json` (`{server: {our, server}}` knots **including a real EGF coupling**, not an identity line). **The client headline (onlymove rank) maps the RAW rating through M (untimed); every server translation — EGF among them — maps the TIME-ADJUSTED rating** (`rank-translation.js`); the dock is dropped ONLY for the headline, a client display choice. `fit_population_constants` READS α/center through from `rating_to_rank.json` into `population_constants.json` (no separate time fit). `package_for_pwa` copies both curve files across (single-writer). The module is **production-clean** — config baked as module constants, NO experimentation code (that lives in `auxiliary/map_rating_to_egf_timed.py`); the consensus model + gauge + time-form are documented in `docs/consensus_mapping_rollout_plan.md` and `docs/egf_anchor_bias_and_time.md`. Run `pipeline.fetch_database` first; `map_rating_to_rank` then needs `ratings/` + `attempts/database.sqlite` (for median solve time) but neither GPU nor the heavy pipeline.

**Rank interpolation/label math is shared between the Worker and the client.** `interpExtrap` (linear interp + end-slope extrapolation) and `rankScalarToLabel` (rank scalar → "5k"/"3d" label; 1k=0, 1d=1, no zero gap) live in `pwa/shared/rank-math.js`, imported by the Worker (`src/index.js`, bundled by wrangler) and by client modules (`rank-translation.js`, `rank-decomposition.js`, bundled by esbuild). Keeping them in one module prevents the server-computed Community rank histogram from drifting against the client's rank display — don't reintroduce a local copy.

**KataGo PyTorch loader requires `.ckpt`, not `.bin.gz`.** `models/kata1-b18c384nbt-...bin.gz` is the binary export the C++ analysis engine reads — not loadable via `torch.load`. The feature-embedding pipeline expects `models/kata1-b18c384nbt-s9996604416-d4316597426/model.ckpt` (extracted from the corresponding `.zip` checkpoint distribution). Don't point `extract_activations.py --ckpt` at a `.bin.gz`; KataGo's training code only goes PyTorch → binary, not the other way.

## Conventions to be aware of

- `tests/` exists but is empty — there is no test runner configured. Don't add a "run the tests" step to claims of completion unless tests are actually added.
- Python code uses absolute imports rooted at the repo (e.g., `from utils.configurations import ...`). Pipeline scripts append `PROJECT_ROOT` to `sys.path` defensively.
- KataGo coordinates skip the letter `I` (so cols are `ABCDEFGHJKLMNOPQRST`). SGF coordinates do not. Helper conversions live in `utils/katago_queries.py` (`katago_to_sgf_coords`) and `pipeline/benchmark_bots.py` (`sgf_to_gtp`). Prefer reusing them over rewriting coordinate math.
- `pwa/README.md` has additional context on the PWA's overall structure (sections 1–5: overview, tech stack, project layout, architecture, dev workflow). Read it before substantive PWA edits.
- **For local DB analysis, prefer the binary `attempts/database.sqlite` over the raw `attempts/database.sql` dump.** Both are produced from `pipeline.fetch_database` and both gitignored. `fetch_database` treats `database.sqlite` as the **canonical merge target** and keeps both artifacts in sync on every run, so you normally don't import by hand. If you ever need to rebuild the `.sqlite` from a raw dump manually: `{ echo "BEGIN;"; cat attempts/database.sql; echo "COMMIT;"; } | sqlite3 attempts/database.sqlite` — the `BEGIN/COMMIT` wrapper matters: a full D1 export emits one un-batched `INSERT` per row (~290k for `tsumego_reports`), so without a wrapping transaction sqlite fsyncs per row and the import takes many minutes. **Never pipe the import through `head`/`tail`** — it SIGPIPE-kills `sqlite3` mid-import and silently leaves a partial table. Query the `.sqlite` thereafter (no re-import per session). Note a full `--full` dump only carries the tables that have rows at export time (D1 export drops empty tables), whereas the incremental path's regenerated dump carries every table it discovered remotely (so e.g. an empty `history_refresh_log` is present).
- **Many artifact directories hold 100k+ files** — `tsumegos/9/` (~123k SGFs), `activations/9/` (~123k .npz), `tsumegos/13/` and `activations/13/` (~20k each), `embeddings/joint/per_cell/<size>/` (per-tid files), and shard zips. **Shell globs like `ls dir/*.npz` will silently expand past `ARG_MAX` and report 0** — verified false-negative on `activations/9/`. Use `find <dir> -maxdepth 1 -name '*.ext' -printf . | wc -c` (or `find ... | wc -l` if newlines are safe) to count, and `find ... -exec` / `xargs -0` to iterate. The same trap applies to anything piping a glob into another command. Treat any directory under `tsumegos/`, `activations/`, `embeddings/`, `attempts/`, `ratings/`, or `pwa/tsumegos/<size>/` as "may exceed argv" by default.
