# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

YoseTsumego / onlymove.net — a Go (Baduk/Weiqi) tsumego pipeline. KataGo generates problems and rates them; the rated set is packaged into zip archives served by a Cloudflare-hosted PWA. There are four cooperating subsystems:

1. **`pipeline/`** — eight executable scripts run in order (see "Pipeline commands" below). Each is a standalone `python -m pipeline.<step>` entrypoint. Three auxiliary scripts (`refresh_meta.py`, `sync_labels.py`, `fit_rank_curves.py`) patch `pwa/tsumegos/` artifacts without rerunning the heavy pipeline; `refresh_meta.py`/`sync_labels.py` are covered in the embedding architecture note and `fit_rank_curves.py` in the rank architecture note below.
2. **`utils/`** — shared logic: `KatagoController` (subprocess + thread-safe query dispatcher), `KatagoQueries` (analysis-engine wrapper), `ProblemFinder` (move-difficulty heuristics), `add_variations` (SGF tree construction), `models` (KataGo network downloads), `configurations` (global knobs).
3. **`pwa/`** — vanilla-JS ESM PWA built with esbuild, deployed as a Cloudflare Worker. The Worker entrypoint is `pwa/src/index.js` handles five HTTP routes — `POST /report` (per-attempt logging), `GET /push/vapid-public-key`, `POST /push/subscribe`, `POST /push/unsubscribe`, `POST /schedule` (upserts the user's recall-reminder schedule) — plus a cron-driven `scheduled()` handler that walks `recall_schedule` and delivers due Web Push notifications, and an SPA fallback that derives board size from `/9` or `/13`. Static assets ship via the `[assets]` binding in `wrangler.toml`. D1 binding `DB` → database `tsumego-reports`, with tables `tsumego_reports` (per-attempt log: `user_id, problem, success, created_at, size, move, time_used, review_time, is_repeat`; no `UNIQUE(user_id, problem)` constraint, so repeat attempts produce their own rows), `push_subscriptions`, and `recall_schedule`.
4. **`analysis_server/`** — a tiny HTTP server wrapping KataGo for the PWA's analysis fallback when SGFs lack embedded win-rate data.

Plus `auxiliary/` (one-off diagnostics, legacy code; not part of the main flow) and `vast_orchestration.py` (rents Vast.ai GPU instances to run the heavy pipeline steps remotely).

## Pipeline commands

Always invoke pipeline modules through the venv's Python so PYTHONPATH resolves correctly:

```bash
./.venv/bin/python3 -m pipeline.fetch_database        # pull D1 attempts via wrangler
./.venv/bin/python3 -m pipeline.tune_engine           # tune nnMaxBatchSize / numAnalysisThreads in bots/analysis.cfg
./.venv/bin/python3 -m pipeline.generate_tsumegos     # long-running generator → tsumegos/<size>/
./.venv/bin/python3 -m pipeline.benchmark_bots        # bots solve generated tsumegos → attempts/<size>/
./.venv/bin/python3 -m pipeline.rank_tsumegos_and_bots  # PyTorch mixture-of-sigmoids rating model → ratings/<size>/
./.venv/bin/python3 -m pipeline.extract_activations   # KataGo trunk activations per problem → activations/<size>/<id>.npy (GPU; resumable)
./.venv/bin/python3 -m pipeline.build_embedding       # rating-residualized PCA over activations → embeddings/<size>/
./.venv/bin/python3 -m pipeline.package_for_pwa       # zip + lookup.txt + embedding_meta.json → pwa/tsumegos/<size>/ (ships raw ratings; rank-agnostic)
```

Survey-driven rank calibration (board-independent, not part of the in-order run; needs only `attempts/database.sql`, no GPU):

```bash
./.venv/bin/python3 -m pipeline.fit_rank_curves       # rank_surveys → pwa/tsumegos/{rating_to_rank.json, rank_map.json}
```

Run on a remote Vast.ai GPU instead: `python vast_orchestration.py` (no args prints subcommands; only `tune`, `generate`, `benchmark` are remoted — the rest stay local).

Local testing must go through `npm run dev`: the Worker runs `/report` and the SPA fallback (URL-based size hints), so opening the static bundle alone will misbehave. Deployment is **manual** — there is no git-triggered auto-deploy.

## Architecture notes that span multiple files

**Tsumego identity is symmetry-aware and single-solution.** Filenames come from `get_orientation_invariant_hash` (`pipeline/generate_tsumegos.py:154`) — SHA-256 taken over all 8 D4 transforms of the board, with `min()` picking a canonical orientation. The dataset therefore cannot contain two problems that are rotations or reflections of each other; `tsumego_id` is the symmetry-canonical hash truncated to 8 hex chars. By generator design every problem has exactly one correct first move (the `solution` returned by `ProblemFinder.create_problem`); downstream code can rely on the "one canonical answer per problem" invariant.

**Board size — two supported modes: 9x9 and 13x13.** Both ship in production; the PWA picks one from the URL path (`/9` or `/13`) via the SPA fallback in `pwa/src/index.js`, and the D1 `report` endpoint records `size` per attempt. On the **pipeline side**, the size is a config-file switch: edit `BOARD_SIZE` in `utils/configurations.py` and re-run the pipeline — there is no in-process multi-size support, no CLI flag, and no automatic dual-size run. Artifact directories are keyed by size: `tsumegos/<size>/`, `attempts/<size>/`, `ratings/<size>/`, `pwa/tsumegos/<size>/`. To refresh both sizes, run the full pipeline once with `BOARD_SIZE = 9`, then again with `BOARD_SIZE = 13`.

**On the client, rank + stats + the learned models are merged across sizes; histories, `M` curves, and problem pools stay per-size.** From the user's perspective 9x9 and 13x13 share one rank (front-page label, problem selection, recall eligibility) and one stats page. `pwa/js/state.js` splits storage into per-size buckets (`answerHistory`, `problemHistory`, `nextTsumego`) and single shared values (`userRank`, `momentum`, the recall model `modelParams`/`adamState`, the weakness model `weaknessParams`/`weaknessAdam`/`weaknessSe`/`weaknessAxisCov`). A `mergeSharedAcrossSizes_v2` migration collapses the old per-size buckets: `userRank = max(rank_9, rank_13)` (a strong 9x9 player immediately gets hard 13x13 problems), momentum follows the higher-ranked size, and the model buckets are dropped so the shared models retrain from scratch. `getMergedAnswerHistory()` returns the time-sorted union of both buckets, each entry tagged with `size`; the recall model, weakness model, and the whole stats panel (`showDetailedStats`) train/render from it. Pooling is sound because every feature they read is board-independent — `problemRank` is the EGF-anchored internal rank (a normalized 0.5 means the same EGF rank on either board), and the embedding axes are jointly fit across sizes. Play-time size-awareness is preserved: a recall problem can only be re-shown on its own board, so `getRecallCandidates` takes an explicit `history` (defaults to the active size; the merged union is passed only for stats counts) and `buildRecallSchedule(size)` reads the shared model + shared rank but that size's history. Two consumers needed real work to pool: the recall logistic gained a `SIZE_IS_13` fixed effect (9x9 = baseline) whose coefficient ÷ logit-per-rank is the stats panel's "stronger/weaker on 13x13" readout; and the skill decomposition (`rank-decomposition.js`) now pools in **internal-rank space** with a per-attempt slope `LOGIT_PER_RATING / |M'(rating)|` (each attempt mapped through its own size's curve), so both sizes share one skill curve without the rank-space slope bias.

**KataGo binary selection.** `utils/katago_controller.py` reads `KATAGO_PATH` from env, defaulting to `bots/katago` (OpenCL build). `vast_orchestration.py` uploads `bots/katago_cuda` and sets `KATAGO_PATH=bots/katago_cuda` on the remote. Don't hardcode the binary path; rely on the env var.

**`bots/analysis.cfg` is hardware-tuned in place.** `pipeline.tune_engine` rewrites `numAnalysisThreads` and `nnMaxBatchSize` for the current GPU. `vast_orchestration.py`'s `setup` ships the local cfg once but `update` deliberately skips it so remote tuning isn't clobbered. If you edit the cfg, expect the tuner to overwrite your changes.

**`KatagoController` is thread-safe by design.** A single master reader thread fans responses out via per-query `threading.Event`s keyed on query IDs. `send_query` is blocking from the caller's perspective. Multiple worker threads in `generate_tsumegos.py` and `benchmark_bots.py` rely on this.

**Models live outside git.** `models/` is gitignored. `utils/models.get_model(filename)` lazily downloads from `media.katagotraining.org` (or GitHub for 9x9 / human models) on first use. The default model is `MODEL_FULL` (`kata1-b18c384nbt-...`).

**PWA SGF format carries embedded analysis.** Each branch comment in a tsumego SGF is `"<winrate>%/<score>"` (e.g., `"86.4%/3.1"`). Client-side analysis (`pwa/js/sgf.js`) reads this directly; only when missing does it call the server (`pwa/js/api.js` → `analysis_server/server.py`). Don't strip these comments when manipulating SGFs.

**PWA state is centralized.** `pwa/js/state.js` holds the single mutable object; all changes go through exported setters. `state.appMode` switches between `'solving'` (game-logic.js), `'analyzing'` (analysis.js), and `'linked'` (rank-frozen URL-shared problems). Click handling in `board.js` routes by `appMode`.

**Worker-version-driven graceful reload.** `pwa/build.mjs` writes `pwa/src/version.js` so the Worker imports the same hash the client gets via the esbuild `define`. Every `/report` response stamps `X-App-Version`; if it differs from the client's `APP_VERSION`, the client sets `state.reloadPending`. `maybeReload` fires from `setAcceptClicks(true)` only when `appMode !== ANALYZING`, so the refresh always lands between problems — never mid-review. New JS-side features that depend on the Worker version (e.g. embedding/ratings backfills keyed by content hashes shipped in `embedding_meta.json`) ride this reload signal.

**Feature-embedding recommender (per-component weakness mining).** Per-cell, not per-problem: every legal first-move cell gets its own K-dim embedding, so the system can score both the **correct** move (a property of the position) and the move the user **actually picked** on a wrong attempt.

*Extraction* — `pipeline/extract_activations.py` runs a vendored PyTorch copy of KataGo b18 (`utils/katago_vendor/`, bootstrapped via `utils/katago_torch.py`) and captures the post-skip-add output of all 18 residual blocks (18 × 384 = 6912 floats) **at every legal cell**. Output: `activations/<size>/<id>.npz` with `candidates (n_legal, 6912) fp16`, `xys (n_legal, 2) int32`, `correct_idx () int32`.

**Row order is board-scan order (sorted by `(y, x)`), NOT SGF-variation order, and the cell set is a *superset* of the SGF's root variations.** (The script's own docstring still claims SGF-variation order with `correct_idx` always 0; that is stale — the on-disk corpus is scan-order with a *non-zero* `correct_idx` recording where the correct move lands in the scan. Verified May 2026 across the 13×13 corpus: e.g. `00000f4c` has `correct_idx=38`.) Two consequences every downstream consumer must respect, and currently does:
  - **Pick the correct row by `correct_idx`, never positionally.** `build_embedding._load_correct_vec` does this (`build_embedding.py:102` → `candidates[int(correct_idx)]`); do not assume row 0.
  - **The npz embeds every legal cell; SGF root variations are a pruned subset, plus the SGF carries a `pass` variation the npz never embeds.** So npz ⊇ {SGF non-pass variations}: every move a user can actually click is embedded (no picked-move ever misses), but ~10% of problems have extra embedded cells with no SGF variation, and 100% have a `pass` that is not embedded. Map cells by `(x, y)` coordinate, not by index, when crossing the npz↔SGF boundary.

*Joint embedding fit* — `pipeline/build_embedding.py` fits a joint PCA across all configured sizes on the **correct-cell row only** (residualize per-feature on `[rating, size_is_13]` jointly, z-score, randomized SVD with K=64, then standardize component scores to unit variance). **Then by default rotates the K-dim subspace with FastICA using a `skew` contrast** (`_skew_contrast`, `G(u) = u³/3, g(u) = u²` — the 3rd-cumulant objective). After convergence, axes are sign-canonicalized so skewness is non-negative, which makes the **positive tail the heavy tail that concentrates the motif and the negative tail Gaussian baseline by construction** — i.e. negative scores don't represent an "opposite motif," they represent "no motif present." That asymmetry is the reason the recommender, the `labels.json` curation, and `inspect_extreme_problems.py` all treat the positive side as the only meaningful direction. `--rotation none` (raw PCA) and `--ica-fun {logcosh, exp, cube}` (symmetric contrasts) are also supported; under those the two sides would be symmetric, but production uses skew. Output to `embeddings/joint/{pca.npz, per_problem.csv, explained_variance.csv, extreme_problems.json, labels.json}`. `per_problem.csv` carries `size` so packaging filters by it. After the fit, `write_per_cell_projections` fans out the projection (PCA + ICA rotation) to **every cell of every problem** in parallel workers and writes `embeddings/joint/per_cell/<size>/<tid>.npz` with `embeddings (n_cells, K) fp16` + `xys (n_cells, 2) int32`. `labels.json` is a manually-curated map of PC index → `{positive}` human labels; under skew-ICA only the positive tail carries a motif (the negative tail is Gaussian baseline), so there is no `negative` side. **Labels survive PCA refits**: on each `build_embedding` run, prior `pca.npz` loadings are snapshotted before being overwritten; after the new fit, each previously labeled PC is matched to the new PC with maximum |cosine similarity| in the original 6912-dim feature space (above 0.8 threshold). The label is carried only when the signed cosine is positive; a negative-cosine match points at a different motif (axes are sign-canonicalized to positive-skew), so the label is dropped rather than carried. Survivors carry `auto_mapped_from` and `auto_mapped_cos` for traceability; below-threshold matches reset to null. `pipeline/sync_labels.py` is a fast sync that pushes a hand-edited `labels.json` into the joint `pwa/tsumegos/embedding_meta.json` without rezipping.

*Packaging* — `pipeline/package_for_pwa.py` ships two things per shard:
1. The correct-move embedding (length K=64) joined into the shard's `metadata.json` under `embedding` — what `weaknessScore` reads against any candidate problem.
2. A sibling `<hash>.embeddings.bin` per shard (fp16, K floats per cell, all problems concatenated **in SGF root-variation order**), plus an `embeddings_index.json` inside the zip mapping `{tid: {offset, n_cells}}`. This is the picked-move sidecar: the PWA Range-fetches `bytes=offset+i·bytes_per_cell..offset+(i+1)·bytes_per_cell-1` to recover the embedding at cell index `i` of a tsumego, where `i = children.indexOf(moveNode)` over the SGF root variations.

   **The bin order is set here, not upstream.** Because the npz is scan-order and a superset (see *Extraction*), `package_for_pwa.project_cells_for_problem` re-parses each SGF and rebuilds the per-cell rows in SGF-variation order via an `(x, y) → npz row` map — dropping the extra scan-order cells and the `pass`. This reorder is **load-bearing**, not defensive: the PWA indexes the bin by SGF-variation position, so shipping raw scan order would silently return the wrong cell's embedding for every picked move. The sgfmill parse dominates packaging time, so shard building is parallelized across processes (`--workers`, default `os.cpu_count()`); `--no-sgf-reorder` skips the parse but is correct **only** if the npz has been pre-reordered into SGF-variation order upstream (it has not, on current `build_embedding` output).

The joint `pwa/tsumegos/embedding_meta.json` carries `K`, `dtype` (`float16`), `bytes_per_cell` (so the PWA can decode the bin without guessing), `embedding_version`, and `labels` (variance curve, extreme problems, kurtosis, etc. live in `embeddings/joint/` locally as inspection artifacts and aren't shipped).

*PWA model — augmented weakness regression.* `pwa/js/weakness.js` trains a logistic regression with **2K+2 params**:
```
P(correct) = σ(α + γ·rating
                + Σ β_correct[k] · correct_emb[k]
                + Σ β_picked[k]  · picked_emb[k])
```
The `γ·rating` term is actually `γ·problemRank` (the board-independent internal rank), and the model is a **single shared instance trained on `getMergedAnswerHistory()`** (both sizes pooled — the embedding axes are joint, so this is well-posed); see the cross-size merge note above. `β_correct[k]` is the position's effect (problem's correct-move embedding); `β_picked[k]` is the user's choice effect (whatever they actually clicked). On correct attempts `picked_emb = correct_emb`, so those rows inform the sum `β_correct + β_picked` jointly; wrong attempts with a sidecar-fetched `pickedEmbedding` disambiguate the two. Recommendation scoring uses `(β_correct + β_picked)` against the candidate's correct-move embedding — algebraically equivalent to assuming "user will pick correctly" on the unseen problem. `problem-loader.js`'s `selectProblem` weights candidates by `quality · exp(WEAKNESS_TEMPERATURE · weaknessScore)`. Because the embedding is skew-ICA-oriented (positive tail = motif present, negative tail ≈ baseline), the recommender is effectively asymmetric in practice: large positive scores along an axis where the user is weak get mined; large negative scores don't represent an "opposite motif" the user is good at, just baseline problems with no motif. Don't read symmetry into the linear model. Ridge-regularized with `RIDGE_LAMBDA = 200` (calibrated by held-out CV in `auxiliary/calibrate_priors.py`); cold start (≤20 attempts with embeddings): `weaknessScore` returns 0, weighting collapses to pure quality. Weakness training also stores a Laplace-approx posterior diagonal SE + per-axis 2×2 cov on `(β_correct[k], β_picked[k])` so the stats UI can render sign-quadrant probabilities (`too much / not often enough / bad at / no issue`) via `pwa/js/bivariate-normal.js` (Owen's-T-based bivariate-normal CDF). `computeExpectedRecommenderPenalty()` reports the recommender's expected logit drag vs uniform weighting over the candidate pool.

*Picked-move fetch.* `pwa/js/picked-embedding.js` Range-fetches the per-cell sidecar. Two entry points:
- `fetchPickedEmbedding({tsumegoId, cellIndex, zipFilename, boardSize})` — live path, called from `game-logic.handleBoardClick` on every move via `state.embeddingsIndexCache` (loaded alongside shard metadata in `problem-loader`). The cell index is `children.indexOf(moveNode)` against the SGF root variations — same order as extraction/packaging, no coordinate recomputation.
- `fetchPickedEmbeddingWithIndexEntry(...)` — backfill path, used by `embedding-backfill.js` when iterating shards.

Answer-history entries now carry `embedding` (correct-move, from shard `metadata.json`), `pickedCellIndex` (SGF variation index), and `pickedEmbedding` (decoded sidecar fp16).

*Backfill + invalidation.* `pwa/js/embedding-backfill.js` runs on app load: fetches the joint `embedding_meta.json` once (version, labels, K/dtype/bytes_per_cell all joint), then iterates per size — for each shard that legacy answer-history entries reference, it fills missing `embedding` fields from `metadata.json` and missing `pickedEmbedding` fields by Range-fetching the sidecar with the entry's stored `pickedCellIndex`. Entries older than `MODEL_INPUT_HISTORY_LENGTH` get both fields stripped to keep localStorage bounded. Because the weakness model is now a single shared instance (see the cross-size merge note), an embedding wipe on *either* size clears the shared `weaknessParams`/`Adam`/`Se`/`AxisCov`, and a single `trainWeakness()` retrain runs once after the whole walk (not per size). Refits auto-invalidate: `build_embedding.py` writes a content-hash `embedding_version` into `pca.npz` (computed over the projection-relevant arrays — feature mask/means/stds, OLS coefs, PCA components/mean/stds, ICA unmixing/stds), `package_for_pwa.py` surfaces it in `pwa/tsumegos/embedding_meta.json`, and the PWA wipes stale embeddings (correct + picked) per size whenever the localStorage-cached version differs. No manual JS edit needed on refit.

Extraction needs ~8 GPU minutes per 1k problems on a Quadro M2200; remote it via Vast.ai for full-corpus runs.

**Ranks are derived client-side from raw ratings; packaging is rank-agnostic.** `package_for_pwa.py` ships exactly one number per problem in `metadata.json` — `rating`, the raw black-box scalar from `ratings/<size>/tsumego_ratings_final.csv` (no rank, no `rank_index`, no `/29`); shard `min_rating`/`max_rating` are raw too. It never reads or writes any rank artifact. The rating→rank map `M` is fitted separately (see next note) and the client does *all* conversion. On ingest, `problem-loader.js` derives `p.rank` (normalized 0..1 = `applyM(rating)/29`, via `normalizedRankForSize` in `rank-decomposition.js`) and leaves `p.rating` raw; zip boundaries become `minRank`/`maxRank`. Everything rank-shaped reads `rank`: problem selection, the rank label (`getDescriptiveRank`), recall (`model.js`), and the weakness model (`weakness.js`). `state.userRank` is now a single value shared across both sizes (see the cross-size merge note), and the skill decomposition pools both sizes in internal-rank space (it no longer estimates in raw-rating space — each attempt is mapped through its size's `M` first). **`M` is required** — `main.js` awaits `loadRatingRankMap()` at init and aborts if it can't load (no fallback). Answer-history entries store both `problemRating` (raw) and `problemRank` (0..1); `embedding-backfill.js` migrates/refreshes both, triggered by the per-size `ratings_version` (raw-rating content hash in `embedding_meta.json`) **and** by a client-computed curve-version (`ratingRankCurveVersion`) so a `fit_rank_curves` re-fit with unchanged ratings still refreshes stored ranks. **Consequence:** re-running `fit_rank_curves` updates every displayed/derived rank on next load with no re-package; only a raw-rating change needs `package_for_pwa`. Don't reintroduce a baked rank into `metadata.json` — `rating` means raw everywhere now.

**`M` (rating→rank) is EGF-anchored and jointly fitted from surveys.** `pipeline/fit_rank_curves.py` fits, in ONE objective, the per-board rating→internal-rank curve AND the per-(non-EGF-)server rank couplings over all `rank_surveys` declarations. Internal rank ≡ EGF rank (the hub, identity); EGF declarations anchor the curve directly while every other server's declarations also bend the curve where they land (so kyu-heavy non-EGF cohorts calibrate the kyu range instead of being stamped with extrapolated-cubic ranks that drag the dan range — the failure mode of the older frozen-stage fit). The cubic (`auxiliary.fit_statistics_shapes`, pinned to humanv0_8k/3k) is only a shape prior (`--rating-lambda`, `--lambda`). Outputs go straight to the served paths: `pwa/tsumegos/rating_to_rank.json` (per-board `{ratings, rank_indices}` knots that `M` interpolates) and `pwa/tsumegos/rank_map.json` (board-independent per-server interpolation knots `{server: {our, server}}` in rank-scalar units; `rank-translation.js` interpolates the user's *continuous* internal rank through them and rounds only for display — so a weak vs strong same-band player can land on different server ranks — EGF = identity). Run `pipeline.fetch_database` first to refresh `attempts/database.sql` (the survey + attempts source); `fit_rank_curves` then needs neither GPU nor the heavy pipeline.

**KataGo PyTorch loader requires `.ckpt`, not `.bin.gz`.** `models/kata1-b18c384nbt-...bin.gz` is the binary export the C++ analysis engine reads — not loadable via `torch.load`. The feature-embedding pipeline expects `models/kata1-b18c384nbt-s9996604416-d4316597426/model.ckpt` (extracted from the corresponding `.zip` checkpoint distribution). Don't point `extract_activations.py --ckpt` at a `.bin.gz`; KataGo's training code only goes PyTorch → binary, not the other way.

## Conventions to be aware of

- `tests/` exists but is empty — there is no test runner configured. Don't add a "run the tests" step to claims of completion unless tests are actually added.
- Python code uses absolute imports rooted at the repo (e.g., `from utils.configurations import ...`). Pipeline scripts append `PROJECT_ROOT` to `sys.path` defensively.
- KataGo coordinates skip the letter `I` (so cols are `ABCDEFGHJKLMNOPQRST`). SGF coordinates do not. Helper conversions live in `utils/katago_queries.py` (`katago_to_sgf_coords`) and `pipeline/benchmark_bots.py` (`sgf_to_gtp`). Prefer reusing them over rewriting coordinate math.
- `pwa/README.md` has additional context on the PWA's overall structure (sections 1–5: overview, tech stack, project layout, architecture, dev workflow). Read it before substantive PWA edits.
- **Many artifact directories hold 100k+ files** — `tsumegos/9/` (~123k SGFs), `activations/9/` (~123k .npz), `tsumegos/13/` and `activations/13/` (~20k each), `embeddings/joint/per_cell/<size>/` (per-tid files), and shard zips. **Shell globs like `ls dir/*.npz` will silently expand past `ARG_MAX` and report 0** — verified false-negative on `activations/9/`. Use `find <dir> -maxdepth 1 -name '*.ext' -printf . | wc -c` (or `find ... | wc -l` if newlines are safe) to count, and `find ... -exec` / `xargs -0` to iterate. The same trap applies to anything piping a glob into another command. Treat any directory under `tsumegos/`, `activations/`, `embeddings/`, `attempts/`, `ratings/`, or `pwa/tsumegos/<size>/` as "may exceed argv" by default.
