# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

YoseTsumego / onlymove.net — a Go (Baduk/Weiqi) tsumego pipeline. KataGo generates problems and rates them; the rated set is packaged into zip archives served by a Cloudflare-hosted PWA. There are four cooperating subsystems:

1. **`pipeline/`** — nine executable scripts run in order (see "Pipeline commands" below). Each is a standalone `python -m pipeline.<step>` entrypoint. `package_for_pwa` is the single writer of `pwa/tsumegos/`; there are no side-channel patch scripts — to publish a labels-only or curve-only change without rebuilding zips, re-run `package_for_pwa` (its per-size change detection skips the heavy shard rebuild). Survey-driven rank calibration (`map_rating_to_rank.py`) and population-constant fitting (`fit_population_constants.py`) are board-independent and run outside the in-order pipeline — see the rank architecture note below.
2. **`utils/`** — shared logic, **split into two subpackages that import nothing from each other** (verified when the split was made, and worth keeping true): **`utils/katago/`** is the Go/KataGo side — `controller` (`KatagoController`: subprocess + thread-safe query dispatcher), `queries` (`KatagoQueries`, the analysis-engine wrapper), `problem_finder` (`ProblemFinder`, move-difficulty heuristics), `add_variations` (SGF tree construction, including `construct_initial_sgf`), `coords`, `models` (KataGo network downloads), `board_render`, `torch_model` (bootstraps `vendor/`, the vendored PyTorch KataGo — it puts that directory on `sys.path` so `import katago.…` resolves there; that top-level `katago` package is the VENDOR's, distinct from this `utils.katago`, and they do not shadow each other). **`utils/rating/`** is the statistical side — `features` (the rating trunk's inputs), `ratings_io` (the `ratings/` artifacts + curve reader), `fit_rank_curves`, `rank_surveys`, `residual_axes`, `slope_calibration`, `rank_curve_shape`. `utils/constants.py` (was `configurations.py`) holds the few values both need — `ALL_BOARD_SIZES`, `KOMI`, `RULES`, `DEFAULT_MODEL`, the debug flag.
3. **`pwa/`** — vanilla-JS ESM PWA built with esbuild, deployed as a Cloudflare Worker. The Worker entrypoint `pwa/src/index.js` handles these HTTP routes — `POST /report` (per-attempt logging; `createdAt` is REQUIRED in the payload — the CLIENT owns the event time (it mints one ms per attempt, stores it as the entry's `date`, and the row is inserted VERBATIM, so row.created_at === entry.date exactly and sync matching is exact) — and the server only sanity-bounds it, REFUSING (never rewriting) with `400 {error, serverNow}` on missing/future(+2min)/stale(−7d) so the client can self-correct once and resend (a silent rewrite would recreate the dup-mint precondition); responds `{serverId, userSeq, digest}` (no createdAt echo) — `serverId` the row id stamped on the matching answerHistory entry (its presence = acked; the id-cursor + digest key) so sync pulls skip the device's own rows; `userSeq` the per-profile attempt count, the **digest sync signal** (a jump past the device's expected seq = another device wrote → pull); see the account-sync note below), `POST /sync` (account sync: pages the user's reports newer than the client's **`sinceId` AUTOINCREMENT-id cursor** — gap-free for rows inserted with a historical `created_at` such as an offline flush — at 1000 rows; every response also carries a `serverSeq`/`serverDigest`/`serverMaxId` digest summary for the cheap in-sync check; an optional `limit` shrinks the page — `limit: 1` is the client's frontier/existence probe. A request without a valid `sinceId` (a pre-redesign client on the retired created_at cursor) gets an empty no-op so it just resyncs on reload — see the account-sync note below), `GET /push/vapid-public-key`, `POST /push/subscribe`, `POST /push/unsubscribe`, `POST /schedule` (recall-reminder schedule; **diff mode** — the client keeps a per-row hour-rounded snapshot in localStorage and sends only changed rows + explicit removals, since each upsert bills the row plus its two partial indexes and replace-all is the heaviest D1 write path; legacy `{schedule}` replace-all still accepted; every call, even an empty diff, bumps `push_subscriptions.last_seen_at`, the cron's mid-session suppression watermark), `POST /rank-survey` (per-server rank declarations → `rank_surveys`), `POST /share-event` (share-link create/open analytics → `share_events`; the client sends user/problem/size and, for opens, `document.referrer`, while the worker stamps the Cloudflare edge geo-IP `country`), `GET /server-stats` (serves the cached community-stats blob — see the server-stats note below) — plus a cron-driven `scheduled()` handler that walks `recall_schedule` to deliver due Web Push notifications **and** recomputes `server_stats` (≥23h old or on a version change), and an SPA fallback that derives board size from `/9` or `/13`. Static assets ship via the `[assets]` binding in `wrangler.toml`. D1 binding `DB` → database `tsumego-reports`, tables: `tsumego_reports` (per-attempt log: `user_id, problem, success, created_at, size, move, time_used, review_time, is_repeat`, plus the per-profile sync-digest columns `user_seq` (attempt count) + `running_sum` (Σ rowHash(id) exclusive prefix), lazy-seeded in the INSERT — see the account-sync note; no `UNIQUE(user_id, problem)` constraint, so repeat attempts produce their own rows; **indexed on `created_at`** — `idx_tsumego_reports_created` — for the server-stats window scan, **and on `(user_id, id)`** — `idx_tsumego_reports_user_id` — for the per-user id-cursor `/sync` scan + the digest's O(1) latest-row lookup (the legacy `(user_id, created_at)` index was dropped with the created_at `/sync` path; on the live D1 drop it AFTER the deploy, never before)), `push_subscriptions` (one row per device — `endpoint` PK, `user_id` indexed — so the recall cron fans each due reminder out to all of a user's devices; per-device throttle + dead-endpoint cleanup, per-account active-session suppression), `recall_schedule`, `rank_surveys`, `share_events`, and `server_stats` (single-row JSON cache, `key='latest'`). Schema lives in `pwa/schema.sql` (idempotent `CREATE … IF NOT EXISTS`); apply new tables/indexes to the remote D1 with `npx wrangler d1 execute tsumego-reports --remote --file=schema.sql`.
4. **`analysis_server/`** — a tiny HTTP server wrapping KataGo for the PWA's analysis fallback when SGFs lack embedded win-rate data.

Plus `auxiliary/` (one-off diagnostics, legacy code; not part of the main flow) and `vast_orchestration.py` (rents Vast.ai GPU instances to run the heavy pipeline steps remotely).

## Pipeline commands

Always invoke pipeline modules through the venv's Python so PYTHONPATH resolves correctly:

```bash
./.venv/bin/python3 -m pipeline.fetch_database        # INCREMENTAL by default: pull only new tsumego_reports rows (by AUTOINCREMENT id) + re-fetch the small tables whole, merge into db/d1.{sqlite,sql}, sync local D1. --full forces a complete re-download (auto-used when there's no local db/d1.sqlite baseline)
./.venv/bin/python3 -m pipeline.tune_engine <size>    # tune nnMaxBatchSize / numAnalysisThreads in bots/analysis.cfg (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.generate_tsumegos <size>  # long-running generator → tsumegos/<size>/ (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.benchmark_bots <size> # bots solve generated tsumegos → attempts/<size>/ (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.extract_activations   # KataGo trunk activations per problem → activations/<size>/<id>.npz (GPU; resumable); feeds both the rating features (bw_act) and build_axes
./.venv/bin/python3 -m pipeline.cache_rating_features  # build BOTH aggregate caches the rating trainer reads — run before train_rating. (a) the candidate-move-eval cache `activations/_signal_cache/move_evals_<size>.npz` that the move block reads, and (b) the correct-cell activation vectors `activations/_signal_cache/correct_vecs_<size>.npy` + `correct_ids_<size>.json` (read by utils.rating.features.load_joint_activations), built by `utils.rating.features.build_correct_vec_cache` which this step calls FIRST — correct_ids is both the rated set and this step's own tid set, so one command keeps them in lockstep. Both are INCREMENTAL and RECONCILE IN BOTH DIRECTIONS — new tids are added (so a tsumego TOP-UP is picked up automatically; a stale correct_ids would silently drop the new problems from the rated set) and departed tids are PRUNED (so a corpus purge leaves no orphan rows). "Up to date" means the cached tid set EQUALS the target set, never just "nothing new to add" — the earlier `not to_extract` short-circuit stranded 344+162 purged rows in move_evals. `--force` re-extracts the move features only; `--rebuild-activation-cache` additionally re-reads every activation .npz (hours — for a corrupt cache, not routine). **The .npz set must be a SUBSET of `tsumegos/<size>/`, asserted before any work** (`_assert_activations_subset_of_corpus`) — ONE-DIRECTIONAL: corpus ⊋ activations is normal (extraction is resumable, so a fresh top-up has SGFs with no .npz yet), but an .npz with no SGF is a hard failure, because `correct_ids` is derived from that listing and an orphan silently promotes a problem that NO LONGER EXISTS into the rated set — it gets features, a rating, a slope and a floor, ships nowhere (packaging works off `tsumegos/`), and nothing downstream can tell it from a real one. Found in production 2026-08-02: one 13x13 .npz left by a pre-canonical-id removal had been feeding a phantom through the whole rating chain since May. **Any unreadable input is likewise an ABORT, never a dropped row**: a corrupt .npz raises out of the worker, and a non-finite row inherited from an older cache is refused at write time (the tmp is removed, the existing cache left intact). The rejected alternative is a NaN row, which is invisible — the tid stays in correct_ids while `_fit_joint_pca`'s finite mask removes it from the fit, so the problem leaves the rated set with nothing anywhere recording it. (The per-problem npz artifacts — activations, per_cell embeddings — are inherently incremental via file existence; only these two roll-up caches needed explicit incremental support.)
./.venv/bin/python3 -m pipeline.train_rating       # SINGLE-PASS rating-gauge cross-board 4PL rating model → ratings/<size>/ (joint fit of all three heads + learned ceiling, two divergence barriers, phase-2 in-sample global slope-scale fit; 80%-clear rating). PRODUCTION-ONLY: takes NO CLI args (config baked in as module constants; always seed 0 → ratings/); features bw_act+move+phase so run pipeline.extract_activations + pipeline.cache_rating_features first (the game-phase block’s SGF-parse cache auto-builds on first load via utils.rating.features.load_joint_game_phase); the full experiment surface (--production-flags, --gauge, the barrier/EIV knobs, the staged legacy configs, eval suite, alternative objectives) lives in auxiliary.rating_dev.train_rating_staged (and …_research)
./.venv/bin/python3 -m pipeline.build_axes            # supervised residual SKILL AXES (replaced the ICA embedding 2026-07-18) → axes/; incremental K, needs attempts DB + ratings/ + rating_to_rank.json; run AFTER train_rating + map_rating_to_rank
./.venv/bin/python3 -m pipeline.package_for_pwa       # SINGLE writer of pwa/tsumegos/: zip + lookup.txt + embedding_meta.json + copies the rating→rank curve across; change-detects per size (skips unchanged shard rebuilds; --force to override). Reads ratings/.
```

## Rating pipeline (combined cross-board MLP-2PL)

The rating backend writes under `ratings/`, and `package_for_pwa` ships it to `pwa/tsumegos/`. The three commands — `train_rating`, `map_rating_to_rank`, `package_for_pwa` — are listed under "Pipeline commands" above.

Key design (validated by the model-comparison series; the surviving write-up is `docs/methodology.md`): a single model `P = σ(a_p·θ_u + d_p)` pooled across 9×9+13×13 with a **shared per-user ability θ**; features are **joint-PCA activations ⊕ common-column bot winrate ⊕ a candidate-move-eval block ⊕ the game-phase raw components** (`bw_act` + move + phase; `pipeline.cache_rating_features` must build the move cache first, the phase cache auto-builds). There are **NO per-problem residual parameters — the shared feature net IS the model** (`d_p = diff_mlp(feat)`, `a_p = softplus(b0+slope(feat))`): the **human first-time attempts** (the only training target) train the net directly, an attempted problem's value departs from the feature-conditional mean only through dropout-limited memorization via the activation features, and never-attempted problems get the pure feature prediction (bot data enters only via the features). **The 2PL slope `a_p` is the per-problem discrimination**, shipped **raw** as the per-problem `slope` field (no min-max repackaging, no separate `quality` field). The client uses it two ways: (1) as the per-attempt success-curve slope in its rank estimator (see the rank-derivation note); (2) as the problem-selection weight ∝ the Fisher information the problem provides at the 80%-clear anchor, **`I = a_p²·anchorInfo(floor)`** (`problemInfoWeight` in `rank-decomposition.js`; sharp = quadratically more informative, guessable = down-weighted; no arbitrary [0,1] range). `anchorInfo` (`irt.js`) is the FULL 4PL information per unit slope², `(span·q(1−q))²/(0.8·0.2)` with `q = σ(κ(floor))` — the same `g²/(p(1−p))` the window MLE accumulates, evaluated at a zero rank gap. It replaced the bare `a_p²` (2026-07-26): the difficulty-matched pool does hold `P(1−P)` ≈ 0.16 constant, but the 4PL's floor and lapse flatten `dP/dθ` without flattening the Bernoulli variance, so the same 80% clear rate carries strictly LESS information — 0.60–0.73× the 2PL value across the shipped floor range (p5–p95 ≈ 0.05–0.32), and that factor does NOT cancel in the pool. **The selection effect alone is near-nil** (within a pool the floors are similar, so the factor spans ~1.1× against a ~30× spread in `a_p²` — ~1% of the probability mass; 2–8% on a fit whose floors span 0.14–0.52). The reason the constant was worth fixing is the SE floor, where the same assumption WAS load-bearing — see the rank-derivation note. **Rating = `(logit(0.8) − d_p)/a_p = b_p + logit(0.8)/a_p`** — the ability at which the user clears the problem **80% of the time** (`CALIBRATION_P`, the margin the PWA serves *and* anchors at), NOT the 50%-point `b_p = −d_p/a_p`; shipped RAW as the per-problem `rating` (the percentile winsor that used to tame the low-slope tail was removed 2026-07-25 — the divergence barriers keep the tails finite at the source, and the clip only erased the ordering of the top/bottom 1% of the corpus; the trainer prints the rating percentiles each run as the tail-sanity check). The slope-dependent 80% correction is load-bearing: a flat low-discrimination problem needs more ability to clear at 80% than its 50%-point implies, so two equal-`b_p` problems differ in true 80%-difficulty — and a monotone rating→rank map cannot recover that per-problem reordering, so it must be built at the rating stage (the consensus mapping re-anchors users' 80%-clear ratings against whatever scalar is shipped, so it stays self-consistent). `map_rating_to_rank` then maps it to the latent consensus rank and writes ONE shared rating→rank curve to both board keys, self-contained (it fits every server coupling, EGF included, itself). Critically it anchors on each survey user's **80%-clear v2-rating** (the same `fit_user_rating` @ `CALIBRATION_P=0.8` the client/`utils.rating.fit_rank_curves` use, pooled across boards), **NOT raw θ**: θ is the 2PL 50%-point (`θ = b_p ⇒ P = 0.5`), so a θ-anchored curve would mis-display every user's 80%-clear rating by ~4.4 ranks. The curve is a shared monotone piecewise-linear fit with a uniform-spacing (linear) prior. The fit is joint (rating→rank + per-server couplings via `fit_joint_shared`), reusing `utils.rating.fit_rank_curves`' stateless helpers (`fit_user_rating`, `ordinal_nll_vec`, …). `package_for_pwa` ships `rating` + raw `slope` per problem; the `rating_model` tag in `embedding_meta.json` records provenance (`"v2"`), and the PWA does not branch on it. Open calibration item: the corpus hard tail (KataGo-hard, unattempted) extrapolates far beyond the human rank knots. **Production fit = ONE SINGLE-PASS joint fit under the RATING GAUGE (2026-07-24; replaced the staged two-phase coordinate descent).** `pipeline.train_rating` is the **production-only** trainer (takes no CLI args; the shipped config is baked in as module constants — there is no argparse, so it always trains seed 0 and writes straight to `ratings/`). All three per-problem heads AND the global ceiling train together in one 200-epoch pass, made well-posed by three measured ingredients instead of phases: (1) the **rating gauge** — the 4PL scale freedom (rating×s, slope/s, ability×s) is pinned on the PROBLEM side by hard-whitening the difficulty head to mean 0 / std 1 (BatchNorm-style: train batches use their own attempt-weighted stats and update an EMA, eval uses the EMA so scored ratings live in the trained gauge), with per-profile ability left FREE (its spread settles ≈1.2); (2) a **shallow-slope penalty** `1e-4·mean(1/a_raw²)` on the PRE-clamp slope (gradient alive at the SLOPE_FLOOR rail) — one-sided and threshold-free, it closes the hard-tail blowup where a no-win/unattempted problem's slope collapses flat and the 80%-clear rating diverges through `logit(·)/a` (pre-fix ~1–3% of the corpus at the rail, ratings to ±hundreds); (3) a **high-floor penalty** `0.01·mean(softplus(o_c − o_div)²)` in the floor head's LOGIT space, centered where the floor crosses `CALIBRATION_P` (derived from the serve margin, λ detached) — the easy-side mirror (floor → 0.8 sends the rating to −∞). Both weights were selected by held-out-logloss sweep (the tails come in at ~zero cost; ~10× higher starts homogenizing real floor/slope structure — don't raise them casually). The penalties act on the OFFENDING PARAMETER, never the derived rating: a direct penalty on the rating is measured-Goodhart (the optimizer inflates floors on hard problems to cancel the number; held-out calibration collapses below the constant predictor), and const-examinee pseudo-counts / one-sided-row filtering are likewise measured-rejected (floor homogenization + ceiling collapse; outcome-selection bias). **`PCA_DIM` (the joint-PCA activation width, single source `pipeline/train_rating.py`, imported by `build_axes` + `utils/rating/residual_axes`) is 128 and that is MEASURED-OPTIMAL — don't sweep it again (2026-07-27).** 8/16/32/64/128/256 were run end-to-end (each dim its own ratings → rank map → population constants → axes, since the axes consume the same features): on held-out-problem logloss, 3 seeds with a paired problem-clustered bootstrap, every other width is worse than 128 (Δ vs 128: d8 +0.0066, d16 +0.0038, d32 +0.0014, d64 +0.0005 = tie, **d256 +0.0035**), and on the axes' own walk-forward gain 128 also wins outright (peak 0.712 vs 0.631 next-best). **256 is refuted from both directions** — it costs about as much rating accuracy as cutting to 16, carries the highest slope p50 of any arm (the memorization signature), and buys nothing on personalization; wider activations let the difficulty head fingerprint problems, which is the failure dropout exists to suppress. 64 ties on ratings but collapses to the K=3 floor on axes. The feature trunk is `bw_act` ⊕ the move-eval block ⊕ the game-phase raw components `[moves_before_position, main_line_len]` (utils.rating.features.load_joint_game_phase — metric-neutral on the held-out suite, included by FEATURE-PARITY POLICY: the rating model and the secondary-axis models train from the same shared data sources; no dedicated dropout — 2 smooth columns cannot fingerprint problems) with **0.3 dropout uniformly — on each input block (act/bw/move) AND between the trunk's own hidden layers** (0.3 maximizes survey-ρ and held-out flatness and sits at the held-out-LL floor; less dropout overfits). **All three input blocks use COLUMN granularity — every feature column dropped independently (2026-07-26; the activation block previously used BLOCK dropout, one keep bit per row for all 128 PCs at once).** Paired 3-seed measurement (same holdout split per seed, cluster-bootstrapped by problem): column granularity is worth **+0.006 / +0.006 / +0.012 nats** of held-out-problem logloss, every seed's 95% CI excluding zero, and it **shrinks the phase-2 correction** (gain 8.0→5.5 mnat, s 1.63→1.52 mean across seeds) at unchanged survey ρ. The dose response is a broad plateau (0.3 ≈ 0.5, 0.7 slightly worse) degrading only past ~0.9. Mechanism: block dropout leaves the fingerprint FULLY INTACT on 1−p of rows, so the net learns a present/absent regime pair and memorizes freely in the majority one, whereas column dropout never presents the same 128-wide code twice — the exact CONJUNCTION memorization needs is unreliable on every row while the smooth low-order signal survives everywhere (and at p≈0.9, where few PCs survive, it reverts to the block regime, as the mechanism predicts). **Weight decay is measured-REJECTED as a substitute for ANY of this dropout (2026-07-26)**: decoupled AdamW decay on the trunk weight matrices (θ/biases/λ excluded — decaying θ is the theta-compression failure and under the rating gauge θ carries the free scale), swept 1e-5…1.0 at a resolved optimum of 0.03, reaches only **0.664** held-out replacing all dropout — worse than the **0.5245 constant predictor**, vs dropout's 0.497 — and recovers just **14%** of the loss when replacing only the trunk dropout (0.5981 → 0.5844 against 0.4973). Signature: flat/no effect across 1e-5…1e-2, then general degradation, never selective memorization suppression — slope p50 stays at 4.84 (healthy ≈1.35, unregularized 7.8) because a LOW-NORM readout of a near-unique 128-dim code still fingerprints. The two dropout kinds are also **strongly super-additive** — removing the trunk dropout costs 0.101 nats and the feature-block dropouts ~0.024, but removing both costs 0.230 — so they suppress different failure modes and no single norm penalty can stand in for either. The move-eval block (winning move ⊕ 9 alts' winrate/score) is **ρ-neutral and only marginally better on held-out LL** (≈−0.0006 at the 0.3 trunk dropout); it ships by product decision, not because the metrics demand it. **Validation (paired seed-0 holdout, the 2026-07-24 gauge/penalty series): the single-pass fit ties the staged pipeline on held-out-problem logloss (≈0.497), improves cross-fitted survey ρ ≈ +0.012, and ships sane tails unclipped (rail empty, ratings ~[−4, +13], floors keep their full spread, λ ≈ 0.03–0.04)** — with the whole staged apparatus (phases, pins, learned globals, fixed-point logic) deleted. The model trains on human attempts alone, with **no mechanistic floor, no hierarchical-slope shrinkage prior, and no bot-anchor examinees** — bot-anchor examinees are deliberately excluded because they steepen the per-problem slope (mean ~1.38 vs ~1.23 human-only) with no held-out-logloss benefit. The ceiling λ is **learned (≈0.03)**, so `fit_population_constants` reads that λ through. The trainer then runs **PHASE 2 — the in-sample global slope-scale fit (`fit_global_slope_scale`, 2026-07-25; replaced the client-replica walk-forward stage)**: the frozen eval-mode model rerun over EVERY first-time attempt on a scorable problem (no cohort cull — the walk-forward's causal protocol could only score heavy users' post-warmup rows, ~62% of attempt mass) with the phase-2 ability field REFIT free (one θ per user × non-overlapping 2-month block; refit is load-bearing — plugging in FIXED abilities attenuates the fitted scale (error-in-regressor), while the refit-at-every-s profile likelihood is certificate-clean FOR THE SLOPE: on synthetic outcomes generated at true s=1 it returns ~1.00) and ONE global scalar trained that phase 1 held at unity — the slope scale s (ships as `quality` = s·slope, s ≈ 1.6). **The FLOOR ships UNSCALED (2026-07-28).** A floor scale f was fitted here alongside s until the same certificate was pointed at it and showed it is an ARTIFACT OF THE ESTIMATOR, not a property of the data: on outcomes generated at a true f=1 the fit returns 0.90 (pooled over 15 replicates × 3 ability-drift levels, se 0.007, 14 SE from unity), while the real-data estimate was 0.92 — i.e. inside the artifact, with practically nothing left to correct. Cause: abilities are profiled from the same rows they score, so each absorbs part of its unit's realised luck, and the floor is the one parameter that stays fully identified exactly where those abilities are worst — at the low rail ∂P/∂slope → 0 with the saturating sigmoid while ∂P/∂floor → 1 (there the response IS the floor), and the ceiling λ is held fixed, so ability noise pulls the floor down one-directionally and the slope barely at all (s bias is an order of magnitude smaller: −1.1% jointly, +1.9% with the floor held fixed, i.e. in the CONFIGURATION THAT NOW SHIPS — the joint fit's slightly cleaner slope was a biased floor compensating, a cancellation not worth relying on). Bias tracks 1/(rows per ability unit) across five unit granularities × three drift levels, the Neyman–Scott signature. Shipping f would have shipped the bias as signal. Verified NOT an optimizer artifact (f flat from step 1000 to 10000, real and synthetic) and NOT the degenerate one-sided units (27% of units, 0.9% of rows). Harness + the rejected alternatives (bootstrap de-biasing, split-panel jackknife, cross-fitting, thin-unit merging): `auxiliary/rating_dev/eval_phase2_units.py`. Pure BCE — no dropout (nothing stochastic remains), no barriers (they act on the frozen heads) — in the CLIENT's response form pivoting at the shipped rating (mode-'slope' semantics: ratings stay the 80%-clear anchors; scaling around the trainer's internal 50%-point would rescale the rating axis itself). Fully deterministic (zero/mean inits, full-batch Adam, no RNG). **An in-sample refit does NOT re-absorb the multiplier to 1** (the old EIV rationale for out-of-sample fitting is measured-wrong): frozen-θ plug-in gives 1.62 (attenuation-biased low), free-θ 1.71–1.77 across unit granularities, walk-forward 1.667 — all one plateau, every criterion within ~0.1 mnat of the others' optima. `utils/rating/slope_calibration.py` keeps the walk-forward as the client-condition validation harness (its own certificate: s = 0.993 on true params). **The multiplier's cause is REGULARIZATION-INDUCED SCALE COMPRESSION, established by parametric bootstrap (2026-07-24; the earlier errors-in-variables/ability-noise explanation is measured-WRONG — within-user drift sd is only ~0.14 gauge units, predicting s ≈ 1.01, and every ability-noise treatment was invariant: certainty weighting inert, sampling-ELBO worse, Gauss–Hermite quadrature marginal likelihood worse still, s→1.78, because its population prior adds MORE shrinkage).** The bootstrap (`--synthetic-outcomes` in the harness: outcomes regenerated from the fitted model itself — static known θ per attempt, identical row structure — then the full recipe retrained on them) reproduces the real multiplier on clean data (s 1.686 vs real 1.667) while the criterion applied to the TRUE generating params returns s = 0.993, i.e. the walk-forward is unbiased and the machinery manufactures the whole effect. Head-by-head hybrid attribution: the fitted per-problem RATING scale is compressed toward the feature-conditional mean by k ≈ 0.76 attempt-weighted, and the client measures gaps in shipped-rating units, so the true response profile is 1/k ≈ 1.32× steeper per claimed unit than the shipped slope (rating-error-only s = 1.323 ≈ 1/k exactly); per-problem slope shrinkage (geo-mean 0.92) and floor homogenization compound it to ~1.67. **The compressing regularizer is DROPOUT specifically** (dropout-0 ablations: walk-forward s collapses to ≈1.05 real / 1.08 synthetic — but held-out-problem logloss explodes to 0.727, BELOW the constant predictor, with memorized slopes p50 ≈ 7.8; the barriers are exonerated — without them the rating scale EXPLODES, the failure they guard against; no weight decay exists, plain Adam). So s ≈ 1 and generalization are mutually exclusive with this feature set: dropout limits per-problem fingerprint memorization (its purpose), which caps how much idiosyncratic (feature-inexpressible) difficulty the fitted values carry, and the walk-forward scale is the measured price. **The needed correction is FLAT across attempt-count strata on real data** (stratified walk-forward: residual per-bin multiplier 0.96–1.03 after the global constant — the bootstrap's attempt-dependent k is an artifact of measuring against the generating model, whose light-attempt values are already pure prior; vs TRUTH the feature bottleneck (light problems) and dropout-limited memorization (heavy problems) compose to a roughly uniform factor), so a PER-COUNT correction is ruled out and the global scalar is the right form ALONG THAT AXIS — keep the stage and don't re-attempt ability-noise fixes. **Flatness is measured against attempt count ONLY** (and by an ad-hoc analysis — no stratification harness is committed): rating, slope and FLOOR strata are unchecked, and the floor axis is the prime suspect because the hybrid attribution's third component IS floor homogenization, a floor-dependent effect a single scalar cannot express (then the hard rating tail, where fitted values lean hardest on feature extrapolation). Treat one scalar as UNREFUTED rather than established until those strata are measured the same way; don't add per-problem/per-count corrections meanwhile. **The explicit-random-effect escape route is also measured-DEAD (2026-07-24): per-problem difficulty residuals co-trained JOINTLY are degenerate in every configuration (four distinct escape routes measured: difficulty-as-floor, slope-residual outcome-pinning, pre-whitening ridge evasion via trunk scale deflation, post-whitening raw-scale runaway — a per-problem parameter co-trained with the differentiable gauge always finds a scale freedom), and the statistically sound FROZEN two-stage EB fit (1-D MAP per problem vs the frozen recipe, τ EM-learned) is healthy but yields NOTHING out-of-user: τ = 0.30 shipped-rating units is real, but at median ~2 attempts/problem the posterior shrinkage is ~0.06, out-of-user walk-forward gain +0.02 mnat/attempt, honest s ~unchanged (a full-data δ-fit shows s→2.0 with +33 mnat, which is pure self-leakage — per-problem residuals break the walk-forward's exogeneity assumption, so any residual eval MUST be fold-by-user). The idiosyncratic difficulty the compression suppresses is per-problem UNIDENTIFIABLE at current data density, making the global multiplier essentially optimal, not just pragmatic. Mixup likewise measured-rejected (can't replace dropout — LL 0.590; on top of it, more compression for −ρ). The one untested ceiling-raiser is D4 symmetry augmentation of the activations (feature-side, needs no per-problem identification).** Single-seed in production — seed-reproduction confirmed at seeds 1/2 (the barriers' LL cost stays ±0.001, rail empty, ρ within 0.004 of the free fit every seed; cells in the 2026-07-24 experiment series). **The full experiment surface — `--production-flags` (reproduces this shipped config), `--gauge`, the divergence-barrier weights, the EIV probes (`--theta-posterior`, `--certainty-weight-k`, `--theta-quadrature`), the staged/M0b legacy configs (`--staged`, `--stage-plan`, `--separate-trunks`, hier/mech-floor/residual machinery), the held-out / survey-ρ / time-adjusted-ρ eval suite, and the alternative objectives (even-error DRO, gap-balance, kNN) — lives in `auxiliary.rating_dev.train_rating_staged`** (the production superset; `…_research` holds a non-staged research variant of the same surface), so a test tweak can't break the shipped ratings. The staged structural study (difficulty↔slope coupling, the ceiling's order-dependence vs floor, the fixed-point search) lives in the staged trainer's own flags. Do experiments there; the even-error DRO study (its flatness↔cost knee, and why centering on the per-bin base-rate loss is load-bearing — raw-loss DRO/CVaR chase the aleatoric floor and lose to ERM) is reproducible through that trainer's `--even-error` flag. The PWA reads the same `rating` + `slope` fields regardless of model internals.

## Architecture notes that span multiple files

**Tsumego identity is symmetry-aware and single-solution.** Filenames come from `get_orientation_invariant_hash` (`pipeline/generate_tsumegos.py:154`) — SHA-256 taken over all 8 D4 transforms of the board, with `min()` picking a canonical orientation. The dataset therefore cannot contain two problems that are rotations or reflections of each other; `tsumego_id` is the symmetry-canonical hash truncated to 8 hex chars. This invariant is corpus-wide clean since the 2026-07-21 id surgery (the pre-09/2025 move-sequence-hash ids were renamed to canonical, duplicate positions collapsed, and the DB rewritten through the committed `surgery/id_map.json`; `auxiliary/check_corpus_ids.py` re-verifies, and `--emit-map` regenerates a surgery map if a future defect ever needs one). By generator design every problem has exactly one correct first move (the `solution` returned by `ProblemFinder.create_problem`); downstream code can rely on the "one canonical answer per problem" invariant. **That answer is also `variation_nodes[0]`, and generation ENFORCES it rather than assuming it** — `promote_winning_first_move` (`utils/katago/add_variations.py`) reorders the decision node's children so the move the SHIPPED evaluation comments name (highest winrate for the mover, score breaking exact ties — the client's `findBestMoveFromChildren` rule) leads. The two can disagree at generation time: the solution written first is what `ProblemFinder.is_valid` verified on a deeper re-read, while the candidates' comments come from later passes at their own playout budgets. Reorder, don't discard — such a position is still well-posed, and `first_move_is_well_formed` (the separate single-solution gate) passes it. **The invariant is load-bearing because the two consumer kinds read the solution differently**: the client picks by evaluation and is order-blind, while every backend stage takes it POSITIONALLY (`extract_activations`' `correct_idx`, `benchmark_bots`' grading), so a misordered file silently feeds a LOSING move's activations into the rating features and the shipped per-problem axis vector while still playing correctly in the app. `auxiliary/check_tsumego_sequences.py` re-verifies the corpus (`winner is NOT variation_nodes[0]` must be 0). Note the SGF variation order is NOT what the activation npz uses — that is board-scan order, addressed by `correct_idx` (see the extraction note below).

**Board size — two supported modes: 9x9 and 13x13.** Both ship in production; the PWA picks one from the URL path (`/9` or `/13`) via the SPA fallback in `pwa/src/index.js`, and the D1 `report` endpoint records `size` per attempt. **`/9` and `/13` are entry-only size HINTS, not persistent addresses.** They are read once at boot (`getBoardSizeFromPath` → `resolveInitialBoardSize` in `pwa/js/main.js`); the chosen size persists in state/localStorage thereafter, not in the URL. `cleanUrl()` (lives in `pwa/js/problem-loader.js`, called from `displayProblem`) **collapses the path to `/` and strips `?id`/`?o`/`?recall` whenever a NON-linked problem is painted**, so once you're on a normal problem the address bar is `/`. Do NOT assume a reload leaves the bar at `/9` or `/13`; it does not. **Linked (shared) problems are the deliberate exception: their `?id`/`?o` are KEPT in the address bar for the whole linked session** (`displayProblem` skips `cleanUrl` while `appMode === LINKED`), so that any reload — a service-worker update takeover (`index.html`'s `controllerchange` → `location.reload()`, the most common one; in-app browsers like Instagram hit it when a stale cached SW is replaced by a freshly-deployed version), the `?id`-404 / repeated-load-failure reloads in `problem-loader.js`, the version-mismatch `maybeReload`, or a manual refresh — **re-enters the SAME shared problem at boot** (`parseUrlIntent` reads `?id`) instead of dropping to the standing challenge. The URL is cleaned the instant the user moves on to a non-linked problem (`returnToChallenge`/`advanceToNextProblem` → `displayProblem`). On the **pipeline side** there is no single global `BOARD_SIZE` and no in-process dual-size run. The three single-size generation steps — `pipeline.tune_engine`, `pipeline.generate_tsumegos`, `pipeline.benchmark_bots` — take a **mandatory positional `size` arg** (`{9,13}`), which is threaded through the utils (`KatagoQueries(controller, board_size)` owns it as a public `board_size` attribute; `KatagoController.start_engine(model, board_size, …)`, `ProblemFinder` reads `queries.board_size`, and the leaf helpers `construct_initial_sgf(…, board_size)` / `get_child_move(…, board_size)` take it explicitly). The downstream steps (`extract_activations`, `build_axes`, `train_rating`, `map_rating_to_rank`, `package_for_pwa`) instead iterate `ALL_BOARD_SIZES` and process both sizes in one run — they take no size arg. Artifact directories are keyed by size: `tsumegos/<size>/`, `attempts/<size>/`, `ratings/<size>/`, `pwa/tsumegos/<size>/`. To refresh both sizes, run each generation step once per size (e.g. `… generate_tsumegos 9` then `… generate_tsumegos 13`), then run the downstream steps once. On the remote, `vast_orchestration.py run <step> <size>` forwards the size verbatim (validated locally against `ALL_BOARD_SIZES`).

**On the client, rank + stats + the learned models are merged across sizes; histories, `M` curves, and problem pools stay per-size.** From the user's perspective 9x9 and 13x13 share one rank (front-page label, problem selection, recall eligibility) and one stats page. `pwa/js/state.js` keeps `answerHistory` as ONE unified cross-size array (date-ordered, each entry tagged with `size`; the recent working set in localStorage, the older tail in IndexedDB — see the answerHistory-storage-split note below) plus single shared values (`userRank`, `serveRank`, the recall model `modelParams`/`adamState`, the weakness model `weaknessParams`/`weaknessAdam`/`weaknessSe`/`weaknessAxisCov`); the only per-size persisted bucket is `challengeProblem`. (A `mergeSharedAcrossSizes_v2` migration flattens any legacy per-size rank/model buckets: `userRank = max(rank_9, rank_13)` — a strong 9x9 player immediately gets hard 13x13 problems — and the model buckets are dropped so the shared models retrain.) `getMergedAnswerHistory()` returns that unified array (the WORKING SET), each entry tagged with `size`; the recall and weakness models train from it (they slice the recent window, so the working set suffices). The stats panel (`showDetailedStats`, in `pwa/js/stats-ui.js`) instead awaits `getMergedFullAnswerHistory()` so its charts span the whole career (working set + IndexedDB tail). Pooling is sound because every feature they read is board-independent — `problemRank` is the consensus internal rank (a normalized 0.5 means the same internal rank on either board), and the embedding axes are jointly fit across sizes. Play-time size-awareness is preserved: a recall problem can only be re-shown on its own board, so `getRecallCandidates` takes an explicit `history` (defaults to the active size; the merged union is passed only for stats counts) and `buildRecallSchedule(size)` reads the shared model + shared rank but that size's history. Two consumers do real work to pool: the recall logistic carries a `SIZE_IS_13` fixed effect (9x9 = baseline) whose coefficient ÷ logit-per-rank is the stats panel's "stronger/weaker on 13x13" readout; and the skill decomposition (`rank-decomposition.js`) pools in **internal-rank space** with a per-attempt slope `LOGIT_PER_RATING / |M'(rating)|` (each attempt mapped through its own size's curve), so both sizes share one skill curve without the rank-space slope bias.

**answerHistory storage is split: a unified working set in localStorage, the cold tail in IndexedDB.** `answerHistory` is ~99% of localStorage and on heavy users overflows the ~5MB quota, so `pwa/js/state.js` keeps the most-recent `ANSWER_HISTORY_WORKING_SET` (3000, `constants.js`) attempts — unified across both sizes — as a synchronous localStorage array; everything older is evicted to IndexedDB via `pwa/js/history-store.js` (`appendTail`/`getTail`/`updateTail`/`clearTail`, durable via `navigator.storage.persist()`, every method a safe no-op/empty if IDB is unavailable so play degrades to working-set-only, never breaks). 3000 is the largest hot window the app uses on the *merged* history (the recall-candidate replay warms over the last 3000), so the working set is a superset of every synchronous read: all the existing consumers read `state.answerHistory` (a cached active-size filtered view of the unified array) or `getMergedAnswerHistory()` (the working set) and already slice ≤3000 (`getRecallCandidates` −3000, the models −`MODEL_INPUT_HISTORY_LENGTH`). Only the full-career charts await `getMergedFullAnswerHistory()` (tail ⧺ working set, de-duped by `(problemId, date)`). The write path stays synchronous — `setAnswerHistoryForSize`/`updateAnswerHistory` route through one `reconcileSize` that replaces a size's entries in the unified array and persists; a debounced `evictColdTail()` then appends overflow to IDB **and confirms before trimming** the in-memory/localStorage working set (crash-safe seam: a kill mid-evict leaves a de-duped dup in both, never a gap; an IDB-unavailable append keeps the rows in the working set). `initHistoryStorage()` runs once at boot (the state-epoch gate at `state.js` import time has already settled the storage shape) — `main.js` awaits it before the embedding backfill writes, freeing localStorage on a quota-stressed device. The cold tail feeds ONLY the full-career chart (it is all older than `MODEL_INPUT_HISTORY_LENGTH`, carries no embeddings, and no model reads it). A **curve-only** refit recomputes the tail's `problemRank` from its stored raw rating (`backfill.js` via `updateTail`, no shard walk). A **ratings change** instead re-derives the tail's full rating fields from the shards — the SAME shard walk the working set uses, extended to the tail's problem ids — because the tail's ratings are frozen at eviction time, so after a re-rate they go stale AND device-dependent (each device evicted at a different rating era), and the chart plots them: two synced devices' Rank-tab graphs diverged at the start until this. A problem that left the corpus has its rating fields STRIPPED rather than left stale (the attempt stays, rating-less; `flattenAttempts` then drops it from every estimate — front-page rank, chart, weakness, recall all already skip rating-less/embedding-less rows). An account switch `clearTail()`s then re-splits the full pull. Two accepted tradeoffs, both kept synchronous on purpose: a re-draw of a problem last seen >3000 attempts ago is treated as new (repeat-detection scans the working set only), and `timeAdjustDeltaRating` uses the working-set median solve time.

**KataGo binary selection.** `utils/katago/controller.py` reads `KATAGO_PATH` from env, defaulting to `bots/katago` (OpenCL build). `vast_orchestration.py` uploads `bots/katago_cuda` and sets `KATAGO_PATH=bots/katago_cuda` on the remote. Don't hardcode the binary path; rely on the env var.

**`bots/analysis.cfg` is hardware-tuned in place.** `pipeline.tune_engine` rewrites `numAnalysisThreads` and `nnMaxBatchSize` for the current GPU. `vast_orchestration.py`'s `setup` ships the local cfg once but `update` deliberately skips it so remote tuning isn't clobbered. If you edit the cfg, expect the tuner to overwrite your changes.

**`KatagoController` is thread-safe by design.** A single master reader thread fans responses out via per-query `threading.Event`s keyed on query IDs. `send_query` is blocking from the caller's perspective. Multiple worker threads in `generate_tsumegos.py` and `benchmark_bots.py` rely on this.

**Models live outside git.** `models/` is gitignored. `utils.katago.models.get_model(filename)` lazily downloads from `media.katagotraining.org` (or GitHub for 9x9 / human models) on first use. The default model is `MODEL_FULL` (`kata1-b18c384nbt-...`).

**PWA SGF format carries embedded analysis.** Each branch comment in a tsumego SGF is `"<winrate>%/<score>"` (e.g., `"86.4%/3.1"`). Client-side analysis (`pwa/js/sgf.js`) reads this directly; only when missing does it call the server (`pwa/js/api.js` → `analysis_server/server.py`). Don't strip these comments when manipulating SGFs.

**PWA state is centralized.** `pwa/js/state.js` holds the single mutable object; all changes go through exported setters. `state.appMode` switches between `'solving'` (game-logic.js), `'analyzing'` (analysis.js), and `'linked'` (rank-frozen URL-shared problems). Click handling in `board.js` routes by `appMode` (LINKED clicks go through game-logic, same as SOLVING). **Linked-mode attempts are deliberately recorded nowhere:** `sendReport` and `updateUserStats` (`attempt-recorder.js`) both early-return on `state.problemHistory[0]?.linked` (the canonical flag, set in `problem-loader.js`), so a solved shared-link problem reaches neither D1 (`tsumego_reports`) nor local `answerHistory`. Keep the two guards in lockstep on that one flag — a rank-frozen share must not count toward the corpus, anyone's stats, or the server-stats/rank histograms.

**Account sync: the userId IS the account credential; history syncs by append-only cursor.** The 8-char `userId` (crypto-random — `generateUserId` in `state.js`; exactly 8 chars everywhere, enforced by the Worker's `isValidUserId` since the 2026-07-21 surgery normalized the legacy long ids) doubles as the account password: the Account dialog (hamburger → More, `account-ui.js`) shows it, and entering another code on a device adopts that account (`account-sync.js switchAccount`: wipes account-derived localStorage, reloads; init's `maybeFinishAccountSwitch` then clears the IndexedDB history tail, pulls the full server history, and re-splits it into the working set + tail before the first problem load). Sync is pull-based over `POST /sync` because `tsumego_reports` is append-only — a cursor fully captures "what changed", no content hash. **The cursor is the AUTOINCREMENT `id` (`sinceId`), not `created_at`**: id is arrival order, so a row inserted with a historical `created_at` — an offline flush, a backfill — still gets a fresh high id and is pulled. (created_at stays as event time: charts, stats window, recall intervals; a `/sync` request without a valid `sinceId` is a plain `400`.) **The local representation is MIRROR-BY-ID**: the device's acked history is a 1:1 mirror of the server's rows keyed by `serverId` — identity is the row id, and the merge (`mergeRowsForSize`) does **no timestamp dedup**: a row is "had" iff its id is in the working set or the tail (`getTailSyncIndex` in `history-store.js`), so the digest matches the server **by construction**. A **complete from-0 pull is a TRUE MIRROR sync in both directions**: rows the device lacks merge in, and local acked rows the server no longer has are deleted by the deletion pass (`mirrorDeletePass` — working set AND tail via `pruneTail`, which also collapses evict-seam and tail-internal duplicate ids), so every digest-divergence direction converges to an exact match. `pullReports` settles any pending debounced eviction BEFORE snapshotting the tail index — an eviction landing mid-pull would be invisible to the snapshot, re-insert as working-set copies, and make the deletion pass churn against it (found on the heaviest account during the epoch rollout). Invariants in `account-sync.js`: (1) the cursor advances **only from pulls**, never from this device's report acks; (2) own rows are recognized on pull by their **id** — `/report` returns the row id and `recordReportAck` stamps it (serverId presence = acked); ack-less (offline) entries are claimed by an **EXACT `created_at === date` match** (client-owned event time — no fuzzy window; every era-conditional claim path was retired with the 2026-07-21 state epoch); (3) only an account switch or the epoch gate's re-adoption pulls from the beginning (`fromStart`); a fresh/empty account just falls back to a cheap from-0 pull. **SUM-FIRST digest backstop**: every `/sync` response carries `serverSeq`/`serverDigest`/`serverMaxId` (user_seq + Σ rowHash(id), always defined — the digest chain is a table invariant since the surgery materialized every row, and the INSERT maintains it), and every `/report` response carries `userSeq` + `digest` (the post-insert sum). Count and sum are CO-EQUAL divergence signals — `digestMismatch` returns 'gap'/'surplus'/'content' as log labels only, and any of them escalates to the full mirror reconcile (`checkInSync`; no accept-and-remember state — mirror semantics guarantee convergence). The per-report check (`checkSyncSignal(userSeq, digest)`) treats a seq jump past `lastSeq + 1` as "another device wrote" → debounced incremental pull, and an equal-seq digest as a content check via a 3s-deferred, staleness-guarded compare against the local digest (working-set walk + the tail digest CACHED in `history-store.js`, invalidated by its writers) — so an active session is fully self-verifying with no polling. Merged rows become skeleton entries; `fillSyncedHistoryFields` (`backfill.js`) fills ratings from `problem_params.bin`, correct-move embeddings from the lookup-aligned sidecar, and derives `pickedCellIndex` from the reported move for wrong attempts: **every stored `move` is in the canonical orientation-0 frame** (`buildReportPayload` inverse-transforms the click through the served orientation; the surgery NULLed the pre-2026-07-07 served-frame repeat moves, so no era gate remains). The front-page rank is the **linear-information window MLE** (`estimateWindowRank` in `rank-decomposition.js`) — a **pure function** of the recent first-time history: a positionally-weighted 4PL Newton fit over the last `WIN_CAP`=500 attempts, warm-started at the prior rank, R clamped to a wide [−34.5, 25.5] range (so sub-20k kyu still extrapolates; the clamp is a numerical guard, not a display floor). The per-problem slope `a_p` enters through the Fisher information, so a sharp problem pins the rank harder; `serveRank` adds an uncertainty-scaled UCB bonus (`WIN_UCB_K`·max(0, se−se_floor)) that problem SELECTION uses while display uses the raw `rank`. **`se_floor` is RANK-DEPENDENT, not a constant** (`localSeFloor` in `rank-decomposition.js` → `seFloorForMeanInfo` in `rank-window.js`): it is the irreducible SE a full at-rank window would leave, `1/√(WIN_PRIOR_INFO + ((WIN_CAP+1)/2)·⟨I⟩)`, where `⟨I⟩ = ⟨anchorInfo(floor)·slope²⟩` is the mean per-attempt 4PL information of the ≤50 corpus problems nearest the estimate **already loaded** on the active size (no fetch on the hot path; the selector's shard loading keeps the pool warm; the per-problem transform runs only on those 50). The mean is UNWEIGHTED on purpose — it describes the post-convergence steady state, where selection is weakness-driven rather than information-driven. **`⟨I⟩` is the FULL 4PL information, not the 2PL `0.16·⟨slope²⟩` (fixed 2026-07-26)**: the old constant ignored the guessing floor and the lapse, claiming ~1.4× more information than a real at-rank window can deliver, so the floor sat 0.07–0.27 stones BELOW the SE `windowMLE` actually converges to (worst in the 17k–8k bands, where the curves are flattest). Consequences of the mismatch, both now gone: `max(0, se − se_floor)` never reached zero, so every converged user carried a permanent fraction-of-a-stone over-serve; and `rankConverged` (se < 2×floor) fired later than its "within 2× of the best achievable" intent, holding users in the information regime past the point weakness personalization should have taken over. Verified end-to-end on a simulated full at-rank window: residual bonus 0.14–0.33 stones under the old floor vs ≤0.03 under the new one. Flat-curved kyu problems carry so little rank information that even a full window floors at ~1.3 stones (vs the old constant 0.35, which implied a slope only dan problems reach — leaving kyu users perpetually served ~1 stone above rank and never converging); sharp dan curves floor near 0.3. So the bonus collapses to the user's OWN rank at convergence on every part of the ladder. When nothing is loaded near the rank yet (Worker, or a client before any shard loads) it falls back to the constant `WIN_SE_FLOOR` — harmless since se dominates the bonus that early. The Worker's `estimateWindowRankFromFlat` (leaderboard) passes no floor callback, so it is unaffected. Because the estimate is a pure function of the merged recent history, device adoption and an incremental foreign sync are the **same operation** — recompute from scratch; there is no loop state to warm and no anchor to recover. `retrainAfterMerge` (`account-sync.js`) has three modes: `adopt` (account switch) re-fits over the new account's full merged history seeded from the data (the prior account's rank is irrelevant); `feed` (ongoing merge) re-fits warm-started from the current rank; `reconcile` (one-off local backfill) leaves the rank untouched (the merged rows are ancient). The recompute runs **silently** (no overlay), so the next live answer's reported rank change is that tsumego's effect alone — a freshly-synced foreign batch moves the rank between problems, never inside the shown delta. Every device sees the same multiset of recent attempts, so they converge to the same rank regardless of how the attempts were batched. After every merge, `retrainAfterMerge` also fires `refreshShownProblemAfterSync` (`problem-loader.js`) — and the tab-visible resume trigger fires it on EVERY resume, merge or not, since a recall can enter its window from time alone while the tab was hidden. It re-runs the NORMAL problem-presentation selection (a due recall wins subject to the stochastic recall-share gate — see the recall-serving note below; the refresh path rolls the gate only when INTRODUCING a recall over an idle novel, never to swap a shown recall away — else the standing challenge), so a problem solved on another device is swapped off screen and a newly-due recall can appear; an actual swap goes through a GREY `fadeOverlay` with a localized "Problem updated" notice (grey deliberately — white/red are the correct/wrong answer cues). The standing `challengeProblem` is kept by default, so sync can never dodge a served challenge — recalls only delay it; the single exception is that the user completed that exact problem on another client (now inside the recent-repeat window, `challengeAlreadyAnswered`), which makes it illegal to serve, so only then is it swapped for a freshly selected one. The refresh touches the board only when a problem sits idle in SOLVING mode (never mid-answer, in review/analysis, or over a linked problem), and skips the repaint when selection lands on the problem already shown (no timer reset, no recall re-orientation). (This replaced an earlier momentum-loop design — `momentum-rank.js`, hybrid replay, `feedAttemptsThroughLoop` — entirely.) Pulls run on load, tab-visible, and the `online` event — **unthrottled** (an up-to-date incremental poll reads ~0–1 D1 rows via the user-id index, so a session resume merges — and can refresh the shown problem — immediately; overlapping triggers collapse via the in-flight guard, and only the outbox's full-pull flush keeps a throttle); **active sessions need no polling at all** — every `/report` response carries `userSeq` (the per-profile attempt count), and `checkSyncSignal` triggers a debounced pull when it lands past the device's expected `lastSeq + 1` (= another device wrote in between). An up-to-date poll and the latest-row digest summary read ~0–1 D1 rows **via `idx_tsumego_reports_user_id`, which must stay in place**. **Recall serving is volume-targeted via a stochastic gate; stability has NO ceiling.** A due recall wins a serve decision only with probability `recallServeShare()` (`pwa/js/recall-model.js`) — the constant-volume equilibrium share for a TARGET daily volume A and the user's base window-open delay τ0 (their fitted r=0 stability, so between-user memory variance is priced in). **A is `SHARE_VOLUME_FRACTION` = HALF the user's own trailing-week daily average, not the average itself** (2026-07-27): the balance point is solved for the volume a LIGHT day delivers, so a user practising below their usual pace still gets through every due recall, and on an average day the pool is over-served and drains. The direction is the opposite of what "half" suggests — the working window is measured in ATTEMPTS, so a lower target volume spans more days, a ladder entry must climb further before graduating out of it, and the served share RISES (at the shipped `GROWTH` the halving adds ln2/GROWTH ≈ 0.85 rungs, worth a few points of share across the plausible volume/τ0/entry-rate range). The guillotine falls at ladder rung `k = ln(3000/(A·τ0))/GROWTH`, a ladder entry consumes `E = (0.8^-k − 1)/0.2` recall serves before graduating (0.8 = retention at the R=0.80 window open = per-serve success probability, streak resets included), and with `e` = the recent failed-below-rank fraction of novel serves the balanced recall:novel ratio is `ρ = e·E`, served share `ρ/(1+ρ)`. While the share is not estimable (no model / no week volume / <20 recent novels / no rank) due recalls always win — the pre-gate behavior — and the gate FAILS OPEN on any estimator error (`recallGateAllows` in `problem-loader.js`; `selectNextProblem`'s never-throws contract). The roll happens BEFORE the recall is built (a gated-out recall costs no shard fetch) and is **DETERMINISTIC — hashed from (most-due candidate id, last recorded attempt date), not Math.random()**: the tab-visible `refreshShownProblemAfterSync` re-derives the serve decision's own outcome instead of re-rolling (independent resume rolls would compound — n task-switches give a due recall 1−(1−share)^n chances to swap onto an idle novel), while every new attempt (local or synced) re-seeds, so genuine serve decisions stay independent Bernoulli(share) draws. A gated-out recall stays in its window for a later roll or ages out unserved — that pruning is the pool's decay channel, so the pool self-stabilizes at any volume. Notification clicks (`?recall=1`, `main.js`) bypass the gate. Complementary invariant: `stabilityDaysForRepeat` has NO upper clamp (the old `MAX_STABILITY_DAYS = 365` turned graduation into a perpetual ~81-day recycle, so the recall pool could only grow and unrestricted serving drifted toward 100% recalls); graduation is the streak's exponential interval (×e^GROWTH ≈ 2.17 per success) outgrowing the `RECALL_CANDIDATE_HISTORY_LENGTH` = 3000-attempt working window, and `!isFinite(S)` maps to Infinity = never-due (a candidate with R pinned at 1 is simply not in the [0.60, 0.80] window; `buildRecallSchedule` skips it explicitly). Don't reintroduce a stability ceiling — overflow needs none (lnS is a small linear form) and the equilibrium depends on its absence. **MEASURED against the attempt log by `auxiliary/eval_recall_model.py` (2026-07-28, ~16k scheduled serves on clean post-cutoff chains, sub-6h unschedulable pairs excluded; full write-up in docs/methodology.md §2.8):** served recalls clear 71.2% pooled — the window AVERAGE, since R runs 0.80→0.60, so `X_SERVE = 0.8` is the band's UPPER EDGE, not what a serve realizes. **The test against 0.80 is ONE-SIDED — it is a CEILING, not a tolerance edge**: memory decays from the moment of answering, the window OPENS at 20% forgotten and CLOSES at 40%, so 0.80 is the LEAST forgetting the schedule ever serves at. Where in the window the user returns is unobservable and NOT reconstructable, but they aren't waiting in the app, so serves spread across it and should average near its middle (~0.70). Below the ceiling = consistent (the scheduler can't control when in the window the user returns); AT or ABOVE = the model understates that rung's stability. Measured: rung 0 = 66.9% (29σ below ceiling, correct); rung 1 = 80.1% (ON it), rung 2 = 81.3% (+1.1σ), rung 3 = 87.3% (+3.7σ) — **every rung above 0 breaches**, and rung 1 alone is a fifth of all serves. Same in trailing 30d and 60d. It is a POPULATION constant, measured: pooled OR 1.93/1.95/1.96 across min-events cuts of 5/10/20, I²=0%/5%/23% (Cochran Q 99 on 100 df at the loosest = pure sampling noise), 86%→96% of users in the expected direction, and **42% of users have NO r≥1 rows inside the 500-attempt client fit window** (median 1) — a per-user step would be its own prior for most of them and would compete with LN_C for the same rows. Return promptness is a per-user HABIT that sets where in the window their serves land — unobservable, but stable per user, so the WITHIN-USER contrast differences it out and is the sharp instrument. The rung-0→1 rise is WITHIN-USER, not composition (Mantel-Haenszel stratified by user OR=1.94, 13.7σ, 155 users, implying 79.7% vs 80.1% observed; and climbers are the WEAKER group at rung 0 — 66.5% vs 72.3% — so composition suppresses the rise) and it is CONFINED to that first step (rung 2 vs 1 OR=1.13, 1.3σ = null). All of it reproduces on the trailing 30/60 days. Consequence for the shipped share is SMALL (feeding the measured rates into the same reset chain moves E by ≤20% over k=2…6, a few points of share) — delivery is a SEPARATE question and its raw number is mostly confounds: 0.55 serves/entry over 30d becomes 1.17 once you keep only users still playing at the horizon's end and problems BELOW the user's level (the candidate filter deliberately excludes at/above-level problems, and failures concentrate exactly there), against 2.63 windows those users were actually present for — so ~45% of real opportunities are taken, and the gate is DESIGNED to decline some. Pausing (`recallPausedUntil`) is invisible in the DB and is NOT deducted. Don't quote the raw 0.55. Within a rung the elapsed gap carries no measurable signal and the retention computation scores WORSE than a constant held-out (spread ~6× too wide, Platt slope 0.17) — but every interval was scheduler-chosen, so that is a statement about the policy on its own serves, NOT about retention as a law. **WHY the step exists**: r=0 means the previous attempt FAILED (that's how an entry joins the ladder), r=1 means it was the FIRST SUCCESS after a failure — so rung0→rung1 is lapse-state → success-state, not one more ladder step. This is the one place the model is NON-standard: SM-2/FSRS give a lapse its OWN formula (interval reset / distinct post-lapse stability function), while here `LN_C` doubles as both population base AND post-lapse stability and the first success gets the same `GROWTH` as the fifth. Matches the data: the carrier is BINARY (did the last attempt succeed) not a count — rung2 vs rung1 is null. Competing reading (survivorship on per-(user,problem) memorability the model has no term for) predicts the same shape and is NOT separable at this repeat density; model-visible selection covers only ×1.08 of the ×1.81 (mean z rises +0.22, KAPPA 0.343). Fix is identical either way. **SHIPPED as `first_success_step` in population_constants.json** (`lnS = LN_C + KAPPA·(z−Z0) + GROWTH·r + first_success_step·[r≥1]`, recall-model.js): an INDICATOR, not a second growth rate — the 2nd success adds nothing (rung2-vs-1 null). Fit by MOMENT MATCHING, **never by retention likelihood** (the likelihood scores predictions on intervals the scheduler itself chose, and sizes the step ~3x too small). Under the exponential form, scaling an interval by f scales ln R by f, so the multiplier taking a rung from realized p to target q is ln(q)/ln(p) — no fit needed. For rung-0 parity: rung1 ×1.81, rung2 ×1.94, rung3 ×2.95, i.e. steps of **×1.81 at the first success and ×1.07 at the second** (= a first-success step of ≈0.6 added to lnS, leaving GROWTH alone) — the same shape the within-user ORs give. Fitting that step by LIKELIHOOD instead sizes it at ×1.20 and buys only 0.002 nats held-out (a FREE per-rung effect, the ceiling on any reshaping, buys 0.004 against an 0.08-nat deficit to a constant) — that is the likelihood being the WRONG INSTRUMENT, not the correction being wrong: it scores predictions on intervals the scheduler itself chose, and a scheduling change moves those intervals. **This correction pulls AGAINST delivery** (longer intervals = fewer serves per entry in a fixed horizon), which is the real reason to hesitate. Recalibrating the spread is likewise not worth it (Platt-recalibrated 0.6162 vs constant 0.6185 vs rung-only 0.6105). And rung-only beating the model is a DIAGNOSTIC, not a candidate — the scheduler needs a due TIME, which a per-rung rate cannot produce.

**Worker-version-driven graceful reload.** `pwa/build.mjs` writes `pwa/src/version.js` so the Worker imports the same hash the client gets via the esbuild `define`. Every `/report` response stamps `X-App-Version`; if it differs from the client's `APP_VERSION`, the client sets `state.reloadPending`. `maybeReload` fires from `setAcceptClicks(true)` only when `appMode !== ANALYZING`, so the refresh always lands between problems — never mid-review. New JS-side features that depend on the Worker version (e.g. embedding/ratings backfills keyed by content hashes shipped in `embedding_meta.json`) ride this reload signal. **`computeVersion()` folds a hash of every inlined data file (`INLINED_DATA_FILES` — `embedding_meta.json` + the curve/rank-map/population JSONs) into `APP_VERSION`** so the reload signal moves on a data-only re-ship: `pwa/tsumegos/` is **gitignored**, so a git-HEAD-only version would be blind to a `package_for_pwa` re-ship from the same commit (the original cause of the cross-device staleness — see the data-version note).

**Served data files are cache-busted by a content `data_version`, not `APP_VERSION`; `embedding_meta.json` is inlined.** The bug this fixes: data files were fetched `?v=${APP_VERSION}` and cached **cache-first by URL** (`sw.js`), but `APP_VERSION` was `git rev-parse HEAD` while the served data (`pwa/tsumegos/`) is **gitignored** — so a `package_for_pwa` re-ship from the same commit served a **stale** `metadata.json` indefinitely, and a device could stamp the current `ratings_version` while its per-attempt `rating`/`slope`/`floor` came from an older shard set (the gate then skipped forever → two devices on one account rendered different rank graphs). The fix is a content-addressed chain rooted in **one inlined manifest**: (1) `package_for_pwa` writes `data_version = hash(metadata.json files)` into `embedding_meta.json` (covers shards transitively — each `metadata.json` lists every shard's content-hash filename); (2) `embedding_meta.json` is **inlined into the JS bundle** via `pwa/js/data-version.js` (`import`, dropped from dist by `DIST_DEAD_FILES`) — it can never be served stale, and `DATA_VERSION` is read synchronously from it; (3) the only query-busted fetches — `metadata.json` and `lookup.txt` (`problem-loader.js`, `backfill.js`) — use `?v=${DATA_VERSION}`; shard `.zip`/`.embeddings.bin` are already content-addressed by filename (NOTE: Workers static assets answer Range requests with **200 + the full body** — no 206s, cached or not, verified in production — so the `.bin` "Range" fetchers download whole files, slice the requested bytes client-side (`sliceRangeResponse` in `picked-embedding.js`, which also rejects a 206 whose Content-Range offset mismatches), and let the SW cache the full 200 like any asset; `pwa/_headers` (copied to dist by the build) additionally gives `/assets/*` immutable and `/tsumegos/*` + `/lookup.txt` 1-day browser cache-control — safe because the assets layer is deploy-consistent (per-deploy manifest, content-hash blobs; header changes verified to appear instantly across deploys even on cf-cache-status HIT responses) and all fixed-name fetches rotate their `?v` cache key with `data_version`); the curve/pop-constant JSONs are inlined. `DATA_VERSION` is stamped into `sw.js` too so the runtime-cache prune keeps `?v ∈ {VERSION, DATA_VERSION}`. **`data_version` (cache freshness) is deliberately separate from `ratings_version`/`embedding_version` (backfill gate):** a ship that only ADDS tsumegos bumps `data_version` (new shards → new `metadata.json`) but not `ratings_version`, so new problems become serveable **lazily** with no history walk; a ratings change bumps `ratings_version` and triggers the **immediate** re-derive. The Worker's server-stats reads `metadata.json`/`lookup.txt` by **fixed path via the `ASSETS` binding** (server-side, no SW, no `?v`), so it always sees current dist and is unaffected.

**Server-wide "Community" stats are a cached, read-cost-sensitive D1 aggregation.** `GET /server-stats` serves a single `server_stats` row (`key='latest'`, JSON blob) aggregating the **preceding 7 days** of `tsumego_reports`. `computeServerStats` (`pwa/src/server-stats.js`) runs **one** window query (`WHERE created_at >= ?`) and does all bucketing in JS — totals, daily activity, by-size split, solving/review time histograms (10s buckets capped at 600s, but **bucketing each user's *median* time, so the histogram counts users, not attempts** — heavy users don't dominate; for review time, which is **cumulative across a problem's repeats** (each repeat re-reports the running total), only the last instance per (user, problem) is kept before taking the median, else the running total double-counts), a **recall-time** distribution (per user, the *median* over problems of the novel→first-repeat gap — from the first in-window non-repeat attempt to the very next attempt on that problem, **≥6h** (shorter gaps are ignored entirely), into hardcoded `6h–1d / 1–2d / 2–3d / 3–4d / 4–5d / 5d+` day bins; only gaps whose novel attempt *failed* count, because the spaced-repetition interval lengthens with each success and isn't comparable), and a per-user attempts-per-active-day distribution (`attemptsPerUserDist`). A backfilled row carries a historical `created_at` but a fresh id, so under this convention it IS the newest and prepending is correct. `update_leaderboard_ranks.mjs` used to order by `created_at` instead, on the grounds that backfill inserted at the id frontier and could seat a months-old attempt "on top" — true, but the fix was to make backfill maintain the buffer like every other writer, not to give one rebuilder its own ordering (which also made the cron a re-introducer: it rebuilt in id order every Monday and undid the refresh). Event order would additionally need a `(user_id, created_at)` index that was deliberately dropped, turning a bounded `BUFFER_CAP` read into a full per-user history scan — 3× the rows read across the leaderboard, 34× for the heaviest user, on a path that runs inside `/report`'s `waitUntil`. So anything that overwrites a row's buffer with a stale snapshot drops whatever landed in between **permanently** — later reports append on top of the shortened list rather than restoring it, and the only rebuild path is `createLeaderboardRow`, which runs only for a user with NO row at all. That is the hazard in `auxiliary/update_leaderboard_ranks.mjs`, the retroactive refresh that moves every row's rank onto a new scale after a re-rate (it recomputes `buffer`/`pred_rank`/`pred_rank_se`/`time_delta_rating` only — `country` and `last_active` are untouched, and the `--populate` pass is `INSERT OR IGNORE` so it cannot clobber an existing row). **Run its fetch CHAINED DIRECTLY into the `--remote` apply, never as two steps** — `python3 -m pipeline.fetch_database && node auxiliary/update_leaderboard_ranks.mjs --remote` — because every attempt reported in the gap between snapshot and write is silently truncated out of that user's buffer, with no error and no recovery; `+0 new tsumego_reports rows` on that fetch is the proof the window was clean. Its ordering rule is separate and also load-bearing: `package_for_pwa` → `npm run deploy` → fetch → update, since running it before the deploy lets the next `/report` recompute on the OLD scale and overwrite the work. **Write endpoints are guarded by two cheap, in-Worker abuse/quota layers plus an external WAF rule.** A spoofed/garbage `/report` (or `/schedule`, `/rank-survey`, `/share-event`, `/push/*`) doesn't just hurt integrity — the INSERT spends D1 write quota, and until purged the row inflates every server-stats `created_at >= ?` window scan for 7 days (read quota, the exact thing `idx_tsumego_reports_created` fights). So writes are defended *upstream* of D1, cheapest-first: (1) an **outer Cloudflare dashboard WAF rate-limiting rule** (account config, **not in the repo** — documented in `wrangler.toml`; 100 POST/10s per IP matching **ALL POSTs by method** — no path list, so every write endpoint incl. new ones like `/register` is covered automatically, nothing to add per-endpoint — blocked requests never invoke the Worker = zero Worker+D1 cost); (2) **per-IP Workers rate-limit bindings** (`RL_REPORT` 100/60s for the high-volume `/report`, `RL_WRITE` 50/60s shared by the rest), declared as `[[unsafe.bindings]] type=ratelimit` in `wrangler.toml` and checked in the `fetch` dispatcher **before any handler touches D1** (`rateLimited()` keys on `CF-Connecting-IP`, **fails open** on a missing binding or limiter error so a misconfig never drops a legit write); (3) **in-memory format validation** in each handler (no D1 reads) — `isValidProblemId` (`^[0-9a-f]{8}$`, the symmetry-canonical hash) and `isValidUserId` (`^[A-Za-z0-9_-]{1,40}$`) reject malformed identity fields before the INSERT. Limits were calibrated from the production dump (heaviest real user ≈24 reports/60s incl. review re-reports, p99.9=20), giving ~4× headroom for NAT'd shared IPs. **Deliberately format-only** — we don't check the problem id against the real corpus (that needs a bundled set/Bloom filter); the rate limiter bounds valid-looking spoofs. Two consequences: any **deploy smoke test must POST a real 8-hex `problem` id** (a free-form marker is rejected with 400), and `pipeline.fetch_database` is **unaffected** — `wrangler d1 export` hits `api.cloudflare.com` with an API token, a different hostname than the `onlymove.net` zone the WAF guards (the binding limiter never runs for it either). Activating any of this needs a manual `npm run deploy` (+ the manual WAF rule); there's no auto-deploy. **A fourth, deliberate layer is the MAINTENANCE FREEZE** (`MAINTENANCE_MODE` in `wrangler.toml` `[vars]`, `maintenanceFrozen`/`serviceUnavailable` in `guards.js`): `"1"` makes EVERY POST route return `503 {error:'maintenance'}` with `Retry-After`, and makes `scheduled()` early-return. It is checked in the `fetch` dispatcher **before the rate limiter and before any handler touches D1**, so a frozen request costs one Worker invocation and zero D1. It exists so DB surgery (`auxiliary/purge_tsumegos.mjs`) can run against a table that is standing still — its digest fix-ups are stated RELATIVE to a snapshot, so a row inserted between snapshot and apply would be shifted against a chain it never joined, silently. Freezing is safe because `sendReport` only acks on `res.ok`: a 503 leaves the attempt un-acked and the durable outbox re-uploads it afterwards with its original event time, so the freeze reuses the offline path instead of adding a client-side maintenance mode. `/sync` is frozen too (though it is a read) so no client can observe a half-applied surgery. GETs stay up so the app keeps serving problems; the one writer left is the lazy `server_stats` recompute, which only rewrites its own cache row. Procedure in `docs/db_surgery_runbook.md`.

**`pipeline.fetch_database` is incremental by default and read-cost-sensitive.** D1 bills rows read, and `tsumego_reports` is ~290k rows (>99% of the DB) while every other table combined is <1000 — so re-exporting the whole DB each run would waste almost all of those reads. The default path pulls **only new `tsumego_reports` rows via `WHERE id > MAX(local id)`** (`id` is the table's `AUTOINCREMENT` PK), which the PK index serves reading just the matching rows, and re-fetches every *other* table whole (cheap). **The cursor MUST be `id`, not `created_at`:** the PWA→D1 backfill (`POST /report-backfill`, see the account-sync note) inserts historical attempts with their *client* `created_at`, so a `created_at` cursor would silently skip those backfilled rows even though they were just inserted — whereas `AUTOINCREMENT id` always increases with insertion order, catching them. `tsumego_reports` being append-only (no `UNIQUE`, never UPDATEd/DELETEd) makes the `id` cursor provably gap-free: after a complete pull we hold the contiguous prefix `[1..N]`, and all new rows are `> N`. The fetch is **schema-tolerant and never hardcodes the table list** (except the one name `tsumego_reports`): it discovers tables from the remote `sqlite_master`, full-refreshes each (drop + recreate from the remote DDL + refill), and only if `tsumego_reports`' column set drifts does it re-pull that table whole. Implementation: `db/d1.sqlite` is the **canonical merge target** (rows fetched via `wrangler d1 execute --remote --json`, inserted parameterized — zero escaping bugs), then `db/d1.sql` is **regenerated from it** in a quoted-table-name + positional-`VALUES` form that every `.sql`-parsing consumer in the repo accepts (some require the quoted name, others forbid a column list — this form satisfies both). The `db/` snapshot is read-only as far as the pipeline is concerned; the **wrangler dev (local) D1 is the read-write one** (the PWA is tested against it and scribbles disposable rows into it), so each fetch simply **resets it to the remote state by `shutil.copyfile`-ing `d1.sqlite` straight onto the miniflare D1 file** (`.wrangler/state/v3/d1/miniflare-D1DatabaseObject/<hash>.sqlite`, the one that isn't `metadata.sqlite`) and deleting its stale `-wal`/`-shm` sidecars — discarding local test writes on purpose, and far faster than a wrangler reimport (verified: D1 read/write still work; its internal `_cf_*` tables aren't required). Stop `npm run dev` before fetching — overwriting the file under a live workerd corrupts its view. The wrangler-import path (`update_local_d1`) survives only as the first-run fallback that *creates* a not-yet-existing local D1. `--full` forces a complete `wrangler d1 export` + SQLite rebuild (also auto-used when no `d1.sqlite` baseline exists). Still WAF-unaffected — both `d1 export` and `d1 execute --remote` hit `api.cloudflare.com`, not the guarded `onlymove.net` zone.

**Skill-axes recommender (per-component weakness mining).** The axes are per-problem SKILL DIMENSIONS (supervised residual axes — see *Axes fit* below) but shipped per-CELL: every legal first-move cell gets its own K-dim vector, so the system can score both the **correct** move (a property of the position) and the move the user **actually picked** on a wrong attempt.

*Extraction* — `pipeline/extract_activations.py` runs a vendored PyTorch copy of KataGo b18 (`utils/katago/vendor/`, bootstrapped via `utils/katago/torch_model.py`) and captures the post-skip-add output of all 18 residual blocks (18 × 384 = 6912 floats) **at every legal cell**. Output: `activations/<size>/<id>.npz` with `candidates (n_legal, 6912) fp16`, `xys (n_legal, 2) int32`, `correct_idx () int32`.

**Row order is board-scan order (sorted by `(y, x)`), NOT SGF-variation order, and the cell set is a *superset* of the SGF's root variations.** `extract_activations.process_one_sgf` enumerates every legal cell for the player to move (the color of `variation_nodes[0]`) in scan order and records a `correct_idx` pointing at the correct move's scan position (non-zero in general; e.g. 13×13 `00000f4c` has `correct_idx=38` — verified byte-for-byte that a re-extraction reproduces the on-disk corpus). Do not instead walk the SGF's pruned variations in document order with `correct_idx=0`: that ships a non-superset cell set and does not match the on-disk corpus. Two consequences every downstream consumer must respect:
  - **Pick the correct row by `correct_idx`, never positionally.** Every consumer (the activation-cache builder feeding `utils.rating.features`, `pipeline.build_axes`' per-cell fanout) selects `candidates[int(correct_idx)]`; do not assume row 0.
  - **The npz embeds every legal cell; SGF root variations are a pruned subset, plus the SGF carries a `pass` variation the npz never embeds.** So npz ⊇ {SGF non-pass variations}: every move a user can actually click is embedded (no picked-move ever misses), but ~10% of problems have extra embedded cells with no SGF variation, and 100% have a `pass` that is not embedded. Map cells by `(x, y)` coordinate, not by index, when crossing the npz↔SGF boundary.

*Axes fit* — `pipeline/build_axes.py` (production, NO flags; replaced the skew-ICA `build_embedding` on 2026-07-18 — validation trail summarized in `docs/methodology.md`) trains the **supervised residual-axes model** in `utils/rating/residual_axes.py`: on top of a per-user difficulty baseline, K per-problem axis loadings are learned so per-user positions explain the between-user response residuals — axes are DEFINED by validated human variation, not activation statistics. The **fixed training regimen is load-bearing** (each element fixed a measured failure): g is a direct LINEAR head on the features with unit-RMS columns (free loading scale subsidizes cloning one strong direction; a trunk-shared g can only combine r-relevant features), a lenient mutual+r orthogonality penalty (0.5), and the first 3 axes warm-started at the hand-crafted scalar directions (wr-gap / score-gap / phase-ratio — the learned refinements subsume them). The population residual-difficulty head r is quarantined in the model and **never shipped**. Features are the rating trainer's EXACT inputs (same loaders, same joint-PCA cache/seed — LITERAL parity with `pipeline.train_rating`) plus the rating model's outputs (rating/slope/floor/rank). **K is selected incrementally**: K grows from 3 while the held-out walk-forward LL gain (production-form 4PL baseline, 2-fold by user) stays within `STOP_FRACTION` (3%) of the running peak; the selected K is the last before the breach, so the axis set grows naturally with data volume. **The per-user fit inside that criterion carries the client's own shrinkage (2026-07-27)**: each eval user's axis coefficients are fit under a Gaussian prior whose scale is estimated IN-FOLD by empirical Bayes from a robust (median-absolute-deviation) spread of the per-user coefficients — in-fold because the candidate K has no shipped `weakness_axis_lambda` yet and using one would be circular, robust because the pass that supplies those coefficients is the unpenalized one. Unpenalized, a trailing window whose axis columns are near-collinear (with each other or with rank) admits an effectively unbounded coefficient — `_irls_off` runs undamped Newton steps with no convergence test — and the resulting ~1e7 scores leave the pooled calibration conditioned around 1e14, where **rounding decides the result**: a production run scored −2080 mnat/attempt and selected K=2 while a re-run on identical inputs gave +0.70. This is NOT a property of the user or of history length (the worst case had 1249 attempts, a 731/518 split, a full-length window, after eight healthy blocks), and excluding such users is measured-WRONG in principle: a window that cannot be fit with finite coefficients is one the axes separate unusually well, so dropping it selects on the outcome and deletes the strongest evidence. The pooled axis score is also **standardized before the calibration fit** — a converged logistic fit is invariant to an affine rescale of a regressor, so this changes no fitted value (verified identical to 3 dp on both folds) and only removes the conditioning. Adding the prior RAISED held-out gain (0.697 → 0.792) and moved the selection from K=4 to K=5: unshrunk per-user fits penalize higher axis counts, because more coefficients per user overfit harder when nothing shrinks them. **Selection REFUSES (raises) on a non-positive or non-finite peak**, and asserts the selected K never falls below `K_START`: the stop rule is a FRACTION of the peak, which inverts once the peak is negative — the first candidate breaches against itself and `K_START − 1` gets written out as if it were a decision. Output to `axes/{per_problem.csv, axes.npz, labels.json, label_anchors.npz, per_cell/}`; `axes.npz` carries the model + the content-hash `embedding_version` packaging ships. The per-cell fanout writes `per_cell/<size>/<tid>.npz` (`embeddings (n_cells, K) fp16` + `xys`) WITHOUT retraining anything per cell: the axes are linear and only the joint-PCA activation block varies per cell, so a cell's value = the problem's shipped value + weights·(cell activation z − correct-cell activation z) (the basis lives in the joint-PCA cache via `utils.rating.features.load_joint_activation_basis`). **That projection is FOLDED into one raw-activation matrix (2026-07-27)** — the shipped value is `prob_value + (z(cell) − z(correct cell)) @ delta_w`, and the difference annihilates every additive term (activation mean, PCA mean, post-PCA mean) while the two scalings and the PCA rotation compose, so `delta_full = ((C.T / s1) / s2) @ delta_w` is built once and a cell's value is `(cand − cand[ci]) @ delta_full`, one matmul K columns wide instead of PCA_DIM. This is a ~53× speedup of the projection step and the reason the fanout stopped dominating the run (5.5 h → ~27 min for the corpus, the whole step 19758 s → 2805 s): the PCA_DIM-wide matmul is small enough that threaded BLAS spends longer starting and joining threads than computing (single-threaded it was 14× faster), and the fanout runs one worker process per core. Exact to within one fp16 step (reassociation rounding to an adjacent representable neighbour), verified by driving the real worker against the previous formula. **`labels.json` is v4 and TWO-TAILED** (`{version: 4, space, _doc, bank, components}`): each component may name its `positive` tail, its `negative` tail, or both (+ `_i18n` variants) — some axes only have a nameable motif on one side. Axis identity survives refits via **frozen per-motif loading anchors** (`label_anchors.npz`: per motif, its loading vector over the fit's problems; new axes match by |corr| ≥ 0.8 over shared tids, greedy 1-1, never against the previous refit — no transitive drift). An axis matching an anchor with NEGATIVE correlation is **sign-flipped to the anchor's canonical orientation before anything is written**, so labels never swap sides. **Identity is APPEND-ONLY and the write ENFORCES it (2026-07-27)**: a motif that drops out of the current fit keeps both its banked label text (`labels.json`'s `bank`) and its frozen anchor row, so a later fit that recovers that direction re-adopts the name instead of minting a stranger — and `build_axes` compares what it is about to persist against what it loaded and **raises before touching ANY artifact** if an anchor or bank entry would disappear (checked before the first write, not beside the write it guards, so an abort cannot leave `axes.npz` disagreeing with the labels). This matters asymmetrically: a loading, a value, a whole fit can be recomputed, but a frozen anchor is the ONLY record of what a motif's direction was and a human's name the only record of what it meant. The one path that may legitimately retire a bank — a `space` mismatch — now archives the old anchors alongside the old labels instead of overwriting them. (Enforcement added after the retention path, which had never actually run in production, truncated `label_anchors.npz` from 5 motifs to 2 on the first fit that selected a smaller K; recovered from git, which is why these three files are TRACKED and must stay so.) Unmatched axes get fresh `ax_<8hex>` motif ids with null labels — and **`package_for_pwa` REFUSES to ship while any component has neither tail labeled** (the expected flow: new data → build_axes grows an axis → a human eyeballs its extremes via `auxiliary.rating_dev.inspect_residual_axes --per-problem` — it renders both tails of every production axis straight from `axes/per_problem.csv` — names it in `labels.json`, re-runs packaging). The companion `auxiliary.inspect_axis_inputs` answers the other half — which INPUTS drive an axis (`--quick` reads `axes.npz` alone; the head is linear on standardized columns so `|W[k,j]|` IS influence per standard deviation), how CONCENTRATED that reliance is (participation ratio = effective column count, since a block can dominate the total merely by being wide), each TAIL separately as the exact additive decomposition of the axis value, and correlation against every frozen anchor so a new axis can be placed as a known motif, a near-miss, or genuinely new. Every block is nameable except the activations; note the "bot winrate" block is whatever `attempts/<size>/*.txt` the loader globs, which includes the non-bot `heuristic` and `sgf_move` columns. Editing label TEXT in `labels.json` then re-running `package_for_pwa` publishes it on the cheap no-rebuild path, as before.

*Packaging* — `pipeline/package_for_pwa.py` ships two things per shard, plus one corpus-wide sidecar:
1. The correct-move axis vector (length K = the selected axis count) joined into the shard's `metadata.json` under `embedding` — what `weaknessScore` reads against any candidate problem.
2. A sibling `<hash>.embeddings.bin` per shard (fp16, K floats per cell, all problems concatenated **in SGF root-variation order**), plus an `embeddings_index.json` inside the zip mapping `{tid: {offset, n_cells}}`. This is the picked-move sidecar: the PWA Range-fetches `bytes=offset+i·bytes_per_cell..offset+(i+1)·bytes_per_cell-1` to recover the embedding at cell index `i` of a tsumego, where `i = children.indexOf(moveNode)` over the SGF root variations.
3. `pwa/tsumegos/lookup.embeddings.bin` — the **lookup-aligned correct-move sidecar**: row i is the K-dim fp16 correct-cell embedding of the problem on `lookup.txt` line i (lookup is id-sorted and spans both sizes, so the line index — which the client already has from its lookup.txt binary search — doubles as the row address; no keys, no offsets). Emitted like `problem_params.bin` (`emit_correct_embeddings`, every non-sentinel run, straight from `per_problem.csv` + the final lookup.txt — no shard rebuild), and folded into `data_version` so it can never cache-desync from lookup.txt. **Row alignment is the contract**: it must be written after the run's final lookup.txt; the client additionally verifies the file size against its line count via `Content-Range` and poisons the sidecar for the session on mismatch. Ids missing from `per_problem.csv` get an all-zeros row the client treats as absent. This is what lets the backfills fetch a correct-move embedding as one ~130-byte Range request instead of downloading the ~2MB shard zip whose `metadata.json` carries the same vector.

   **The bin order is set here, not upstream.** Because the npz is scan-order and a superset (see *Extraction*), `package_for_pwa.project_cells_for_problem` re-parses each SGF and rebuilds the per-cell rows in SGF-variation order via an `(x, y) → npz row` map — dropping the extra scan-order cells, while the `pass` variation (never embedded) gets an **all-zeros placeholder row** so bin row i == SGF child index i exactly (`BIN_FORMAT_REV` 2; rev 1 skipped the pass, which shifted every row after a non-last pass off by one against the PWA's `children.indexOf` — and the pass is not last in ~half of 9x9 / ~3/4 of 13x13 problems). The rev is folded into the **shipped** `embedding_version` (`shipped_embedding_version` = pca-content hash + `-b<rev>`), so a bin-layout change wipes/re-derives clients' stored picked embeddings through the standing version gate and rebuilds shards without `--force`. This reorder is **load-bearing**, not defensive: the PWA indexes the bin by SGF-variation position, so shipping raw scan order would silently return the wrong cell's embedding for every picked move. The sgfmill parse dominates packaging time, so shard building is parallelized across processes (`--workers`, default `os.cpu_count()`).

The joint `pwa/tsumegos/embedding_meta.json` carries `K` (the SELECTED axis count — grows with data, never hardcode it), `dtype` (`float16`), `bytes_per_cell` (so the PWA can decode the bin without guessing), `embedding_version` (from `axes.npz`), and the two-tailed `labels`.

*PWA model — augmented weakness regression.* `pwa/js/weakness.js` trains a logistic regression with **2K+2 params**:
```
P(correct) = σ(α + γ·rating
                + Σ β_correct[k] · correct_emb[k]
                + Σ β_picked[k]  · picked_emb[k])
```
The `γ·rating` term is actually `γ·problemRank` (the board-independent internal rank), and the model is a **single shared instance trained on `getMergedAnswerHistory()`** (both sizes pooled — the embedding axes are joint, so this is well-posed); see the cross-size merge note above. `β_correct[k]` is the position's effect (problem's correct-move embedding); `β_picked[k]` is the user's choice effect (whatever they actually clicked). On correct attempts `picked_emb = correct_emb`, so those rows inform the sum `β_correct + β_picked` jointly; wrong attempts with a sidecar-fetched `pickedEmbedding` disambiguate the two. Recommendation scoring (`weaknessScore`, changed 2026-07-10) uses the **contrast** `(β_correct − β_picked)` against the candidate's correct-move embedding — the model-identified over/under **direction** of the weakness (the continuous analogue of the level-2 sign test below), so selection is **direction-aware**: it **up-weights** motifs the user underplays / is generically bad at (`β_correct < 0`) and **down-weights** motifs the user overplays (`β_correct > 0, β_picked < 0`). Equivalently it treats the unseen problem's "generic wrong move" as `−correct_emb` (to first order the user, when wrong, plays away from the correct move along the weak axis) — candidate-varying, so unlike a *fixed* generic move (which would cancel out of the normalized `weightedRandomSelect`) it actually informs the ranking. This **replaced the old sum `(β_correct + β_picked)` scoring**, which applied `β_picked` to the correct move directly — a category error that **inverted the overplay case** (up-weighting the very motif-is-correct problems an overplayer should see LESS of, so they got easier). The per-axis EB prior shrinks `β_picked` toward 0 when there's no picking signal, so the contrast degrades gracefully to `β_correct` alone. Detection (levels 1/2 below) is untouched — level 1 still flags on the SUM, and `β_picked` still drives the level-2 sign test — only selection consumption changed. `problem-loader.js`'s selection is TWO-REGIME (2026-07-18, replaced the `quality · exp(T·score)` product): while the rank estimate is converging (`rankConverged()` in rank-decomposition.js — stored `state.rankSe` ≥ 2× the local se floor, fail-closed) it weights by `quality` alone (slope² Fisher information); once converged AND the weakness model is trained (`weaknessModelReady()`) it weights by `exp(WEAKNESS_TEMPERATURE · weaknessScore)` alone — no cross-unit balancing. Rationale: slope-priority only changes the served set while the local pool is fresh (a parked user depletes the high-slope tail and converges to the band average regardless), and that fresh phase is exactly when se is high; boundary flapping is a harmless soft blend. The residual axes (2026-07-18) are BIPOLAR, not skew-one-sided: both tails are real directions (measured — no U-shaped even components at z ≥ 3, and users' tail coefficients are near-antipodal on the trade-off axes), so negative scores are the opposite pole of a real dimension, not "no motif". Per-axis tail structure varies: some axes are trade-offs (phase), one is common-competence across tails (score-gap), one is positive-tail-dominant in user variance (wr) — labels.json names each tail independently and may leave one null. Don't read symmetry into the linear model. Ridge-regularized with a **per-axis prior** (`β_k ~ N(0, 1/λ_k)`, `λ_k` applied to both the `β_correct[k]` and `β_picked[k]` slots): the primary is `weakness_axis_lambda` in `population_constants.json` — a length-K vector fit by **empirical Bayes** in `pipeline.fit_population_constants` (EM with a Laplace E-step over per-user MAP fits estimates the between-user variance `τ_k²` of each axis's weakness coefficient; shipped as `λ_k = 2/τ_k²` so the client's implied prior on the identified sum `β_correct + β_picked` is exactly `N(0, τ_k²)` — axes users genuinely differ along get a loose prior, no-signal axes stay pinned; the factor of 2 exists because the offline fit has ONE coefficient per axis while the client applies λ_k to BOTH slots, so reading the shipped number as a plain inverse variance mis-states the prior — and the level-one threshold — by 2×). **That EM accumulates a second moment about ZERO, which is the between-user variance only if each axis's POOLED coefficient is itself zero — an assumption `fit_population_constants` now measures every run and HALTS on (2026-07-27).** It reports per axis the pooled mean, the genuine spread, and `mean²/second-moment` — the share of shipped "variance" that is really displacement — and refuses past `WEAKNESS_MEAN_SHARE_MAX` (`--allow-axis-mean` overrides). The bar is on the SHARE, not significance: with hundreds of users a negligible mean sits many standard errors from zero, so a p-value would halt on nothing that matters. The share is also the only form that can't be evaded by rescaling an axis — shifting a loading is absorbed by the free per-user intercept and scaling it moves mean and spread together, so mean-over-spread is invariant and **no normalization of the shipped values can cure a breach**. A breach is read as the `build_axes` residual-difficulty quarantine LEAKING (a coefficient non-zero for everyone is difficulty, not a weakness), so the halt points upstream; re-centring the client's prior on a shipped per-axis mean is the fallback for a mean genuinely about users, not the first response — it would make the numbers self-consistent while leaving an axis carrying difficulty that belongs to the rating model. There is NO scalar fallback: a missing/length-mismatched vector makes the client SKIP weakness training (transient cache skew), so an axes refit that changes K MUST be followed by `fit_population_constants` before packaging — **enforced since 2026-07-27 by `check_axis_prior`, a package_for_pwa PRE-FLIGHT** that REFUSES the run unless `weakness_axis_lambda` is exactly K finite positive entries. Pre-flight, not a gate beside the axis-label check: it must abort before the first (expensive) shard write — the old failure surfaced only in `copy_curve`, after the whole rebuild — and it must cover the embeddings-absent path, which skips `load_embeddings` entirely yet still republishes population_constants.json onto frozen shards (there it resolves K from the served `embedding_meta.json` instead of `per_problem.csv`). Cold start (≤20 attempts with embeddings): `weaknessScore` returns 0, weighting collapses to pure quality. Weakness training also stores a Laplace-approx posterior diagonal SE + per-axis 2×2 cov on `(β_correct[k], β_picked[k])`, and the Weaknesses pane (`stats-weaknesses.js`) runs **two-level detection** on them: **level 1** flags axis k as a weakness when the posterior of the identified **sum** `β_correct[k] + β_picked[k]` (variance `var_c + var_p + 2·cov`) is credibly negative — never the correct/picked split, which is prior-dominated because ~80% of rows have `picked = correct` (every correct attempt + the missing-pickedEmbedding fallback); **level 2** qualifies the direction with a **paired sign test on `picked_emb[k] − correct_emb[k]` over the user's own wrong attempts** (`computeAxisDirections` in `stats-compute.js`; each error attributed to the flagged axis with the largest |contrast| since axes co-load; exact Beta-posterior direction probability) — overshoot → "too much", undershoot → "not often enough", inconclusive → "inconsistently" as the honest residual. The sign test needs no assumption about which moves are reasonable alternatives: the single-solution invariant makes the correct move the canonical reference. **Multiplicity is controlled by an expected-false-flag BUDGET on level 1, not by the per-axis bar** (2026-07-26): level 1 screens every axis and K grows with the corpus, so a fixed credibility bar lets the expected number of spurious issues grow linearly with K — the pane would get noisier as the data improves. Candidates clearing the per-axis bar are admitted strongest-first while the running sum of their posterior error probabilities `1 − p` stays within `WEAK_FALSE_FLAG_BUDGET`; by linearity of expectation that running sum IS the expected number of spurious issues in the shown list, so the bound is pathwise, holds for any K, and needs NO independence assumption — which is the point, since the axes co-load and their posteriors are correlated (a Bonferroni-style bar on K would have to assume that away, and would also spend power on axes that never come close). The budget must stay ≥ `1 − WEAK_PROB_THRESHOLD` or even the strongest admissible issue is unaffordable and the pane can never fill. Level 2 needs no adjustment — it phrases a flag level 1 already admitted, so a wrong call there is a mislabel, not an extra issue — but it runs on the budget-truncated set so its winner-take-all error attribution can't divert errors to rows the user never sees. `weaknessAxisCov` is length-checked against K like `weaknessSe` and read with **no zero default**: `weakness.js` already substitutes 0 for a non-finite covariance, so a missing entry means the array is stale against the current K, and under the picked/correct collinearity the cross-covariance is strongly negative and dominates the sum variance — defaulting it to 0 moves the threshold rather than erring on the safe side of it. (This replaced an earlier four-way sign-quadrant scheme — `bivariate-normal.js`, deleted — whose `cov<0` gate was structurally always tripped by the collinearity, so only "inconsistently" ever rendered.)

*Picked-move fetch.* `pwa/js/picked-embedding.js` Range-fetches the per-cell sidecar. Two entry points:
- `fetchPickedEmbedding({tsumegoId, cellIndex, zipFilename, boardSize})` — live path, called from `game-logic.handleBoardClick` on every move via `state.embeddingsIndexCache` (loaded alongside shard metadata in `problem-loader`). The cell index is `children.indexOf(moveNode)` against the SGF root variations — same order as extraction/packaging, no coordinate recomputation.
- `fetchPickedEmbeddingWithIndexEntry(...)` — backfill path, used by `backfill.js` when iterating shards.

Answer-history entries carry `embedding` (correct-move, from shard `metadata.json`), `pickedCellIndex` (SGF variation index), and `pickedEmbedding` (decoded sidecar fp16).

*Backfill + invalidation.* `pwa/js/backfill.js` runs on app load: reads the **inlined** joint `embedding_meta.json` (version, labels, K/dtype/bytes_per_cell all joint — a build-time `import` via `data-version.js`, not a fetch; see the data-version cache note), then iterates per size — it fills missing `embedding` fields from the lookup-aligned correct-move sidecar (`fillCorrectEmbeddingsViaSidecar`: binary-search the id in the already-fetched lookup.txt lines → fetch that ~130-byte row of `lookup.embeddings.bin`; repeats share a memoized fetch; hosts that ignore Range — wrangler dev AND production Workers assets — cost one whole-file download, cached by the SW and served row-by-row from memory thereafter) and missing `pickedEmbedding` fields by Range-fetching each shard's per-cell bin with the entry's stored `pickedCellIndex` — the per-problem byte offsets live in the zip's `embeddings_index.json`, so the picked fill is the **only** embedding fill that still downloads shard zips (`walkPickedShards`, only shards carrying such a need). The account-adoption synced fill (`fillSyncedHistoryFields`) uses the same sources, and its zip walk covers just the `syncedMove → pickedCellIndex` derivation (needs the SGF) + the picked fill — measured on a worst-case 2k-attempt adoption: 38 zips vs 342 with the sidecar absent (and ~830 before the problem_params/stamp fixes). Entries older than `MODEL_INPUT_HISTORY_LENGTH` get the embedding fields stripped to keep localStorage bounded. Because the weakness model is a single shared instance (see the cross-size merge note), an embedding wipe on *either* size clears the shared `weaknessParams`/`Adam`/`Se`/`AxisCov`, and a single `trainWeakness()` retrain runs once after the whole walk (not per size). Refits auto-invalidate: `build_axes.py` writes a content-hash `embedding_version` into `axes/axes.npz` (computed over the projection-relevant arrays), `package_for_pwa.py` surfaces it in `pwa/tsumegos/embedding_meta.json`, and the PWA wipes stale embeddings (correct + picked) per size whenever the localStorage-cached version differs. No manual JS edit needed on refit.

Extraction needs ~8 GPU minutes per 1k problems on a Quadro M2200; remote it via Vast.ai for full-corpus runs.

**Ranks are derived client-side from raw ratings; packaging is rank-agnostic.** `package_for_pwa.py` ships per problem in `metadata.json` the raw black-box `rating` (from `ratings/<size>/tsumego_ratings.csv`) and the raw 2PL `slope` a_p (from `tsumego_slopes.csv`, un-normalized — the client uses it as the rank-estimator's per-attempt slope and, with the shipped `floor`, as the selection weight ∝ the 4PL information `a_p²·anchorInfo(floor)`) — no rank at all; shard `min_rating`/`max_rating` are raw too. It does not *compute* ranks (rank-agnostic); the rating→rank map `M` is fitted separately (see next note) into the backend `ratings/` dir, and `package_for_pwa` — the **single writer of `pwa/tsumegos/`** — copies that curve (`rating_to_rank.json` + `rank_map.json`) across into the served path. The client does *all* rating→rank conversion. On ingest, `problem-loader.js` derives `p.rank` (the internal rank = `applyM(rating)`, via `rankForSize` in `rank-decomposition.js`) and leaves `p.rating` raw; zip boundaries become `minRank`/`maxRank`. **The rank is never clamped** — the kyu/dan ladder is what we LABEL, not a bound: `applyM`/`interpExtrap` extrapolate linearly past both end knots, so problems easier than the weakest knot fall below 30k and the (unattempted, KataGo-hard) corpus tail runs past 9d. Treat it as an unbounded continuous coordinate — don't clamp it, don't read it as a percentile. `rank-translation.js` relies on this deliberately (a hidden ladder clamp there once pinned every above-9d value to the 8d-9d border; the clamp now lives only where LABELS are built). Everything rank-shaped reads `rank`: problem selection, the rank label (`getDescriptiveRank`), recall (`recall-model.js`), and the weakness model (`weakness.js`). `state.userRank` is a single value shared across both sizes (see the cross-size merge note), and the skill decomposition pools both sizes in internal-rank space — each attempt is mapped through its size's `M` first, not estimated in raw-rating space. **`M` is required** — `main.js` awaits `loadRatingRankMap()` at init and aborts if it can't load (no fallback). Answer-history entries store `problemRating` (raw), `problemRank` (internal rank), and `problemSlope` (raw a_p — the skill decomposition's per-attempt success-curve slope, converted to internal-rank space as `a_p/|M'|`; legacy entries without it fall back to a constant). The client rank loop closes on this per-problem `a_p`: `rank-decomposition.js`'s `poolLogistic` AND the consensus anchor `fit_user_rating` (`map_rating_to_rank`) both use it, so a sharp problem pins a user's rank more tightly than a flat one. `backfill.js` migrates/refreshes all three, triggered by a **single** `ratings_version` (the joint cross-board rating fit re-rates both boards together, so `data-version.js` collapses the manifest's per-size sub-hashes to one gate value — there is no independent per-board rating version) **and** by a client-computed curve-version (`ratingRankCurveVersion`) so a `map_rating_to_rank` re-fit with unchanged ratings still refreshes stored ranks. The version gate + stamp live ONCE in the orchestrator (`backfillMissingEmbeddings`), wrapped around the per-size work loop (`backfillForSize` does only the per-size shard walk — problems live in per-size shards — and never touches the stamps): the single `embedding`/`ratings`/`curve` stamps are written only AFTER every size's walk has persisted, so **stamp-last = crash-safe** (a shutdown mid-run leaves nothing stamped and the whole backfill re-runs idempotently). The run is bracketed by `backfill: triggered`/`backfill: complete` console logs, and a retrain-if-null guard re-fits the shared weakness model if an interrupted refit left it cleared. **Consequence:** a curve re-fit (`map_rating_to_rank`) writes only to the backend `ratings/`; publish it with `package_for_pwa` — its per-size change detection sees the shard inputs unchanged and **skips the heavy rebuild, copying just the curve** (near-instant), so a curve-only change is cheap but still goes through the single writer. A raw-rating change re-ships shards. (A change to the *packaging format itself* — e.g. adding/renaming a `metadata.json` field — is NOT captured by the input hash, so run `package_for_pwa --force` once after such a code change.) Don't reintroduce a baked rank into `metadata.json` — `rating` means raw everywhere.

**`M` (rating→rank) maps to a latent CONSENSUS rank; every server INCLUDING EGF is a coupling off it (EGF is NOT special).** `pipeline/map_rating_to_rank.py` fits, in ONE objective, the rating→consensus-rank curve, the per-server ordinal couplings (EGF among them — no identity hub), AND the solve-time slope α. The consensus scale would otherwise be free (a gauge freedom, since no server is privileged); it is pinned by a **VERY WEAK** penalty (`GAUGE_WEIGHT≈1`) on the **reliability-weighted (declaration-count-weighted) mean coupling offset** toward identity — weak because the likelihood is flat in the gauge direction so the scale has no motivation to drift, and a strong pin would shrink the real per-server offsets; the data-rich servers (OGS/Fox/EGF/KGS) set the scale, which lands ≈ EGF so the headline barely moves. The curve uses the even_game_winrates.txt cubic SHAPE as a **GENTLE** prior (`LAMBDA_SHAPE=0.3`, softened from the old 3.0 once the all-server latent is no longer EGF-kyu-starved — this also recovered the dan under-rating). It anchors users on their **80%-clear rating** (`fit_user_rating` @ 0.8, pooled, full 4PL) — and **per overlapping 2-month CAREER BLOCK, not one pooled rating per user**: each user's first-time attempts are cut into 60d windows stepped 30d, every block with ≥20 joined attempts gets its own 80%-clear rating and anchors the user's **nearest-in-time declaration** per server (no-drift assumption: surveys only began 2026-05, so older attempt eras carry the same declared rank; a user with no fittable block falls back to the pooled career rating). Block rows are weighted by **attempt mass** (each attempt's unit mass split over the blocks covering it — overlap can't double-count an era) and normalized so each declaration contributes total weight 1. Validated by paired 50-folding CV (`auxiliary/eval_rank_map_cv.py`): held-out NLL −0.04±0.01 and deep-kyu MAE 5.2→4.2 ranks vs the pooled-career anchor, dan band unchanged; the same harness tested errors-in-variables over each rating's Fisher CI and **REJECTED it** (declaration noise dominates; consistently worse held-out — don't add CI weighting). **RATINGS ARE TIME-ADJUSTED THROUGHOUT THE MAPPING**: each declaration's effective rating is `rating + α·(log10 median solve min − center)`, α fit JOINTLY (identified because the time feature is per-user while the curve is f(rating) and each coupling is a per-server constant). Outputs (both board keys identical): `ratings/rating_to_rank.json` (`{ratings, ranks}` + a top-level `time_adjust {alpha_per_log10_min, center_log10_min}`) and `ratings/rank_map.json` (`{server: {our, server}}` knots, both arrays on the one rank scale, **including a real EGF coupling**, not an identity line). **The client headline (onlymove rank) maps the RAW rating through M (untimed); every server translation — EGF among them — maps the TIME-ADJUSTED rating** (`rank-translation.js`); the dock is dropped ONLY for the headline, a client display choice. `fit_population_constants` READS α/center through from `rating_to_rank.json` into `population_constants.json` (no separate time fit). `package_for_pwa` copies both curve files across (single-writer). The module is **production-clean** — config baked as module constants, NO experimentation code (that lives in `auxiliary/map_rating_to_rank_dev.py`); the consensus model + gauge + time-form are documented in `docs/methodology.md`. Run `pipeline.fetch_database` first; `map_rating_to_rank` then needs `ratings/` + `db/d1.sqlite` (for median solve time) but neither GPU nor the heavy pipeline.

**There is ONE internal rank scale, AGA-style, and `pwa/shared/rank-math.js` owns it (2026-07-28).** The convention: **0 is the 1k/1d boundary, every rank is one unit wide, and integers are band EDGES** — 1d = [0, 1), 2d = [1, 2), 1k = [−1, 0), so "2 dan" averages 1.5. It replaced THREE coexisting coordinates (a normalized `applyM(rating)/29`, a rank INDEX with 1k = 19, and a rank SCALAR with 1k = 0 whose integers were band CENTRES); `TOTAL_RANKS`, `RANK_INDEX_OFFSET`, `rankIndexToLabel`, `normalizedRankForSize` and every `·29`/`+19` conversion are GONE, and the `rating_to_rank.json` key is now `ranks` (was `rank_indices`) so a stale reader fails loudly instead of silently double-shifting. It is **AGA-STYLE, not AGA**: real AGA ratings carry a (−1, 1) gap and put 2d at [2, 3), so `agaRankToRating` (`leaderboard-page.js`) stays a real conversion. The module holds `interpExtrap`, `rankToLabel`, `rankLabelToRank` (label → band CENTRE, so the "− 0.5 for the band's lower edge" idiom stays literal), `rankBand` (**FLOOR** — integers are edges), `rankProgress`, and `clampRankBand` (the 30k..9d ladder, for LABELS only — never clamp a rank you compute with). Imported by the Worker (`src/index.js`, bundled by wrangler) and the client (bundled by esbuild): one module, so the server-computed Community rank histogram can't drift against the client's display — don't reintroduce a local copy. **The conversion was LABEL-PRESERVING by construction** (`floor(x − 0.5) ≡ round(x)` across the whole ladder, ties included), verified before/after against HEAD over 24k ratings, 45k (rank, server) pairs, the GoR/AGA tier + activity gates, and 300 synthetic users × 86k attempts through the real `computeRank`: every label, progress percent, SE and time dock identical, every value offset by exactly the scale shift. Any future change here must clear the same bar. Because every STORED rank changed units and a stale value is not detectably wrong (an old normalized `userRank` is a perfectly plausible new rank, and a bare `0` meant 20k but now reads as 1d), it shipped behind **state epoch 2** (`js/state-epoch.js`) — the wipe also refits the per-user recall and weakness models, whose fitted coefficients were expressed in the old units. `DEFAULT_USER_RANK` (`state.js`) is the named cold-start stand-in for that reason.

**KataGo PyTorch loader requires `.ckpt`, not `.bin.gz`.** `models/kata1-b18c384nbt-...bin.gz` is the binary export the C++ analysis engine reads — not loadable via `torch.load`. The feature-embedding pipeline expects `models/kata1-b18c384nbt-s9996604416-d4316597426/model.ckpt` (extracted from the corresponding `.zip` checkpoint distribution). Don't point `extract_activations.py --ckpt` at a `.bin.gz`; KataGo's training code only goes PyTorch → binary, not the other way.

## Conventions to be aware of

- `tests/` exists but is empty — there is no test runner configured. Don't add a "run the tests" step to claims of completion unless tests are actually added.
- Python code uses absolute imports rooted at the repo (e.g., `from utils.constants import ...`). Pipeline scripts append `PROJECT_ROOT` to `sys.path` defensively.
- KataGo coordinates skip the letter `I` (so cols are `ABCDEFGHJKLMNOPQRST`). SGF coordinates do not. Helper conversions live in `utils/katago/queries.py` (`katago_to_sgf_coords`) and `pipeline/benchmark_bots.py` (`sgf_to_gtp`). Prefer reusing them over rewriting coordinate math.
- `pwa/README.md` has additional context on the PWA's overall structure (sections 1–5: overview, tech stack, project layout, architecture, dev workflow). Read it before substantive PWA edits.
- **For local DB analysis, prefer the binary `db/d1.sqlite` over the raw `db/d1.sql` dump.** Both are produced from `pipeline.fetch_database` and both gitignored. `fetch_database` treats `d1.sqlite` as the **canonical merge target** and keeps both artifacts in sync on every run, so you normally don't import by hand. If you ever need to rebuild the `.sqlite` from a raw dump manually: `{ echo "BEGIN;"; cat db/d1.sql; echo "COMMIT;"; } | sqlite3 db/d1.sqlite` — the `BEGIN/COMMIT` wrapper matters: a full D1 export emits one un-batched `INSERT` per row (~290k for `tsumego_reports`), so without a wrapping transaction sqlite fsyncs per row and the import takes many minutes. **Never pipe the import through `head`/`tail`** — it SIGPIPE-kills `sqlite3` mid-import and silently leaves a partial table. Query the `.sqlite` thereafter (no re-import per session). Note a full `--full` dump only carries the tables that have rows at export time (D1 export drops empty tables), whereas the incremental path's regenerated dump carries every table it discovered remotely (so e.g. an empty `history_refresh_log` is present).
- **Many artifact directories hold 100k+ files** — `tsumegos/9/` (~123k SGFs), `activations/9/` (~123k .npz), `tsumegos/13/` and `activations/13/` (~20k each), `axes/per_cell/<size>/` (per-tid files), and shard zips. **Shell globs like `ls dir/*.npz` will silently expand past `ARG_MAX` and report 0** — verified false-negative on `activations/9/`. Use `find <dir> -maxdepth 1 -name '*.ext' -printf . | wc -c` (or `find ... | wc -l` if newlines are safe) to count, and `find ... -exec` / `xargs -0` to iterate. The same trap applies to anything piping a glob into another command. Treat any directory under `tsumegos/`, `activations/`, `axes/`, `attempts/`, `ratings/`, or `pwa/tsumegos/<size>/` as "may exceed argv" by default.
