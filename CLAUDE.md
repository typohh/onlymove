# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

YoseTsumego / onlymove.net — a Go (Baduk/Weiqi) tsumego pipeline. KataGo generates problems and rates them; the rated set is packaged into zip archives served by a Cloudflare-hosted PWA. Four cooperating subsystems:

1. **`pipeline/`** — fourteen standalone `python -m pipeline.<step>` entrypoints run in order. `package_for_pwa` is the single writer of `pwa/tsumegos/`; there are no side-channel patch scripts.
2. **`utils/`** — shared logic, **split into two subpackages with a one-way, import-time boundary** (worth keeping true): `utils/katago/` imports nothing from `utils/rating/`, and importing any `utils/rating/` module loads nothing from `utils/katago/` — the engine-side helpers the rating side needs (the conclusion predicate, the eval-comment parser, the board simulator, the coordinate conversions) are single-sourced there and imported INSIDE the functions that use them, the pattern `motif_rules` states. `utils/katago/` is the Go/KataGo side — `controller` and `queries` (the engine subprocess and its thread-safe dispatcher), `problem_finder`, `add_variations` (SGF tree construction), `coords`, `models` (network downloads), `board_render`, `sgf_parsing`, and `torch_model`, which bootstraps `utils/katago/vendor/`, the vendored PyTorch KataGo (that top-level `katago` package is the VENDOR's, distinct from this `utils.katago`; they do not shadow each other). `utils/rating/` is the statistical side — features, the trunk's layer stack (`mirt_net`, stated ONCE: `train_mirt` fits it and `write_mirt_per_cell` rebuilds it to project every cell, and a stack matching by shape while differing in its activation loads cleanly and projects through the wrong function), `ratings_io` (the `ratings/` artifacts, the M curve and the per-server couplings — `load_M`/`apply_M`, `load_rank_map` with `internal_to_server`/`declared_to_internal`, `load_time_adjust`, and the `interp_extrap` pair the JS `interpExtrap` mirrors; it is **deliberately stdlib+numpy**, which is why the interpolators live here rather than in the scipy-importing `fit_rank_curves`, and `package_for_pwa` and `se_floor` depend on that staying true), `fit_rank_curves`, `rank_surveys`, `rank_curve_shape`, `motif_rules`, `se_floor`, `tail_agreement`, `model_constants`. `residual_axes` and `slope_calibration` are retired two-stage machinery with no production importer — only `auxiliary/rating_dev/` reads them. `utils/constants.py` holds the few values both sides need — `ALL_BOARD_SIZES`, `KOMI`, `RULES`, the retired-id path, the debug flag — and imports from neither side; `DEFAULT_MODEL` is engine-side and lives in `utils.katago.models`.
3. **`pwa/`** — vanilla-JS ESM PWA built with esbuild, deployed as a Cloudflare Worker (`pwa/src/index.js`), with a D1 binding `DB` → database `tsumego-reports`. Schema is `pwa/schema.sql` (idempotent `CREATE … IF NOT EXISTS`); apply new tables/indexes to the remote D1 with `npx wrangler d1 execute tsumego-reports --remote --file=schema.sql`. Routes, tables and the client architecture are in `docs/` — see below.
4. **`analysis_server/`** — a tiny HTTP server wrapping KataGo for the PWA's analysis fallback when SGFs lack embedded win-rate data. `server.py` runs on the cloud box (stdlib + sgfmill only — deployed with no repo beside it); `worker.py` runs on a fast machine and takes that box's work over while it is up.

Plus `auxiliary/` (diagnostics, surgery scripts, the rating-model research surface, and `vast_orchestration.py`, which rents Vast.ai GPU instances for the heavy generation steps; not part of the main flow) and `ablations/` (repeatable seeded measurements against what SHIPS — the rating fit, the rank map, the client's estimators, the activation encoder; the figures the docs and `pwa/about.html` quote; see its README for the contract and for the split against `auxiliary/`).

## Pipeline commands

Always invoke pipeline modules through the venv's Python so PYTHONPATH resolves correctly:

```bash
./.venv/bin/python3 -m pipeline.fetch_database            # incremental pull of new tsumego_reports rows + small tables whole → db/d1.{sqlite,sql} + local D1. --full re-downloads; --db-dir DIR fetches a private throwaway snapshot and leaves db/ + the dev D1 alone
./.venv/bin/python3 -m pipeline.tune_engine <size>        # tune bots/analysis.cfg for this GPU (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.generate_tsumegos <size>  # long-running generator → tsumegos/<size>/
./.venv/bin/python3 -m pipeline.benchmark_bots <size>     # bots solve generated tsumegos → attempts/<size>/
./.venv/bin/python3 -m pipeline.extract_activations       # the activation network's final trunk state at every legal cell → activations/<size>/<id>.npz (GPU; resumable)
./.venv/bin/python3 -m pipeline.extract_ownership_swing   # ownership swing per problem → activations/_signal_cache/ownership_swing.csv (GPU; resumable). MANDATORY, not diagnostic: two motif rules are written over it and build_motif_proxies aborts without it
./.venv/bin/python3 -m pipeline.extract_ownership_maps    # ownership map per intersection after a pass, the answer and the next 4 SGF-order moves → activations/_signal_cache/ownership_maps/ (GPU; resumable). MANDATORY: territory, influence and yose are written over it
./.venv/bin/python3 -m pipeline.cache_rating_features     # both roll-up caches: correct-cell vectors (the trunk's activation block, and the rated-set id list) + move evals (the "all" comparison layout, the axis analyses, the alt-cell coordinate). Incremental, reconciles both ways
./.venv/bin/python3 -m pipeline.build_motif_proxies       # rule verdicts per problem → axes/motif_proxies.npz. A rule/threshold change needs --force
./.venv/bin/python3 -m pipeline.train_mirt                # single-stage rating + K skill axes in ONE fit → ratings/ + axes/{per_problem.csv,axes.npz}
./.venv/bin/python3 -m pipeline.write_mirt_per_cell       # per-legal-cell axis vectors → axes/per_cell/<size>/<tid>.npz. Resumable
./.venv/bin/python3 -m pipeline.map_rating_to_rank        # → ratings/{rating_to_rank.json, rank_map.json}. Backend; package_for_pwa publishes it
./.venv/bin/python3 -m pipeline.fit_population_constants  # → ratings/population_constants.json (retention, time bias, rank prior, career skill smoother). Backend
./.venv/bin/python3 -m pipeline.package_for_pwa           # SINGLE writer of pwa/tsumegos/. Change-detects per size; --force to override
```

Remote: `./.venv/bin/python3 -m auxiliary.vast_orchestration` (no args prints subcommands; only `tune`, `generate`, `benchmark` are remoted — the rest stay local).

**Run order is a hard data dependency, not a convention** — `methodology.md` §3.1 spells out each edge. Two steps mislead: `map_rating_to_rank` and `fit_population_constants` are board-independent and need no GPU, but **board-independent is not detachable** and both sit INSIDE the sequence. `fit_population_constants` reads nothing from `axes/` — it fits no per-axis quantity, so an axis refit does not require re-running it.

**Every step aborts on a missing or unreadable per-problem input rather than skipping the row**, and every id-keyed cache reconciles in BOTH directions ("up to date" means the sets are EQUAL, not that there is nothing new to add). The reasoning and the per-step detail are in `docs/pipeline_operations.md`.

**Several steps run for HOURS, none checkpoint, and a naively launched run WILL be killed part-way:**

- **A shell that backgrounds with `&` and then exits takes the child down with it** (SIGTERM, exit 143) — including a wrapper that backgrounds the real work and returns. Launch detached: `setsid nohup ./.venv/bin/python3 -u -m pipeline.<step> > /tmp/<step>.log 2>&1 < /dev/null &`.
- **`timeout N` kills at N with exit 124 and no partial result.** A too-short guess is indistinguishable from a crash after the fact.
- **Piping through `tail`/`head` buffers until exit**, so a healthy run looks hung and a dead one looks alive. Use `-u`, redirect to a file, poll the file.

**Never stop a running job to decide, investigate, or fix something.** The test before killing one is not "is something wrong?" but **"is the fault in the thing that is RUNNING?"** — localise the defect to the producer's own output first. A pending decision about how to READ, interpret, filter or publish what a job writes is never a reason to pause the job writing it; the output is already right or already wrong and pausing changes neither. Nor is "the results may be superseded" — finishing costs nothing extra. Answer the question from a sample of what it has ALREADY written, with the job still running, and deploy fixes at the next natural start. (Measured cost of getting this wrong: a two-GPU fleet stopped twice during the SGF repair, both times over a reader-side predicate, with the written files correct in both cases.)

`train_mirt` runs a FIXED 7000-epoch budget under a cosine decay of both rates to zero, several hours — **the shipped fit holds NO rows aside** (`STOP_ROW_FRAC` is 0: with a fixed budget a split decides nothing and only withholds data), so its log carries the training loss alone; an ablation arm holds 3% aside (`HELD_ASIDE_FRAC`) and prints that split as a record, never a stopping rule. Either trace improves in bursts separated by flat stretches, so **do not read a long run as a hung one**. **The budget is bounded ABOVE as well as below — don't lengthen it for "more convergence".** The decay freezes the fit where it stands, so a budget past the point where the held-out-PROBLEM score turns locks the overfit in (measured: 12000 is worse than 7000 by more than the run-to-run spread, and the constant rate turns the same way past its own budget).

**The steps that write `ratings/`, `activations/`, `axes/` and `pwa/tsumegos/` overwrite IN PLACE — do NOT copy them aside before a refit.** They are derived; the inputs (corpus, attempt log, committed code) are what's kept, and a bad fit is reverted by re-running the step. The exceptions are two TRACKED files nothing can regenerate: `axes/labels.json` and `axes/label_anchors.npz`. `motif_proxies.npz` and `axes.npz` are NOT tracked despite being a fit's input and output; see `docs/pipeline_operations.md`.

**Two live routes return 404 ON PURPOSE, and probing them by hand reads as an outage — use `npm run status` rather than a bare `curl`.** (a) `/`, `/9` and `/13` have no file behind them: the SPA fallback rewrites them **only for a navigation-shaped request** (`sec-fetch-dest: document`, or an `Accept` naming text/html), because an asset-style miss must keep 404ing so a stale service worker re-fetches instead of receiving HTML where JS is expected — and `curl` defaults to `Accept: */*`. (b) The `INLINED_DATA_FILES` (`build.mjs`) are compiled into the bundle, so `/tsumegos/{rating_to_rank,rank_map,population_constants,se_floor,embedding_meta}.json` 404 — **a 200 there is the real regression**, since it would let a client fetch a curve under a fixed name with no `?v=` and pin itself to a stale one. `check_live_status.mjs` asserts both directions plus the freeze state (`--expect-frozen` / `--expect-unfrozen`), and **it retries**: a deploy propagates over seconds, so an unfreeze still reporting `maintenance` on the first probe is usually propagation, not a failed unfreeze.

## The rating + axes fit (`pipeline.train_mirt`)

**One model produces the rating and the K skill axes together**, a compensatory M4PL where the axes are factors 2…K+1 and the rating is factor 1:

`P = c_p + (1 − c_p − λ)·σ( a_p·(θ_u − b_p) + Σ_k g_k(x_p)·v_u[k] )`

**ONE TRUNK feeds difficulty, slope, floor and the axes** — a `Linear`'s output rows are independent, so this is exactly a shared head emitting `(b, a, c, g_1..g_K)`. The axis path is COUPLED, so the trunk learns what the AXES need and not only what the rating needs; detaching measures the same but is feature reuse rather than a joint fit. **The trunk floor reproduces only under the ability prior and the base-rate start below** — served attempts sit near each problem's 80% point and barely inform the curve beneath it, so without them the per-problem floors land somewhere different every seed. **Don't move the floor to a linear map of the inputs to stop that**: it reproduces by having no room to drift, but it lets a heavy user be parked far below every problem and explained by floors. Evidence: `auxiliary/rating_dev/exploration_tf3_refit.md`.

**Ability carries a population prior whose variance is the data's own, and the fit starts at the population's clearance** (`THETA_LAPLACE`, `INIT_BASE_RATE`). The prior is a Laplace-EM step each epoch (σ² = mean of (θ − mean)² + 1/I_u, detached), so it has no weight to tune — **don't replace it with a learned variance** (maximising jointly over abilities and their variance collapses every ability to one value) **or a fixed-strength ridge** (needs a constant, and under the sd gauge it shrinks the scale and hands users to the floors). Without the prior a user can be explained entirely by floors; without the base-rate start the floor is the cheapest early intercept and lands wherever its weak gradient leaves it. Evidence: `auxiliary/rating_dev/exploration_tf3_refit.md`.

Method: `methodology.md` §1.5–§1.14. Evidence for every constant, ablation and sweep: `mirt_benchmark.md`. Six things bind from outside those:

- **The trunk sees ACTIVATIONS + BOT WINRATE + the board-size flag**, stated once as `PRODUCTION_BLOCKS` (`utils/rating/model_constants.py`) and read from there by `train_mirt`, `write_mirt_per_cell` and the ablation projections — a second layout switch feeds a checkpoint columns it was not fitted with, and both arms are well-formed matrices. The answer-derived blocks (move evals, ownership swing, game phase) are OUT because the same trunk is fanned out over every legal cell, where they describe each alternative cell by the CORRECT move. **They stay mandatory steps** — `build_motif_proxies` is written over them — so they reach the fit as the taught directions, not as columns.
- **`train_mirt` aborts without the motif proxies and `axes/labels.json`** — it derives no directions of its own. It **retires any existing `axes/per_cell/`** by renaming it, because this fit's `per_problem.csv` beside the previous fit's `per_cell/` ships a shard whose two embedding sources disagree, and both files are individually well-formed so nothing downstream can catch it.
- **It does not select K.** K equals the number of `components` in `labels.json` — the SHIPPING decision, one axis per taught rule, not a loss curve. `K_AXES` (`utils/rating/model_constants.py`) must match it, and the failure is one-sided: abort when `components` is shorter, silent TRUNCATION when longer. See `docs/motif_axes_workflow.md`.
- **`ORTHO_RATING` keeps the axes off the shipped triple — rating, slope and floor — and it is scored PER TAIL** (`tail_weight(+g)` and `tail_weight(−g)` penalised separately), **not per axis.** A whole-axis correlation is a linear statistic and cannot see a symmetric dependence, so a fit recorded as rating-orthogonal on that basis can carry laden tails at both ends. Penalising difficulty alone only displaces the leak into slope or floor. Expect the resulting axes to be **unfamiliar** — forbidding the correlation forbids the entangled motifs and returns different ones.
- **Read the combined column, PAIRED.** `axis adds` rises with K whether or not the model predicts better, because more axes mechanically absorb more residual — and **axis value is a property of the holdout draw**: over four independent draws it ran +3.59 to −1.44 mnat, two of four negative. **Never quote a single-draw axis-adds figure as the effect.** Comparing ARMS wants the draw PINNED (paired); estimating a MAGNITUDE wants it MOVING, and a figure produced under the first must not be quoted as though it came from the second.
- **A DETACHED mutual-orthogonality penalty keeps the axes apart from EACH OTHER; the teaching pull keeps each ON its rule; neither does the other's job.** `ORTHO_AXES` (0.25) acts on loadings from a detached copy of the trunk output (`ORTHO_AXES_DETACH`), and the detachment is what makes it affordable: reaching the trunk at 0.5 on a free fit the term costs the rating 13 mnat, detached on the taught fit it is +1.9 mnat better (7 of 8 seeds) with seven distinct directions instead of five and identity unchanged. **Don't undetach it, and don't drop it expecting the pull to hold seven** — nothing else prices two axes carrying one direction (the isotropic ridge on unit-scaled axes rewards it), the pull alone holds about five, and a fit with the pull off spends seven axes on about three; don't read a free fit's opposite tails as two motifs. The weight is adopted at the one point measured; a sweep on the taught fit is owed. `ablations/panels/detach.json`, `ablations/panels/axis_space.json`.
- **An opening learning-rate ramp is measured-rejected — don't re-try it.** 250, 500 and 1000 epochs at eight seeds on a pinned draw move the held-out-problem level inside the seed spread (p 0.4–0.7), and the four-seed reading that suggested one was the upper half of that spread. The knob (`lr_warmup_epochs`) stays for `ablations/panels/ramp.json`; the regime pins it, so a record with a ramp never straddles one without.
- **`slope_scale` is 1.0 and slopes ship as fitted** — no post-hoc multiplier.
- **AN OBVIOUS IMPROVEMENT FOUND BY AN ABLATION BECOMES THE NEW BASELINE**, and everything measured afterwards is measured against it. Two consequences follow and both are load-bearing. A panel's arms are only comparable to each other, so **a baseline change does not invalidate a finished panel's internal contrast** — it invalidates comparing that panel's arms to a later baseline's. That is mechanized, not remembered: every arm record pins the REGIME it ran under (`epochs`, `lr_schedule`, the mutual term's weight and detachment — a shipped arm's config is `{}` under any baseline, so the config cannot tell a stale one from a current one), every producer refuses a panel whose arms straddle one (`panel_regime`), and re-measuring a panel under a new baseline **archives its records to `dev_runs/<panel>.<old regime>/` first** rather than overwriting them, on the box and locally alike — the pool skips arms that have records, so an unarchived panel silently re-runs nothing. And redoing finished ablations against the new baseline is the LOWEST priority: new ground first, re-measurement last. What counts as obvious is a contrast that holds its sign across seeds with no demonstrated cost — and "no demonstrated cost" includes asking what the likelihood cannot see, since every arm that has ever beaten this baseline did so by removing a constraint the likelihood does not score.
- **A SINGLE RUN RESOLVES ALMOST NOTHING.** Under the decayed schedule that ships, the final held-out-problem level moves about two millinats run to run at a FIXED holdout draw; under a constant rate it was roughly double that, and the shipped value was additionally whichever point of a wandering band the last epoch landed on — which is what the decay was adopted for, its level being at parity. Two millinats is still as wide as most differences worth arguing about here, so **every arm of a refit comparison runs at two or more seeds** and a contrast is quoted on the AGREEMENT OF ITS SEEDS, never on one number — within a seed the arms hold aside the same rows and the delta is paired, across seeds nothing may be subtracted. **A patience rule is not an option** under either schedule: under the decay the rate reaching zero IS the stop, and replayed on constant-rate traces a rule answers mostly to its own setting and picks an epoch WORSE than the final one at every setting and seed tried. **A schedule is compared at matched WORK** — the recorded learning-rate integral in constant-rate epochs; a cosine to zero delivers half its epoch count — never at matched epochs. `ablations/panels/` holds the panels, `docs/methodology.md` §1.8 the statement.

## Invariants that span multiple files

### Corpus and generation

- **Tsumego identity is symmetry-aware and single-solution.** SHA-256 over all 8 D4 transforms, `min()` canonical, truncated to 8 hex — so the set cannot hold two problems that are rotations or reflections of each other. **The answer is `variation_nodes[0]` BY CONSTRUCTION**: `construct_initial_sgf` writes the verified solution as the decision node's first child and every later pass only APPENDS (`get_child_move` reuses or `new_child()`s), so nothing can displace it. EVERY consumer reads it positionally — `extract_activations`' `correct_idx`, `benchmark_bots`' grading, row 0 of the per-cell block, the client's `isCorrectMove`. **Don't re-derive the answer from the eval comments anywhere.** They are a shallower annotation than the search that verified the solution; the client used to pick by them and that was the one place the app could disagree with every backend stage. Nothing reorders the decision node's children either — the guard that used to (`promote_winning_first_move`) was measured to have never fired across all 220,463 live problems and is gone. `auxiliary/check_tsumego_sequences.py` re-verifies.
- **`tsumegos/retired_ids.txt` ids are treated as taken.** Removing a problem keeps its `tsumego_reports` rows, so a reused id silently inherits a stranger's history — the one failure mode that raises nothing anywhere and cannot be untangled afterwards.
- **"Read to a conclusion" means TWO CONSECUTIVE PASS NODES in the subtree** — `subtree_reaches_conclusion` (`utils/katago/add_variations.py`) and `subtreeReachesConclusion` (`pwa/js/analysis.js`), which must agree. The writer creates the second pass only where its recursion reached the terminal, so this is exact, and **nothing in the file is annotated** — a marker property saying the same thing stands a second source of truth beside the structure that can disagree with it. **Don't weaken it to "a pass anywhere in the subtree"** — that is the deduction behind two corpus purges, and it still over-accepts by 2× on refuted first moves (2.2% against 1.1%), which is how a solver gets offered a line that ends in a LOSS. **Don't reach for document order or visit counts either**: KataGo ranks `moveInfos` by LCB, not raw visits, so the followed move is not the highest-visit one at 20.8% of multi-child nodes, and a max-visit walk finds only 42.5% of the answers the pass test finds. The predicate only narrows the DISPLAY pool; **correctness is `children[0]` and never reads the tree at all**.
- **SGF branch comments are `"<winrate>%/<score>/<visits>"`** and client-side analysis reads them directly. Don't strip them when manipulating SGFs. The third field is the search depth behind the estimate, and it exists because its absence let a corpus-wide 30-visit annotation pass unnoticed — every value looked exactly like a deep one. **Every parser matches the first two fields with an UNANCHORED search, so a pre-field comment still reads**; a comment with no third field is a 30-visit value by construction, which is what `parse_eval_visits` reports for it. **Exactly two functions write one, and neither downgrades**: `set_eval_comment` (`utils/katago/add_variations.py`) for the corpus, and its client twin `setEvalComment` (`pwa/js/sgf.js`) for analysis-server answers, which must keep the same format and the same rule. A comment is replaced only by an estimate resting on more visits, which is what lets the shallow sweep run last without undoing the deep passes, and makes re-running any pass over its own output a no-op. **Write the engine's own winrate, never a placeholder** — a fabricated one outranks every real sibling anywhere these comments are ranked (the client's white-reply display, the move-eval features, the motif rules).
- **A problem exists in three orderings**: the activation npz (board-scan, a SUPERSET of the SGF's cells), the SGF root variations (pruned, plus a `pass` the npz never embeds), and the published per-cell bin (SGF order, with an all-zeros row for the pass). **Pick the correct row by `correct_idx`, never positionally; map cells by `(x, y)`, never by index, when crossing npz↔SGF.**
- **The activation store holds the activation network's FINAL TRUNK STATE (`trunkfinal`), `ACT_STORE_DIM` channels per legal cell, and the fit reads them standardized and UNROTATED** (`PCA_DIM` equals the store width). **A block's reported output is its increment, not the trunk state** — don't substitute a block output, or a concatenation of them, for it. Every npz is stamped with its source (`source_fp`) and a resumed extraction aborts on a mixed store. **A change of activation network is total, and must end with `cache_rating_features --rebuild-activation-cache`** — the id-keyed caches reconcile by id set and cannot see a same-width change. `docs/corpus_and_engine.md`.
- Full detail, plus `auxiliary/audit_solution_lines.py` and the pruning approach it measured-rejects: `docs/corpus_and_engine.md`.

### KataGo

- **Don't hardcode the binary path** — launch through `resolve_katago` (`utils/katago/binary.py`), which picks the `bots/` build per machine (a CUDA build only on answering a probe query, else the OpenCL `bots/katago`), puts the venv's `nvidia-*` library directories on `LD_LIBRARY_PATH`, and caches the choice per host; `KATAGO_PATH` overrides it.
- **`bots/analysis.cfg` is hardware-tuned in place** by `pipeline.tune_engine`; expect hand edits to be overwritten.
- **`requireMaxBoardSize = true` in `bots/analysis.cfg` belongs to THIS repo's config only.** It turns the NN-buffer maximum into an exact requirement, and an off-size query kills KataGo's async bot thread with a message on stderr and NO response on stdout — so the caller waits out its full query timeout on a request that can never be answered. The pipeline never notices (single-size runs); `worker.py` passes `false` and runs one engine sized to the largest board.
- **`KatagoController` is thread-safe by design** — one master reader thread fans responses out via per-query events, so `send_query` blocks from the caller's view.
- **Models live outside git** and download lazily. **`DEFAULT_MODEL` is the transformer network and needs engine v1.17+**; an older build exits at load, so a new machine needs a current `bots/` binary before anything engine-driven runs. The residual b18 is a bot only. **The PyTorch loader needs a `.ckpt`, not the `.bin.gz`** (`get_checkpoint`) — KataGo converts PyTorch → binary and not back, so one is not derivable from the other.

### Backend fits and publishing

- **Three sidecars are row-aligned to `lookup.txt` and only to each other**: `lookup.embeddings.bin` (correct-move vectors), `lookup.altstats.bin` (the availability null, `2*K` little-endian uint32 MASSES — `altstats_bytes_per_row`/`altstats_dtype` in `embedding_meta.json`) and `lookup.offsets.bin` (each problem's per-cell block address, `<u4 offset + u1 n_cells`). Alignment holds only WITHIN one packaging run, so all three fold into `data_version` and must cache-bust together — a client pairing one run's masses with another run's answer vector is well-formed and wrong. `lookup.offsets.bin` exists so a reader can address a 780-byte block without the 2MB zip that `embeddings_index.json` lives inside; the in-zip copy stays for the client, which already holds the zip. A fourth file, per-shard `<size>/<hash>.cells.bin`, is the same cells' BOARD POINTS as uint8 `y*size+x` (255 = pass) — it needs no addressing of its own, since a problem's codes start at `offset // bytes_per_cell` and run `n_cells` bytes. It exists so a reported move COORDINATE can be turned back into a variation index without the SGF. **The coordinate is what the record keeps, and the index is derived from it** — reordering a problem's root variations re-points every stored index while leaving the coordinate correct, so don't be tempted to store the index in D1 instead.
- **`db/ignored_users.txt` lists accounts (the LLM players, `auxiliary/llm_player/`) whose attempts stay in D1 and the mirror but enter no fit. A new pipeline reader of `tsumego_reports` or the survey rows must filter them**: `not_ignored_sql()` / `read_ignored_users()` in `utils/constants.py`. Don't filter in `fetch_database` instead, because the leaderboard refresh rebuilds these accounts' ranks from the mirror.
- **`package_for_pwa` is the single writer of `pwa/tsumegos/`.** A labels-only or curve-only change publishes by re-running it (change detection skips the shard rebuild). **A change to the packaging FORMAT is not captured by the input hash — run `--force` once after such a code change.**
- **A problem's rating, slope and floor have NO DEFAULT anywhere.** Every shipped problem carries all three and packaging aborts otherwise, so a default is only ever reached by corrupt data, which it then hides. The backend raises on a rated problem missing one (`load_size_value_maps`, `fit_user_rating`); the client skips such an entry (`flattenAttempt`, `hasProblemParams`) and never fills it. A problem absent from the ratings ENTIRELY is a retired one, and its attempts simply drop out.
- **Packaging is rank-agnostic**: it ships the raw rating, the raw slope and the floor, no rank, and shard bounds are raw too. The client does all conversion. **`rating` means raw everywhere** — don't reintroduce a baked rank into `metadata.json`.
- **`M` maps to a latent CONSENSUS rank; every server INCLUDING EGF is a coupling off it.** Ratings are time-adjusted throughout the mapping, so **any accuracy statistic against a DECLARED server rank must be computed on the TIME-ADJUSTED rating** — a raw comparison has the two sides in different units and fails SILENTLY, the wrong number still being a plausible one. `ablations/check_mapped_vs_declared_rank.py` emits both and they are NOT interchangeable: only **`err_server`** (time-adjusted, forward-mapped into that server's own units) is quotable, while **`err_internal`** (raw, pooled internal units) exists in the `--csv` output alone; and the per-server user-weighted rho it does not print is defined in `auxiliary/rating_dev/validate_ratings.py`. **These figures are PUBLISHED in `pwa/about.html` in FOUR languages (en/zh/ja/ko)** — re-measure and update all four in the same pass as a rank-map change.
- **The rank mapping anchors on POINTS, not labels.** A declaration is its band's centre (4d = 4.5 dan); a linked account's active EGD/AGAR heartbeat replaces the declaration beside it as a continuous anchor (`observation_frame`, scored as a density where a declaration is a band's mass). A user's profile splits only at 0.5 ranks from the run's mean, with a doubled threshold to return (`stable_runs`) — never key a split on the band label, which fires at every edge crossing. The `rank.honesty_*` figures compare verified ratings against the fit, so `ablations.rank_calibration_figures` measures them on a declarations-only refit (`map_rating_to_rank --no-verified`, in a scratch copy of `ratings/`) — never against the shipped mapping.
- **The rank mapping SCREENS declarations before its final fit, and everything scoring the mapping must honour that.** `map_rating_to_rank` fits once, scores every declaration by the contamination mixture's own junk posterior, drops those above 0.5 and refits, writing the dropped rows to `ratings/declaration_exclusions.csv`. Read them with `load_declaration_exclusions` (`ratings_io`) — scoring a row the curve was fitted without measures the exclusion, not the mapping. The cut is the posterior's decision boundary, NOT the largest gap in the sorted scores: a knee exists in any sample, so cutting there descends to wherever the decay flattens. One pass only — iterating converges on an arbitrarily clean set. `docs/methodology.md` §1.12.
- **Axis labels are optional to ship and an unnamed axis is silent, not broken** — it still steers selection and carries its share of the reading; the client declines to print it, and there is deliberately no placeholder label. Naming workflow and tail-agreement tooling: `docs/motif_axes_workflow.md` — **agreement is ordinal only, with NO calibrated naming threshold**; inspection of the boards is what decides a name, and a numeric bar must not be reintroduced from the retired one-sample calibration.

### Client

- **PWA state is centralized** in `pwa/js/state.js`; all changes go through exported setters. **A linked problem is a client-side try-out and is INVISIBLE to everything downstream.** `updateUserStats` and `sendReport` both early-return on the canonical `linked` flag, so a linked attempt enters neither local history nor D1 — which means it can never acquire an embedding, alt-stat counts, or any other derived per-attempt field, and never needs a sidecar, a shard block or a lookup row. **No new data path — sidecar, backfill, refit endpoint — has to account for linked mode; do not raise it as a consideration.** The one live obligation is that those two existing guards stay in lockstep on that single flag.
- **`/9` and `/13` are entry-only size HINTS, not persistent addresses** — read once at boot, then `cleanUrl()` collapses the path. Linked problems are the deliberate exception, which is what makes any reload re-enter the same shared problem instead of dropping to the standing challenge.
- **Rank, stats and the learned models merge across sizes; histories, curves and problem pools stay per-size.**
- **`reanchorRank` is the SINGLE writer of the three rank slots.** `userRank` (the posterior mean) is what everything CALIBRATED reads — never feed a shifted value here or the calibration loop closes on it; `displayRank` is what the user is told; `serveRank` is what selection targets. **Serving must not follow the display down** (it starves the estimator), and **the serve-gap cap must not go back to a constant** — a constant doesn't limit the offset, it INVERTS it.
- **The rank is never clamped** — `applyM`/`interpExtrap` extrapolate past both end knots, so treat it as an unbounded continuous coordinate. Clamping lives only where LABELS are built. **`pwa/shared/rank-math.js` owns the one internal rank scale** (0 = the 1k/1d boundary, one unit per rank, integers are band EDGES) and is imported by both the Worker and the client — **don't make a local copy**. Any change to that scale must be label-preserving by construction and shipped behind a state-epoch bump.
- **The SE floor is a SHIPPED CORPUS CURVE (`se_floor.json`), not a runtime scan.** Its geometry is single-sourced in `utils/rating/se_floor.py` across the step that picks the grid and the step that emits the curve. **Do not go back to measuring it per-reader** — the dominant cost is the reader that holds nothing, which concedes the floor to zero and lands the shown rank a whole band low.
- **A stored per-attempt field is governed by its generation's DEVICE-LEVEL version — there is no per-row stamp.** Two conditions hold it up: nothing writes a derived field while its own build's generation and the device's disagree, and the re-derive reaches EVERY holder. That second one is an **enumeration** — any new place that stores a problem object must be added to it, and it has been wrong three times.
- **Every long re-derive pass must checkpoint in batches, not once at the end.** A version stamp written last marks the work DONE but says nothing about work already paid for, and these passes are network walks that get killed routinely. The rest of the chain (`/sync`, `evictColdTail`, the cold-tail passes, `pruneRemovedProblems`, the account switch) is already interruption-safe — do not "fix" it.
- **There is NO shipped weakness constant of any kind** — both motif readings stand against a neutral point of the user's own: the tendency reading against the per-problem AVAILABILITY NULL, the strength reading against zero residual effect. **The null is VISITS-LINEAR**: per axis, the strict above/below quantities are the summed VISITS of the alternatives the board offered, not how many there are — each weighs the search its own evaluation rests on, and **a comment with no third field is 30 visits by the repo-wide convention** (`parse_eval_visits`, its client twin `getVisitsFromComment`), which is part of the null's DEFINITION, not a fallback. Still parameter-free: nothing is fitted and no other player enters. Because the weights are integers, both masses are exact integer sums and **the two producers agree EXACTLY** — `computeAltStats(rows, correctVec, weights)` (`pwa/js/picked-embedding.js`) against `alt_stat_masses` (`pipeline/package_for_pwa.py`); **`computeAltStats` refuses a call with no weights** rather than returning a count-shaped quartet in the wrong units. **The null is PRECOMPUTED at packaging** (`lookup.altstats.bin`) rather than rederived per reader: it depends only on the problem and its answer, never on the player. **Only a path holding the problem's SGF may compute it** — the live click path, which has the board — and **every other path reads the published masses** (`/refit`'s JSON, or `fetchAltStatMasses`' lookup-row Range); nothing may fall back to counting. Its reference is **row 0 of the problem's own per-cell block** — the answer, which generation pins as the first root variation — NOT the nominally equivalent vector in `metadata.json` or `lookup.embeddings.bin`. Those come from a separate computation and are not bit-identical, so referencing one compares cells across two projections and moves a count on ~2 problems in 100; row 0 is also what the live path uses. `emit_alt_stats` asserts row 0 is not the all-zero pass row, which makes packaging a corpus-wide check of the answer-first ordering. **Readers treat the pair as a mass, never a sample size** — a `> 0` admission test and the denominator of `above/(above+below)`, both scale-free. **Don't reintroduce a population baseline to "correct" any of them** (the two things it would correct for are exactly what make the reading about the user's RANK rather than their play), and **don't put the tendency test back on a fixed 50% null** — that reports the problem MENU as a property of the player (measured on the shipped bank: it flags the most menu-skewed motif for ~81% of testable users against ~42% under the availability null, and the menu decides the population lean's sign on 4 of 7 axes; `ablations.motif_null_figures`).
- **`MOTIF_Z` is ONE constant gating three things** (problem-motif display, the serve flag, the stats admission bar), locked so they cannot drift apart — retuning it anywhere retunes all three.
- **Candidates come from the unbroken run of loaded shards containing the serve rank's own band — never `state.allProblems` at large.** The serve draw is the flagged categories PLUS one NEUTRAL no-criterion slot, ALWAYS. Don't gate the motif slots on rank convergence, don't sample proportional to any weight, and don't argmax the information slot (it is itself a ko selector in the SDK/low-dan range).
- **`stabilityDaysForRepeat` has no upper clamp — don't reintroduce one.** Graduation IS the interval outgrowing the working window; a ceiling turns it into a perpetual recycle and serving drifts toward all recalls.
- All of the above in full, with the measurements: `docs/pwa_client.md`.

### Worker, sync and D1

- **`POST /refit` is an ACCELERATOR, never a dependency.** It answers a batch of history rows from the lookup-aligned sidecars it holds resident, so a re-derive stops opening one shard zip per problem (measured: a median 500-attempt window's wrong attempts span ~20 distinct shards, ~49MB of zips, against ~112KB over the endpoint). Every caller is best-effort — on 503, 409 or offline the original sidecar + shard passes run behind it unchanged and fill the rest, which is why nothing downstream may be made conditional on it. It takes the played move as EITHER a variation index (a locally recorded row has one) or a board coordinate (a synced row has only that), resolves the coordinate against the cell map, and always echoes the resolved index back for the caller to store. The client sends the lookup ROW it already resolved, so `dataVersion` equality is what makes that address safe; it reads published assets only and touches no D1. **It caches picked CELLS, never shard bins** — the full per-cell space is ~156MB against a 128MB isolate, but the space a refit can ever ask about is only cells a player actually picked (~39k distinct (problem, cell) pairs corpus-wide, 1.15 per failed problem), so a bin is read, the wanted cells are lifted out and the bin is dropped. Don't put a bin LRU back: a 200-problem batch spans ~173 shards, so bins essentially never repeat.
- **The userId IS the account credential; history syncs by append-only cursor.** The cursor is the AUTOINCREMENT `id` (`sinceId`), **never `created_at`**, because backfill inserts historical event times at the id frontier. A device's acked history is a 1:1 **mirror** of the server's rows keyed by `serverId`, so a complete from-0 pull converges in both directions and there is no timestamp dedup anywhere. **`idx_tsumego_reports_user_id` must stay in place.** The client-side daily full-pull cap is display only — the real one is server-side in `src/handlers/sync.js`, so the two must change together. Protocol: `docs/client_sync_and_cache.md`.
- **Google sign-in is a LOOKUP KEY ONTO AN ACCOUNT CODE, never a second kind of account.** A Google login ends in the SAME `switchAccount` a typed code goes through. `pwa/shared/google-auth.js` holds the client id ONCE, imported by the Worker (which pins every ID token's `aud` to it) and the browser — that pin is the only thing stopping a token minted for any OTHER site from logging its bearer in here. **EMPTY means the feature is off everywhere with no second switch.** `http://localhost:8787` belongs on a SEPARATE dev client, never the production one. `POST /google/signin` RESOLVES and writes nothing; only the opaque subject id is stored.
- **Never resolve a precached asset through `caches.match()`** — it searches caches in CREATION order, which puts the runtime cache ahead of the precache from the first deploy onward, and a badly-stored copy is then served for the life of the install.
- **Served data files are cache-busted by a content `data_version`, not `APP_VERSION`.** `pwa/tsumegos/` is gitignored, so a git-HEAD version is blind to a `package_for_pwa` re-ship from the same commit: any fixed-name data fetch must carry `?v=${DATA_VERSION}`, and content-hash-named files need nothing. **`data_version` (cache freshness) is deliberately separate from `ratings_version`/`embedding_version` (the re-derive gate).** **The stamp and the files it hashes travel together or not at all**: `pwa/tsumegos/` and `pwa/lookup.txt` move between machines by copy, and one run's `embedding_meta.json` beside another run's shards tells every cached client its shard list is current while those zips 404 — a reload cannot fix it, the key never having moved. `npm run build` recomputes the stamp from the files and refuses a tree where they disagree (`pwa/scripts/data-check.mjs`, twin of `compute_data_version`). Packaging is deterministic, so once a wrong set HAS been served under a value, only bumping `DATA_VERSION_EPOCH` (both halves) and repackaging moves it.
- **Write endpoints are guarded by three cheap layers upstream of D1, plus a maintenance freeze.** Validation is **deliberately format-only**, so any deploy smoke test must POST a real 8-hex problem id. **`MAINTENANCE_MODE` is a wrangler SECRET, not a `[vars]` entry** — a var of that name would collide with it and win on the next deploy, silently thawing an open window. A rollout lands UNEVENLY, so a freeze counts as confirmed only when several consecutive probes agree; the authoritative check that no write slipped through is the before/after `MAX(id)` comparison, never the probe alone. Never put the flag behind a per-request D1 or KV lookup. `docs/worker_operations.md`, `docs/db_surgery_runbook.md`.
- **D1 bills rows read**, which shapes two things. `pipeline.fetch_database` is incremental by `id` — **stop `npm run dev` before fetching** (it overwrites the miniflare D1 file), and **re-run rather than re-authenticate** on a spurious `code: 7403`, which is not a credentials problem. And the Community stats are ONE shared 7-day window query bucketed in JS, so **`idx_tsumego_reports_created` must stay indexed**; don't split it back into per-metric queries, and don't take rank off that window scan — what it measures is the difficulty a user was SERVED.
- **A player LINKS THEMSELVES on the leaderboard and NOTHING VERIFIES THE CLAIM.** Exclusivity and reversibility stand in for verification, both server-enforced. **Unlinking keeps the account's heartbeat rows** — they are its dated record, read by the rank-mapping fit like survey answers — and `declaredJsonSql` shows them only while a binding exists. **Every statement that writes or deletes `rank_surveys` rows must refresh `leaderboard.declared` in the same batch (`refreshDeclaredStmt`)** — the page reads that cache, never the log. The row stores the SHOWN rank, so est-vs-verified on that table is **not** a calibration measurement. `auxiliary/update_leaderboard_ranks.mjs` runs under the freeze and `--remote` opens and closes its own window; a post-re-rate refresh is `package_for_pwa` → `npm run deploy` → that script, in that order. `docs/leaderboard_and_community_stats.md`.
- **A leaderboard alias is the user's OWN pick, stored as the English triplet in `user_aliases` and translated only for display.** Precedence is a linked `display_name` > alias > `Anonymous`, with `hidden_profiles` withholding the linked name but NOT the alias (a hidden player shows their alias, else `Anonymous`), and **`user_aliases` is NOT pruned with `leaderboard`**. Edit the vocabulary ONLY in `pwa/shared/alias-words.js` and re-run `pwa/scripts/gen-alias-seed.mjs --write` — a word table and the bundle that disagree make the picker offer words the Worker then rejects. `docs/leaderboard_and_community_stats.md`.
- **The monthly historical boards are frozen from a peak tracker on the live `leaderboard` rows, and identity is resolved at READ time.** `best_rank`/`best_rank_timed`/`best_rank_month` hold the current UTC month's peak and are written by the **attempt paths ONLY** — the weekly `reconcileBuffers` must not touch them, or a rebuild of an inactive user is attributed to a month they never played; `auxiliary/update_leaderboard_ranks.mjs` REBUILDS them (and every finished month) by replaying the novel attempt log in one O(n) pass (`monthlyPeaksFromAttempts` / `windowRankWalk`), while `--no-history` clears them instead, because a peak on the old rank scale must not be mixed into a new month's snapshot. The month-change cron freezes the finished month into `monthly_leaderboards` as JSON of **raw user ids**, which `readMonthlyLeaderboard` resolves on the fly through `external_ids`/`user_aliases`/`hidden_profiles`, so an unlink, an alias re-pick or a hide applies to history. Retention is **5 weeks, not 7 days**, so a month's first days survive to the freeze; the page and the Community histogram still filter `last_active` to the trailing week. `docs/leaderboard_and_community_stats.md`.

## Conventions to be aware of

- **`tests/` covers MIRRORED code and the `utils/` import boundary, nothing else** — `./.venv/bin/python3 -m pytest`, seconds, needs `node`. Each twin test calls the shipped client module under node (`tests/js_bridge.mjs`) on the inputs its Python mirror gets and demands the same answer. **Changing either half of a twin means running them; adding a mirrored function means adding its twin test**, with the JS half in a module node can import (no DOM at load). Tests over `pwa/tsumegos/` JSON skip on an unpackaged tree. Fits, estimators and published figures are the ablations' job, and there is no CI: for anything else, verification is manual — for pipeline changes, run the step and check its printed diagnostics; for PWA changes, `npm run dev` and exercise the path in the browser.
- **Every number `pwa/about.html` or `docs/methodology.md` quotes is a `<span data-fig="KEY">` backed by `ablations/figures.json`, and `npm run build` fails on a mismatch.** A sentence leaning on a figure it does not quote carries an invisible `<!-- fig-guard: KEY OP NUMBER -->` beside it, checked against the same ledger — a violated guard means the sentence, not the number, needs rewriting. Don't edit the number in the document — re-run its producer (`./.venv/bin/python3 -m ablations --tier about`, minutes; `--tier methodology` adds the GPU measurements), read the printed span diff for sentences the new value invalidates, then commit ledger and documents together. The dates `methodology.md` says its figures were measured between are `data-fig-measured` spans filled from the same ledger (`--sync` rewrites them without measuring) — one overall range per document, never a date beside a claim. Producers hard-fail on any surprise in their inputs, so a run is also a check on the shipped artifacts. `ablations/README.md`.
- Python code uses absolute imports rooted at the repo (e.g. `from utils.constants import ...`). Pipeline scripts append `PROJECT_ROOT` to `sys.path` defensively.
- **KataGo coordinates skip the letter `I`; SGF coordinates do not. Every conversion lives in `utils/katago/coords.py`** — reuse those helpers rather than rewriting coordinate math, and add a new one there rather than beside its caller.
- `pwa/README.md` has additional context on the PWA's overall structure (overview, tech stack, project layout, architecture, dev workflow). Read it before substantive PWA edits.
- **For local DB analysis, prefer the binary `db/d1.sqlite` over the raw `db/d1.sql` dump.** Both come from `pipeline.fetch_database`, both are gitignored, and it keeps them in sync on every run, so you normally don't import by hand. If you ever rebuild the sqlite manually: `{ echo "BEGIN;"; cat db/d1.sql; echo "COMMIT;"; } | sqlite3 db/d1.sqlite` — the wrapper matters, because a full D1 export emits one un-batched INSERT per row and without a transaction sqlite fsyncs per row. **Never pipe the import through `head`/`tail`**: it SIGPIPE-kills `sqlite3` mid-import and silently leaves a partial table. Note a `--full` dump carries only tables that had rows at export time, whereas the incremental path's regenerated dump carries every table it discovered remotely.
- **Many artifact directories hold 100k+ files**, and **shell globs like `ls dir/*.npz` silently expand past `ARG_MAX` and report 0** — a verified false negative on `activations/9/`, not a theoretical one. Count with `find <dir> -maxdepth 1 -name '*.ext' -printf . | wc -c` and iterate with `find … -exec` or `xargs -0`. Treat anything under `tsumegos/`, `activations/`, `axes/`, `attempts/`, `ratings/` or `pwa/tsumegos/<size>/` as "may exceed argv" by default.
