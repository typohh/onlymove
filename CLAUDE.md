# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

YoseTsumego / onlymove.net — a Go (Baduk/Weiqi) tsumego pipeline. KataGo generates problems and rates them; the rated set is packaged into zip archives served by a Cloudflare-hosted PWA. There are four cooperating subsystems:

1. **`pipeline/`** — eleven executable scripts run in order (see "Pipeline commands" below). Each is a standalone `python -m pipeline.<step>` entrypoint. `package_for_pwa` is the single writer of `pwa/tsumegos/`; there are no side-channel patch scripts — to publish a labels-only or curve-only change without rebuilding zips, re-run `package_for_pwa` (its per-size change detection skips the heavy shard rebuild). Survey-driven rank calibration (`map_rating_to_rank.py`) and population-constant fitting (`fit_population_constants.py`) take no size arg and need no GPU, but **board-independent is not detachable — both sit INSIDE the sequence** (`docs/methodology.md` §3.1): `build_axes` reads `ratings/rating_to_rank.json`, so the curve must exist first, and `fit_population_constants` derives K from `axes/per_problem.csv`, so it must follow the axes.
2. **`utils/`** — shared logic, **split into two subpackages that import nothing from each other** (verified when the split was made, and worth keeping true): **`utils/katago/`** is the Go/KataGo side — `controller` (`KatagoController`: subprocess + thread-safe query dispatcher), `queries` (`KatagoQueries`, the analysis-engine wrapper), `problem_finder` (`ProblemFinder`, move-difficulty heuristics), `add_variations` (SGF tree construction, including `construct_initial_sgf`), `coords`, `models` (KataGo network downloads), `board_render`, `torch_model` (bootstraps `vendor/`, the vendored PyTorch KataGo — it puts that directory on `sys.path` so `import katago.…` resolves there; that top-level `katago` package is the VENDOR's, distinct from this `utils.katago`, and they do not shadow each other). **`utils/rating/`** is the statistical side — `features` (the rating trunk's inputs), `ratings_io` (the `ratings/` artifacts + curve reader), `fit_rank_curves`, `rank_surveys`, `residual_axes`, `slope_calibration`, `rank_curve_shape`. `utils/constants.py` (was `configurations.py`) holds the few values both need — `ALL_BOARD_SIZES`, `KOMI`, `RULES`, `DEFAULT_MODEL`, the debug flag.
3. **`pwa/`** — vanilla-JS ESM PWA built with esbuild, deployed as a Cloudflare Worker. The Worker entrypoint `pwa/src/index.js` handles these HTTP routes — `POST /report` (per-attempt logging; `createdAt` is REQUIRED in the payload — the CLIENT owns the event time (it mints one ms per attempt, stores it as the entry's `date`, and the row is inserted VERBATIM, so row.created_at === entry.date exactly and sync matching is exact) — and the server only sanity-bounds it, REFUSING (never rewriting) with `400 {error, serverNow}` on missing/future(+2min)/stale(−7d) so the client can self-correct once and resend (a silent rewrite would recreate the dup-mint precondition); responds `{serverId, userSeq, digest}` (no createdAt echo) — `serverId` the row id stamped on the matching answerHistory entry (its presence = acked; the id-cursor + digest key) so sync pulls skip the device's own rows; `userSeq` the per-profile attempt count, the **digest sync signal** (a jump past the device's expected seq = another device wrote → pull); see the account-sync note below), `POST /sync` (account sync: pages the user's reports newer than the client's **`sinceId` AUTOINCREMENT-id cursor** — gap-free for rows inserted with a historical `created_at` such as an offline flush — at 1000 rows; every response also carries a `serverSeq`/`serverDigest`/`serverMaxId` digest summary for the cheap in-sync check; an optional `limit` shrinks the page — `limit: 1` is the client's frontier/existence probe. A request without a valid `sinceId` (a pre-redesign client on the retired created_at cursor) gets an empty no-op so it just resyncs on reload — see the account-sync note below), `GET /push/vapid-public-key`, `POST /push/subscribe`, `POST /push/unsubscribe`, `POST /schedule` (recall-reminder schedule; **diff mode** — the client keeps a per-row hour-rounded snapshot in localStorage and sends only changed rows + explicit removals, since each upsert bills the row plus its two partial indexes and replace-all is the heaviest D1 write path; legacy `{schedule}` replace-all still accepted; every call, even an empty diff, bumps `push_subscriptions.last_seen_at`, the cron's mid-session suppression watermark), `POST /rank-survey` (per-server rank declarations → `rank_surveys`), `POST /share-event` (share-link create/open analytics → `share_events`; the client sends user/problem/size and, for opens, `document.referrer`, while the worker stamps the Cloudflare edge geo-IP `country`), `GET /server-stats` (serves the cached community-stats blob — see the server-stats note below) — plus a cron-driven `scheduled()` handler that walks `recall_schedule` to deliver due Web Push notifications **and** recomputes `server_stats` (≥23h old or on a version change), and an SPA fallback that derives board size from `/9` or `/13`. Static assets ship via the `[assets]` binding in `wrangler.toml`. D1 binding `DB` → database `tsumego-reports`, tables: `tsumego_reports` (per-attempt log: `user_id, problem, success, created_at, size, move, time_used, review_time, is_repeat`, plus the per-profile sync-digest columns `user_seq` (attempt count) + `running_sum` (Σ rowHash(id) exclusive prefix), lazy-seeded in the INSERT — see the account-sync note; no `UNIQUE(user_id, problem)` constraint, so repeat attempts produce their own rows; **indexed on `created_at`** — `idx_tsumego_reports_created` — for the server-stats window scan, **and on `(user_id, id)`** — `idx_tsumego_reports_user_id` — for the per-user id-cursor `/sync` scan + the digest's O(1) latest-row lookup (the legacy `(user_id, created_at)` index `idx_tsumego_reports_user_created` was dropped with the created_at `/sync` path, on the live D1 too — when retiring an index, drop it only AFTER the deploy that stops reading it)), `push_subscriptions` (one row per device — `endpoint` PK, `user_id` indexed — so the recall cron fans each due reminder out to all of a user's devices; per-device throttle + dead-endpoint cleanup, per-account active-session suppression), `recall_schedule`, `rank_surveys`, `share_events`, and `server_stats` (single-row JSON cache, `key='latest'`). Schema lives in `pwa/schema.sql` (idempotent `CREATE … IF NOT EXISTS`); apply new tables/indexes to the remote D1 with `npx wrangler d1 execute tsumego-reports --remote --file=schema.sql`.
4. **`analysis_server/`** — a tiny HTTP server wrapping KataGo for the PWA's analysis fallback when SGFs lack embedded win-rate data.

Plus `auxiliary/` (one-off diagnostics, legacy code; not part of the main flow) and `vast_orchestration.py` (rents Vast.ai GPU instances to run the heavy pipeline steps remotely).

## Pipeline commands

Always invoke pipeline modules through the venv's Python so PYTHONPATH resolves correctly:

```bash
./.venv/bin/python3 -m pipeline.fetch_database        # INCREMENTAL by default: pull only new tsumego_reports rows (by AUTOINCREMENT id) + re-fetch the small tables whole, merge into db/d1.{sqlite,sql}, sync local D1. --full forces a complete re-download (auto-used when there's no local db/d1.sqlite baseline)
./.venv/bin/python3 -m pipeline.tune_engine <size>    # tune nnMaxBatchSize / numAnalysisThreads in bots/analysis.cfg (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.generate_tsumegos <size>  # long-running generator → tsumegos/<size>/ (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.benchmark_bots <size> # bots solve generated tsumegos → attempts/<size>/ (size ∈ {9,13}, mandatory)
./.venv/bin/python3 -m pipeline.extract_activations   # KataGo trunk activations per problem → activations/<size>/<id>.npz (GPU; resumable); feeds both the rating features (bw_act) and build_axes
./.venv/bin/python3 -m pipeline.cache_rating_features  # build BOTH aggregate caches the rating trainer reads — run before train_rating. (a) the candidate-move-eval cache `activations/_signal_cache/move_evals_<size>.npz` that the move block reads, and (b) the correct-cell activation vectors `activations/_signal_cache/correct_vecs_<size>.npy` + `correct_ids_<size>.json` (read by utils.rating.features.load_joint_activations), built by `utils.rating.features.build_correct_vec_cache` which this step calls FIRST — correct_ids is both the rated set and this step's own tid set, so one command keeps them in lockstep. Both are INCREMENTAL and RECONCILE IN BOTH DIRECTIONS — new tids are added (so a tsumego TOP-UP is picked up automatically; a stale correct_ids would silently drop the new problems from the rated set) and departed tids are PRUNED (so a corpus purge leaves no orphan rows). "Up to date" means the cached tid set EQUALS the target set, never just "nothing new to add" — the earlier `not to_extract` short-circuit stranded 344+162 purged rows in move_evals. `--force` re-extracts the move features only; `--rebuild-activation-cache` additionally re-reads every activation .npz (hours — for a corrupt cache, not routine). **The .npz set must be a SUBSET of `tsumegos/<size>/`, asserted before any work** (`_assert_activations_subset_of_corpus`) — ONE-DIRECTIONAL: corpus ⊋ activations is normal (extraction is resumable, so a fresh top-up has SGFs with no .npz yet), but an .npz with no SGF is a hard failure, because `correct_ids` is derived from that listing and an orphan silently promotes a problem that NO LONGER EXISTS into the rated set — it gets features, a rating, a slope and a floor, ships nowhere (packaging works off `tsumegos/`), and nothing downstream can tell it from a real one. Found in production 2026-08-02: one 13x13 .npz left by a pre-canonical-id removal had been feeding a phantom through the whole rating chain since May. **Any unreadable input is likewise an ABORT, never a dropped row**: a corrupt .npz raises out of the worker, and a non-finite row inherited from an older cache is refused at write time (the tmp is removed, the existing cache left intact). The rejected alternative is a NaN row, which is invisible — the tid stays in correct_ids while `_fit_joint_pca`'s finite mask removes it from the fit, so the problem leaves the rated set with nothing anywhere recording it. (The per-problem npz artifacts — activations, per_cell embeddings — are inherently incremental via file existence; only these two roll-up caches needed explicit incremental support.)
./.venv/bin/python3 -m pipeline.train_rating       # SINGLE-PASS rating-gauge cross-board 4PL rating model → ratings/<size>/ (joint fit of all three heads + learned ceiling, two divergence barriers, phase-2 in-sample global slope-scale fit; 80%-clear rating). PRODUCTION-ONLY: takes NO CLI args (config baked in as module constants; always seed 0 → ratings/); features bw_act+move+phase so run pipeline.extract_activations + pipeline.cache_rating_features first (the game-phase block’s SGF-parse cache auto-builds on first load via utils.rating.features.load_joint_game_phase); the full experiment surface (--production-flags, --gauge, the barrier/EIV knobs, the staged legacy configs, eval suite, alternative objectives) lives in auxiliary.rating_dev.train_rating_staged (and …_research)
./.venv/bin/python3 -m pipeline.map_rating_to_rank      # rank_surveys + db/d1.sqlite (timed attempts for the career-block anchors + median solve time) → ratings/{rating_to_rank.json (curve + a top-level time_adjust{alpha,center}), rank_map.json (per-server couplings INCL EGF)}. CONSENSUS model (rating→consensus rank→every server incl EGF; time α fit jointly); anchors are overlapping 2-month CAREER-BLOCK ratings, attempt-mass-weighted, each declaration normalized to total weight 1 (see the `M` note below). BACKEND; package_for_pwa publishes it. Production-clean (no experiment flags; the CV harness that validated the anchors is auxiliary/eval_rank_map_cv.py)
./.venv/bin/python3 -m pipeline.build_axes            # supervised residual SKILL AXES (replaced the ICA embedding 2026-07-18) → axes/; incremental K, needs attempts DB + ratings/ + rating_to_rank.json; run AFTER train_rating + map_rating_to_rank
./.venv/bin/python3 -m pipeline.fit_population_constants  # ratings/ 3PL params + attempts DB (+ axes/per_problem.csv & rating_to_rank.json for the weakness-model ridge λ) → ratings/population_constants.json (retention/time-bias constants (incl. `first_success_step`, the POST-LAPSE term — see the recall note; MOMENT-MATCHED from the within-user rung-0-vs-rung-1+ odds ratio, never likelihood-fitted) AND the per-axis weakness_axis_lambda (length K, mandatory — no scalar fallback); the time-adjust {alpha,center} is READ THROUGH from rating_to_rank.json, NOT fit here; BACKEND; package_for_pwa publishes it; the PWA build inlines it into the JS bundle. Also runs the ZERO-MEAN CHECK on that prior and HALTS past the bar — `--allow-axis-mean` overrides deliberately)
./.venv/bin/python3 -m pipeline.package_for_pwa       # SINGLE writer of pwa/tsumegos/: zip + lookup.txt + embedding_meta.json + copies the rating→rank curve across; change-detects per size (skips unchanged shard rebuilds; --force to override). Reads ratings/.
```

Run on a remote Vast.ai GPU instead: `python vast_orchestration.py` (no args prints subcommands; only `tune`, `generate`, `benchmark` are remoted — the rest stay local).

**Several of these steps run for HOURS, none of them checkpoint, and a naively launched run WILL be killed part-way — losing all of it.** `build_axes` is the clearest case (~50 min per K candidate, three or more candidates, then a full-data refit and the per-cell fanout: 3+ hours end to end); `generate_tsumegos`, `benchmark_bots` and `extract_activations` are the same order or worse. Three ways such a run dies quietly, and what to do instead:

- **A shell that backgrounds with `&` and then exits takes the child down with it** (SIGTERM, exit 143) — including a wrapper that backgrounds the real work and then returns. Launch detached: `setsid nohup ./.venv/bin/python3 -u -m pipeline.<step> > /tmp/<step>.log 2>&1 < /dev/null &`.
- **`timeout N` kills at N with exit 124 and no partial result.** Don't wrap a step in a timeout unless you are certain it exceeds the real runtime; a too-short guess is indistinguishable from a crash after the fact.
- **Piping through `tail`/`head` buffers everything until exit**, so a healthy long run looks hung and a dead one looks alive. Run python with `-u`, redirect to a file, and poll the file.

**`axes/`, `ratings/`, `activations/` and `pwa/tsumegos/` are all gitignored, and the steps that write them overwrite IN PLACE** — a commit is not a rollback point for any of them. Before a refit, copy the current artifacts aside (for axes: `axes/{axes.npz,labels.json,per_problem.csv,label_anchors.npz}`), or a fit that comes out wrong leaves nothing to go back to.

## Rating pipeline (combined cross-board MLP-2PL)

The rating backend writes under `ratings/`, and `package_for_pwa` ships it to `pwa/tsumegos/`. The three commands — `train_rating`, `map_rating_to_rank`, `package_for_pwa` — are listed under "Pipeline commands" above.

**The full derivation and the measurement trail live in `docs/methodology.md` §1.3–1.11.** What follows is only what you need in order not to break it. `P = floor + (1 − floor − lapse)·σ(a_p·(θ_u − b_p))`, one shared feature net across 9×9+13×13 with a shared per-user ability, **no per-problem residual parameters** — the net IS the model, so never-attempted problems get a real feature-conditional curve and an attempted problem departs from it only through dropout-limited memorization.

`pipeline.train_rating` is the **production-only** trainer: no argparse, config baked in as module constants, always seed 0, always writes `ratings/`. Run `pipeline.extract_activations` then `pipeline.cache_rating_features` first — the move-eval cache is a hard prerequisite; the game-phase SGF-parse cache auto-builds on first load. The entire experiment surface (alternative gauges, barrier weights, EIV probes, the staged legacy configs, the held-out/survey-ρ eval suite, alternative objectives) lives in `auxiliary.rating_dev.train_rating_staged`, so a test tweak cannot reach the shipped ratings. Its `--production-flags` reproduces the shipped **configuration**, meaning the FIRST PASS only — the research trainer has no phase 2, so its slope/floor outputs are first-pass values.

**What ships per problem** (`package_for_pwa` → `metadata.json`): `rating` = the 80%-clear point (`CALIBRATION_P` = 0.8, the margin the PWA serves *and* anchors at), raw and UNSCALED; `slope` = the discrimination MULTIPLIED by the phase-2 calibration scalar; `floor` = unscaled. So a published slope and a first-pass slope from a training log are different quantities — don't compare them (§1.11). "Raw" throughout means *not repackaged* (no bounded remap, no rank baked in), never "first-pass". The `rating_model` tag in `embedding_meta.json` records provenance only; the PWA does not branch on it.

**`PCA_DIM` (the joint-PCA activation width) is 128 and that is MEASURED-OPTIMAL — don't sweep it again (2026-07-27).** Single source `pipeline/train_rating.py`, imported by `build_axes` + `utils/rating/residual_axes`. 8/16/32/64/128/256 were each run end-to-end (own ratings → rank map → population constants → axes); 128 wins from both directions and 256 is refuted, carrying the memorization signature. §1.3.

**Measured-rejected — do not re-attempt** (each cost a full study; §1.5, §1.7, §1.10): weight decay as a substitute for ANY of the dropout; per-problem residual parameters in any configuration; bot-anchor examinees; a per-attempt-count slope correction; ability-noise / errors-in-variables treatments; mixup; and a direct penalty on the derived rating, which is Goodhart-able through the floor — **the divergence barriers must act on the OFFENDING PARAMETER** (pre-clamp slope, floor in logit space), never on the rating. The one untested ceiling-raiser is D4 symmetry augmentation of the activations.

**Dropout is 0.3 at COLUMN granularity** on the three wide blocks (activations / bot winrate / move-eval) and between the trunk's hidden layers; the two game-phase columns and the size indicator are deliberately outside every mask. Feature-block dropout is applied **by column range**, so a new feature block inserted anywhere but last is silently regularized or silently exempted depending on which side of that boundary it lands (§1.3).

**Open, and don't state otherwise.** The phase-2 scalar's constancy is measured against attempt count ONLY — rating, slope and floor strata are unchecked, and the floor axis is the prime suspect — so treat one global scalar as UNREFUTED rather than established, and don't add per-problem or per-count corrections meanwhile. The corpus hard tail (KataGo-hard, unattempted — about a third of the published set) is extrapolated rather than interpolated, and per-problem calibration there is not established.

## Architecture notes that span multiple files

**Tsumego identity is symmetry-aware and single-solution.** Filenames come from `get_orientation_invariant_hash` (`pipeline/generate_tsumegos.py:154`) — SHA-256 taken over all 8 D4 transforms of the board, with `min()` picking a canonical orientation. The dataset therefore cannot contain two problems that are rotations or reflections of each other; `tsumego_id` is the symmetry-canonical hash truncated to 8 hex chars. This invariant is corpus-wide clean since the 2026-07-21 id surgery (the pre-09/2025 move-sequence-hash ids were renamed to canonical, duplicate positions collapsed, and the DB rewritten through the committed `surgery/id_map.json`; `auxiliary/check_corpus_ids.py` re-verifies, and `--emit-map` regenerates a surgery map if a future defect ever needs one). By generator design every problem has exactly one correct first move (the `solution` returned by `ProblemFinder.create_problem`); downstream code can rely on the "one canonical answer per problem" invariant. **That answer is also `variation_nodes[0]`, and generation ENFORCES it rather than assuming it** — `promote_winning_first_move` (`utils/katago/add_variations.py`) reorders the decision node's children so the move the SHIPPED evaluation comments name (highest winrate for the mover, score breaking exact ties — the client's `findBestMoveFromChildren` rule) leads. The two can disagree at generation time: the solution written first is what `ProblemFinder.is_valid` verified on a deeper re-read, while the candidates' comments come from later passes at their own playout budgets. Reorder, don't discard — such a position is still well-posed, and `first_move_is_well_formed` (the separate single-solution gate) passes it. **The invariant is load-bearing because the two consumer kinds read the solution differently**: the client picks by evaluation and is order-blind, while every backend stage takes it POSITIONALLY (`extract_activations`' `correct_idx`, `benchmark_bots`' grading), so a misordered file silently feeds a LOSING move's activations into the rating features and the shipped per-problem axis vector while still playing correctly in the app. `auxiliary/check_tsumego_sequences.py` re-verifies the corpus (`winner is NOT variation_nodes[0]` must be 0). Note the SGF variation order is NOT what the activation npz uses — that is board-scan order, addressed by `correct_idx` (see the extraction note below).

**Board size — two supported modes: 9x9 and 13x13.** Both ship in production; the PWA picks one from the URL path (`/9` or `/13`) via the SPA fallback in `pwa/src/index.js`, and the D1 `report` endpoint records `size` per attempt. **`/9` and `/13` are entry-only size HINTS, not persistent addresses.** They are read once at boot (`getBoardSizeFromPath` → `resolveInitialBoardSize` in `pwa/js/main.js`); the chosen size persists in state/localStorage thereafter, not in the URL. `cleanUrl()` (lives in `pwa/js/problem-loader.js`, called from `displayProblem`) **collapses the path to `/` and strips `?id`/`?o`/`?recall` whenever a NON-linked problem is painted**, so once you're on a normal problem the address bar is `/`. Do NOT assume a reload leaves the bar at `/9` or `/13`; it does not. **Linked (shared) problems are the deliberate exception: their `?id`/`?o` are KEPT in the address bar for the whole linked session** (`displayProblem` skips `cleanUrl` while `appMode === LINKED`), so that any reload — a service-worker update takeover (`index.html`'s `controllerchange` → `location.reload()`, the most common one; in-app browsers like Instagram hit it when a stale cached SW is replaced by a freshly-deployed version), the `?id`-404 / repeated-load-failure reloads in `problem-loader.js`, the version-mismatch `maybeReload`, or a manual refresh — **re-enters the SAME shared problem at boot** (`parseUrlIntent` reads `?id`) instead of dropping to the standing challenge. The URL is cleaned the instant the user moves on to a non-linked problem (`returnToChallenge`/`advanceToNextProblem` → `displayProblem`). On the **pipeline side** there is no single global `BOARD_SIZE` and no in-process dual-size run. The three single-size generation steps — `pipeline.tune_engine`, `pipeline.generate_tsumegos`, `pipeline.benchmark_bots` — take a **mandatory positional `size` arg** (`{9,13}`), which is threaded through the utils (`KatagoQueries(controller, board_size)` owns it as a public `board_size` attribute; `KatagoController.start_engine(model, board_size, …)`, `ProblemFinder` reads `queries.board_size`, and the leaf helpers `construct_initial_sgf(…, board_size)` / `get_child_move(…, board_size)` take it explicitly). The downstream steps (`extract_activations`, `build_axes`, `train_rating`, `map_rating_to_rank`, `package_for_pwa`) instead iterate `ALL_BOARD_SIZES` and process both sizes in one run — they take no size arg. Artifact directories are keyed by size: `tsumegos/<size>/`, `attempts/<size>/`, `ratings/<size>/`, `pwa/tsumegos/<size>/`. To refresh both sizes, run each generation step once per size (e.g. `… generate_tsumegos 9` then `… generate_tsumegos 13`), then run the downstream steps once. On the remote, `vast_orchestration.py run <step> <size>` forwards the size verbatim (validated locally against `ALL_BOARD_SIZES`).

**On the client, rank + stats + the learned models are merged across sizes; histories, `M` curves, and problem pools stay per-size.** From the user's perspective 9x9 and 13x13 share one rank (front-page label, problem selection, recall eligibility) and one stats page. `pwa/js/state.js` keeps `answerHistory` as ONE unified cross-size array (date-ordered, each entry tagged with `size`; the recent working set in localStorage, the older tail in IndexedDB — see the answerHistory-storage-split note below) plus single shared values (`userRank`, `displayRank`, `serveRank`, the recall model `modelParams`/`adamState`, the weakness model `weaknessParams`/`weaknessAdam`/`weaknessSe`/`weaknessAxisCov`); the only per-size persisted bucket is `challengeProblem`. (A `mergeSharedAcrossSizes_v2` migration flattens any legacy per-size rank/model buckets: `userRank = max(rank_9, rank_13)` — a strong 9x9 player immediately gets hard 13x13 problems — and the model buckets are dropped so the shared models retrain.) `getMergedAnswerHistory()` returns that unified array (the WORKING SET), each entry tagged with `size`; the recall and weakness models train from it (they slice the recent window, so the working set suffices). The stats panel (`showDetailedStats`, in `pwa/js/stats-ui.js`) instead awaits `getMergedFullAnswerHistory()` so its charts span the whole career (working set + IndexedDB tail). Pooling is sound because every feature they read is board-independent — `problemRank` is the consensus internal rank (a normalized 0.5 means the same internal rank on either board), and the embedding axes are jointly fit across sizes. Play-time size-awareness is preserved: a recall problem can only be re-shown on its own board, so `getRecallCandidates` takes an explicit `history` (defaults to the active size; the merged union is passed only for stats counts) and `buildRecallSchedule(size)` reads the shared model + shared rank but that size's history. Two consumers do real work to pool: the recall logistic carries a `SIZE_IS_13` fixed effect (9x9 = baseline) whose coefficient ÷ logit-per-rank is the stats panel's "stronger/weaker on 13x13" readout; and the skill decomposition (`rank-decomposition.js`) pools in **internal-rank space** with a per-attempt slope `LOGIT_PER_RATING / |M'(rating)|` (each attempt mapped through its own size's curve), so both sizes share one skill curve without the rank-space slope bias.

**answerHistory storage is split: a unified working set in localStorage, the cold tail in IndexedDB.** `answerHistory` is ~99% of localStorage and on heavy users overflows the ~5MB quota, so `pwa/js/state.js` keeps the most-recent `ANSWER_HISTORY_WORKING_SET` (3000, `constants.js`) attempts — unified across both sizes — as a synchronous localStorage array; everything older is evicted to IndexedDB via `pwa/js/history-store.js` (`appendTail`/`getTail`/`updateTail`/`clearTail`, durable via `navigator.storage.persist()`, every method a safe no-op/empty if IDB is unavailable so play degrades to working-set-only, never breaks). 3000 is the largest hot window the app uses on the *merged* history (the recall-candidate replay warms over the last 3000), so the working set is a superset of every synchronous read: all the existing consumers read `state.answerHistory` (a cached active-size filtered view of the unified array) or `getMergedAnswerHistory()` (the working set) and already slice ≤3000 (`getRecallCandidates` −3000, the models −`MODEL_INPUT_HISTORY_LENGTH`). Only the full-career charts await `getMergedFullAnswerHistory()` (tail ⧺ working set, de-duped by `(problemId, date)`). The write path stays synchronous — `setAnswerHistoryForSize`/`updateAnswerHistory` route through one `reconcileSize` that replaces a size's entries in the unified array and persists; a debounced `evictColdTail()` then appends overflow to IDB **and confirms before trimming** the in-memory/localStorage working set (crash-safe seam: a kill mid-evict leaves a de-duped dup in both, never a gap; an IDB-unavailable append keeps the rows in the working set). `initHistoryStorage()` runs once at boot (the state-epoch gate at `state.js` import time has already settled the storage shape) — `main.js` awaits it before the embedding backfill writes, freeing localStorage on a quota-stressed device. The cold tail feeds ONLY the full-career chart (it is all older than `MODEL_INPUT_HISTORY_LENGTH`, carries no embeddings, and no model reads it). A **curve-only** refit recomputes the tail's `problemRank` from its stored raw rating (`backfill.js` via `updateTail`, no shard walk). A **ratings change** instead re-derives the tail's full rating fields from the shards — the SAME shard walk the working set uses, extended to the tail's problem ids — because the tail's ratings are frozen at eviction time, so after a re-rate they go stale AND device-dependent (each device evicted at a different rating era), and the chart plots them: two synced devices' Rank-tab graphs diverged at the start until this. A problem that left the corpus has its rating fields STRIPPED rather than left stale (the attempt stays, rating-less; `flattenAttempts` then drops it from every estimate — front-page rank, chart, weakness, recall all already skip rating-less/embedding-less rows). An account switch `clearTail()`s then re-splits the full pull. Two accepted tradeoffs, both kept synchronous on purpose: a re-draw of a problem last seen >3000 attempts ago is treated as new (repeat-detection scans the working set only), and `timeAdjustDeltaRating` uses the working-set median solve time.

**Account sync: the userId IS the account credential; history syncs by append-only cursor.** Full protocol — the id cursor, mirror-by-id semantics, the sum-first digest backstop, the offline outbox, the state-epoch gate, and the invariants in `account-sync.js` — is `docs/client_sync_and_cache.md`. What must not be broken from anywhere else: the 8-char `userId` doubles as the account password (entering another code adopts that account); the cursor is the AUTOINCREMENT `id` (`sinceId`), **never `created_at`**, because backfill inserts historical event times at the id frontier; a device's acked history is a 1:1 **mirror** of the server's rows keyed by `serverId`, so a complete from-0 pull converges in both directions and there is no timestamp dedup anywhere; the front-page rank is a **pure function** of the recent merged history (`estimateWindowRank`), so adoption and incremental sync are the same operation — recompute, no loop state to warm (there is no warm start at all: the estimator is a grid posterior over the shipped population prior, never over its own previous value); **`idx_tsumego_reports_user_id` must stay in place** (it is what makes an up-to-date poll read ~0–1 rows); and the client-side daily full-pull cap is display only — the real one is server-side in `src/handlers/sync.js`, so the two must be changed together. Known gaps: the ignored-problems list is per-device, and linked-mode attempts are recorded nowhere (see the PWA-state note above).

**The live rank is a grid posterior over a measured population prior, and THREE ranks come out of it.** Model, the prior's provenance and survivorship caveat, and the offsets: `docs/methodology.md` §2.3, `docs/client_sync_and_cache.md`. The rules that bind from elsewhere: `pipeline.fit_population_constants` fits `rank_prior` (a log-density on a rank grid) and it is **MANDATORY with no fallback** — an unanchored estimator still returns a number, it just tracks wherever it last drifted, so the failure is invisible. The prior is **never** the user's own previous estimate (that was the overshoot root cause: it damps steps but anchors level to nothing, and early windows are frequently all-correct/all-wrong where the unpenalized likelihood has no interior maximum). The posterior is evaluated on a GRID, not by Newton+Laplace, because the population is bimodal and so is a short-window posterior — a mode fit would report a falsely tight `se`, the unsafe direction for every offset built on it. From that one posterior: **`userRank`** = the mean, the honest number everything CALIBRATED reads (server-coupling anchors, the Worker's `pred_rank`, recall, weakness) — never feed a shifted value here or the calibration loop closes on it; **`displayRank`** = `mean + K_DISPLAY·excess` (`K_DISPLAY` = −2), what the user is told (badge, rank-change overlay, the rank-translation modal, and the Rank chart's front-page-rank line — the chart's slow SKILL line deliberately stays on the mean); **`serveRank`** = `min(mean + excess, displayRank + serveGapCap(attempts))`, what selection targets. `excess` = `max(0, se − seFloor)` so all three collapse onto the mean at convergence and neither offset leaves permanent bias. **Serving must NOT simply follow the display down** — measured: it starves the estimator (successes on far-below problems carry no information, `se` never falls, the display never recovers) and a beginner sits several ranks under their true rank for hundreds of attempts. **The gap resolves to `min(3·excess, cap)`, so the CAP — not the UCB term — is what binds through onboarding and therefore what sets how fast a strong user is found.** It is `1 + the current run of correct answers` (`serveGapCap`, reset by any miss, never zero) — **NOVEL attempts only**, since `flattenAttempts` filters `isRepeat`/`linked` before the array reaches it (Worker side: `is_repeat = 0` in the leaderboard buffer), and that is deliberate: a missed REVIEW is evidence about forgetting, not about serve difficulty. **The point of the streak form is the ASYMMETRY, obtained with no branch and no threshold**: a weak player misses often so their run stays short and the cap stays near its floor, while a strong player's run grows monotonically and the cap stops binding within ~10 attempts. Measured (fixed-ability sim, shipped corpus, first 30 problems of a true 20k, share landing >3 ranks above them): streak 13.3%, constant-5 12.0%, **attempt-count 64.9%** — so `cap = attempts` reaches the same speed by serving beginners far over their head, and is the specific thing this form exists to avoid. **Do not put it back to a constant.** A constant `c` doesn't just limit the bonus, it INVERTS it — `display + c` is BELOW the mean whenever `excess > c/2`, i.e. all of onboarding at `c` = 5, so the app serves under its own best guess and starves exactly as above (measured at `c` = 5: an unlimited-strength player needs ~38 first-time attempts to reach a dan badge vs ~25 under the streak rule, and a simulated fixed-ability 20k clears 0.91 of what it is served against the 0.80 target). The accepted cost is that the badge-vs-served gap is bounded only in distribution (typically ~2 ranks, 10+ during a long run) rather than by a constant.

**Recall serving is volume-targeted via a stochastic gate; stability has NO ceiling.** Model, equilibrium and the full measurement against the attempt log: `docs/methodology.md` §2.8 (harness `auxiliary/eval_recall_model.py`). The operating rules:

A due recall wins a serve decision only with probability `recallServeShare()` (`pwa/js/recall-model.js`), the constant-volume equilibrium share solved at **`SHARE_VOLUME_FRACTION` = HALF the user's trailing-week daily average** — deliberately, and note the direction is the opposite of what "half" suggests: the working window is counted in ATTEMPTS, so a lower assumed volume makes the served share RISE. While the share is not estimable (no model / no week volume / too few recent novels / no rank) due recalls always win, and the gate **FAILS OPEN** on any estimator error (`recallGateAllows` in `problem-loader.js`; `selectNextProblem`'s never-throws contract). The roll happens BEFORE the recall is built, so a gated-out recall costs no shard fetch, and it is **DETERMINISTIC — hashed from (most-due candidate id, last recorded attempt date), not `Math.random()`**: the tab-visible `refreshShownProblemAfterSync` must re-derive the same decision rather than re-roll, since independent resume rolls would compound into `1−(1−share)^n` chances to swap a due recall onto an idle novel. Every new attempt re-seeds, so genuine serve decisions stay independent Bernoulli(share) draws. Notification clicks (`?recall=1`, `main.js`) bypass the gate.

**`stabilityDaysForRepeat` has NO upper clamp — don't reintroduce one.** Graduation IS the streak's exponential interval outgrowing the `RECALL_CANDIDATE_HISTORY_LENGTH` working window; a ceiling turns graduation into a perpetual recycle, so the pool can only grow and serving drifts toward 100% recalls. Overflow needs no clamp (lnS is a small linear form) and `!isFinite(S)` maps to Infinity = never-due, which `buildRecallSchedule` skips explicitly.

**`first_success_step` is fit by MOMENT MATCHING, never by retention likelihood** (`fit_population_constants`). It is an INDICATOR on "the previous attempt succeeded", not a second growth rate — the second success adds nothing measurable. The likelihood is the wrong instrument here: it scores predictions on intervals the scheduler itself chose, and sizes the step about threefold too small. Two cautions when quoting the measurements: the 0.80 test is ONE-SIDED (a ceiling, not a tolerance edge — a serve realizes less retention than the window's open), and the raw delivery figure of ~0.55 serves per entry is mostly confound — don't quote it (§2.8).

**Worker-version-driven graceful reload.** `pwa/build.mjs` writes `pwa/src/version.js` so the Worker imports the same hash the client gets via the esbuild `define`. Every `/report` response stamps `X-App-Version`; if it differs from the client's `APP_VERSION`, the client sets `state.reloadPending`. `maybeReload` fires from `setAcceptClicks(true)` only when `appMode !== ANALYZING`, so the refresh always lands between problems — never mid-review. New JS-side features that depend on the Worker version (e.g. embedding/ratings backfills keyed by content hashes shipped in `embedding_meta.json`) ride this reload signal. **`computeVersion()` folds a hash of every inlined data file (`INLINED_DATA_FILES` — `embedding_meta.json` + the curve/rank-map/population JSONs) into `APP_VERSION`** so the reload signal moves on a data-only re-ship: `pwa/tsumegos/` is **gitignored**, so a git-HEAD-only version would be blind to a `package_for_pwa` re-ship from the same commit (the original cause of the cross-device staleness — see the data-version note).

**Served data files are cache-busted by a content `data_version`, not `APP_VERSION`; `embedding_meta.json` is inlined.** The content-addressed chain, the Range-request behaviour of Workers static assets, and the `_headers` rules are in `docs/client_sync_and_cache.md`. The rule that governs new code: `pwa/tsumegos/` is **gitignored**, so a git-HEAD version is blind to a `package_for_pwa` re-ship from the same commit — any fixed-name data fetch must carry `?v=${DATA_VERSION}` (read synchronously from the inlined manifest via `pwa/js/data-version.js`), and content-hash-named files need nothing. **`data_version` (cache freshness) is deliberately separate from `ratings_version`/`embedding_version` (backfill gate):** a ship that only ADDS tsumegos bumps `data_version` so new problems become serveable lazily with no history walk, while a ratings change bumps `ratings_version` and triggers the immediate re-derive.

**Server-wide "Community" stats are a cached, read-cost-sensitive D1 aggregation.** Metric-by-metric definitions (the median-per-user bucketing, the review-time double-count fix, the recall-gap bins) are in `docs/leaderboard_and_community_stats.md`. The cost rules, which are the reason the shape is what it is: **D1 bills rows read, so `created_at` MUST stay indexed (`idx_tsumego_reports_created`)** — without it every window scan is a full-table scan that blows the daily read quota — and there is **ONE shared 7-day window query over `tsumego_reports`**, bucketed in JS; don't split it back into per-metric queries. The rank histogram and country distribution deliberately do NOT come from that scan: they ride the small `leaderboard` table scan the `/leaderboard` page already runs, reading each active player's stored `pred_rank` verbatim. **Don't reintroduce a serving-difficulty proxy for rank** — it was biased in both directions and the buffer fit costs no extra D1 rows.

**The `/leaderboard` page is a compute-on-read display resolver with a UNITS selector; the "Verified" column shows ONLY machine-verified linked-account ratings — human survey declarations are never revealed.** The full resolver — the three-table stitch in `readLeaderboardRows`, the EGD/AGA heartbeats and their activity gates, the units frames, the country fallback chain, the hide opt-out, and the stored-column history — is `docs/leaderboard_and_community_stats.md`. **Write endpoints are guarded by three cheap layers upstream of D1, plus a maintenance freeze.** Layer-by-layer detail, the calibration behind the limits, and the freeze's rationale are in `docs/worker_operations.md`. What you need when touching a write path: a spoofed write costs D1 write quota *and* inflates every server-stats window scan for 7 days, so writes are defended cheapest-first — an outer **Cloudflare WAF rule** matching ALL POSTs by method (zone config, applied out of band via `pwa/waf/rate-limit-rule.sh`; new endpoints are covered automatically), **per-IP Workers rate-limit bindings** checked in the dispatcher before any handler touches D1 (**fails open**, so a misconfig never drops a legit write), and **in-memory format validation** (`isValidProblemId`, `isValidUserId`) before the INSERT. Validation is **deliberately format-only**, with two consequences: any deploy smoke test must POST a real 8-hex problem id, and `pipeline.fetch_database` is unaffected because it hits `api.cloudflare.com`, not the guarded zone. The fourth layer is **`MAINTENANCE_MODE`**: `"1"` makes every POST return `503 {error:'maintenance'}` and `scheduled()` early-return, checked before the rate limiter and before any D1 access. It exists so snapshot-relative operations run against tables that are standing still; freezing is safe because `sendReport` only acks on `res.ok`, so the durable outbox re-uploads afterwards with the original event time. Procedure: `docs/db_surgery_runbook.md`.

**`pipeline.fetch_database` is incremental by default and read-cost-sensitive.** Implementation detail — the schema-tolerant table discovery, the `d1.sqlite` merge target, the local-D1 reset by file copy — is in `docs/worker_operations.md`. The two rules: D1 bills rows read and `tsumego_reports` is >99% of the DB, so the default path pulls **only new rows via `WHERE id > MAX(local id)`**; and **the cursor MUST be `id`, not `created_at`**, because `POST /report-backfill` inserts historical attempts with their client event time, which a `created_at` cursor would silently skip. Append-only makes the id cursor provably gap-free. Stop `npm run dev` before fetching — the fetch overwrites the miniflare D1 file, and doing that under a live workerd corrupts its view. `--full` forces a complete re-download.

**Skill-axes recommender (per-component weakness mining).** The axes are per-problem SKILL DIMENSIONS (supervised residual axes — see *Axes fit* below) but shipped per-CELL: every legal first-move cell gets its own K-dim vector, so the system can score both the **correct** move (a property of the position) and the move the user **actually picked** on a wrong attempt.

*Extraction* — `pipeline/extract_activations.py` runs a vendored PyTorch copy of KataGo b18 (`utils/katago/vendor/`, bootstrapped via `utils/katago/torch_model.py`) and captures the post-skip-add output of all 18 residual blocks (18 × 384 = 6912 floats) **at every legal cell**. Output: `activations/<size>/<id>.npz` with `candidates (n_legal, 6912) fp16`, `xys (n_legal, 2) int32`, `correct_idx () int32`.

**Row order is board-scan order (sorted by `(y, x)`), NOT SGF-variation order, and the cell set is a *superset* of the SGF's root variations.** `extract_activations.process_one_sgf` enumerates every legal cell for the player to move (the color of `variation_nodes[0]`) in scan order and records a `correct_idx` pointing at the correct move's scan position (non-zero in general; e.g. 13×13 `00000f4c` has `correct_idx=38` — verified byte-for-byte that a re-extraction reproduces the on-disk corpus). Do not instead walk the SGF's pruned variations in document order with `correct_idx=0`: that ships a non-superset cell set and does not match the on-disk corpus. Two consequences every downstream consumer must respect:
  - **Pick the correct row by `correct_idx`, never positionally.** Every consumer (the activation-cache builder feeding `utils.rating.features`, `pipeline.build_axes`' per-cell fanout) selects `candidates[int(correct_idx)]`; do not assume row 0.
  - **The npz embeds every legal cell; SGF root variations are a pruned subset, plus the SGF carries a `pass` variation the npz never embeds.** So npz ⊇ {SGF non-pass variations}: every move a user can actually click is embedded (no picked-move ever misses), but ~10% of problems have extra embedded cells with no SGF variation, and 100% have a `pass` that is not embedded. Map cells by `(x, y)` coordinate, not by index, when crossing the npz↔SGF boundary.

*Axes fit* — `pipeline/build_axes.py` (production, NO flags) trains the supervised residual-axes model in `utils/rating/residual_axes.py`. **Model, training regimen, K-selection criterion, the anchor/identity scheme and the rank-collinearity analysis: `docs/methodology.md` §1.14.** Run it AFTER `train_rating` + `map_rating_to_rank` (it needs the attempts DB, `ratings/` and `rating_to_rank.json`). Features are the rating trainer's EXACT inputs — same loaders, same joint-PCA cache and seed, LITERAL parity with `pipeline.train_rating` — plus the rating model's outputs; the population residual-difficulty head is quarantined in the model and **never shipped**.

Output to `axes/{per_problem.csv, axes.npz, labels.json, label_anchors.npz, per_cell/}`; `axes.npz` carries the model plus the content-hash `embedding_version` that packaging ships. **K is SELECTED and grows with the data — never hardcode it**; consumers read it from `embedding_meta.json`. The per-cell fanout needs no retraining (the axes are linear and only the activation block varies per cell).

Two ship gates, both in `package_for_pwa`, both of which will stop a run cold:
- It **REFUSES to ship while any axis component has neither tail labeled.** Expected flow: new data → `build_axes` grows an axis → a human eyeballs its extremes with `auxiliary.rating_dev.inspect_residual_axes --per-problem` (renders both tails straight from `axes/per_problem.csv`) → names it in `labels.json` → re-run packaging. Editing label TEXT alone then re-running publishes on the cheap no-rebuild path.
- **An axes refit that changes K MUST be followed by `pipeline.fit_population_constants` before packaging** — `check_axis_prior` is a PRE-FLIGHT that refuses unless `weakness_axis_lambda` is exactly K finite positive entries. There is no scalar fallback: a missing or length-mismatched vector makes the client silently SKIP weakness training.

`auxiliary.inspect_axis_inputs` answers the other half — which INPUTS drive an axis, how concentrated that reliance is, each tail as an exact additive decomposition, and correlation against every frozen anchor so a new axis can be placed as a known motif or genuinely new. Every block is nameable except the activations; note its "bot winrate" block is whatever `attempts/<size>/*.txt` the loader globs, which includes the non-bot `heuristic` and `sgf_move` columns.

*Packaging* — `pipeline/package_for_pwa.py` ships two things per shard, plus one corpus-wide sidecar:
1. The correct-move axis vector (length K = the selected axis count) joined into the shard's `metadata.json` under `embedding` — what `weaknessScore` reads against any candidate problem.
2. A sibling `<hash>.embeddings.bin` per shard (fp16, K floats per cell, all problems concatenated **in SGF root-variation order**), plus an `embeddings_index.json` inside the zip mapping `{tid: {offset, n_cells}}`. This is the picked-move sidecar: the PWA Range-fetches `bytes=offset+i·bytes_per_cell..offset+(i+1)·bytes_per_cell-1` to recover the embedding at cell index `i` of a tsumego, where `i = children.indexOf(moveNode)` over the SGF root variations.
3. `pwa/tsumegos/lookup.embeddings.bin` — the **lookup-aligned correct-move sidecar**: row i is the K-dim fp16 correct-cell embedding of the problem on `lookup.txt` line i (lookup is id-sorted and spans both sizes, so the line index — which the client already has from its lookup.txt binary search — doubles as the row address; no keys, no offsets). Emitted like `problem_params.bin` (`emit_correct_embeddings`, every non-sentinel run, straight from `per_problem.csv` + the final lookup.txt — no shard rebuild), and folded into `data_version` so it can never cache-desync from lookup.txt. **Row alignment is the contract**: it must be written after the run's final lookup.txt; the client additionally verifies the file size against its line count via `Content-Range` and poisons the sidecar for the session on mismatch. Ids missing from `per_problem.csv` get an all-zeros row the client treats as absent. This is what lets the backfills fetch a correct-move embedding as one ~130-byte Range request instead of downloading the ~2MB shard zip whose `metadata.json` carries the same vector.

   **The bin order is set here, not upstream.** Because the npz is scan-order and a superset (see *Extraction*), `package_for_pwa.project_cells_for_problem` re-parses each SGF and rebuilds the per-cell rows in SGF-variation order via an `(x, y) → npz row` map — dropping the extra scan-order cells, while the `pass` variation (never embedded) gets an **all-zeros placeholder row** so bin row i == SGF child index i exactly (`BIN_FORMAT_REV` 2; rev 1 skipped the pass, which shifted every row after a non-last pass off by one against the PWA's `children.indexOf` — and the pass is not last in ~half of 9x9 / ~3/4 of 13x13 problems). The rev is folded into the **shipped** `embedding_version` (`shipped_embedding_version` = pca-content hash + `-b<rev>`), so a bin-layout change wipes/re-derives clients' stored picked embeddings through the standing version gate and rebuilds shards without `--force`. This reorder is **load-bearing**, not defensive: the PWA indexes the bin by SGF-variation position, so shipping raw scan order would silently return the wrong cell's embedding for every picked move. The sgfmill parse dominates packaging time, so shard building is parallelized across processes (`--workers`, default `os.cpu_count()`).

The joint `pwa/tsumegos/embedding_meta.json` carries `K` (the SELECTED axis count — grows with data, never hardcode it), `dtype` (`float16`), `bytes_per_cell` (so the PWA can decode the bin without guessing), `embedding_version` (from `axes.npz`), and the two-tailed `labels`.

*PWA model — augmented weakness regression.* `pwa/js/weakness.js` trains a logistic regression with **2K+2 params**:
```
P(correct) = σ(α + γ·rating
                + Σ β_correct[k] · correct_emb[k]
                + Σ β_picked[k]  · picked_emb[k])
```
**Model, the contrast-vs-sum argument, the two-level detection and the false-finding budget: `docs/methodology.md` §2.9.** `γ·rating` is actually `γ·problemRank` (the board-independent internal rank), and this is a **single shared instance trained on `getMergedAnswerHistory()`** — both sizes pooled, well-posed because the axes are jointly fit; see the cross-size merge note above. The operating rules:

**Selection scores the CONTRAST `(β_correct − β_picked)`; detection level 1 flags on the SUM. Don't unify them** — they answer different questions and the split is what makes each identifiable (~80% of rows have `picked = correct`, so the correct/picked split alone is prior-dominated). `problem-loader.js`'s selection is TWO-REGIME: while the rank estimate is converging (`rankConverged()`, fail-closed) it weights by `quality` alone; once converged AND `weaknessModelReady()` it weights by `exp(WEAKNESS_TEMPERATURE · weaknessScore)` alone — no cross-unit balancing. Cold start (≤20 attempts with embeddings): `weaknessScore` returns 0 and weighting collapses to pure quality.

**The residual axes are BIPOLAR, not skew-one-sided** — both tails are real directions, so a negative score is the opposite pole of a real dimension, not "no motif". Per-axis tail structure varies and `labels.json` may leave one tail null. Don't read symmetry into the linear model.

**The per-axis ridge prior is `weakness_axis_lambda` from `population_constants.json`, length K, mandatory.** Shipped as `λ_k = 2/τ_k²`; **the factor of 2 is there because the client applies `λ_k` to BOTH the `β_correct[k]` and `β_picked[k]` slots**, so reading the shipped number as a plain inverse variance mis-states the prior — and the level-one threshold — by 2×. There is **NO scalar fallback**: a missing or length-mismatched vector makes the client silently SKIP weakness training (see the `check_axis_prior` pre-flight in the axes note).

**`fit_population_constants` runs a ZERO-MEAN CHECK on that prior every run and HALTS past `WEAKNESS_MEAN_SHARE_MAX`** (`--allow-axis-mean` overrides deliberately). The EM accumulates a second moment about zero, which is the between-user variance only if each axis's pooled coefficient is itself zero. The bar is on the SHARE of "variance" that is really displacement, not on significance — with hundreds of users a negligible mean sits many standard errors from zero — and the share is the one form no rescaling of an axis can evade. **Read a breach as the `build_axes` residual-difficulty quarantine LEAKING** (a coefficient non-zero for everyone is difficulty, not weakness), so fix it upstream; re-centring the client's prior on a shipped per-axis mean would make the numbers self-consistent while leaving an axis carrying difficulty that belongs to the rating model.

`weaknessAxisCov` is length-checked against K like `weaknessSe` and read with **no zero default**: `weakness.js` already substitutes 0 for a non-finite covariance, so a missing entry means the array is STALE against the current K — and under the picked/correct collinearity the cross-covariance is strongly negative and dominates the sum variance, so defaulting it to 0 moves the detection threshold rather than erring on the safe side of it.

*Picked-move fetch.* `pwa/js/picked-embedding.js` Range-fetches the per-cell sidecar. Two entry points:
- `fetchPickedEmbedding({tsumegoId, cellIndex, zipFilename, boardSize})` — live path, called from `game-logic.handleBoardClick` on every move via `state.embeddingsIndexCache` (loaded alongside shard metadata in `problem-loader`). The cell index is `children.indexOf(moveNode)` against the SGF root variations — same order as extraction/packaging, no coordinate recomputation.
- `fetchPickedEmbeddingWithIndexEntry(...)` — backfill path, used by `backfill.js` when iterating shards.

Answer-history entries carry `embedding` (correct-move, from shard `metadata.json`), `pickedCellIndex` (SGF variation index), and `pickedEmbedding` (decoded sidecar fp16).

*Backfill + invalidation.* `pwa/js/backfill.js` runs on app load: reads the **inlined** joint `embedding_meta.json` (version, labels, K/dtype/bytes_per_cell all joint — a build-time `import` via `data-version.js`, not a fetch; see the data-version cache note), then iterates per size — it fills missing `embedding` fields from the lookup-aligned correct-move sidecar (`fillCorrectEmbeddingsViaSidecar`: binary-search the id in the already-fetched lookup.txt lines → fetch that ~130-byte row of `lookup.embeddings.bin`; repeats share a memoized fetch; hosts that ignore Range — wrangler dev AND production Workers assets — cost one whole-file download, cached by the SW and served row-by-row from memory thereafter) and missing `pickedEmbedding` fields by Range-fetching each shard's per-cell bin with the entry's stored `pickedCellIndex` — the per-problem byte offsets live in the zip's `embeddings_index.json`, so the picked fill is the **only** embedding fill that still downloads shard zips (`walkPickedShards`, only shards carrying such a need). The account-adoption synced fill (`fillSyncedHistoryFields`) uses the same sources, and its zip walk covers just the `syncedMove → pickedCellIndex` derivation (needs the SGF) + the picked fill — measured on a worst-case 2k-attempt adoption: 38 zips vs 342 with the sidecar absent (and ~830 before the problem_params/stamp fixes). Entries older than `MODEL_INPUT_HISTORY_LENGTH` get the embedding fields stripped to keep localStorage bounded. Because the weakness model is a single shared instance (see the cross-size merge note), an embedding wipe on *either* size clears the shared `weaknessParams`/`Adam`/`Se`/`AxisCov`, and a single `trainWeakness()` retrain runs once after the whole walk (not per size). Refits auto-invalidate: `build_axes.py` writes a content-hash `embedding_version` into `axes/axes.npz` (computed over the projection-relevant arrays), `package_for_pwa.py` surfaces it in `pwa/tsumegos/embedding_meta.json`, and the PWA wipes stale embeddings (correct + picked) per size whenever the localStorage-cached version differs. No manual JS edit needed on refit.

Extraction needs ~8 GPU minutes per 1k problems on a Quadro M2200; remote it via Vast.ai for full-corpus runs.

**Ranks are derived client-side from raw ratings; packaging is rank-agnostic.** `package_for_pwa.py` ships per problem the raw `rating`, the raw slope `a_p` and the `floor` — **no rank at all**; shard `min_rating`/`max_rating` are raw too. The rating→rank map `M` is fitted separately into the backend `ratings/`, and `package_for_pwa` — the single writer of `pwa/tsumegos/` — copies that curve across. The client does *all* rating→rank conversion: `problem-loader.js` derives `p.rank = applyM(rating)` on ingest and leaves `p.rating` raw. **Don't reintroduce a baked rank into `metadata.json` — `rating` means raw everywhere.**

**The rank is never clamped.** The kyu/dan ladder is what we LABEL, not a bound: `applyM`/`interpExtrap` extrapolate linearly past both end knots, so problems easier than the weakest knot fall below 30k and the unattempted KataGo-hard tail runs past 9d. Treat it as an unbounded continuous coordinate — don't clamp it, don't read it as a percentile. A hidden ladder clamp in `rank-translation.js` once pinned every above-9d value to the 8d–9d border; clamping now lives only where LABELS are built. **`M` is required** — `main.js` awaits `loadRatingRankMap()` at init and aborts if it can't load, with no fallback.

Answer-history entries store `problemRating` (raw), `problemRank` (internal) and `problemSlope` (raw `a_p`). `backfill.js` refreshes all three, triggered by a **single** `ratings_version` (the joint cross-board fit re-rates both boards together, so there is no per-board rating version) **and** by a client-computed `ratingRankCurveVersion`, so a `map_rating_to_rank` re-fit with unchanged ratings still refreshes stored ranks. The version gate and stamp live ONCE in the orchestrator, wrapped around the per-size work loop: stamps are written only AFTER every size's walk has persisted, so **stamp-last = crash-safe** and an interrupted run re-runs idempotently. **Consequence:** a curve-only re-fit publishes through `package_for_pwa` on the cheap path (change detection sees shard inputs unchanged and copies just the curve); a raw-rating change re-ships shards. A change to the *packaging format itself* is NOT captured by the input hash — run `package_for_pwa --force` once after such a code change.

**`M` (rating→rank) maps to a latent CONSENSUS rank; every server INCLUDING EGF is a coupling off it (EGF is NOT special).** The consensus model, the gauge pin, the shape prior, the career-block anchors and the joint time-slope fit are in `docs/methodology.md` §1.12. Operationally: `pipeline/map_rating_to_rank.py` fits the curve, every per-server coupling and the solve-time slope α in ONE objective, and is **production-clean** — config baked as module constants, no experimentation code (that lives in `auxiliary/map_rating_to_rank_dev.py`; the CV harness is `auxiliary/eval_rank_map_cv.py`). Run `pipeline.fetch_database` first; it then needs `ratings/` + `db/d1.sqlite` for median solve time, but neither GPU nor the heavy pipeline.

Outputs, both board keys identical: `ratings/rating_to_rank.json` (`{ratings, ranks}` plus a top-level `time_adjust {alpha_per_log10_min, center_log10_min}`) and `ratings/rank_map.json` (`{server: {our, server}}` knots, **including a real EGF coupling**, not an identity line). **RATINGS ARE TIME-ADJUSTED THROUGHOUT THE MAPPING**, so: **the client headline (onlymove rank) maps the RAW rating through M (untimed); every server translation — EGF among them — maps the TIME-ADJUSTED rating** (`rank-translation.js`). Dropping the dock for the headline is a client display choice. `fit_population_constants` READS α/center through from `rating_to_rank.json` (no separate time fit), and `package_for_pwa` copies both curve files across under the single-writer rule. Measured-rejected, don't re-add: errors-in-variables weighting over each rating's Fisher CI (declaration noise dominates; consistently worse held-out).

**There is ONE internal rank scale, AGA-style, and `pwa/shared/rank-math.js` owns it.** The convention: **0 is the 1k/1d boundary, every rank is one unit wide, and integers are band EDGES** — 1d = [0, 1), 2d = [1, 2), 1k = [−1, 0), so "2 dan" averages 1.5. It is **AGA-STYLE, not AGA**: real AGA ratings carry a (−1, 1) gap and put 2d at [2, 3), so `agaRankToRating` (`leaderboard-page.js`) stays a real conversion. The module holds `interpExtrap`, `rankToLabel`, `rankLabelToRank` (label → band CENTRE, so the "− 0.5 for the band's lower edge" idiom stays literal), `rankBand` (**FLOOR** — integers are edges), `rankProgress`, and `clampRankBand` (the 30k..9d ladder, for LABELS only — never clamp a rank you compute with). Imported by both the Worker (`src/index.js`) and the client, deliberately: one module, so the server-computed Community rank histogram cannot drift against the client's display. **Don't reintroduce a local copy.** The `rating_to_rank.json` key is `ranks` (a stale reader looking for `rank_indices` fails loudly rather than silently double-shifting), and `DEFAULT_USER_RANK` (`state.js`) is the named cold-start stand-in. Any future change to this scale must clear the same bar the last one did: label-preserving by construction, verified value-by-value across ratings, (rank, server) pairs, the GoR/AGA tier gates and synthetic users through the real `computeRank` — and shipped behind a state-epoch bump, because every STORED rank changes units and a stale value is not detectably wrong.

**KataGo PyTorch loader requires `.ckpt`, not `.bin.gz`.** `models/kata1-b18c384nbt-...bin.gz` is the binary export the C++ analysis engine reads — not loadable via `torch.load`. The feature-embedding pipeline expects `models/kata1-b18c384nbt-s9996604416-d4316597426/model.ckpt` (extracted from the corresponding `.zip` checkpoint distribution). Don't point `extract_activations.py --ckpt` at a `.bin.gz`; KataGo's training code only goes PyTorch → binary, not the other way.

## Conventions to be aware of

- **There are no tests and no test runner** — no `tests/` directory, no CI. Don't add a "run the tests" step to claims of completion unless tests are actually added, and don't assume a change is covered by anything automated. Verification is manual: for pipeline changes, run the step and check its printed diagnostics; for PWA changes, `npm run dev` and exercise the path in the browser.
- Python code uses absolute imports rooted at the repo (e.g., `from utils.constants import ...`). Pipeline scripts append `PROJECT_ROOT` to `sys.path` defensively.
- KataGo coordinates skip the letter `I` (so cols are `ABCDEFGHJKLMNOPQRST`). SGF coordinates do not. Helper conversions live in `utils/katago/queries.py` (`katago_to_sgf_coords`) and `pipeline/benchmark_bots.py` (`sgf_to_gtp`). Prefer reusing them over rewriting coordinate math.
- `pwa/README.md` has additional context on the PWA's overall structure (sections 1–5: overview, tech stack, project layout, architecture, dev workflow). Read it before substantive PWA edits.
- **For local DB analysis, prefer the binary `db/d1.sqlite` over the raw `db/d1.sql` dump.** Both are produced from `pipeline.fetch_database` and both gitignored. `fetch_database` treats `d1.sqlite` as the **canonical merge target** and keeps both artifacts in sync on every run, so you normally don't import by hand. If you ever need to rebuild the `.sqlite` from a raw dump manually: `{ echo "BEGIN;"; cat db/d1.sql; echo "COMMIT;"; } | sqlite3 db/d1.sqlite` — the `BEGIN/COMMIT` wrapper matters: a full D1 export emits one un-batched `INSERT` per row (~290k for `tsumego_reports`), so without a wrapping transaction sqlite fsyncs per row and the import takes many minutes. **Never pipe the import through `head`/`tail`** — it SIGPIPE-kills `sqlite3` mid-import and silently leaves a partial table. Query the `.sqlite` thereafter (no re-import per session). Note a full `--full` dump only carries the tables that have rows at export time (D1 export drops empty tables), whereas the incremental path's regenerated dump carries every table it discovered remotely (so e.g. an empty `history_refresh_log` is present).
- **Many artifact directories hold 100k+ files** — `tsumegos/9/` (~123k SGFs), `activations/9/` (~123k .npz), `tsumegos/13/` and `activations/13/` (~20k each), `axes/per_cell/<size>/` (per-tid files), and shard zips. **Shell globs like `ls dir/*.npz` will silently expand past `ARG_MAX` and report 0** — verified false-negative on `activations/9/`. Use `find <dir> -maxdepth 1 -name '*.ext' -printf . | wc -c` (or `find ... | wc -l` if newlines are safe) to count, and `find ... -exec` / `xargs -0` to iterate. The same trap applies to anything piping a glob into another command. Treat any directory under `tsumegos/`, `activations/`, `axes/`, `attempts/`, `ratings/`, or `pwa/tsumegos/<size>/` as "may exceed argv" by default.
