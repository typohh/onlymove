# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

YoseTsumego / onlymove.net — a Go (Baduk/Weiqi) tsumego pipeline. KataGo generates problems and rates them; the rated set is packaged into zip archives served by a Cloudflare-hosted PWA. There are four cooperating subsystems:

1. **`pipeline/`** — eight executable scripts run in order (see "Pipeline commands" below). Each is a standalone `python -m pipeline.<step>` entrypoint. `package_for_pwa` is the single writer of `pwa/tsumegos/`; there are no side-channel patch scripts — to publish a labels-only or curve-only change without rebuilding zips, re-run `package_for_pwa` (its per-size change detection skips the heavy shard rebuild). Survey-driven rank calibration (`map_rating_v2_to_egf.py`) and population-constant fitting (`fit_population_constants.py`) are board-independent and run outside the in-order pipeline — see the rank architecture note below.
2. **`utils/`** — shared logic: `KatagoController` (subprocess + thread-safe query dispatcher), `KatagoQueries` (analysis-engine wrapper), `ProblemFinder` (move-difficulty heuristics), `add_variations` (SGF tree construction), `models` (KataGo network downloads), `configurations` (global knobs).
3. **`pwa/`** — vanilla-JS ESM PWA built with esbuild, deployed as a Cloudflare Worker. The Worker entrypoint `pwa/src/index.js` handles these HTTP routes — `POST /report` (per-attempt logging; responds `{createdAt, prevCreatedAt}` — the server-stamped timestamp the client stores on the matching answerHistory entry as `serverCreatedAt` so sync pulls can skip the device's own rows, plus the user's previous-latest report timestamp, the account-sync piggyback signal), `POST /sync` (account sync: returns the user's reports newer than a `since` created_at cursor, paginated at 1000 rows with page boundaries kept off timestamp ties; an optional `limit` shrinks the page — `limit: 1` is the client's account-existence probe — see the account-sync note below), `GET /push/vapid-public-key`, `POST /push/subscribe`, `POST /push/unsubscribe`, `POST /schedule` (recall-reminder schedule; **diff mode** — the client keeps a per-row hour-rounded snapshot in localStorage and sends only changed rows + explicit removals, since each upsert bills the row plus its two partial indexes and replace-all is the heaviest D1 write path; legacy `{schedule}` replace-all still accepted; every call, even an empty diff, bumps `push_subscriptions.last_seen_at`, the cron's mid-session suppression watermark), `POST /rank-survey` (per-server rank declarations → `rank_surveys`), `POST /share-event` (share-link create/open analytics → `share_events`; the client sends user/problem/size and, for opens, `document.referrer`, while the worker stamps the Cloudflare edge geo-IP `country`), `GET /server-stats` (serves the cached community-stats blob — see the server-stats note below) — plus a cron-driven `scheduled()` handler that walks `recall_schedule` to deliver due Web Push notifications **and** recomputes `server_stats` (≥23h old or on a version change), and an SPA fallback that derives board size from `/9` or `/13`. Static assets ship via the `[assets]` binding in `wrangler.toml`. D1 binding `DB` → database `tsumego-reports`, tables: `tsumego_reports` (per-attempt log: `user_id, problem, success, created_at, size, move, time_used, review_time, is_repeat`; no `UNIQUE(user_id, problem)` constraint, so repeat attempts produce their own rows; **indexed on `created_at`** — `idx_tsumego_reports_created` — for the server-stats window scan, **and on `(user_id, created_at)`** — `idx_tsumego_reports_user_created` — for the per-user `/sync` cursor scan), `push_subscriptions` (one row per device — `endpoint` PK, `user_id` indexed — so the recall cron fans each due reminder out to all of a user's devices; per-device throttle + dead-endpoint cleanup, per-account active-session suppression), `recall_schedule`, `rank_surveys`, `share_events`, and `server_stats` (single-row JSON cache, `key='latest'`). Schema lives in `pwa/schema.sql` (idempotent `CREATE … IF NOT EXISTS`); apply new tables/indexes to the remote D1 with `npx wrangler d1 execute tsumego-reports --remote --file=schema.sql`.
4. **`analysis_server/`** — a tiny HTTP server wrapping KataGo for the PWA's analysis fallback when SGFs lack embedded win-rate data.

Plus `auxiliary/` (one-off diagnostics, legacy code; not part of the main flow) and `vast_orchestration.py` (rents Vast.ai GPU instances to run the heavy pipeline steps remotely).

## Pipeline commands

Always invoke pipeline modules through the venv's Python so PYTHONPATH resolves correctly:

```bash
./.venv/bin/python3 -m pipeline.fetch_database        # INCREMENTAL by default: pull only new tsumego_reports rows (by AUTOINCREMENT id) + re-fetch the small tables whole, merge into attempts/database.{sqlite,sql}, sync local D1. --full forces a complete re-download (auto-used when there's no local database.sqlite baseline)
./.venv/bin/python3 -m pipeline.tune_engine           # tune nnMaxBatchSize / numAnalysisThreads in bots/analysis.cfg
./.venv/bin/python3 -m pipeline.generate_tsumegos     # long-running generator → tsumegos/<size>/
./.venv/bin/python3 -m pipeline.benchmark_bots        # bots solve generated tsumegos → attempts/<size>/
./.venv/bin/python3 -m pipeline.train_rating_v2       # STAGED self-consistent cross-board 4PL rating model → ratings_v2/<size>/ (2-phase coordinate descent; 80%-clear rating). PRODUCTION-ONLY: only --out-dir/--seed; the full experiment surface (joint M0b + staged flags, --stage-plan, --separate-trunks, eval suite, alternative objectives) lives in auxiliary.rating_dev.train_rating_v2_staged (and …_research)
./.venv/bin/python3 -m pipeline.extract_activations   # KataGo trunk activations per problem → activations/<size>/<id>.npz (GPU; resumable)
./.venv/bin/python3 -m pipeline.build_embedding       # rating-residualized PCA over activations → embeddings/<size>/
./.venv/bin/python3 -m pipeline.package_for_pwa       # SINGLE writer of pwa/tsumegos/: zip + lookup.txt + embedding_meta.json + copies the rating→rank curve across; change-detects per size (skips unchanged shard rebuilds; --force to override). Reads ratings_v2/.
```

Survey-driven rank calibration and population-constant fitting (both board-independent, not part of the in-order run; need `ratings_v2/` + the `attempts/` DB, no GPU). Both write only to the backend `ratings_v2/`; `package_for_pwa` copies their outputs into `pwa/tsumegos/` (single-writer rule):

```bash
./.venv/bin/python3 -m pipeline.map_rating_v2_to_egf      # rank_surveys → ratings_v2/{rating_to_rank.json, rank_map.json} (BACKEND; package_for_pwa publishes it to pwa/tsumegos/)
./.venv/bin/python3 -m pipeline.fit_population_constants  # ratings_v2/ 3PL params + attempts DB → ratings_v2/population_constants.json (BACKEND; package_for_pwa publishes it; the PWA build inlines it into the JS bundle)
```

Run on a remote Vast.ai GPU instead: `python vast_orchestration.py` (no args prints subcommands; only `tune`, `generate`, `benchmark` are remoted — the rest stay local).

## Rating pipeline (combined cross-board MLP-2PL)

The rating backend writes under `ratings_v2/` — the only rating backend (the name is historical) — and `package_for_pwa` ships it to `pwa/tsumegos/`. The three commands — `train_rating_v2`, `map_rating_v2_to_egf`, `package_for_pwa` — are listed under "Pipeline commands" above.

Key design (validated in `docs/rating_model_comparison_results.md`): a single model `P = σ(a_p·θ_u + d_p)` pooled across 9×9+13×13 with a **shared per-user ability θ**; features are **joint-PCA activations ⊕ common-column bot winrate** (`bw_act`). The feature heads are a **prior** (`d_p = diff_mlp(feat) + δ_p`, `a_p = softplus(b0+slope(feat)+η_p)`) and the **human first-time attempts** (the only training target) add per-problem residuals `δ_p`/`η_p` on top — ridge-shrunk toward the prior, so sparsely/never-attempted problems fall back to it (bot data enters only via the features). **The 2PL slope `a_p` is the per-problem discrimination**, shipped **raw** as the per-problem `slope` field (no min-max repackaging, no separate `quality` field). The client uses it two ways: (1) as the per-attempt success-curve slope in its rank estimator (see the rank-derivation note); (2) as the problem-selection weight ∝ the Fisher information the problem provides, `I = a_p²·P(1−P)` — and since selection draws from a difficulty-matched pool (the 50 nearest in rank, all ≈80%-clear) `P(1−P)` is ~constant, so the weight is simply **`a_p²`** (sharp = quadratically more informative; no arbitrary [0,1] range). **Rating = `(logit(0.8) − d_p)/a_p = b_p + logit(0.8)/a_p`** — the ability at which the user clears the problem **80% of the time** (`CALIBRATION_P`, the margin the PWA serves *and* anchors at), NOT the 50%-point `b_p = −d_p/a_p`; winsorized to tame the low-slope tail, shipped as the per-problem `rating`. The slope-dependent 80% correction is load-bearing: a flat low-discrimination problem needs more ability to clear at 80% than its 50%-point implies, so two equal-`b_p` problems differ in true 80%-difficulty — and a monotone rating→rank map cannot recover that per-problem reordering, so it must be built at the rating stage (the EGF mapping re-anchors users' 80%-clear ratings against whatever scalar is shipped, so it stays self-consistent). `map_rating_v2_to_egf` then anchors it to EGF and writes ONE shared rating→rank curve to both board keys, self-contained (it reproduces the server↔EGF coupling fit itself). Critically it anchors on each survey user's **80%-clear v2-rating** (the same `fit_user_rating` @ `CALIBRATION_P=0.8` the client/`utils.fit_rank_curves` use, pooled across boards), **NOT raw θ**: θ is the 2PL 50%-point (`θ = b_p ⇒ P = 0.5`), so a θ-anchored curve would mis-display every user's 80%-clear rating by ~4.4 ranks. The curve is a shared monotone piecewise-linear fit with a uniform-spacing (linear) prior. The fit is joint (rating→rank + per-server couplings via `fit_joint_shared`), reusing `utils.fit_rank_curves`' stateless helpers (`fit_user_rating`, `ordinal_nll_vec`, `build_server_curves`, …). `package_for_pwa` ships `rating` + raw `slope` per problem; the `rating_model` tag in `embedding_meta.json` records provenance (`"v2"`), and the PWA does not branch on it. Open calibration items: `--lambda-resid` (prior precision) is set by hand, and the corpus hard tail (KataGo-hard, unattempted) extrapolates far beyond the human rank knots. **Production fit = STAGED self-consistent two-phase coordinate descent.** `pipeline.train_rating_v2` is the **production-only** trainer (only `--out-dir`/`--seed`; the shipped config is baked in `main()`). Phase 1 fits the per-problem difficulty AND simultaneously **LEARNS a single global slope + global floor + global ceiling** (`--global-stage1`); phase 2 individualizes the per-problem slope + per-problem floor and keeps refitting the global ceiling, while difficulty is held at its phase-1 values by a soft L2 consistency penalty (Adam's per-parameter scale-invariance lets difficulty drift ~0.3 units regardless of the penalty weight; that drift is the joint re-optimization and is fine). The feature trunk is `bw_act` with **0.3 act/bw dropout**. **Learning the globals jointly with the rating auto-finds the self-consistent anchors — no hand fixed-point search, so it stays calibrated as the corpus drifts** (the `--stage-*-const`/`--lapse-init` values are only inits; the globals land near slope ~1.3 / floor ~0.15–0.20 / ceiling ~0.97). The model trains on human attempts alone, with **no mechanistic floor, no hierarchical-slope shrinkage prior, and no bot-anchor examinees** — bot-anchor examinees are deliberately excluded because they steepen the per-problem slope (mean ~1.38 vs ~1.23 human-only) with no held-out-logloss benefit. The ceiling λ is **learned (≈0.03)**, so `fit_population_constants` reads that λ through. Difficulty↔slope coupling leaves the per-problem slope mean ~0.1 above the learned global (intrinsic residual, not a bug). Single-seed in production — multi-seed plus the structure-table / `eval_strong_user_error` checks are the open validation. **The full experiment surface — the joint M0b config, every flag, the held-out / survey-ρ / time-adjusted-ρ eval suite, `--stage-plan` (arbitrary phase orders), `--two-stage`, `--separate-trunks` (per-head trunks for EXACT freezing), `--free-lapse`, and the alternative objectives (even-error DRO, gap-balance, kNN) — lives in `auxiliary.rating_dev.train_rating_v2_staged`** (the production superset; `…_research` holds the pre-staged surface), so a test tweak can't break the shipped ratings. The staged structural study (difficulty↔slope coupling, the ceiling's order-dependence vs floor, the fixed-point search) is in `docs/rating_backbone_overfit_and_feature_dropout.md`. Do experiments there; the even-error DRO study (its flatness↔cost knee, and why centering on the per-bin base-rate loss is load-bearing — raw-loss DRO/CVaR chase the aleatoric floor and lose to ERM) is in `docs/rating_model_comparison_results.md` (the `--even-error` section; reproduce via `auxiliary.compare_rating_models --even-error`). The PWA reads the same `rating` + `slope` fields regardless of model internals.

## Architecture notes that span multiple files

**Tsumego identity is symmetry-aware and single-solution.** Filenames come from `get_orientation_invariant_hash` (`pipeline/generate_tsumegos.py:154`) — SHA-256 taken over all 8 D4 transforms of the board, with `min()` picking a canonical orientation. The dataset therefore cannot contain two problems that are rotations or reflections of each other; `tsumego_id` is the symmetry-canonical hash truncated to 8 hex chars. By generator design every problem has exactly one correct first move (the `solution` returned by `ProblemFinder.create_problem`); downstream code can rely on the "one canonical answer per problem" invariant.

**Board size — two supported modes: 9x9 and 13x13.** Both ship in production; the PWA picks one from the URL path (`/9` or `/13`) via the SPA fallback in `pwa/src/index.js`, and the D1 `report` endpoint records `size` per attempt. On the **pipeline side**, the size is a config-file switch: edit `BOARD_SIZE` in `utils/configurations.py` and re-run the pipeline — there is no in-process multi-size support, no CLI flag, and no automatic dual-size run. Artifact directories are keyed by size: `tsumegos/<size>/`, `attempts/<size>/`, `ratings_v2/<size>/`, `pwa/tsumegos/<size>/`. To refresh both sizes, run the full pipeline once with `BOARD_SIZE = 9`, then again with `BOARD_SIZE = 13`.

**On the client, rank + stats + the learned models are merged across sizes; histories, `M` curves, and problem pools stay per-size.** From the user's perspective 9x9 and 13x13 share one rank (front-page label, problem selection, recall eligibility) and one stats page. `pwa/js/state.js` keeps `answerHistory` as ONE unified cross-size array (date-ordered, each entry tagged with `size`; the recent working set in localStorage, the older tail in IndexedDB — see the answerHistory-storage-split note below) plus single shared values (`userRank`, `momentum`, the recall model `modelParams`/`adamState`, the weakness model `weaknessParams`/`weaknessAdam`/`weaknessSe`/`weaknessAxisCov`); the only per-size persisted bucket is `challengeProblem`. (A `mergeSharedAcrossSizes_v2` migration flattens any legacy per-size rank/momentum/model buckets: `userRank = max(rank_9, rank_13)` — a strong 9x9 player immediately gets hard 13x13 problems — momentum follows the higher-ranked size, and the model buckets are dropped so the shared models retrain.) `getMergedAnswerHistory()` returns that unified array (the WORKING SET), each entry tagged with `size`; the recall and weakness models train from it (they slice the recent window, so the working set suffices). The stats panel (`showDetailedStats`, in `pwa/js/stats-ui.js`) instead awaits `getMergedFullAnswerHistory()` so its charts span the whole career (working set + IndexedDB tail). Pooling is sound because every feature they read is board-independent — `problemRank` is the EGF-anchored internal rank (a normalized 0.5 means the same EGF rank on either board), and the embedding axes are jointly fit across sizes. Play-time size-awareness is preserved: a recall problem can only be re-shown on its own board, so `getRecallCandidates` takes an explicit `history` (defaults to the active size; the merged union is passed only for stats counts) and `buildRecallSchedule(size)` reads the shared model + shared rank but that size's history. Two consumers do real work to pool: the recall logistic carries a `SIZE_IS_13` fixed effect (9x9 = baseline) whose coefficient ÷ logit-per-rank is the stats panel's "stronger/weaker on 13x13" readout; and the skill decomposition (`rank-decomposition.js`) pools in **internal-rank space** with a per-attempt slope `LOGIT_PER_RATING / |M'(rating)|` (each attempt mapped through its own size's curve), so both sizes share one skill curve without the rank-space slope bias.

**answerHistory storage is split: a unified working set in localStorage, the cold tail in IndexedDB.** `answerHistory` is ~99% of localStorage and on heavy users overflows the ~5MB quota, so `pwa/js/state.js` keeps the most-recent `ANSWER_HISTORY_WORKING_SET` (3000, `constants.js`) attempts — unified across both sizes — as a synchronous localStorage array; everything older is evicted to IndexedDB via `pwa/js/history-store.js` (`appendTail`/`getTail`/`updateTail`/`clearTail`, durable via `navigator.storage.persist()`, every method a safe no-op/empty if IDB is unavailable so play degrades to working-set-only, never breaks). 3000 is the largest hot window the app uses on the *merged* history (the momentum/recall replay warms over the last 3000), so the working set is a superset of every synchronous read: all the existing consumers read `state.answerHistory` (a cached active-size filtered view of the unified array) or `getMergedAnswerHistory()` (the working set) and already slice ≤3000 (`getRecallCandidates` −3000, the models −`MODEL_INPUT_HISTORY_LENGTH`). Only the full-career charts await `getMergedFullAnswerHistory()` (tail ⧺ working set, de-duped by `(problemId, date)`). The write path stays synchronous — `setAnswerHistoryForSize`/`updateAnswerHistory` route through one `reconcileSize` that replaces a size's entries in the unified array and persists; a debounced `evictColdTail()` then appends overflow to IDB **and confirms before trimming** the in-memory/localStorage working set (crash-safe seam: a kill mid-evict leaves a de-duped dup in both, never a gap; an IDB-unavailable append keeps the rows in the working set). `initHistoryStorage()` runs once at boot **after `runMigrations()`** (so the legacy `{9,13}` bucket shape is flattened into the unified array in full *first*, then split) — `main.js` awaits it before the embedding backfill writes, freeing localStorage on a quota-stressed device. The cold tail feeds ONLY the charts (it is all older than `MODEL_INPUT_HISTORY_LENGTH`, carries no embeddings, and no model reads it), so a curve refit only recomputes its `problemRank` from the stored raw rating (`embedding-backfill.js` via `updateTail`, deliberately no shard walk), and an account switch `clearTail()`s then re-splits the full pull. Two accepted tradeoffs, both kept synchronous on purpose: a re-draw of a problem last seen >3000 attempts ago is treated as new (repeat-detection scans the working set only), and `timeAdjustDeltaRating` uses the working-set median solve time.

**KataGo binary selection.** `utils/katago_controller.py` reads `KATAGO_PATH` from env, defaulting to `bots/katago` (OpenCL build). `vast_orchestration.py` uploads `bots/katago_cuda` and sets `KATAGO_PATH=bots/katago_cuda` on the remote. Don't hardcode the binary path; rely on the env var.

**`bots/analysis.cfg` is hardware-tuned in place.** `pipeline.tune_engine` rewrites `numAnalysisThreads` and `nnMaxBatchSize` for the current GPU. `vast_orchestration.py`'s `setup` ships the local cfg once but `update` deliberately skips it so remote tuning isn't clobbered. If you edit the cfg, expect the tuner to overwrite your changes.

**`KatagoController` is thread-safe by design.** A single master reader thread fans responses out via per-query `threading.Event`s keyed on query IDs. `send_query` is blocking from the caller's perspective. Multiple worker threads in `generate_tsumegos.py` and `benchmark_bots.py` rely on this.

**Models live outside git.** `models/` is gitignored. `utils/models.get_model(filename)` lazily downloads from `media.katagotraining.org` (or GitHub for 9x9 / human models) on first use. The default model is `MODEL_FULL` (`kata1-b18c384nbt-...`).

**PWA SGF format carries embedded analysis.** Each branch comment in a tsumego SGF is `"<winrate>%/<score>"` (e.g., `"86.4%/3.1"`). Client-side analysis (`pwa/js/sgf.js`) reads this directly; only when missing does it call the server (`pwa/js/api.js` → `analysis_server/server.py`). Don't strip these comments when manipulating SGFs.

**PWA state is centralized.** `pwa/js/state.js` holds the single mutable object; all changes go through exported setters. `state.appMode` switches between `'solving'` (game-logic.js), `'analyzing'` (analysis.js), and `'linked'` (rank-frozen URL-shared problems). Click handling in `board.js` routes by `appMode` (LINKED clicks go through game-logic, same as SOLVING). **Linked-mode attempts are deliberately recorded nowhere:** `sendReport` and `updateUserStats` (`user-stats.js`) both early-return on `state.problemHistory[0]?.linked` (the canonical flag, set in `problem-loader.js`), so a solved shared-link problem reaches neither D1 (`tsumego_reports`) nor local `answerHistory`. Keep the two guards in lockstep on that one flag — a rank-frozen share must not count toward the corpus, anyone's stats, or the server-stats/rank histograms.

**Account sync: the userId IS the account credential; history syncs by append-only cursor.** The 8-char `userId` (crypto-random for new users — `generateUserId` in `state.js`; legacy `Math.random` ids grandfathered) doubles as the account password: the Account dialog (hamburger → More, `account-ui.js`) shows it, and entering another code on a device adopts that account (`account-sync.js switchAccount`: wipes account-derived localStorage, reloads; init's `maybeFinishAccountSwitch` then clears the IndexedDB history tail, pulls the full server history, and re-splits it into the working set + tail before the first problem load). Sync is pull-based over `POST /sync` because `tsumego_reports` is append-only — a `created_at` cursor fully captures "what changed", no content hash. Three invariants in `account-sync.js`: (1) the cursor advances **only from pulls**, never from this device's report acks (an ack-advanced cursor would skip concurrent foreign rows with earlier timestamps); (2) own rows are recognized on pull by exact `serverCreatedAt` match — `/report` echoes its timestamp and `recordReportAck` stamps it on the entry — with a greedy ±10-min fuzzy claim for ack-less (offline) entries; (3) an existing device initializes its cursor to *now* (its local state already covers its own history) — only an account switch pulls from `''`. Merged rows become skeleton entries; `fillSyncedHistoryFields` (`embedding-backfill.js`) fills rating/rank/slope/floor/embeddings from the shards and derives `pickedCellIndex` from the reported move for **non-repeat** wrong attempts only (new problems are served at orientation 0 = identity; repeats are randomly reoriented, unrecoverable). The front-page momentum-rank loop is touched by the MLE exactly **once per device adoption, never again**: on account switch, (rank, momentum) is recovered via the **hybrid replay** in `momentum-rank.js` (the pure momentum-rank step shared with the live loop in `user-stats.js` — one source of truth, don't fork it) — rank *level* from the skill decomposition evaluated at the rank-window start, then the live dynamics replayed on top (momentum warmed over the last 3000 attempts, rank integrated only through the last 200; the split is measured: momentum is a contraction that replays converge backward, rank is an integrator with no serving feedback inside a replay, and long rank replays accumulate era-mismatch drift). On **every subsequent merge**, the newly pulled foreign attempts are simply **fed through the live loop** from the device's current state (`feedAttemptsThroughLoop`) — the account behaves as one continuous momentum loop fed by all devices, so alternating devices never drags the rank toward the MLE; devices agree up to attempt-interleaving order (second-order at converged momentum). The loop itself has **no lower rank clamp** (negative normalized rank = below 20k; labels/selection/translation all extrapolate) and a **quality modulation** (`qualityToConfidence`: step ∝ a_p² capped at 1, normalized so the corpus-median problem ≈ the baseline step — currently near-vacuous because the backend ridge-shrinks slopes to a 5.0–5.7 band, but real if a future model ships unshrunk slopes). Pulls run on load and tab-visible (self-throttled to ≥10 min); **active sessions need no polling at all** — every `/report` response also carries `prevCreatedAt` (the user's latest report *before* this one, fetched in the same D1 batch as the INSERT), and `checkSyncSignal` triggers a debounced pull when the device doesn't recognize that timestamp (= another device wrote it). Both the piggyback SELECT and an up-to-date poll read ~0–1 D1 rows **via `idx_tsumego_reports_user_created`, which must stay in place**. Known gaps: repeats' picked moves and the ignored-problems list don't round-trip (linked-mode attempts are recorded nowhere — see the PWA-state note above — so there is nothing to round-trip). **TEMPORARY (remove ~August 2026): `POST /report-backfill` + `maybeBackfillLocalHistory`** — before 2026-05-15 (`PER_ATTEMPT_ERA_MS`) clients reported only one row per problem (no repeats/times), so clients hold ~36% more attempts than the server log; each device once runs a full-history reconcile pull (the fuzzy claim relaxes the `is_repeat` match for pre-era rows, which never carried the flag) and uploads the still-un-acked entries with their client timestamps (historical `created_at` ⇒ never enters the server-stats window). Self-staggered by `hash(userId)` as a 5-day ramp (slot = hash % 5 days after `BACKFILL_RAMP_START_MS`, eligible forever once reached — no cycles; bump the constant to the deploy date); measured fleet volume ≈49k rows total (834 actives, worst user ≈5.7k) ⇒ ~10k/day during the ramp vs ~3.2k/day live writes and the 100k/day D1 quota. Once actives have run it (a few weeks), delete the Worker handler, the route, and the client one-off (`BACKFILL_*` block in `account-sync.js`). The Account menu entry is hidden until the device's backfill done-flag is set (`HISTORY_BACKFILL_DONE_KEY`; immediate on devices with nothing to reconcile) — adopting an account elsewhere before its history is fully server-side would silently lose the unreported attempts.

**Worker-version-driven graceful reload.** `pwa/build.mjs` writes `pwa/src/version.js` so the Worker imports the same hash the client gets via the esbuild `define`. Every `/report` response stamps `X-App-Version`; if it differs from the client's `APP_VERSION`, the client sets `state.reloadPending`. `maybeReload` fires from `setAcceptClicks(true)` only when `appMode !== ANALYZING`, so the refresh always lands between problems — never mid-review. New JS-side features that depend on the Worker version (e.g. embedding/ratings backfills keyed by content hashes shipped in `embedding_meta.json`) ride this reload signal.

**Server-wide "Community" stats are a cached, read-cost-sensitive D1 aggregation.** `GET /server-stats` serves a single `server_stats` row (`key='latest'`, JSON blob) aggregating the **preceding 7 days** of `tsumego_reports`. `computeServerStats` (`pwa/src/index.js`) runs **one** window query (`WHERE created_at >= ?`) and does all bucketing in JS — totals, daily activity, by-size split, solving/review time histograms (10s buckets capped at 600s, but **bucketing each user's *median* time, so the histogram counts users, not attempts** — heavy users don't dominate; for review time, which is **cumulative across a problem's repeats** (each repeat re-reports the running total), only the last instance per (user, problem) is kept before taking the median, else the running total double-counts), a **recall-time** distribution (per user, the *shortest* failure→next-attempt gap that is **≥12h** — shorter gaps are ignored entirely — into hardcoded `<1d / 1–2d / 2–3d / 3–5d / 5d+` day bins; recalls following a *success* are excluded because the spaced-repetition interval lengthens with each success and isn't comparable — only first-recall-after-failure gaps count), a per-user attempts-per-active-day distribution, and an **answer-derived** rank histogram (NOT self-reported `rank_surveys`): per active user, the mean internal-rank of their last-7-days **first-time** attempts — sound because problem selection serves difficulty-matched (~80%-clear) problems near the user's rank, so the served set centers on it. Each problem's coarse rating is the midpoint of the shard it lives in (`lookup.txt` resolves problem id→shard hash; per-size `metadata.json` gives that shard's `min/max_rating`), mapped to a rank index via `M` (`rating_to_rank.json`); `computeAnswerRankHist` fetches these via the `ASSETS` binding. Users with `< MIN_RANK_PROBLEMS` (10) distinct first-time problems are dropped; ordered weakest→strongest. **D1 bills rows read, so `created_at` MUST stay indexed (`idx_tsumego_reports_created`)** — without it every `created_at >= ?` is a full-table scan of all history that blows the daily read quota. Keep the one shared window scan; don't split this back into per-metric queries. Freshness: the blob is stamped with `APP_VERSION`; `handleServerStats` recomputes lazily on a version mismatch and returns `Cache-Control: no-store` (otherwise Cloudflare edge-caches the blob; the client also fetches `/server-stats?v=APP_VERSION`); the hourly `scheduled()` cron recomputes on version-mismatch OR ≥23h age. Rendered by `buildServerStatsPane` (`stats-ui.js`) as the Community tab.

**Write endpoints are guarded by two cheap, in-Worker abuse/quota layers plus an external WAF rule.** A spoofed/garbage `/report` (or `/schedule`, `/rank-survey`, `/share-event`, `/push/*`) doesn't just hurt integrity — the INSERT spends D1 write quota, and until purged the row inflates every server-stats `created_at >= ?` window scan for 7 days (read quota, the exact thing `idx_tsumego_reports_created` fights). So writes are defended *upstream* of D1, cheapest-first: (1) an **outer Cloudflare dashboard WAF rate-limiting rule** (account config, **not in the repo** — documented in `wrangler.toml`; ~300 req/60s per IP to the write paths, blocked requests never invoke the Worker = zero Worker+D1 cost); (2) **per-IP Workers rate-limit bindings** (`RL_REPORT` 100/60s for the high-volume `/report`, `RL_WRITE` 30/60s shared by the rest), declared as `[[unsafe.bindings]] type=ratelimit` in `wrangler.toml` and checked in the `fetch` dispatcher **before any handler touches D1** (`rateLimited()` keys on `CF-Connecting-IP`, **fails open** on a missing binding or limiter error so a misconfig never drops a legit write); (3) **in-memory format validation** in each handler (no D1 reads) — `isValidProblemId` (`^[0-9a-f]{8}$`, the symmetry-canonical hash) and `isValidUserId` (`^[A-Za-z0-9_-]{1,40}$`) reject malformed identity fields before the INSERT. Limits were calibrated from the production dump (heaviest real user ≈24 reports/60s incl. review re-reports, p99.9=20), giving ~4× headroom for NAT'd shared IPs. **Deliberately format-only** — we don't check the problem id against the real corpus (that needs a bundled set/Bloom filter); the rate limiter bounds valid-looking spoofs. Two consequences: any **deploy smoke test must POST a real 8-hex `problem` id** (a free-form marker is rejected with 400), and `pipeline.fetch_database` is **unaffected** — `wrangler d1 export` hits `api.cloudflare.com` with an API token, a different hostname than the `onlymove.net` zone the WAF guards (the binding limiter never runs for it either). Activating any of this needs a manual `npm run deploy` (+ the manual WAF rule); there's no auto-deploy.

**`pipeline.fetch_database` is incremental by default and read-cost-sensitive.** D1 bills rows read, and `tsumego_reports` is ~290k rows (>99% of the DB) while every other table combined is <1000 — so re-exporting the whole DB each run would waste almost all of those reads. The default path pulls **only new `tsumego_reports` rows via `WHERE id > MAX(local id)`** (`id` is the table's `AUTOINCREMENT` PK), which the PK index serves reading just the matching rows, and re-fetches every *other* table whole (cheap). **The cursor MUST be `id`, not `created_at`:** the PWA→D1 backfill (`POST /report-backfill`, see the account-sync note) inserts historical attempts with their *client* `created_at`, so a `created_at` cursor would silently skip those backfilled rows even though they were just inserted — whereas `AUTOINCREMENT id` always increases with insertion order, catching them. `tsumego_reports` being append-only (no `UNIQUE`, never UPDATEd/DELETEd) makes the `id` cursor provably gap-free: after a complete pull we hold the contiguous prefix `[1..N]`, and all new rows are `> N`. The fetch is **schema-tolerant and never hardcodes the table list** (except the one name `tsumego_reports`): it discovers tables from the remote `sqlite_master`, full-refreshes each (drop + recreate from the remote DDL + refill), and only if `tsumego_reports`' column set drifts does it re-pull that table whole. Implementation: `attempts/database.sqlite` is the **canonical merge target** (rows fetched via `wrangler d1 execute --remote --json`, inserted parameterized — zero escaping bugs), then `attempts/database.sql` is **regenerated from it** in a quoted-table-name + positional-`VALUES` form that every `.sql`-parsing consumer in the repo accepts (some require the quoted name, others forbid a column list — this form satisfies both). The `attempts/` artifacts are read-only as far as the pipeline is concerned; the **wrangler dev (local) D1 is the read-write one** (the PWA is tested against it and scribbles disposable rows into it), so each fetch simply **resets it to the remote state by `shutil.copyfile`-ing `database.sqlite` straight onto the miniflare D1 file** (`.wrangler/state/v3/d1/miniflare-D1DatabaseObject/<hash>.sqlite`, the one that isn't `metadata.sqlite`) and deleting its stale `-wal`/`-shm` sidecars — discarding local test writes on purpose, and far faster than a wrangler reimport (verified: D1 read/write still work; its internal `_cf_*` tables aren't required). Stop `npm run dev` before fetching — overwriting the file under a live workerd corrupts its view. The wrangler-import path (`update_local_d1`) survives only as the first-run fallback that *creates* a not-yet-existing local D1. `--full` forces a complete `wrangler d1 export` + SQLite rebuild (also auto-used when no `database.sqlite` baseline exists). Still WAF-unaffected — both `d1 export` and `d1 execute --remote` hit `api.cloudflare.com`, not the guarded `onlymove.net` zone.

**The detailed-stats modal is tabbed; its charts size to the viewport.** `showDetailedStats` → `showStatsModal(tabs)` (`stats-ui.js` holds the stats/chart rendering; `model.js` holds only the numeric recall model + stats computation; the dependency is one-directional, stats-ui→model) renders Summary / Weaknesses / Rank / Time / Community pages (a pane with no content is dropped, and the tab bar is omitted when only one remains). Both SVG charts derive their `viewBox` height from the visible modal area (`chartViewBoxHeight`) so each fits whole when scrolled. The Time chart is a Gaussian-kernel-smoothed daily solving/review-time trend — a no-data gap **breaks the line** rather than reading as zero — with a multiplier (exponential-weight) bootstrap CI band (empirical, robust to idle-tab outliers) and daily problem-count bars on a secondary right axis. The hamburger menu (`index.html` + `updateMenuItems` in `ui.js`) is grouped into Practice / Review / More categories; the Review group (share, ignore) shows only in analysis mode.

**Feature-embedding recommender (per-component weakness mining).** Per-cell, not per-problem: every legal first-move cell gets its own K-dim embedding, so the system can score both the **correct** move (a property of the position) and the move the user **actually picked** on a wrong attempt.

*Extraction* — `pipeline/extract_activations.py` runs a vendored PyTorch copy of KataGo b18 (`utils/katago_vendor/`, bootstrapped via `utils/katago_torch.py`) and captures the post-skip-add output of all 18 residual blocks (18 × 384 = 6912 floats) **at every legal cell**. Output: `activations/<size>/<id>.npz` with `candidates (n_legal, 6912) fp16`, `xys (n_legal, 2) int32`, `correct_idx () int32`.

**Row order is board-scan order (sorted by `(y, x)`), NOT SGF-variation order, and the cell set is a *superset* of the SGF's root variations.** `extract_activations.process_one_sgf` enumerates every legal cell for the player to move (the color of `variation_nodes[0]`) in scan order and records a `correct_idx` pointing at the correct move's scan position (non-zero in general; e.g. 13×13 `00000f4c` has `correct_idx=38` — verified byte-for-byte that a re-extraction reproduces the on-disk corpus). Do not instead walk the SGF's pruned variations in document order with `correct_idx=0`: that ships a non-superset cell set and does not match the on-disk corpus. Two consequences every downstream consumer must respect:
  - **Pick the correct row by `correct_idx`, never positionally.** `build_embedding._load_correct_vec` does this (`build_embedding.py:102` → `candidates[int(correct_idx)]`); do not assume row 0.
  - **The npz embeds every legal cell; SGF root variations are a pruned subset, plus the SGF carries a `pass` variation the npz never embeds.** So npz ⊇ {SGF non-pass variations}: every move a user can actually click is embedded (no picked-move ever misses), but ~10% of problems have extra embedded cells with no SGF variation, and 100% have a `pass` that is not embedded. Map cells by `(x, y)` coordinate, not by index, when crossing the npz↔SGF boundary.

*Joint embedding fit* — `pipeline/build_embedding.py` fits a joint PCA across all configured sizes on the **correct-cell row only** (residualize per-feature on `[rating, size_is_13]` jointly, z-score, randomized SVD with K=64, then standardize component scores to unit variance). **Then by default rotates the K-dim subspace with FastICA using a `skew` contrast** (`_skew_contrast`, `G(u) = u³/3, g(u) = u²` — the 3rd-cumulant objective). **FastICA warm-starts from the prior fit's unmixing** (`--ica-warm-start auto`, the default): `compute_ica_warm_start` maps the saved `ica_unmixing` into the new PCA-whitened basis and passes it as `w_init`, so the rotation converges back to the same axes unless the data moved enough to relocate them — refits are reproducible (verified: identical data → 1-iteration convergence, all axes align at 1.0) rather than reshuffling the low-skew tail per seed, which also spares the PWA needless embedding-cache wipes. `--ica-warm-start off` forces random init. After convergence, axes are sign-canonicalized so skewness is non-negative, which makes the **positive tail the heavy tail that concentrates the motif and the negative tail Gaussian baseline by construction** — i.e. negative scores don't represent an "opposite motif," they represent "no motif present." That asymmetry is the reason the recommender, the `labels.json` curation, and `inspect_extreme_problems.py` all treat the positive side as the only meaningful direction. `--rotation none` (raw PCA) and `--ica-fun {logcosh, exp, cube}` (symmetric contrasts) are also supported; under those the two sides would be symmetric, but production uses skew. Output to `embeddings/joint/{pca.npz, per_problem.csv, explained_variance.csv, extreme_problems.json, labels.json}`. `per_problem.csv` carries `size` so packaging filters by it. After the fit, `write_per_cell_projections` fans out the projection (PCA + ICA rotation) to **every cell of every problem** in parallel workers and writes `embeddings/joint/per_cell/<size>/<tid>.npz` with `embeddings (n_cells, K) fp16` + `xys (n_cells, 2) int32`. `labels.json` (v3 = `{version, _doc, bank, components}`) carries human motif labels; under skew-ICA only the positive tail carries a motif (the negative tail is Gaussian baseline), so there is no `negative` side. `components` is keyed by current PC index — `components[k].positive` / `positive_i18n` are what ship and what the PWA reads — and `bank` is a `motif_id → {positive, positive_i18n}` registry that may hold **more motifs than K** (motifs absent from a given fit persist for a later one). **Labels survive refits via an anchored bank, not transitive remapping**: each motif owns a *frozen* direction in the sibling `embeddings/joint/label_anchors.npz` (a `motif_id`-keyed unit vector in the 6912-dim residual feature space), and on each `build_embedding` run `update_labels_and_bank` matches every new axis to the nearest anchor by signed cosine (≥0.8, greedy 1-1). Matching compares against the frozen anchor — *never* the previous refit — so labels can't drift transitively across many refits. Phase 1 banks the prior run's human labels (text lifted into `bank[motif_id]`, anchor direction frozen from the prior fit's loadings the first time a motif appears, refreshed text thereafter); clearing a component's `positive` to null while its `motif_id` persists (used nowhere else) **retires** that motif from bank + anchors. Editing `components[k].positive` relabels; filling `positive` on an unmatched component adds a label. To publish hand-edited `labels.json` changes (text or `positive_i18n`), re-run `package_for_pwa` — it reads `labels.json` straight into the joint `pwa/tsumegos/embedding_meta.json` on **every** run, including the cheap skip-the-shard-rebuild path (so a labels-only change costs nothing beyond the meta rewrite, no rezip).

*Packaging* — `pipeline/package_for_pwa.py` ships two things per shard:
1. The correct-move embedding (length K=64) joined into the shard's `metadata.json` under `embedding` — what `weaknessScore` reads against any candidate problem.
2. A sibling `<hash>.embeddings.bin` per shard (fp16, K floats per cell, all problems concatenated **in SGF root-variation order**), plus an `embeddings_index.json` inside the zip mapping `{tid: {offset, n_cells}}`. This is the picked-move sidecar: the PWA Range-fetches `bytes=offset+i·bytes_per_cell..offset+(i+1)·bytes_per_cell-1` to recover the embedding at cell index `i` of a tsumego, where `i = children.indexOf(moveNode)` over the SGF root variations.

   **The bin order is set here, not upstream.** Because the npz is scan-order and a superset (see *Extraction*), `package_for_pwa.project_cells_for_problem` re-parses each SGF and rebuilds the per-cell rows in SGF-variation order via an `(x, y) → npz row` map — dropping the extra scan-order cells and the `pass`. This reorder is **load-bearing**, not defensive: the PWA indexes the bin by SGF-variation position, so shipping raw scan order would silently return the wrong cell's embedding for every picked move. The sgfmill parse dominates packaging time, so shard building is parallelized across processes (`--workers`, default `os.cpu_count()`); `--no-sgf-reorder` skips the parse but is correct **only** if the npz has been pre-reordered into SGF-variation order upstream (it has not, on current `build_embedding` output).

The joint `pwa/tsumegos/embedding_meta.json` carries `K`, `dtype` (`float16`), `bytes_per_cell` (so the PWA can decode the bin without guessing), `embedding_version`, and `labels` (variance curve, extreme problems, kurtosis, etc. live in `embeddings/joint/` locally as inspection artifacts and aren't shipped).

*PWA model — augmented weakness regression.* `pwa/js/weakness.js` trains a logistic regression with **2K+2 params**:
```
P(correct) = σ(α + γ·rating
                + Σ β_correct[k] · correct_emb[k]
                + Σ β_picked[k]  · picked_emb[k])
```
The `γ·rating` term is actually `γ·problemRank` (the board-independent internal rank), and the model is a **single shared instance trained on `getMergedAnswerHistory()`** (both sizes pooled — the embedding axes are joint, so this is well-posed); see the cross-size merge note above. `β_correct[k]` is the position's effect (problem's correct-move embedding); `β_picked[k]` is the user's choice effect (whatever they actually clicked). On correct attempts `picked_emb = correct_emb`, so those rows inform the sum `β_correct + β_picked` jointly; wrong attempts with a sidecar-fetched `pickedEmbedding` disambiguate the two. Recommendation scoring uses `(β_correct + β_picked)` against the candidate's correct-move embedding — algebraically equivalent to assuming "user will pick correctly" on the unseen problem. `problem-loader.js`'s `selectProblem` weights candidates by `quality · exp(WEAKNESS_TEMPERATURE · weaknessScore)`. Because the embedding is skew-ICA-oriented (positive tail = motif present, negative tail ≈ baseline), the recommender is effectively asymmetric in practice: large positive scores along an axis where the user is weak get mined; large negative scores don't represent an "opposite motif" the user is good at, just baseline problems with no motif. Don't read symmetry into the linear model. Ridge-regularized with `RIDGE_LAMBDA = 200` (calibrated by held-out CV in `auxiliary/calibrate_priors.py`); cold start (≤20 attempts with embeddings): `weaknessScore` returns 0, weighting collapses to pure quality. Weakness training also stores a Laplace-approx posterior diagonal SE + per-axis 2×2 cov on `(β_correct[k], β_picked[k])` so the stats UI can render sign-quadrant probabilities (`too much / not often enough / bad at / no issue`) via `pwa/js/bivariate-normal.js` (Owen's-T-based bivariate-normal CDF).

*Picked-move fetch.* `pwa/js/picked-embedding.js` Range-fetches the per-cell sidecar. Two entry points:
- `fetchPickedEmbedding({tsumegoId, cellIndex, zipFilename, boardSize})` — live path, called from `game-logic.handleBoardClick` on every move via `state.embeddingsIndexCache` (loaded alongside shard metadata in `problem-loader`). The cell index is `children.indexOf(moveNode)` against the SGF root variations — same order as extraction/packaging, no coordinate recomputation.
- `fetchPickedEmbeddingWithIndexEntry(...)` — backfill path, used by `embedding-backfill.js` when iterating shards.

Answer-history entries carry `embedding` (correct-move, from shard `metadata.json`), `pickedCellIndex` (SGF variation index), and `pickedEmbedding` (decoded sidecar fp16).

*Backfill + invalidation.* `pwa/js/embedding-backfill.js` runs on app load: fetches the joint `embedding_meta.json` once (version, labels, K/dtype/bytes_per_cell all joint), then iterates per size — for each shard that legacy answer-history entries reference, it fills missing `embedding` fields from `metadata.json` and missing `pickedEmbedding` fields by Range-fetching the sidecar with the entry's stored `pickedCellIndex`. Entries older than `MODEL_INPUT_HISTORY_LENGTH` get both fields stripped to keep localStorage bounded. Because the weakness model is a single shared instance (see the cross-size merge note), an embedding wipe on *either* size clears the shared `weaknessParams`/`Adam`/`Se`/`AxisCov`, and a single `trainWeakness()` retrain runs once after the whole walk (not per size). Refits auto-invalidate: `build_embedding.py` writes a content-hash `embedding_version` into `pca.npz` (computed over the projection-relevant arrays — feature mask/means/stds, OLS coefs, PCA components/mean/stds, ICA unmixing/stds), `package_for_pwa.py` surfaces it in `pwa/tsumegos/embedding_meta.json`, and the PWA wipes stale embeddings (correct + picked) per size whenever the localStorage-cached version differs. No manual JS edit needed on refit.

Extraction needs ~8 GPU minutes per 1k problems on a Quadro M2200; remote it via Vast.ai for full-corpus runs.

**Ranks are derived client-side from raw ratings; packaging is rank-agnostic.** `package_for_pwa.py` ships per problem in `metadata.json` the raw black-box `rating` (from `ratings_v2/<size>/tsumego_ratings_final.csv`) and the raw 2PL `slope` a_p (from `tsumego_quality_final.csv`, un-normalized — the client uses it as the rank-estimator's per-attempt slope and as the selection weight ∝ `a_p²`) — no rank, no `rank_index`, no `/29`; shard `min_rating`/`max_rating` are raw too. It does not *compute* ranks (rank-agnostic); the rating→rank map `M` is fitted separately (see next note) into the backend `ratings_v2/` dir, and `package_for_pwa` — the **single writer of `pwa/tsumegos/`** — copies that curve (`rating_to_rank.json` + `rank_map.json`) across into the served path. The client does *all* rating→rank conversion. On ingest, `problem-loader.js` derives `p.rank` (normalized 0..1 = `applyM(rating)/29`, via `normalizedRankForSize` in `rank-decomposition.js`) and leaves `p.rating` raw; zip boundaries become `minRank`/`maxRank`. Everything rank-shaped reads `rank`: problem selection, the rank label (`getDescriptiveRank`), recall (`model.js`), and the weakness model (`weakness.js`). `state.userRank` is a single value shared across both sizes (see the cross-size merge note), and the skill decomposition pools both sizes in internal-rank space — each attempt is mapped through its size's `M` first, not estimated in raw-rating space. **`M` is required** — `main.js` awaits `loadRatingRankMap()` at init and aborts if it can't load (no fallback). Answer-history entries store `problemRating` (raw), `problemRank` (0..1), and `problemSlope` (raw a_p — the skill decomposition's per-attempt success-curve slope, converted to internal-rank space as `a_p/|M'|`; legacy entries without it fall back to a constant). The client rank loop closes on this per-problem `a_p`: `rank-decomposition.js`'s `poolLogistic` AND the EGF anchor `fit_user_rating` (`map_rating_v2_to_egf`) both use it, so a sharp problem pins a user's rank more tightly than a flat one. `embedding-backfill.js` migrates/refreshes all three, triggered by the per-size `ratings_version` (raw-rating content hash in `embedding_meta.json`) **and** by a client-computed curve-version (`ratingRankCurveVersion`) so a `map_rating_v2_to_egf` re-fit with unchanged ratings still refreshes stored ranks. **Consequence:** a curve re-fit (`map_rating_v2_to_egf`) writes only to the backend `ratings_v2/`; publish it with `package_for_pwa` — its per-size change detection sees the shard inputs unchanged and **skips the heavy rebuild, copying just the curve** (near-instant), so a curve-only change is cheap but still goes through the single writer. A raw-rating change re-ships shards. (A change to the *packaging format itself* — e.g. adding/renaming a `metadata.json` field — is NOT captured by the input hash, so run `package_for_pwa --force` once after such a code change.) Don't reintroduce a baked rank into `metadata.json` — `rating` means raw everywhere.

**`M` (rating→rank) is EGF-anchored and jointly fitted from surveys.** `pipeline/map_rating_v2_to_egf.py` fits, in ONE objective, the rating→internal-rank curve AND the per-(non-EGF-)server rank couplings over all `rank_surveys` declarations (reusing the stateless helpers in `utils/fit_rank_curves.py` — `fit_user_rating`, `ordinal_nll_vec`, `build_server_curves`, …). Internal rank ≡ EGF rank (the hub, identity); EGF declarations anchor the curve directly while every other server's declarations also bend the curve where they land (so kyu-heavy non-EGF cohorts calibrate the kyu range instead of being stamped with extrapolated ranks that drag the dan range). It writes **ONE shared curve to both board keys** (the v2 ratings are already on a common cross-board scale) with a uniform-spacing (linear) prior; it anchors on each survey user's **80%-clear v2-rating** (`fit_user_rating` @ `CALIBRATION_P=0.8`, pooled across boards), NOT raw θ — see the rating-pipeline section. Outputs go to the **backend** `ratings_v2/rating_to_rank.json` (per-board-key `{ratings, rank_indices}` knots that `M` interpolates) and `ratings_v2/rank_map.json` (board-independent per-server interpolation knots `{server: {our, server}}` in rank-scalar units; `rank-translation.js` interpolates the user's *continuous* internal rank through them and rounds only for display — so a weak vs strong same-band player can land on different server ranks — EGF = identity); `package_for_pwa` then copies both into the served `pwa/tsumegos/` (single-writer rule). Run `pipeline.fetch_database` first to refresh `attempts/database.sql` (the survey + attempts source); `map_rating_v2_to_egf` then needs `ratings_v2/` but neither GPU nor the heavy pipeline.

**Rank interpolation/label math is shared between the Worker and the client.** `interpExtrap` (linear interp + end-slope extrapolation) and `rankScalarToLabel` (rank scalar → "5k"/"3d" label; 1k=0, 1d=1, no zero gap) live in `pwa/shared/rank-math.js`, imported by the Worker (`src/index.js`, bundled by wrangler) and by client modules (`rank-translation.js`, `rank-decomposition.js`, bundled by esbuild). Keeping them in one module prevents the server-computed Community rank histogram from drifting against the client's rank display — don't reintroduce a local copy.

**KataGo PyTorch loader requires `.ckpt`, not `.bin.gz`.** `models/kata1-b18c384nbt-...bin.gz` is the binary export the C++ analysis engine reads — not loadable via `torch.load`. The feature-embedding pipeline expects `models/kata1-b18c384nbt-s9996604416-d4316597426/model.ckpt` (extracted from the corresponding `.zip` checkpoint distribution). Don't point `extract_activations.py --ckpt` at a `.bin.gz`; KataGo's training code only goes PyTorch → binary, not the other way.

## Conventions to be aware of

- `tests/` exists but is empty — there is no test runner configured. Don't add a "run the tests" step to claims of completion unless tests are actually added.
- Python code uses absolute imports rooted at the repo (e.g., `from utils.configurations import ...`). Pipeline scripts append `PROJECT_ROOT` to `sys.path` defensively.
- KataGo coordinates skip the letter `I` (so cols are `ABCDEFGHJKLMNOPQRST`). SGF coordinates do not. Helper conversions live in `utils/katago_queries.py` (`katago_to_sgf_coords`) and `pipeline/benchmark_bots.py` (`sgf_to_gtp`). Prefer reusing them over rewriting coordinate math.
- `pwa/README.md` has additional context on the PWA's overall structure (sections 1–5: overview, tech stack, project layout, architecture, dev workflow). Read it before substantive PWA edits.
- **For local DB analysis, prefer the binary `attempts/database.sqlite` over the raw `attempts/database.sql` dump.** Both are produced from `pipeline.fetch_database` and both gitignored. `fetch_database` treats `database.sqlite` as the **canonical merge target** and keeps both artifacts in sync on every run, so you normally don't import by hand. If you ever need to rebuild the `.sqlite` from a raw dump manually: `{ echo "BEGIN;"; cat attempts/database.sql; echo "COMMIT;"; } | sqlite3 attempts/database.sqlite` — the `BEGIN/COMMIT` wrapper matters: a full D1 export emits one un-batched `INSERT` per row (~290k for `tsumego_reports`), so without a wrapping transaction sqlite fsyncs per row and the import takes many minutes. **Never pipe the import through `head`/`tail`** — it SIGPIPE-kills `sqlite3` mid-import and silently leaves a partial table. Query the `.sqlite` thereafter (no re-import per session). Note a full `--full` dump only carries the tables that have rows at export time (D1 export drops empty tables), whereas the incremental path's regenerated dump carries every table it discovered remotely (so e.g. an empty `history_refresh_log` is present).
- **Many artifact directories hold 100k+ files** — `tsumegos/9/` (~123k SGFs), `activations/9/` (~123k .npz), `tsumegos/13/` and `activations/13/` (~20k each), `embeddings/joint/per_cell/<size>/` (per-tid files), and shard zips. **Shell globs like `ls dir/*.npz` will silently expand past `ARG_MAX` and report 0** — verified false-negative on `activations/9/`. Use `find <dir> -maxdepth 1 -name '*.ext' -printf . | wc -c` (or `find ... | wc -l` if newlines are safe) to count, and `find ... -exec` / `xargs -0` to iterate. The same trap applies to anything piping a glob into another command. Treat any directory under `tsumegos/`, `activations/`, `embeddings/`, `attempts/`, `ratings_v2/`, or `pwa/tsumegos/<size>/` as "may exceed argv" by default.
